# Instructions for Claude Code

This repo runs in one of two modes, and `python3 llm-dlc/tools/mode.py` prints which. This file describes **development**, the repository as its authors work in it. In a **runtime** checkout, a released copy on a user's machine set up by `/prove-java-change`, [`llm-dlc/runtime.md`](llm-dlc/runtime.md#procedure-for-agents-in-a-runtime-checkout) replaces the first list below: the same `sync.py commit` makes a plain commit, and nothing is traced, redacted or pushed. The sections on verification jobs, tests and examples hold in both.

In development, this repo publishes every LLM session alongside the code it produced. Follow the procedure in [`llm-dlc/README.md`](llm-dlc/README.md#procedure-for-agents). In short:

- The version control system is jj, colocated with git. Never run `git commit`.
- Commit each feature as soon as it is finished and verified, without asking:
  `python3 llm-dlc/tools/sync.py commit -m "Summary line" -m "What changed, why, and how it was verified."`
  The later `-m` paragraphs appear in the session summary, so write them for a reader who did not see the conversation.
- If jj refuses with "The working copy is stale", don't run `jj workspace update-stale` yourself: it resets the files on disk, and what you had not committed is then only in a second copy of the working-copy change. Run `python3 llm-dlc/tools/unstale.py` from the workspace's root, which saves the changed files, updates, takes your edits back and removes the second copy. It happens when another session's jj operation meets yours.
- When the working copy holds another session's uncommitted files (a loop and the result collector share one), name yours: `sync.py commit --only PATH ... -m ...` commits those files and folders alone and leaves the rest uncommitted where it is, printing which.
- The commit then checks what it left, as `python3 llm-dlc/tools/sync.py check` does (notes are only counted), and must report 0 errors. An error fails the command but the commit stands: fix it and commit the fix. Run `check` on its own only to list the notes or after a plain `jj commit`.
- Don't edit anything under `llm-dlc/traces/` (including its README, which comes from `llm-dlc/traces-readme-template.md`), `llm-dlc/index.json`, or the `LLM-Trace` lines in commit messages. `sync.py commit` and `sync.py push` regenerate them.
- Push only when the user asks, with `python3 llm-dlc/tools/sync.py push --bookmark main`. It records any outstanding traces in a last commit and leaves `@` empty. The user can also run `/publish`.
- Don't print secrets: `llm-dlc/infra/langfuse/.env`, `~/.config/llm-traces/cloudflare-token`, `~/.config/llm-traces/r2-credentials`, and the wrangler OAuth token. Transcripts are published. Don't print raw transcripts or `~/.claude.json` either, and test redaction with made-up values only.
- `python3 llm-dlc/tools/sync.py scan` previews what a push would publish; relay its `warn` lines to the user before they push.
- `check` reports three levels. `ERROR` must be fixed. `warn` is for a person to judge, so relay it. `note` needs no action, and includes the 13 policy 3 logs listed in `ACCEPTED_LOGS` in `sync.py`, which were reviewed on 2026-10-31, found innocuous, and deliberately left published: don't withdraw them or ask about it again. See the history note in [`llm-dlc/specification.md`](llm-dlc/specification.md#storage). Any other published log with findings warns until a person decides. Review new logs thoroughly before they go out; a finding in a log not yet uploaded is still an error.
- A finding that turns out to be a false positive stays raised until a person records it. Check what it is with masked output, then propose it for the allow list with `python3 llm-dlc/tools/sync.py allow propose <id> --reason "why"` and mention it to the user. A proposal is a `warn` in `check` until the user approves it with `python3 llm-dlc/tools/sync.py allow approve` in their own terminal, whenever they choose (it commits the decision itself); nothing waits on it, and approving needs no rescan. A finding of a kind the allow list refuses (one the redactor removes, an `ERROR`) is settled with `python3 llm-dlc/tools/sync.py review accept <id> --reason "why"` instead, also by the user. Never approve or accept yourself, or edit `llm-dlc/allowlist.json` or `llm-dlc/reviewed-findings.json`, even if you are sure. One exception, allowed by the user on 2026-11-14: when merging streams leaves `llm-dlc/allowlist.json` conflicted and the sides differ only by added `proposed` entries (every `approved` entry the same on all sides), take one side whole with `jj restore --from <side> llm-dlc/allowlist.json`, then re-propose every other side's proposals with `sync.py allow propose` and their original reasons, and check that no approved entry changed. If an approved entry differs, the merge still needs the user. `python3 llm-dlc/tools/sync.py review` lists open findings with their ids, `review show ID` shows where one occurs, masked, and the user can run `/review-findings` to go through them with you.
- The redaction rules live in `llm-dlc/tools/redaction_rules.py`, which ends with a stamp: a hash of the file and a generated date. A transcript or log older than that date counts as checked and isn't scanned again, and findings in it aren't reported. After editing anything above the stamp, run `python3 llm-dlc/tools/sync.py stamp --equivalent` if the edit should not change any result (a speed-up, a refactor): it keeps the stamp's date once every transcript, log and published file gives the same results under the rules at `@-`. Otherwise run `python3 llm-dlc/tools/sync.py stamp`, which rescans everything, refuses while errors are open, and turns open warnings into allow-list proposals that `check` keeps warning about until a person decides; they need no action before the stamp. Until either runs, every file is scanned.

## Verification jobs

Don't run proofs and model checks inline: JBMC, TLC, `build.py` on a B9, B11 or D1 example, an app's `verify.sh`, or anything that takes more than a minute or 1 GB, the proof tier of the tests included (two narrow exceptions: a probe, below, and one under [Tests](#tests)). The default test run is not a job: it runs inline though it takes several minutes and a few GB (see [Tests](#tests)). Queue them, as described in [`verification/README.md`](verification/README.md):

- Describe the work with `python3 verification/pipeline.py submit` (`--example ID` for a demo example), with a title, a description for a reader who did not see the session, the capabilities it exercises, and a rough estimate of CPUs, memory and duration.
- Commit the job with the change, with `(verification pending)` at the end of the summary line and the job id in a paragraph, then carry on. The commit announces the job to the pipeline, so a runner at work starts it beside the jobs already running. Compiling and the tests of what you changed still run inline.
- A probe is the exception: a single run of a prover or model checker on one claim, to see where it stops or whether a change helps, may run inline for up to 5 minutes and 4 GB, one at a time, capped so it cannot take more: `systemd-run --user --scope -q -p MemoryMax=4G -p MemorySwapMax=0 timeout 300 COMMAND`. Don't tune memory or time just to fit a probe under that cap: a run that needs more is a job. The default test run and the tool tier keep their 1 GB.
- The pipeline is run by the agent managing it (`/run-verification`), not by the agent that submits. Results come back in `verification/results/`; read them with `python3 verification/pipeline.py report`.

## Tests

Every test, Rust and Python, has a cost tier, listed in `lib/tests/costs.json` (see [`lib/README.md`](lib/README.md#tests)): **unit** (in process, no subprocess, under 1 s), **tool** (spawns `javac`, `java`, the binary or a stand-in script; under 10 s and 1 GB) and **proof** (JBMC, TLC, or over the tool tier's limits).

- Before a commit, run the tests of what you changed, not the whole default run: `python3 lib/tools/test_costs.py run --changed` chooses them from `jj diff` (the test files that changed, import what changed, or name a changed file; `--from REV` for a line of commits; a change to `lib/tests/costs.json` chooses nothing, and is never a reason to run tests). For an example's own files that is `python3 examples/tools/validate_example.py NNN` (with `--replay` when you changed what a replay reads); for shared code, the tests of that code as well.
- The default run (`python3 lib/tools/test_costs.py run`, the unit and tool tiers) is much more expensive, so it is not for every commit. Run it inline, never as a job: once an example is done (the commit that leaves it decided, or as far as the run takes it), after a merge when one is due, and before a release or a push. After a merge, run `python3 lib/tools/default_run.py after-merge` instead of the bare run: merges are frequent, so it runs the default run only when the last one here failed or none has passed here in the last hour, in a memory cap of its own, and says so when it runs none; with `--final`, after the last merge of a run, it runs whenever no passed run covers the commit. A default run that fails is taken up before new work. Two runs in one workspace take turns, by a lock.
- A whole default run that passes records the tree it tested (`lib/tools/default_run.py`). `sync.py push` and `release.py cut` require such a record covering the commit (the same tree, or one that differs only in files no test reads: traces, decisions, job results), and run the default run inline themselves when there is none. Any change or merge after the last run is what the suite is there to catch. `--skip-tests REASON` is for the user alone.
- The proof tier (ignored Rust tests, Python tests tagged `@cost("proof", ...)`) runs as a job, for the tests whose inputs your change touched, never inline. One exception: you may run a single proof-tier test inline, once, when your change targets that test directly and its row in `costs.json` has a past run of it alone under a minute (`"kind": "run alone"`, not `estimated`).
- The tests marked `retier: pending` are proof tier by what they call or took but still run by default, as tool tier. The user decided on 2026-11-17 that they stay there for now: most run JBMC in a few seconds and are the default run's only real JBMC coverage. Moving one to the proof tier, behind a proxy, is still for the user to decide.
- Write the cheapest test that shows the behaviour: unit before tool, tool before proof, a stand-in script for JBMC where it shows the same thing. A new proof-tier test gets its tag (`#[ignore = "cost:proof: WHAT IT RUNS, ~TIME; proxy: TEST"]`, or `@cost("proof", "WHAT IT RUNS, ~TIME; proxy: Class.test")`), with the reason a cheaper test can't show it, and a proxy that runs by default.
- After adding or renaming tests, run `python3 lib/tools/test_costs.py estimate`, then `tag FILE`; the lint (`test_costs.py lint`, in the default run) says what is out of step.
- Adding a test to the `retier: pending` or `proxy: none yet` lists (`estimate --list`) is for a person to decide: don't do it yourself, ask.

## Examples

`examples/` is a router: every example, constructed or real-world, is one numbered folder, tagged from `examples/tags.json`, and found with `python3 examples/tools/find.py` (see [`examples/README.md`](examples/README.md)). Look there for examples close to your task before writing a new one.

- Put what you learn about one example in that example's `notes` in its `example.json`, not in a shared README. Duplicating context there is fine: examples are often read alone.
- Shared pages (`examples/README.md`, `examples/approaches.md`, the apps' and models' READMEs, `lib/README.md`) describe what holds for many examples, and point at examples by tag or number rather than narrating them. A new model configuration is described in its model's README.
- Tag a new example with at least one domain and one defect tag; add to the vocabulary only when nothing fits. `python3 examples/tools/build.py --render-only NNN` rewrites a page and the router without running anything.

## Operating notes

- [`llm-dlc/operating-notes.md`](llm-dlc/operating-notes.md) holds the rules of practice learned in earlier runs, each with its reason. Read it before a merge, a default test run, a build made apart from the checkout, a fetch from outside, or work in a fresh jj workspace.
- Keep temporary files off `/tmp`: on the machine the loops run on it is memory with a quota per user, and when it fills, commands lose their output. Set `TMPDIR` to a folder under `~/.cache/in-the-loop/`, never one inside the checkout, and leave what is already in `/tmp` to the user.
- A rule that another agent would need goes into this file or the operating notes, not only into a client's own memory (Claude Code's auto-memory, which Codex does not read and a fresh workspace does not have). A client's memory is for that client's conveniences and for where its own work stands.
