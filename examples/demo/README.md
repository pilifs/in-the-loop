# Demo examples

[← Examples](../README.md): these are the constructed examples over this repository's own subject systems; the [real-world examples](../real-world/README.md) are pull requests to published libraries.

> **Start with examples 034 to 056** if you work on the JVM itself or on the libraries closest to it, **023 to 033 and 075 to 080** if you build services on Spring Boot, or **013 to 022** if you build the replicated systems under them, then 006 to 012. Examples 001 to 005 were created by Opus 5.5, the rest by Fable 5.1.
> The later examples go significantly beyond what can be achieved with type checking.

Each example is one code change to a subject system, run through a formal verifier, with the verdict and why it matters.
Together they show what verification catches that code review and tests miss, and what it lets through.
None of it needs the reader to write a specification: each verifier derives its statement from the code, the types, the previous version, or a one-line property committed next to the code.

There are four subject systems. [Box Office](apps/boxoffice/README.md) (examples 001 to 012) is a ticketing system of two Spring Boot services over Kafka, verified by the Java proof of concept in [`tools/contracts`](tools/contracts/README.md).
[Quorum](apps/quorum/README.md) (examples 013 to 022, 057 to 074 and 081 to 098) is a library of the pure decision kernels a replicated system is built from, Raft's vote rule and role machine, quorum arithmetic, backoff, a hybrid logical clock, last-writer-wins resolution, and a two-phase-commit coordinator and participant, with the nodes around them for the trace check.
[Crosscut](apps/crosscut/README.md) (examples 023 to 033 and 075 to 080) is the kernels behind the cross-cutting concerns of a Spring Boot service: the transaction interceptor's rollback rule, a circuit breaker, a retry policy, a rate limiter, an `Idempotency-Key` receiver, a Kafka partitioner and batch commit, a JWT validator's clock skew and a cache's expiry.
[Mica](apps/mica/README.md) (examples 034 to 056) is the decision kernels of a small JVM written in Java: the class initialization procedure of JVMS §5.5, the type checker's assignability relation, access control, `idiv` and `fcmp` with their corner cases, a `lookupswitch` bisection and the sort of its pairs, the exception table's handler lookup and its well-formedness check, the stack map frame offsets, the length of a `Code` attribute, constant pool numbering, `max_stack`, javac's switch heuristic, a power-of-two table size and the modified UTF-8 of the constant pool.
The three are verified by [`jvmcontract`](../../lib/README.md), the Rust tool, with no JVM in the loop: a bytecode interpreter checking the kernels of a bytecode interpreter.
One proof is unfinished: [a regression proof of `ModifiedUtf8#encodeInto`](apps/mica/pending/README.md) is proved up to 4 characters, and needs a machine with more memory at the default of 8.

The examples use five approaches, numbered as in [`approaches.md`](../approaches.md). The common principle is that a checked-in artifact may change only where the developer intends a change, and the diff of that artifact is what the reviewer approves.

A type system could do some of what 001 to 005 do. It could not find a one-cent rounding drift across 2^96 inputs (006), prove that a pricing change touches only the groups it says it touches (007), notice that a codec started loading classes named by Kafka messages (009), or produce the nine-step interleaving in which a paid customer loses their seat and their refund (011).
Nor could it tell that a Raft vote rule rewritten as "longest log wins" will elect a leader that overwrites committed entries (013), that `(n + 1) / 2` is not a majority (015), that a hybrid logical clock with one branch folded away hands out a timestamp older than the message it just received (018), or that a two-phase-commit coordinator which presumes commit on timeout commits over a participant's no vote that is still in flight (020).
Nor that a transaction rollback rule rewritten as "a RuntimeException rolls back" commits after an `OutOfMemoryError` (025), that a switch rewrite of a retry policy stops retrying the 5xx statuses it did not name (027), that an idempotency key which runs a retry while the first attempt is in flight executes the request twice (029), or that a Kafka partitioner written with `Math.abs` sends one key in two billion to a negative partition (023).
Nor that a verifier which answers "everything is an `Object`" one line too early lets an uninitialized object through (038), that a NaN check written as `== Float.NaN` turns `fcmpl` into `fcmpg` (035), that an `idiv` with an overflow check throws where the specification says to return `Integer.MIN_VALUE` (034), or that a class initialization with one rule for every requester deadlocks on its own thread (043).
Nor that a Raft server which grants a vote without adopting the candidate's term votes twice and elects two leaders (059), a bug in how two kernels compose that each kernel's own contract approves, or that one timeout rule for every role makes a leader resign into an election against itself (060), or that a candidate which retries its election without voting for itself again elects two leaders (062), which the model finds three ways, as a run, as the one step that breaks its inductive invariant, and in a cluster of four; or that a candidate which retries in the same term, proved safe under every safety configuration, leaves three candidates asking each other forever (063), a liveness failure that only the fourth configuration, fairness, can state, while a candidate that stands down on a timeout instead is proved safe and live (064); or that a leader which ignores vote requests from newer terms votes twice in a term (065), because the vote rule assumes the role machine ran first; or that a leader which treats a vote request of its own term as impossible, and throws, crashes on the loser of a split vote (066), an exception the model proves dead for the one input the kernel already throws on and reachable in four steps for the new one; or that a two-phase-commit coordinator which commits after aborting, once the late votes are all yes, splits the participants (067), found as a nine-step run and as the one step that leaves the model's inductive invariant, while a coordinator that answers late votes with its decision again is proved safe both ways (068). Nor that a vote rule which lets a voter switch candidates within a term, to settle split votes faster, elects two leaders that hold each other's votes (069), the vote rule being the election model's second generated operator; or that a vote rule without the election restriction, on the reasoning of Viewstamped Replication that a new leader collects what it lacks, elects the one server whose log a deposed leader left behind, lacking the entry the others have committed (070), which only the configuration that leaves a server behind can see, the four with equal logs having nothing to refuse; or that the arithmetic around that rule, rewritten to rank logs by length before term, grants the vote the restriction exists to refuse (071), which the model cannot see, since it repeats the arithmetic rather than generates it, and the property proofs of `grant` can.
Nor could it say what a verdict rests on: a vote rule that refuses a repeat request (072) and a follower that leads on a late majority (074) verify under all six configurations of the election model, because an RPC that is one step never asks a voter twice and never counts a vote late, and a reply that waits on the wire changes neither, and TLC's coverage, read back against the rows of the generated contract, is what reports both verdicts as vacuous, with the rows no step takes listed on every model-checking page; while a vote rule that throws on a term the voter has not adopted (073) has nine rows no run takes, which the invariant that no kernel ever throws turns into the theorem the change asked for. Nor that a role machine which adopts the term of any reply but its own (081) sends a term backwards when the reply is from a term the candidate has left, or that one which holds such a reply impossible, and throws (082), crashes on a routine late reply: the model's own simplification, that an RPC is one step, was the only thing keeping the rows for such a reply dead under its five configurations, and a sixth, in which a vote reply waits on the wire, takes them and finds the two runs in five steps and four; the logging of such replies (083) is verified by that configuration, where the other five would have verified it vacuously. Nor that a candidate that stands down for a rival of its own term (084) votes twice in it, or that a leader that yields to a candidate of its own term (085) lets the term elect twice, one leader after the other: every state invariant holds in such runs, since a vote is forgotten the moment the voter moves on and a leader that has stepped down is a follower like any other, and a seventh configuration, in which two history variables record every term led and every vote cast, reports the paper's own claims about a run in four steps and five; a leader that answers such a candidate with its heartbeats instead (086) is proved the term's only leader under all seven.
Nor that a circuit breaker which restarts its wait on every call it refuses (075) stays open forever under a caller that keeps calling, over a dependency that came back at step six, or that a half-open breaker which starts its probes over on a failed one (077) probes a dead dependency forever with no wait between the rounds: every invariant of the breaker holds in every state of both runs, and only the liveness properties, written one per fate of the dependency, can say that the runs themselves are wrong; while a half-open breaker that judges its probes by their failure rate, as Resilience4j does (076), is proved safe and live under both configurations. Nor that an idempotency sweeper which releases a record in progress by its age alone (078) releases it under a worker that is alive, so that the retry executes beside the first attempt, or that a record which drops its expired response but keeps its key (080) answers a late retry with a response that is gone: the model's record never expired before, so the kernel's rows for expiry had never been taken by any run, and only a second configuration in which the sweeper can act at any point can judge them; a record that expires into a tombstone refusing late retries (079) is proved safe under both.
Nor that a two-phase-commit coordinator which waits for the last vote when every vote so far is yes leaves a prepared participant holding its locks forever (057), a liveness failure no invariant and no deadlock check can state, found under the model's fairness conditions; or that a grace period for that last vote, with a second timeout, keeps every participant deciding and still implements transaction commit (058). Nor that a coordinator which aborts the transaction on restart reverses a commit one participant has already applied (087), which only a model that lets the coordinator crash can see, or that one with nothing to redo on restart leaves a logged decision unsent and a prepared participant waiting forever (088), the restart that logged it cut short by a second crash, while a coordinator that resumes collecting on restart is proved safe and live (089). Nor that the node around the coordinator broadcasts its decision before it logs it (090), or logs its tally only with a decision and so loses the counted votes in a crash (091): changes to the glue that no contract and no configuration of the model sees, caught by holding the nodes' own recorded runs, crashes injected, to the model's next-state relation, which also shows a participant that votes no when it gives up taking only steps the model has (092). Nor that a participant which releases its locks on restart aborts a transaction the coordinator committed on its yes vote (093), the blocking property of two-phase commit broken, which only a model that lets the participants crash can see, or that a participant node which sends its vote before logging it restarts as if it had not voted (094), caught by its recorded run at the step where the vote is out and the log still says working, while a restarted participant that votes no rather than wait for the coordinator's timer is proved safe and live (095).
Nor that a Raft follower which takes a leader's entries after a previous entry of another term, the consistency check relaxed to save a round trip, ends with two logs that share an entry over different histories (096), the log matching property broken in twelve steps of a model with the logs live, or that a leader which commits an earlier term's entry once a majority holds it (097) does so while a rival elected without it is about to overwrite it, figure 8 of the paper, which three terms verify and the configuration sized for it finds in sixteen; while a follower that drops a conflicting previous entry the moment it refuses the request is proved safe under both (098).
Nor that a rewritten binary search still finds every key in every sorted table (046), that an exception table whose `end_pc` is read as inclusive hands an exception to the wrong handler (047), or that a constant-pool encoder which writes supplementary characters in four bytes produces a class no JVM will load (048).
Nor that a stack map offset loop with its first-frame special case removed still places every frame (049), that a `Code` attribute length which leaves out its nested attributes' headers is six bytes short per attribute (050), that a constant-pool numbering which counts the `long` entry itself points one past it (051), or that `max_stack` is still the deepest point when the depth is checked only after a push (052), the refutations shrunk to a witness of one element.
Nor that an `idiv` which leaves division by zero to the host throws exactly where the check it removed did (053), or that a class file check which compares `end_pc` like the other offsets rejects every handler that covers the last instruction of a method (054), both on the exceptional path a throws clause brings under the proof.
Nor that an encoder which zero-terminates the string into the caller's buffer overwrites a byte past what it returns (055), or that a `lookupswitch` pair sort which compares keys by difference swaps two keys just over 2^31 apart (056), the first against a frame condition and the second against a permutation, both stated with JML's `\old`.

The *Existing tests* column is measured, not claimed: the generator runs the module's unit tests against each patch. A **missed** entry means the tests pass and the change would have shipped.

**Verdicts:**
- **✗ Violation:** behaviour changed, but the developer did not intend it. The build fails, with a concrete witness: an input whose outcome changed, a call site that gained a capability, or a step-by-step run of the system that breaks an invariant.
- **✓ Verified:** the code behaves exactly as its contract, its previous version, or its invariants say, for every possible input or interleaving within the stated bounds.
  An intended change passes once its contract is regenerated or its scope is declared, and that diff or declaration is what the reviewer approves.
- **⚠ Unverifiable:** the verifier refuses to give a verdict, for example because the code is no longer provably pure. The build fails, because "we could not check" must not read as "fine".

## How to read an example

Each example's page has the same sections:

| Section | Content |
|---|---|
| Summary table | Verdict, categories, severity if the change shipped unnoticed, what kind of change it was, the verified unit, the approach |
| The change | What the developer meant to do, the code before and after, and the patch |
| What the verifier found | The counterexamples (inputs whose outcome changed, capability changes, or a trace of the system), the reason for refusing, or the contract diff |
| Would the existing tests have caught it? | The module's unit tests, run against the same patch: the baseline the verifier is compared with |
| Why it matters | The production risk |
| Why the verdict is right | How the verifier reached it, and why it is a proof and not a sample |
| What to do | The resolution |
| Evidence | The verifier's console output and SARIF report, unedited; the JDK APIs a proof trusted; for a symbolic proof, the generated statement the prover checked |

For a state machine (014, 020, 021, 025, 026, 029, 030, 042, 043, 057, 058), the page also draws the machine the patched code implements, from its derived contract, with unreachable and terminal states marked.

Everything a verifier says is generated by running it, so no example can claim a result the tool did not produce.
The generator also fails when a verdict differs from the example's `expected.verdict`, so the examples double as regression tests of the verifiers.


It needs Java 25, JBMC for the B9 and B11 examples, TLC (`~/tools/tla2tools.jar`, as [`setup`](../setup/README.md) installs it) for the D1 examples, and `cargo` (or a built `lib/target/release/jvmcontract`, or `JVMCONTRACT` pointing at one) for the Quorum, Crosscut and Mica examples; no Docker.
A Box Office example takes from a few seconds to a minute, because its patch is applied to a temporary copy of the Gradle build, which is then compiled, tested and verified. A Quorum, Crosscut or Mica example takes a second or two: `javac`, the tests, and `jvmcontract`.

To add an example:

1. Make the change in your working copy, and save it with `jj diff --git > examples/demo/NNN-short-name/change.patch`. Then undo the change.
   A Box Office D1 example changes the Java and the matching action of [`apps/boxoffice/spec/BoxOffice.tla`](apps/boxoffice/spec/BoxOffice.tla) in the same patch; a Quorum, Crosscut or Mica D1 example changes the state machine the model is built around (the coordinator, the Raft role machine, the receiver, the class initialization), and the model picks the change up through the regenerated contract; `build.py` picks the model by the example's `subject.symbol`, and runs it under every configuration the model lists (the two-phase-commit model has five, the Raft model seven), the verdict being the first configuration that fails; a later configuration that reports the headline run again is said to, without the trace. A configuration may name a `spec` of its own, a module that extends the model, and a trace writer (`traces`), a test-side main class run on the patched classes whose output is the module of recorded runs the specification walks; the example's `subject.symbol` may then be one of the glue methods the model lists as `traced`.
2. Write `examples/demo/NNN-short-name/example.json`, following [`schema/example.schema.json`](schema/example.schema.json). An editor that understands JSON Schema will complete and check the fields.
   The `approach.id` picks the verifier, and the `subject.file` picks the subject system. For B9, `change.intendedInputs` declares the inputs the change is meant to affect. For B11, the property is the one declared for the symbol in the app's `properties.contract` ([Quorum](apps/quorum/src/contract/properties.contract), [Crosscut](apps/crosscut/src/contract/properties.contract), [Mica](apps/mica/src/contract/properties.contract)).
3. Run `python3 examples/demo/tools/build.py NNN`, and read the generated page.
