# Examples

Every example here runs a formal verifier over compiled Java and reports a verdict with its witness: *verified*,
*violation* with the input or the trace, or *unverifiable* with the reason. They are in one folder, numbered in one
sequence, and told apart by their fields and tags:

- **Constructed** examples (`origin: constructed`) are code changes written for this repository's four subject
  systems, each chosen to show what one verification approach catches that review and tests miss, or lets through.
  [`tools/build.py`](tools/build.py) applies each one's patch, runs the verifier, and generates its page, so no
  page claims a result the tool did not produce.
- **Real-world** examples (`origin: real-world`) are pull requests and commits to published Java libraries, verified
  from their bytecode with the [`/verify-bytecode`](../plugins/jvmcontract/README.md) skill, as they came. Each
  folder's README is the report.

## Find an example

The examples are meant to be searched: when you have a change to verify, a model to write or a verdict to explain,
look for the examples closest to it and read those, rather than all of them.

```bash
python3 examples/tools/find.py raft stale reply            # free text, ranked by tags, title, summary and notes
python3 examples/tools/find.py --tag liveness --approach D1   # filters; --tag repeats, and all must match
python3 examples/tools/find.py --system Mica --verdict violation
python3 examples/tools/find.py --list-tags                 # the vocabulary, with counts
python3 examples/tools/find.py --json idempotency retry      # for an agent: id, path, tags, summary, notes
```

Each example carries tags in three facets, from the vocabulary in [`tags.json`](tags.json):

- **domain**: what the code does (`leader-election`, `distributed-transactions`, `resilience`, `class-files`, ...);
- **defect**: what goes or could go wrong (`integer-overflow`, `stale-messages`, `liveness`, `crash-recovery`, ...);
- **technique**: how it is verified beyond the approach (`tla-liveness`, `tla-coverage`, `confined-change`,
  `jml-quantifiers`, `jdk-models`, ...).

Besides those: the approach (B8 to D1, below), the subject system, the verdict, whether the existing tests caught
it, the categories (functional, security, ...), the severity and the kind of change. [`index.json`](index.json) has
all of it for every example, with its notes; the sections [All examples](#all-examples) and
[Examples by tag](#examples-by-tag) below are the same, for reading.

A few starting points:

| If you are working on | Start with |
|---|---|
| The JVM itself, class files, or libraries close to it | 034 to 056 ([jvm-internals](#tag-jvm-internals)) |
| Spring Boot services: transactions, retries, breakers, idempotency, Kafka, JWT | 023 to 033 and 075 to 080 ([resilience](#tag-resilience), [idempotency](#tag-idempotency)) |
| Replicated systems: Raft, two-phase commit, clocks | 013 to 022, then [leader-election](#tag-leader-election), [log-replication](#tag-log-replication), [distributed-transactions](#tag-distributed-transactions) |
| A TLA+ model of your own | 011, 020, 059, then the [technique tags](#examples-by-tag) starting with `tla-` |
| A pull request to a library | 105 to 109 ([open-source-libraries](#tag-open-source-libraries)) |
| A verdict that seems wrong, or no verdict | [solver-limits](#tag-solver-limits), [jdk-models](#tag-jdk-models), [tla-coverage](#tag-tla-coverage) |

## Approaches

Six approaches, numbered as in [`approaches.md`](approaches.md). The common principle: a checked-in artifact may
change only where the developer intends a change, and the diff of that artifact is what the reviewer approves. None
needs the reader to write a specification: each verifier derives its statement from the code, the types, the
previous version, or a one-line property committed next to the code.

| Approach | What is checked | How it is proved | Examples |
|---|---|---|---|
| [B8 Behavioural contracts](tools/contracts/README.md) | A method's outcome on every input of a finite domain | Purity proved from bytecode, then every input executed | [B8](#approach-b8) |
| [B9 Regression verification](tools/contracts/README.md#regression-verification-methods-with-unbounded-inputs) | A method with unbounded inputs behaves as its previous version, outside the inputs the developer declared as changed | Both versions compiled into one program; JBMC proves the statement or finds a counterexample, replayed on the JVM | [B9](#approach-b9) |
| [B10 Capability contracts](tools/contracts/README.md#capability-contracts-what-a-module-can-do) | What a module's bytecode can reach: the clock, the network, randomness, reflection, class loading, threads | Closed-world inspection of every call site in the compiled classes | [B10](#approach-b10) |
| [B11 Property proofs](../lib/README.md#how-a-property-proof-works) | A property the developer states about a method, on every input: a postcondition, a law, with JML quantifiers over arrays, a throws clause, `\old` | A generated harness assumes, calls and asserts; JBMC proves it or finds an input, which the tool shrinks and replays | [B11](#approach-b11) |
| [B12 Boundary contracts](../lib/README.md#how-a-boundary-contract-is-checked) | Where Spring enters a module (routes, listeners, schedules, bean definitions, configuration keys), the advice on each bean (transactions, security, validation, caching, retries), and the places where an annotation does not do what it says: self-invocation, advice the proxy cannot intercept, a checked exception that commits, a lost `@Async` result, constraints never enforced, a GET with side effects; and under each entry point what it reaches (reads, writes, sends, calls, publishes) | The `RUNTIME` annotations read from the class files, with a closed-world walk over the module's own calls | [B12](#approach-b12) |
| [D1 Protocol model checking](apps/boxoffice/spec/README.md) | A protocol's safety invariants over every interleaving within bounds, deadlock, liveness under fairness, refinement, action properties, inductive invariants, and what each verdict rests on | TLC explores a TLA+ model whose state machines are generated from the kernels' B8 contracts, under each configuration the model lists | [D1](#approach-d1) |

The model-checking techniques each have a tag: [tla-liveness](#tag-tla-liveness),
[tla-refinement](#tag-tla-refinement), [tla-inductive-invariant](#tag-tla-inductive-invariant),
[tla-action-property](#tag-tla-action-property), [tla-symmetry](#tag-tla-symmetry),
[tla-history-variables](#tag-tla-history-variables), [tla-coverage](#tag-tla-coverage),
[tla-trace-validation](#tag-tla-trace-validation), [tla-fault-configuration](#tag-tla-fault-configuration),
[tla-unreachable-exception](#tag-tla-unreachable-exception), [tla-deadlock](#tag-tla-deadlock).

**Verdicts:**
- **✗ Violation:** behaviour changed, and the developer did not intend it. The build fails, with a concrete witness:
  an input whose outcome changed, a call site that gained a capability, or a run of the system that breaks an
  invariant.
- **✓ Verified:** the code behaves as its contract, its previous version, or its invariants say, for every input or
  interleaving within the stated bounds. An intended change passes once its contract is regenerated or its scope is
  declared, and that diff or declaration is what the reviewer approves. A model-checking verdict whose changed rows
  no run takes is labelled *vacuously*.
- **⚠ Unverifiable:** the verifier refuses to give a verdict, for example because the code is no longer provably pure
  or the solver did not finish. The build fails: "we could not check" must not read as "fine". Only JBMC's
  `VERIFICATION SUCCESSFUL` is a proof.

The *Existing tests* column is measured, not claimed: the generator runs the module's unit tests against each patch.
**missed** means the tests pass and the change would have shipped.

## How to read an example

A constructed example's page has the same sections every time:

| Section | Content |
|---|---|
| Summary table and tags | Verdict, categories, severity if the change shipped unnoticed, the kind of change, the verified unit, the approach; the tags, linked to the lists below |
| The change | What the developer meant to do, the code before and after, and the patch |
| What the verifier found | The counterexamples (inputs whose outcome changed, capability changes, or a trace of the system), the reason for refusing, or the contract diff; for a state machine, the machine the patched code implements |
| Would the existing tests have caught it? | The module's unit tests, run against the same patch |
| Why it matters, Why the verdict is right, What to do | The production risk, how the verifier reached its verdict, the resolution |
| Notes | What belongs to this example alone: the configuration it needs, the examples it pairs with, what to try next |
| Evidence | The verifier's console output and SARIF report, unedited; the JDK APIs a proof trusted; the generated statement a symbolic proof checked |

A real-world example's page is the `/verify-bytecode` report ([template](../plugins/jvmcontract/skills/verify-bytecode/report-template.md)):
the verdict per changed method, each finding with its witness and command, what no proof reached and why, and how
it was produced. Its `example.json` holds what the router needs, with its notes.

## Run an example

An agent working in this repository doesn't run examples inline: it queues them for the
[verification pipeline](../verification/README.md) with `python3 verification/pipeline.py submit --example ID`.
By hand:

```bash
python3 examples/tools/build.py 002              # run one constructed example, rewrite its page and the router
python3 examples/tools/build.py                  # run every constructed example: the Quorum ones take about ten minutes
python3 examples/tools/build.py --render-only    # rewrite every page and the router from the results there, running nothing
python3 examples/tools/build.py --index-only     # rewrite only the router
```

It needs Java 25, JBMC for B9 and B11, TLC (`~/tools/tla2tools.jar`, as [`setup`](setup/README.md) installs it) for
D1, and `cargo` (or a built `lib/target/release/jvmcontract`, or `JVMCONTRACT` pointing at one) for Quorum, Crosscut
and Mica; no Docker. A Box Office example takes from seconds to a minute, since its patch is applied to a copy of the
Gradle build; a Quorum, Crosscut or Mica example takes seconds, and a model-checking one up to a few minutes. A
real-world example is rerun with the commands in its report.

## Add an example

Take the next free number; constructed and real-world examples share the sequence.

**A constructed example:**

1. Make the change in your working copy, save it with `jj diff --git > examples/NNN-short-name/change.patch`, and
   undo the change. A Box Office D1 example changes the Java and the matching action of
   [`BoxOffice.tla`](apps/boxoffice/spec/BoxOffice.tla) in one patch; a Quorum, Crosscut or Mica D1 example changes a
   kernel a model is generated from, and the model picks the change up through the regenerated contract. `build.py`
   picks the model by `subject.symbol` and runs it under every configuration the model lists; how a model's
   configurations and trace writers are declared is in `build.py`'s model tables and the model's README.
2. Write `examples/NNN-short-name/example.json` following [`schema/example.schema.json`](schema/example.schema.json),
   with `origin: constructed`. `approach.id` picks the verifier and `subject.file` the subject system. For B9,
   `change.intendedInputs` declares the inputs the change is meant to affect, and when the method's signature
   changed, `change.previousSymbol` names the previous version, `change.previousArguments` gives its
   arguments as expressions over the new parameters, and `change.resultsAgreeWhen` relates a result that changed
   its type or meaning to the previous one (`previous == (result <= 0)`); for B11, the property is the one
   declared for the symbol in the app's `properties.contract`. For B9 and B11 on a javac app, `approach.engine: native`
   runs the tool's own checker instead of JBMC, for a method over integers; for B9, `approach.unwind` raises the loop
   unwinding bound when a loop of the method needs more than the default sixteen turns. A B9 subject may be a method
   of a record whose components are primitive, or take or return one: the proof is on the components; a static
   method that became a record's method is related to its previous version by `change.previousArguments` over the
   components (`this.start, this.size, failedIndex`), and a record whose components changed, or a record's method
   made static, by a constructor call among them (`new Backoff(this.baseMillis, this.capMillis), attempt`).
3. Tag it from [`tags.json`](tags.json): at least one domain and one defect tag, and the technique tags that apply.
   Add a tag to the vocabulary only when none fits, with a description that says when to reach for it.
4. Write its notes (below), and queue it for the pipeline (`pipeline.py submit --example NNN`), or run
   `python3 examples/tools/build.py NNN` and read the page.

**A real-world example:**

1. Run `/verify-bytecode <pull request>`. It leaves `report.md` and every harness, statement and JBMC log in its
   working directory. For a commit rather than a pull request, check out the commit and its parent into two worktrees
   and run the same proofs by hand, as 109 did. When a library's class reads a JDK class JBMC has no model of, a
   violation is an artifact until there is one: the tool's [models](../lib/models/README.md) are on the class path by
   themselves (`jvmcontract models` lists them), and a class beyond them needs a model added there.
2. Copy the report to `examples/NNN-<library>-<number>-short-name/README.md`. Keep every number tied to the run: the
   witness, the verdict lines and the times as the tool printed them, and the exact commands. Say what the run did not
   reach and why, and say so where a proof was made on a file compiled alone rather than by the library's build. Link
   the library's source rather than copying it.
3. Write its `example.json` with `origin: real-world`, `source`, `verdictLabel` (the verdicts in one line), tags and
   notes, and run `python3 examples/tools/build.py --index-only`.

Good subjects for real-world examples have small Maven or Gradle builds, an active pull request flow, and static
utility methods over primitives and primitive arrays, where the regression and property proofs land:

| Library | Build | Where the proofs land | Examples so far, and what to try next is in their notes |
|---|---|---|---|
| [Apache Commons Numbers](https://github.com/apache/commons-numbers) | Maven, multi-module | `ArithmeticUtils` (`gcd`, `lcm`, `pow`, `isPowerOfTwo`, `remainderUnsigned`, `divideUnsigned`), `Precision`, `DD` | [105](105-commons-numbers-223-pow-of-minus-two-to-the-31/README.md) |
| [Joda-Time](https://github.com/JodaOrg/joda-time) | Maven, one module | `org.joda.time.field.FieldUtils` (`safeAdd`, `safeSubtract`, `safeMultiply`, `safeNegate`, `safeToInt`), with `@throws ArithmeticException` in every Javadoc | none yet: `--only org.joda.time.field.FieldUtils#safeMultiply(long, int)` on any pull request shows the overflow contract proved, though no recent pull request touches `FieldUtils` itself |
| [Apache Commons Codec](https://github.com/apache/commons-codec) | Maven, one module | `Hex`, `BaseNCodec` helpers, `PureJavaCrc32`, `MurmurHash3` | [109](109-commons-codec-43a9aa66-hex-decoding-restricted-to-ascii/README.md) |
| [jackson-core](https://github.com/FasterXML/jackson-core) | Maven, one module | `NumberOutput`, `NumberInput`, `CharTypes` | [108](108-jackson-core-1203-division-by-1000-as-multiply-and-shift/README.md) |
| [Apache Commons Lang](https://github.com/apache/commons-lang) | Maven, one module | `ArrayUtils` over primitive arrays, `BooleanUtils`, `CharUtils`, `NumberUtils.compare` | [106](106-commons-lang-1750-reverse-with-min-value-end-index/README.md), [107](107-commons-lang-1585-subarray-length-overflow/README.md) |

What does not work well: `String`-heavy libraries (jsoup, Commons Text), anything whose build takes longer than the
proofs (Guava, Netty), and methods whose only parameters are objects. The limits are the tool's, in the
[library README](../lib/README.md#limits); the skill's [reference](../plugins/jvmcontract/skills/verify-bytecode/reference.md#costs-so-you-can-budget)
has the measured costs to budget by.

## Where notes go

Write what you learn about one example in **that example's `notes`** in its `example.json`: which configuration or
bound it needs and why, which examples it pairs with or contrasts with (by number), what made it hard, what to try
next. An agent often reads one example alone, so a note may repeat context that a shared page also has.

Shared pages say only what holds for many examples, and point at examples by tag or number rather than narrating
them: this page (the router), [`approaches.md`](approaches.md) (the approaches), the apps' and models' READMEs (a
subject system, a model and its configurations; one line naming an example as an illustration is fine), and
[`../lib/README.md`](../lib/README.md) (the tool). A new model configuration is documented in its model's README; the
examples it was made for say why in their notes.
