## Gating every edit

On Security 6.3.0 and Framework 6.1.7, the caller asks the fluent hierarchy's manager about a fresh authentication before each of three edits. A grant submits that edit to the existing binder. Every attempt observes the decision, submitted edit count, child values and reference identities, and field error with rejected value. The finite grid crosses both bean layouts, both role prefixes, six edit orders, and all 16 authority subsets independently at each step. [Public caller](companions/GatedHistories.java)

One oracle evaluates the role graph and updates two modeled children and an error ledger. The other looks up the release manager's decision and the binder state after the exact sequence of submitted edits in the earlier public JVM receipts. A separate observation of a new session supplies the empty sequence for each bean layout. Each route runs every public operation on newly constructed objects. [Runner and oracles](../../lib/benchmark/spring-java-data/gated_histories.py)

Four fresh JVMs each recorded the predicted **258,048 submissions and 36,864 declines** across 98,304 histories. All three attempts declined in 192 histories. The manager declined 10,752 attempts after the binder had already rejected `oops` for `backup.count`. Every one retained that error. The fresh and receipt-based oracles agreed on all 294,912 snapshots, including the 14,016 taken before any edit had been submitted.
