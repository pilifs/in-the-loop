# LLM traces

Every Claude Code session in this repo is published alongside the code it produced.
The aim is to make sharing LLM traces normal: a reader can see the code, the prompts,
the model's reasoning, and every tool call that led to each commit.

A session is Claude Code's or Codex's. A Codex session's log is its rollout file (`~/.codex/sessions/YYYY/MM/DD/rollout-<time>-<session id>.jsonl`), stored as a Claude Code transcript is: as it is, redacted, named by its SHA-256. Only reading differs: [`tools/codex_rollout.py`](tools/codex_rollout.py) gives a rollout's lines as entries shaped like a Claude Code transcript's, one for one and in memory, so the summary, the manifest, the metrics and `check` read both with the same code, and `manifest.client.tool` says which it was (`claude-code` or `codex`). A Codex session belongs to a checkout when it started in it (`session_meta.cwd`), and the session that runs a command is the one Codex names to it (`CODEX_THREAD_ID`), before Claude Code's, since a Codex started from a Claude Code session passes that session's variables on. A loop's run record names the thread that carried its session (`Codex thread THREAD carries session SESSION.`), which is how the loop statistics and the record's published copy find it. A thread that was only asked a question (`tools/ask_codex.py`) is not a session of the checkout: its record is the exchange file. A model with no row in `pricing.json` has tokens and no dollars, and a sum over it says how many calls it left out (`unpriced_calls`).

This page is the specification. [`llm-dlc/README.md`](README.md) has the procedure that agents follow, and the index of sessions.

## Layout

```
llm-dlc/index.json                                        checked in; one row per session
llm-dlc/traces/README.md                                  checked in; every session added up
llm-dlc/traces/metrics.json                               checked in; every session added up, as data
llm-dlc/traces/loops.json                                 checked in; every loop added up, as data
llm-dlc/traces/loops.md                                   checked in; the same, as a page
llm-dlc/pricing.json                                      checked in; list prices, written by hand
llm-dlc/allowlist.json                                    checked in; false positives by value, proposed and approved
llm-dlc/reviewed-findings.json                            checked in; false positives a person reviewed, by hash
llm-dlc/traces-readme-template.md                         checked in; the template for that README
llm-dlc/summary-template.md                               checked in; the template for summary.md
llm-dlc/session-notes/<session-id>.md                     checked in; optional, written by hand
llm-dlc/traces/<session-id>/manifest.json                 checked in
llm-dlc/traces/<session-id>/summary.md                    checked in
llm-dlc/traces/<session-id>/metrics.json                  checked in
llm-dlc/traces/<session-id>/runs/<record>.md              checked in; a loop run's record, redacted
llm-dlc/traces/<session-id>/logs/<sha256>.jsonl.gz        gitignored; uploaded to blob storage
llm-dlc/decisions/<name>.jsonl                            checked in; a parallel run's decisions, appended by decisions.py
llm-dlc/decisions/<name>.md                               checked in; the review view of that record, generated
llm-dlc/artifacts/YYYY/MM/DD/promotion-<id>.json          checked in; a promotion's summary, naming its private inventory
llm-dlc/publication-summary.schema.json                   checked in; what every such summary carries
```

- **Index:** the global manifest, a light list of every session with its title, time span, current log and the commits it made.
  It answers "which session made this commit" and "what happened in October" without opening every manifest.
  The same rows appear as a table in `llm-dlc/README.md`.
- **Traces overview:** `llm-dlc/traces/README.md`, totals and tables over all sessions: tokens, tools, commits and logs. It is rendered from the manifests and session notes alone, when it is published or asked for (see *Rendering* under [Workflow](#workflow)), and `check --rendered` fails if it does not match them.
- **Run record:** what `llm-dlc/tools/feature-loop.sh` wrote of one run in `llm-dlc/loop-summaries/<record>.md` (gitignored): the session it ran, the instruction, a line per commit and how the run ended. `sync` publishes a copy, each line redacted by the transcripts' rules, beside the session the record's header names, and that session's `summary.md` lists its runs under *Loop runs*. A record still being written is republished as it grows. `check` scans each copy: what the redactor would still change is an error, and what it leaves to judge a warning. Only the default workspace publishes records, and only of sessions with a trace there; the records of a run that worked in another workspace are published once they are copied into it (`run_records.py`), which no command of a run does today.
- **Session note:** a correction or context that the log and commits cannot give, such as work committed to another repo. It is written by hand, and appears as *Notes* near the top of `summary.md`.
- **Manifest:** the detailed metadata of one session, meaning one context window plus any windows after a compaction.
  It holds stats, the commits with their full messages, and every referenced log.
- **Summary:** the human-readable view of the session, rendered from `llm-dlc/summary-template.md`: each commit with the message the agent wrote, then each prompt with the final reply.
  It is in the same tree as the manifest, so the summary in a commit describes exactly the log that the commit points at.
- **Decision record:** what a parallel run's conductor decided without the user, and the questions it queued for them (`llm-dlc/loops/stream-conductor.md`, Design 3 and 4). One JSON line per change of state, validated against `llm-dlc/decisions/schema.json`; `llm-dlc/tools/decisions.py` writes it, and nobody edits it by hand. The review view beside it is rendered on every sync and by `regenerate`, and `check` fails if a record breaks the schema or the rules the schema can't state (seq order, ids that exist, a decision the conductor may not take alone, a review it wrote for the user), if its view does not match it, or if the redactor would still change something in it.
- **Log:** the full redacted transcript (prompts, responses, thinking, tool calls and results, and raw API request records), stored gzipped.
  Subagent transcripts are separate logs in the same folder, listed under `subagents`.

Metadata is split this way, a small global index plus a detailed file per session, for two reasons.
A session's manifest changes on every turn of that session only, so separate sessions never edit the same detailed file.
The index is small and fully derived, so a merge conflict in it is resolved by running `sync.py sync`.

## Identifiers

These are the stable part of the design. Everything else may change.

| Identifier | Definition | Properties |
|---|---|---|
| **Session ID** | The UUID that Claude Code assigns to a session, or Codex to a thread | Names the folder and is the Langfuse session ID |
| **Log ID** | `sha256` of the **uncompressed** redacted JSONL | Content-addressed: the file `<sha256>.jsonl.gz` never changes. A new state of the transcript is a new file. Any blob store keyed by the hash can serve it. |
| **Commit → trace** | One message line per session: `LLM-Trace: <session-id> sha256:<log-sha256>` | Standard git trailer syntax: `git interpret-trailers --parse` reads it |
| **Links** | Commits made before 2026-11-21 carry two lines above it: `LLM-Trace-Summary:` (the summary on GitHub, on the `main` branch) and `LLM-Trace-Log:` (the log on the CDN) | For readers only, and no longer written: both said where things would be after a promotion that had not happened yet. Tools ignore them, and take a commit with or without them. `sync.py trace REV` says what a commit's identifier resolves to now: the session, its summary, and its log, public at its URL, withdrawn, or pending and where it waits |
| **Trace → commits** | `manifest.commits[]`: each entry has a jj `change_id` (survives rewrites), plus `commit_id` (the git SHA) once the commit is immutable | Derived from the commit trailers on every sync, so the two directions agree |

**Invariants**, which `sync.py check` verifies:

1. Every `sha256:` in a commit message names a log whose content hashes to that value.
2. A log that a commit points at contains the whole conversation up to that commit.
   Logs are append-only: a later log of the same session starts with the exact bytes of every earlier one.
3. For a commit made with `jj trace-commit`, the `manifest.json` inside that commit's tree has the same `log.sha256` as the commit message.
   Older commits keep their manifest where the layout was at the time: `traces/<session-id>/manifest.json`, then `changes/traces/<session-id>/manifest.json`.
   This holds for a plain `jj commit` or `git commit` too, because a hook reopens the new commit and syncs into it. If `@` already holds trace files, the hook leaves the commit for the next sync, which stamps it with a newer log, and `check` notes that.
4. The tools never change a pushed (immutable) commit. A change gets its `LLM-Trace` line once, when it is committed.
5. `@` stays empty unless someone is working: only `commit` and `push` write tracked trace files, and `push` writes nothing after it pushes.
   So a pushed manifest does not know its own commit's SHA. The next commit records it.

A log's bytes depend on the redaction rules, so `manifest.redaction_policy` records the version.
A new policy produces new log IDs. Logs that commits already point at are kept.

## Manifest fields

| Field | Content |
|---|---|
| `schema` | `llm-trace-manifest/v1` |
| `session_id`, `status` | `open` if the transcript changed in the last 10 minutes when last synced, otherwise `ended` |
| `title`, `first_prompt`, `client`, `models` | What the session was and what ran it. `client` is `{tool, version}`, for example `claude-code` |
| `started`, `ended`, `duration_seconds` | Time span |
| `stats` | Turns, API calls, tool calls and errors, compactions, peak context tokens, and token usage (input, output, cache read, cache write) |
| `tools` | Count of calls per tool |
| `files_touched` | Files written by Edit and Write (repo-relative) |
| `context_windows[]` | The same stats for each window between compactions |
| `log` | The current log: `sha256`, `bytes`, `lines`, `gzip_bytes` and the local `path` |
| `subagents[]` | For each subagent: its stats and its own `log` |
| `commits[]` | Oldest first: `change_id`, `commit_id`, `immutable`, `summary` (null until described), `body` (the message without its summary line and trailers), `log_sha256` |
| `logs` | Every log still referenced (the current one, subagent logs, and each log a commit points at), keyed by `sha256`: `bytes`, `lines`, `gzip_bytes`, `url` once uploaded, and `withdrawn` (the reason) if it was taken down after publication |
| `redaction_policy`, `generator` | How the files were produced |

The manifest is derived data. It is rebuilt from the transcript on every sync, and `summarize()` runs on the redacted entries, so it can also be rebuilt from a published log. Changing its schema is cheap; the identifiers above are not.

## Metrics

`metrics.json` holds what a chart needs, so nobody has to parse a log to draw one. `sync.py` writes it when the session is rendered (at a promotion, a push, or a sync by hand: see *Rendering* under [Workflow](#workflow)), using `tools/metrics.py`, next to the summary it belongs to. Like the manifest it is derived data, and changing its schema is cheap.

It is a function of three inputs and nothing else: the session's current log, its manifest, and `llm-dlc/pricing.json`. So it contains no clock, and `check` rebuilds it and fails if it differs. `check` also fails if its token totals differ from the manifest's, which are counted by separate code, and warns about a model with no price. Free text (prompts, tool labels, error heads) is cut to 200 characters and redacted again after the cut, and the file is scanned like the summary. The file is JSON with one table row per line, so a commit's diff is the rows it added.

The file holds no row for a single model call or tool call. Until 2026-11-21 it did (`llm-trace-metrics/v1`, tables `calls[]` and `tools[]`), and those two tables were 48 MB of the 51 MB the 207 session files came to, 9 MB of them in one two-day session's file, rewritten whole each time. They are the same function of the same three inputs, so they are not stored anywhere: the file names their text by its length and SHA-256 (`events`), and `python3 llm-dlc/tools/sync.py events SESSION [--to FILE]` builds it again from the session's log, read from this workspace or from its public URL and checked against its name, and says whether it is the text the file names. It is, at the revision that rendered the file; under a later price list or `metrics.py` the rows can differ, and the command says so. The text is `llm-trace-metrics-events/v1`: `session_id`, `source`, `pricing_as_of`, and
- `calls[]`, each model call: `seq`, `agent`, `line`, `start`, `end`, `window`, `prompt`, `commit`, `model`, `effort`, `stop_reason`, `context_tokens`, usage, `thinking_ms`, `tools`;
- `tools[]`, each tool call: `seq`, `agent`, `line`, `name`, `call`, `prompt`, `commit`, `start`, `end`, `ms`, `status` (`ok`, `error`, `no_result`), `error_kind`, `result_chars`, `family` (the program, for Bash), `label`, `error`.

A file written before then is still read (`metrics.bounded` gives the same file from it, with no log needed), and the next rendering rewrites it; `check --rendered` reports one that is left.

**Session file** (`llm-trace-metrics/v2`):

| Field | Content |
|---|---|
| `source`, `pricing_as_of` | The log the file was built from, and the price list used |
| `totals` | Prompts, commands, commits, compactions, subagents, tool errors, peak context, and the usage block below |
| `after_last_commit` | The usage block for work no commit points at yet |
| `time` | `elapsed_ms`, `agent_ms`, `model_ms`, `tool_ms`, `busy_ms`, `compaction_ms`, `paused_ms` (see *Time*) |
| `reported` | What Claude Code itself counted, or null (see *Cost*) |
| `by_model`, `by_effort`, `by_tool`, `by_bash_family`, `by_cache_cause` | Group totals, most expensive or most used first |
| `by_day[]` | The usage block of the model calls that started on each UTC day |
| `windows[]` | One row per context window: span, prompts, peak context, usage |
| `compactions[]` | `ts`, `line`, `window` (the one it starts), `trigger`, `pre_tokens`, `post_tokens`, `ms` |
| `pauses[]` | Gaps of 30 minutes or more between records: `start`, `end`, `ms`, `after_prompt` |
| `commits[]` | Oldest first: `change_id`, `summary`, log sizes, `ts`, and the prompts, agent time and usage since the commit before |
| `prompts[]` | Each thing that started work: `kind` (`human`, `command`, `task_notification`), `text`, `chars`, `window`, `commit`, its usage, models and time, and of its model calls the `peak_context_tokens` (the session's own agent), the `efforts`, and `by_model[]` (`model`, `api_calls`, `usd`) |
| `cache_events[]` | Each large cache write and why it happened (see *Cache events*) |
| `events` | The per-call tables this file leaves out: `schema`, the number of `calls` and `tools`, and the `bytes` and `sha256` of their text |

The **usage block** is the same everywhere: `api_calls`, `tool_calls`, `input_tokens`, `output_tokens`, `thinking_tokens` (part of the output), `cache_read_tokens`, `cache_write_tokens` (which is `cache_write_5m_tokens` plus `cache_write_1h_tokens`), `usd`, `uncached_usd` and `unpriced_calls`. A row's numbers add up: the usage of `prompts[]`, of `windows[]`, and of `commits[]` plus `after_last_commit` each equal `totals`.

**Rollup** (`llm-dlc/traces/metrics.json`, `llm-trace-metrics-rollup/v2`): the same totals, time and groups over all sessions, plus `by_day`, `sessions[]` and `commits[]`, where a commit that several sessions worked on is one row naming each of them. It is a function of the session files and the manifests, and each sum in it is the sum of the sessions' own figures. Its `by_tool` and `by_bash_family` rows have no `median_ms`, which `v1` had: a median over all sessions cannot be had from each session's median, and each session's file has its own.

**Loops** (`llm-dlc/traces/loops.json`, `llm-trace-loops/v1`, and `llm-dlc/traces/loops.md`, the same rows as a page): what the unattended loops cost and produced, written by `tools/loop_stats.py` on every sync. They are a function of the session files, the manifests, the published run records and the verification jobs (`verification/jobs/` with `verification/results/`), so `check` rebuilds both and fails if either differs. Statistics never stop a commit: if they cannot be computed, both files say why instead, and `check` warns until `loop_stats.py` is fixed. A loop's turns are prompts like any other in a session file; the loops file only says which prompts were whose:

- **A run with a record** owns the prompts of the session its header names from its `Started` line to its end line. The n-th instruction among them starts cycle n, which is the record's `- cycle n` line when the cycle committed, and in a templated moonshot takes the n-th item of the header's list. A record with no end line (a run that was killed, or is still going) owns prompts up to the next run's start in that session, or up to the first prompt that is not the script's. Records give their times in UTC, as transcripts do.
- **A run with no published record** (every run before 2026-11-06) is read from the prompts alone: consecutive cycles of one instruction (a brief's `Work on the brief in ...`, or one of the first moonshots' one-liners, which `loop_stats.py` lists), ended by a prompt a person typed, by 30 minutes without a turn, by the loop's closing summary, or by the script's own count of cycles starting over. Its `source` is `transcript`.
- **The loop a person ran by hand** on 2026-10-31, before the script existed, is read from the prompts too: three instructions typed that evening, each followed by a commit and a typed `/compact`, which is the cycle the script was written that night to automate. It is the loop `examples-by-hand`, of kind `moonshot by hand`: counted with the moonshots, and told apart by its kind on every row, since no script capped a cycle, checked for a commit or compacted for it.
- **A session whose every prompt is `/run-verification`** is one run of the verification loop.

| Table | One row per | Content |
|---|---|---|
| `totals` | | Everything below added up, the number of verification jobs on record, and how many runs came from records and from transcripts |
| `categories[]` | `moonshot`, `brief`, `verification` | Loops, runs, cycles, cycles with a commit, commits, sessions, models, the usage block, time, jobs, and the median cycle |
| `loops[]` | loop name | The same, with `kind` (`moonshot`, `templated moonshot`, `moonshot by hand`, `brief`, `brief stream`, `verification loop`), `stream_of`, the instruction, and for a templated moonshot `items` and `items_done` |
| `items[]` | item of a templated moonshot | `status` (`done`, `attempted`, `pending`), `attempts` (the cycles that took it), the runs, its commit, usage and time over every attempt, its jobs, and `proof` (`passed`, `failed`, `pending`, `no job`) |
| `runs[]` | run | `run` (the record's name, or one made the same way from its first prompt), `source` (`record`, `transcript`, `session`), `record`, `session_id`, `started`, `ended`, `outcome` (`ended`, `stopped`, `interrupted`, `unrecorded`), `reason`, `model`, `effort`, cycles, commits, usage, time, `interjections` (prompts in it that are not the script's) |
| `cycles[]` | cycle | `run`, `cycle`, `item`, `started`, `ended`, `outcome` (`commit`, `no commit`), `decision`, `commits`, `changes`, `summary`, `turns`, usage, time, `compactions`, `context_tokens` (the context the closing compact found), `peak_context_tokens`, and its jobs |
| `jobs[]` | verification job a cycle submitted | `job`, `loop`, `run`, `cycle`, `item`, `attempts`, `final` (the last rerun), `status` (`passed`, `failed`, `pending`), `wall_seconds`, `cpu_seconds`, `peak_memory_bytes` |

Every cost includes the turns the script adds (the decision to go on, the status line, the compact, the closing summary, a stream's fork turn); `overhead_usd` and `overhead_ms` say how much of it they are. A commit is its cycle's when the session made it during one of the cycle's turns; one stamped on the session later, while it sat idle, is another session's. A job is its cycle's when it was submitted during the cycle and names the cycle's session (`pipeline.py submit` records the session Claude Code runs it in), or, naming none, is named in a commit of the cycle. A job that was rerun (`supersedes`) is one row: its last attempt is the verdict and every attempt's compute is added. `measured` is false for a run or cycle that a record lists but the session file does not reach yet: it counts its commits and no time or cost.

**How rows connect.** `prompt`, `commit`, `window`, `call` and `seq` are indexes into the tables of the same file. `line` is the line of the session's log, counted from 1, so any row can be found in the log. A commit's log is a prefix of the session's log and redaction works line by line, so the line count of that log says which calls came before the commit, even when the two logs were made under different redaction policies. A commit whose log was withdrawn has no line count and shows no work; that work moves to the next commit. Subagent rows have an `agent` id. Their `line` is in the subagent's own log, and they are placed in a prompt by time.

**Cost.** `usd` is tokens times the list price, and `uncached_usd` is what the same calls would cost if nothing were cached. Both are estimates of list price, not a bill: fast mode and web search are not priced. Logs leave out some calls, namely compactions and Haiku side calls, so the sum of `calls[]` is lower than the real cost. Claude Code writes its own count in a `cost-state` record when a session stops, and `reported` keeps the last one: `usd`, per-model usage, `api_ms`, `tool_ms`, lines changed, and `unattributed_usd`, the part of that cost that no call in the log explains. A session that has not stopped yet has no `reported`.

**Time.** `agent_ms` is the span from a prompt to the last record of its turn, summed over prompts. `model_ms` is the time covered by at least one model call, from the request to the last block of the response. `tool_ms` is the same for tool calls, and `busy_ms` for either. These are unions because tool calls run in parallel, so a sum would count overlapping time twice. `tool_ms` comes from timestamps, so it includes time spent waiting for a person to approve a call; `reported.tool_ms` does not.

**Cache events.** A call starts an event if it read under half of the previous call's context, which means the cached prefix was lost, or if it wrote 20,000 tokens or more with the prefix intact. `cause` is the first of these that applies, and `also` lists the others:

| Cause | Meaning |
|---|---|
| `session_start` | The first call of a session or subagent |
| `compaction` | A compaction came between this call and the last |
| `model_switch` | The model changed; caches belong to one model |
| `cache_expired` | The last call started longer ago than the TTL: an hour once the session has written a 1-hour entry, otherwise 5 minutes |
| `effort_change` | The effort level changed |
| `unexplained` | The prefix was lost and the log does not say why |
| `large_input` | One large input, such as a skill or a big tool result. `after_tools` names what the previous call ran, `later_calls` counts the calls in the window that read it again, and `reread_usd` is what those reads cost |

`tokens` is the size of the write, `write_usd` its cost, and `excess_usd` what it cost above reading the same tokens from the cache.

## Workflow

`.claude/settings.json` runs two hooks, and `sync.py` does the rest:

- **End of a turn or session** (`Stop`, `SessionEnd`, `sync.py hook`): sends finished turns to Langfuse (`http://localhost:3000`), if it is configured and running, and leaves the repo alone; without a configuration it reads nothing. It reads the transcript from a cursor kept with the session's Langfuse state in `~/.local/state/llm-traces/`: the start of the first turn not yet sent, used only while the bytes before it have the SHA-256 it recorded under the same rules and tools, so a turn costs about what that turn added. A transcript that was replaced or cut, or any under `LLM_TRACES_FULL=1`, is read whole, from the log `sync` last made of it where that still applies. Nothing depends on this: a transcript stays on disk until a commit or push records it. No finished turn is lost to a failure: the cursor and the record of sent turns move only after Langfuse accepted a send, a resend uses the same trace and span ids (derived from the session and the turn's prompt), so it overwrites rather than duplicates, and a session's state file is replaced atomically, a damaged one meaning a resend of everything. A hook marks its session (`hook_unsent`) before it reads anything and clears the mark once all it found was sent, so one that Langfuse refused, that failed, timed out or was killed leaves the mark, the next hook of that session retries from the cursor, `check` warns about a mark older than two minutes, and `sync.py langfuse SID` (or `--all`) sends the turns by hand, from the transcript while it is on this machine (holding back the last turn of a session written to in the last ten minutes) and from the stored log otherwise. A session no sync has stored a log of yet is sent all the same.
- **After a shell command** (`PostToolUse`, `sync.py hook-commit`): if the command was a plain `jj commit`, `jj new` or `git commit`, traces the new commit as below.
- **Codex.** Both commands read the same payload from Codex, whose `transcript_path` is the session's rollout: from `.codex/hooks.json` in a checkout a person trusts and has reviewed the hooks of, and from `tools/agent_client.py` after each turn of a loop it carried, where Codex would not load a project's hooks. A Codex log is sent to Langfuse read whole, each prompt remembered by an id made of its turn and line, so no turn is sent twice.
- **On a commit** (`sync.py commit`): syncs each session whose inputs or outputs changed since it was last synced, which always includes the one committing (named by Claude Code in `CLAUDE_CODE_SESSION_ID`, besides any whose transcript changed in the last 10 minutes); a session left alone is one that syncing again would not change (see [Local caches](#local-caches)). For each, it redacts what the transcript gained since the last commit, stores a new log snapshot, rewrites the manifest, the summary, the metrics, the index and the overview (each file only if its content changed, and the files over all sessions once, after the last session), stamps the `LLM-Trace` lines, and deletes logs that nothing points at. Earlier changes made in a session get a line only if they lack one. After `jj new` it runs `check` on the result, with the caches below, so the check costs what the commit added rather than the whole history: it prints errors and warnings, counts the notes, and fails if there is an error, though the commit stands. A plain `jj commit` traced by the hook is not checked. A commit does not contact Langfuse: the end-of-turn hook sends finished turns, and `sync.py langfuse SID...` sends those of a session whose hook ran while Langfuse was down or failed.
- **On a push** (`sync.py push`): does the same, stamping `@` for every session with log that no commit points at, runs `check`, uploads the logs, runs `check` again, and freezes `@` as a *Record session traces* commit. It makes that commit only if a log or upload is new, so a repeated push changes nothing. The first `check` runs before anything is uploaded, and the upload itself refuses a log in which the current redaction rules would still change something, so a leak that the rules know about cannot reach the CDN. The second `check` reads the files on disk, so before `jj git push` a last gate reads the revisions the push would move bookmarks to (those named by `--bookmark`, `-r`, `-c` or `--all`, otherwise every bookmark ahead of the remote ones) from git: each must hold, byte for byte, the trace files that `check` read (manifests, summaries, metrics, session notes, the index, the overview, the rollup, the two loops files and the two review lists), and no other file where those live, such as a log; and every `LLM-Trace` line of a commit that the push makes public must name a log whose manifest records its URL, or that was withdrawn. Otherwise nothing is pushed. It costs one `git ls-tree` per revision and a hash of each of those files.
- **Rendering.** The files generated from the manifests and the logs are a session's `summary.md` and `metrics.json` and, over all sessions, `index.json`, the table in `llm-dlc/README.md`, `traces/README.md`, `traces/metrics.json` and the loops' two files. Until 2026-11-21 every commit rewrote them: twelve generated files a commit, megabytes of them for a long session, and a conflict in the global ones at every merge of two lines. Since then a commit and the commit hook write the session's `manifest.json` alone (and a session's first commit its summary and metrics, so that links to them resolve). The rest is rendered when it is published or asked for: by `sync.py promote` in its candidate workspace, by `sync.py push`, and on demand by `sync.py sync` (also spelled `sync.py render`) and `sync.py regenerate`. A session whose transcript is in another workspace's folder, as every session is for a promotion's candidate, is rendered from its stored current log and its manifest, which records the workspace path the summary shortens file names by. So on `develop` these files describe the sessions as they were at the last promotion, and on `main` they are current. `check` compares them with their inputs only when asked (`check --rendered`, as a promotion and a push ask); it always scans them for what the redactor would change, and always checks the manifests, the logs and the trailers.
- **What `check` says besides the traces** (VF-053): an example whose `records/` hold more than 50 loose per-case files in one `cases/` folder is an error, with the command that packs them (`examples/tools/targets/case_pack.py pack ID`; the bytes stay in the repository, in one file a folder); more than 2,000 files under one example's `records/`, or 1,000 entries in one of its folders, is a warning. One hundred commits of the line on neither `develop` nor `main` is a warning too: a checkpoint publishes them. So is a verification result submitted since 2026-11-22 whose `result.json` is over 256 KiB (`verification/layout.py`): a receipt lists every output file, and one that lists thousands says its job should pack them.
- **One at a time** (`Operation` in `sync.py`): every command that writes (`sync`, `commit`, `push`, `upload`, `unpublish`, `stamp`, `allow`, `review`, `init`, and the commit hook) holds an exclusive lock on the repository while it runs; `check` and `scan` hold it shared, so they never read a sync half done. A command that finds it held says which command holds it and waits; the commit hook waits at most 15 s and otherwise leaves the commit to the next sync, which stamps it anyway. The Stop hook takes no lock: it writes only its own cursor. Before each step that an interruption would leave half done, the command writes it to a journal, and clears it after: the commit hook's switch of the working copy to the commit it records, a commit's describe-to-`jj new`, a sync's sessions and global files, and a push's stages. A command that is killed leaves the journal behind, and the next writing command recovers it before it starts: it puts the working copy back if it is still on the recorded commit, rebuilds the global files, and names what an interrupted commit or push left to be run again. SIGTERM and SIGHUP (a hook's 60 s timeout, a closed terminal) unwind like Ctrl-C, so the working copy is put back at once. The lock is `flock`, released by the kernel when its holder dies, and it, the journal and the holder's name are local, in `~/.local/state/llm-traces/locks/`, keyed by the repository's path. Taking the lock costs about 0.1 ms, and the first journaled step one `jj op log` call (about 11 ms), which the journal records so `jj op log` can show what an interrupted command did.

```bash
python3 llm-dlc/tools/sync.py init      # once per clone: jj file-size limit and the two aliases below
jj trace-commit -m "Summary line" -m "Body"   # finish @; its message and its manifest point at the same log
jj trace-push --bookmark main          # record outstanding traces, upload, check, push; leaves @ empty
python3 llm-dlc/tools/sync.py check     # verify hashes, trailers (in the history of @) and redaction
python3 llm-dlc/tools/sync.py check --rendered  # and that every generated file is what its inputs give, as a promotion asks
python3 llm-dlc/tools/sync.py render    # bring the summaries, metrics, index and overview up to date now (the same as `sync`)
python3 llm-dlc/tools/sync.py trace REV # what a commit's LLM-Trace line resolves to: session, summary, and the log's state
python3 llm-dlc/tools/sync.py regenerate  # after a merge: rewrite the generated trace files and decision views, settling their conflicts
python3 llm-dlc/tools/sync.py check --full  # the same, trusting no cached result (LLM_TRACES_FULL=1 for sync and push too)
python3 llm-dlc/tools/sync.py scan      # preview a publish: what was redacted, what to look at (writes nothing)
python3 llm-dlc/tools/sync.py sync --all  # backfill every session of this repo (plain `sync`: only those that changed)
python3 llm-dlc/tools/sync.py perf      # where the last commands' time went (LLM_TRACES_PERF=1 prints it as each ends)
jj log -r 'description(substring:"LLM-Trace:")'   # changes that have traces
```

Plain `jj commit` and `jj describe` also work. The hook adds the `LLM-Trace` lines on the next turn.

## Storage

Logs are gitignored in the repo and published on Cloudflare at a deterministic URL:

```
https://terminalvalue.net/raw-traces/<session-id>/<sha256>.jsonl.gz
```

so anyone can turn the `LLM-Trace:` line of a commit into a download, then check it:

```bash
curl -s https://terminalvalue.net/raw-traces/<sid>/<sha>.jsonl.gz | gunzip | sha256sum   # equals <sha>
```

- **R2 bucket `llm-traces`** holds the files. The object key is the URL path.
- **Worker `raw-traces`** ([`llm-dlc/infra/cdn/`](infra/cdn)) serves them on the route `terminalvalue.net/raw-traces/*`.
  It runs ahead of the Pages site on the same domain, so the site is unaffected and a site deploy cannot remove the logs.
  It is read-only (GET and HEAD only), rejects keys that are not `<uuid>/<64 hex>.jsonl.gz`, serves `application/gzip` without re-encoding, and caches each log at the edge forever (`immutable`).
- **`sync.py upload`** uploads only the logs that commits point at, plus subagent logs; it skips `@`, whose log changes every turn.
  After each upload it downloads the log again through the CDN, verifies its SHA-256, and only then records the URL in `manifest.logs[<sha256>].url`.
  It handles four logs at once (`LLM_TRACES_UPLOAD_JOBS`), so that the CDN reads overlap, and puts each log in R2 through R2's S3 API, signed with SigV4 from an R2 API token in `~/.config/llm-traces/r2-credentials` (`account_id=`, `access_key_id=` and `secret_access_key=` lines; create the token under R2 → Manage R2 API Tokens with *Object Read & Write* on the bucket `llm-traces` only). Puts then run as many at once as logs (`LLM_TRACES_PUT_JOBS` lowers it). Without that file it falls back to wrangler, one put at a time, since every wrangler process shares one OAuth login. `unpublish` deletes the same way. Before a put it verifies the stored `.gz` file against the log's name and scans the log, through the caches `check` keeps (by the `.gz` bytes, then by content), so a log `check` has just scanned is not scanned again; `LLM_TRACES_FULL=1` reads and scans everything. Each URL goes into its manifest as soon as the CDN serves the log, so an interrupted push keeps what it verified.
  `~/.local/state/llm-traces/uploads.json` is the upload record, local to the machine: each log a push started to upload, as *attempted* (written before the put, so the object may be in R2) or *verified* (the CDN served its content afterwards). A log not in it was never attempted from there. The next push names the logs an interrupted one may have uploaded; the manifests and the CDN still decide what is uploaded, and `unpublish` removes the log's entry.
  `jj trace-push` runs the upload before pushing, and its last gate refuses to push a commit that points at a log with no recorded URL, so no pushed commit points at a log nobody else can fetch.
- **`sync.py check --remote`** downloads every recorded upload again and checks its hash.
- **`sync.py unpublish <sid> <sha256> [--reason TEXT]`** takes a log down, for example after a redaction miss: it deletes the R2 object, purges the URL from every edge cache, and removes the URL from the manifest. With a reason, the log is *withdrawn*: the local copy is deleted too, the manifest records the reason under `logs[<sha256>].withdrawn`, the summary lists it under *Notes*, and `check` reports the commits that still point at it as a note rather than an error. The content is gone; the hash in the trailers still identifies what it was.
  Purging needs a Cloudflare API token that wrangler's login cannot grant. Create one with the permissions *Zone → Zone → Read* and *Zone → Cache Purge → Purge* for the zone only, and save it as `~/.config/llm-traces/cloudflare-token` (mode 600). Redaction removes the token from logs.

Deploying the Worker: `cd llm-dlc/infra/cdn && npx wrangler deploy`. Wrangler 4.149 uploads the script, then fails with error 10007 before it creates the route.
The route (`terminalvalue.net/raw-traces/*` → `raw-traces`) was created through the zone's Workers Routes API and already exists, so redeploys only need the script upload.

## Checkpoints

`sync.py checkpoint --rev REV` ([`tools/checkpoint.py`](tools/checkpoint.py)) puts one committed revision on `origin`'s `develop`, so that another agent, or a planner on another machine, can read the code while this machine is still at work. It is not a promotion: it runs no test, renders no trace file, uploads no log, waits for no proof job and no uploader, and confers no test, proof or release status. `main` moves only by a promotion.

- **What it reads.** Git objects and commit messages only. Every jj call it makes ignores the working copy, so another session's uncommitted files are neither snapshotted nor moved, and uncommitted work stays local: `REV` must name exactly one revision that has a description.
- **Where it pushes.** Exactly `SHA:refs/heads/develop` on `origin`, forward only: `develop` must be an ancestor of the revision, and the push carries the commit `develop` was read at, so it cannot land on a branch that moved meanwhile. Any other ref, remote, pattern or force is refused as an argument. If the push's answer is lost, the remote is read before anything is said, so a repeat is one logical push. `--bootstrap` creates `develop` at `main`'s commit, once.
- **What it refuses.** Everything the push would expose for the first time is read, through every outgoing commit and merge parent, since a file deleted at the tip still travels in the parent that held it. Refused: an unresolved conflict; a raw payload path (a session's log snapshot, a private run record, the runner's state, an environment or credential file, the private archive's spool); an unsafe file name; a blob over 16 MiB; a commit with no message or one that `commit --only` set aside; a recognisable credential, or this machine's own secrets or account identifiers, in any blob or message; anything the redactor would still change in a file the trace tools publish; and a redaction decision no person is recorded as having taken. The redactor's context-shaped kinds (`KEY=value`, a home directory) are refused in trace files only: in code and test fixtures they match ordinary text. A gzip blob is read as what it opens to, every member and whatever follows the last, since a pack of an example's per-case records (`examples/tools/targets/case_pack.py`) publishes each byte inside it; one that opens to more than 256 MiB is refused as unread.
- **Cost.** A blob's verdict is kept by its git id under the policy version, the rules and the decisions in force (`~/.local/state/llm-traces/outgoing-verdicts.json`, kinds and counts only), so a checkpoint scans the bytes that are new.
- **Receipt.** Written outside the tree, to `~/.local/state/llm-traces/checkpoints/SHA.json`, and sealed into the private archive as a `checkpoint-receipt`: the commits and tree, what was scanned, and the evidence status. A trace log is `public` when its session's manifest in the pushed tree gives its URL and `pending` otherwise; the private archive's custody is given by state, with what exists on this machine only.
- **Published means immutable.** After the first push the repository's jj configuration counts `develop@origin` among the immutable heads, so no later `sync.py commit` stamps a trailer on a commit others have fetched.

## Promotions

`sync.py promote --rev REV` ([`tools/promote.py`](tools/promote.py)) moves `origin`'s `main` forward to a commit of `develop`, and says three things of it that a checkpoint does not: the default test run passed for this tree, the logs its commits point at are published, and the originals behind it are verified in the private archive. `main` moves at the close of a brief or when the user asks, and work on `develop` goes on throughout. `sync.py push --bookmark main` and `/publish` remain as the older entry point, for a workspace with nothing uncommitted.

- **The frozen set.** `P` is `main` as the remote gives it, `D` the revision named, which must already be on the remote's `develop`. The promotion covers `ancestors(D) − ancestors(P)`, merge parents included, and nothing that lands on `develop` afterwards. A `main` that is not an ancestor of `D` was moved by another promotion: the command refuses, the line takes `main` in by an ordinary merge and is checkpointed, and that merge is promoted. `main` is never forced.
- **The candidate.** Built in a jj workspace of its own beside the default one (`REPO-promote`, made at the first promotion and kept), by that checkout's own tools, so no session's working copy is read or changed. The frozen commits' logs are taken from the workspaces that store them (`adopt-logs`), checked, and uploaded; a failure leaves what was verified, and the same command continues.
- **What blocks.** A frozen commit whose `LLM-Trace` resolves to no published or withdrawn log after the upload (its manifest does not list the log, or no workspace stores it): it is named. An original of a frozen job, session or commit that is not `remote_verified`: the promotion makes one upload pass itself, and names what is left. A job that has no original at all, because it was collected before capture began or on another machine, does not block: it is counted and listed as a gap. A failed trace check, a problem in the bytes the push would add, a redaction decision nobody is recorded as having taken.
- **The publication record** is one commit `C` on `D`, and holds generated files only: the logs' URLs in their sessions' manifests, the regenerated index and overview, and a summary, `llm-dlc/artifacts/YYYY/MM/DD/promotion-ID.json` ([schema](publication-summary.schema.json), at most 64 KiB). The summary gives `P`, `D`, counts of commits, logs and originals by kind and state, and names the private inventory, an ordinary occurrence in the archive that lists every commit, trailer and occurrence the promotion covers, by its occurrence id and SHA-256. A record that changes any other file is refused.
- **The gate.** A passed default run must cover `C`'s tree: the same tree, or one that differs from it only in files no test reads (`lib/tools/default_run.py`), which include `llm-dlc/artifacts/` and the generated session table of `llm-dlc/README.md`, and nothing else of that file. So a run of `D`'s tree covers `C`. When none does, the promotion runs the default run in the candidate, in a memory cap of its own. The gate's record, and the run's log when it ran, are sealed in the archive and must be verified there before `main` moves; a failed gate is recorded too, and leaves `main` at `P`. `--skip-tests REASON` is the user's alone, and the record carries the reason.
- **The pushes.** `C` goes to `main` only if `main` is still `P`, forward only; a lost answer is settled by reading the remote, so a repeat is one promotion. `develop` then goes forward to `C`; when it moved meanwhile, `C` is merged into its tip by an ordinary merge, the generated files are regenerated, and the merge is checkpointed, so later work is kept and the next promotion starts from `main`.
- **The receipt** is outside the tree (`~/.local/state/llm-traces/promotions/ID/receipt.json`, sealed as a `promotion-receipt`): `P`, `D`, `C`, the tree, the gate, the scan, what the remote answered and the time each step took. The state of a promotion under way is beside it, keyed by `P` and `D`; a restart reads it, reuses the record already built, and finishes a promotion whose push went out before its end was written.
- **The review view.** `--dry-run` prints it and changes nothing; a real run prints it first and keeps it as `review.md`. It leads with the source changes from `P` to `D`, one line a finished change, generated records counted apart; then the default run that covers the tree or the fact that none does, the open decisions, and the logs and originals by state, with the commands to drill down by job, session or commit.

## Original outputs

What a job, a run or a session produced is kept whole and private, apart from the redacted traces above, by [`tools/artifacts.py`](tools/artifacts.py). A producer hands its bytes to `capture` before it shortens, replaces or deletes them. This section is the contract; `python3 llm-dlc/tools/artifacts.py --help` lists the commands.

- **Occurrence.** One capture of one logical output: a job attempt's logs, a run's records, a segment of a session transcript. Its id is made at capture from the time, to the microsecond, and 40 random bits (`20261121T180102Z-0412839f2c41a07b`), and ids sort in the order they were made, so a path captured twice, or identical bytes captured twice, are two occurrences. An occurrence records its kind, run, session, job and attempt, the source commit, its logical path, when and where it was captured, and whether it is `complete`, `partial` (with the expected members that never materialized) or `missing` (a gap: nothing to keep, with the reason, whether the bytes were lost or never existed, and what derivatives survive).
- **Object.** Stored bytes, named by the SHA-256 of the *original* bytes they hold: a whole file, a part of a file over 256 MiB, a pack of files under 1 MiB (closed at 32 MiB), or a manifest. Stored gzipped at level 6 with `mtime=0`, as the trace logs are, unless the content is already compressed. The encoding, stored length and stored SHA-256 are recorded apart from the original length and SHA-256. An object is never rewritten, so identical content is stored once per access class.
- **Manifest.** The private inventory of an occurrence, as canonical JSON (`itl-original-manifest/v1`): every member's relative path, type (`file`, `dir`, `symlink`, `other`), mode, length and SHA-256, and the objects, offsets and lengths that hold its bytes. Empty files, links and special files are listed. Its own SHA-256 is the occurrence's inventory digest. On extraction a manifest is refused if a path is absolute or escapes, two members share a path, or a member lies under a file; a link that would leave the tree is reported and not made.
- **Stream.** An append-only file (a session transcript) is captured as segments: each records its generation, byte offset, length, predecessor and the SHA-256 of the whole prefix it completes, so any past prefix restores exactly. A file that no longer begins with what was captured (rotated, replaced, truncated) starts a new generation, whole. A sync seals two things this way, into restricted custody, so they start leaving the machine with the commit that follows them: the transcripts of the sessions it synced, and each file of the workspace's private run records (`llm-dlc/loop-summaries/`), of which only one whose size or time changed since it was last sealed is opened.
- **What else is sealed, and when.** The runner and the collector seal a job's attempt as it ends and as it is collected (`verification/capture.py`). Each attempt has a record and folders of its own on the machine that ran it (`jobs/attempts.py`), so a rerun clears nothing: an attempt whose runner was killed, or whose capture failed, stays where it is until `pipeline.py recover` seals it, and `pipeline.py prune` removes a work directory only once the original sealed from that very attempt is `remote_verified` and its job's result is collected. `python3 llm-dlc/tools/vm_inventory.py protect` seals what no producer does, and can be run again at any time: run and work directories from before the runner captured, what a person set aside from the runner's state (`verification/.state/set-aside/`, restricted, each work directory as what it holds beyond the commit its result names), and the example records of the runs it names. An example's records made outside a job are committed, packed and whole, so Git and `develop` are what keeps them.
- **Spool and journal.** `~/.local/share/in-the-loop/originals/` (`ITL_ORIGINALS_HOME`), on persistent disk outside the checkout, the runner's work directories and `/tmp`. Bytes are streamed to a temporary file, fsynced and installed under their name; then the occurrence's intake record is installed the same way; then a SQLite journal (WAL, full sync) commits it; only then is the capture acknowledged. `recover` journals an intake record a crash left behind and registers sealed files that no record names. A capture that would leave less than the reserve (2 GiB) free fails before it seals anything, and the producer keeps its source.
- **Custody.** `expected → locally_sealed → transferring → remote_verified`, and `retryable_error`, `missing_input`, `integrity_failure`. The uploader (`upload`, restartable, any number at once) commits each attempt before a byte moves, creates the object only if none is there, then reads the object back with a credential, decodes it and compares the original bytes' SHA-256 and length with its name; a size, an ETag or a successful PUT proves nothing. An object already there, from a lost answer or another worker, is judged the same way; other bytes under the same name are an `integrity_failure`, and the sealed copy stays in the spool. When every object of an occurrence and its manifest are verified, an immutable receipt is written to the store, last. `status` shows bytes and counts by state, the oldest unverified capture, disk headroom, retries, and how many original bytes exist on this machine only. Nothing in the tool deletes a byte, in the spool or in the store.
- **Storage.** Two private R2 buckets, with no public URL, no domain, and no binding to the Worker that serves traces: `in-the-loop-originals` (the *ordinary* class: job logs, outputs, diffs, results, work directories, example records, the redacted trace logs) and `in-the-loop-originals-restricted` (the *restricted* class: source transcripts, private run records, and every kind not yet listed as ordinary). Keys: `objects/sha256/<2 hex>/<sha256>.gz|.raw`, `intents/<YYYY>/<MM>/<DD>/<id>.json` (written at capture: a pending occurrence is discoverable), `occurrences/<YYYY>/<MM>/<DD>/<id>.json` (the receipt). For a restricted occurrence the ordinary bucket holds a stub under `restricted/` that says it exists, with no path and no inventory. Three tokens in `~/.config/in-the-loop/` (`r2-originals-writer`, `-reader`, `-restricted-reader`), each scoped to its buckets: the uploader writes, every project agent reads the ordinary class, and only the watcher's private analysis reads the restricted one. `artifacts.py canary` exercises all of this on made-up bytes.
- **Reading.** `list` (by run, job, attempt, session, source revision or digest; `--include-attempts` for every attempt of a job) and `show` tell pending, verified, restricted and missing apart, from the store's receipts, intents and stubs, and on the capturing machine from the journal. `fetch ID --to DIR` reads the receipt, the manifest and the objects, verifies every object and every member, and lays the members out under `DIR` at the occurrence's logical path; `--prefix` restores a stream as it was at that segment. What it verified stays in a private cache (`~/.cache/in-the-loop/originals-cache/`), so the same read works offline. Evidence that is missing, pending, restricted or damaged gives a specific *unavailable* answer, never other bytes. Reading queues no job, applies no output and changes no verdict.
- **Private analysis.** `analyze ID --purpose TEXT` returns lengths, counts and digests of a restricted occurrence, never its bytes or its members' names, and logs the id and the purpose first. It reads this machine's journal and spool when they hold the occurrence, and otherwise the store, with the restricted class's reader: the verified receipt and the inventory it names, checked against its digest, held in memory and kept nowhere.
- **Switching it off.** `ITL_ORIGINALS_OFF=1` makes every capture a no-op; the journal, the spool, the objects and the receipts stay as they are.

## Redaction

Traces are published, so `sync.py` redacts every JSON string, including keys, before hashing. This is redaction policy 7:

- **This machine.** Your home directory becomes `~`, your username becomes `user`, your hostname becomes `host`, and Windows account names in `/mnt/<drive>/Users/<name>` and `<drive>:\Users\<name>` paths become `user`. Your git, jj and Claude account emails (including the part before the `@`, in any letter case) become `user@example.com`.
- **Your accounts.** The identifiers Claude Code records (`organizationUuid`, `accountUuid`, `userID`) are removed wherever they occur: under those keys in the transcript, and inside strings, such as a transcript or `~/.claude.json` echoed by a tool. The same holds for the identifiers Codex records in a session's log (`creator_user_id`, `creator_account_id`, `chatgpt_user_id`, `chatgpt_account_id`), and the account usage Codex writes beside its token counts (`rate_limits`: the plan, the credit balance, how much of each limit is used) is replaced whole by `[REDACTED:account-usage]`. The opaque `signature` of thinking blocks is dropped, and the reasoning Codex records encrypted by OpenAI (any string under `encrypted_content`: reasoning items, content parts, compaction history) becomes `[REDACTED:encrypted-reasoning]`.
- **Local secrets.** The secret values in `llm-dlc/infra/langfuse/.env` and the Basic auth header built from them, the Cloudflare token in `~/.config/llm-traces/cloudflare-token`, the access key id and secret access key in `~/.config/llm-traces/r2-credentials` (not its account id, which is in every R2 endpoint), and wrangler's OAuth tokens in `~/.config/.wrangler/config/default.toml` are removed. Plain URLs in `.env`, such as `NEXTAUTH_URL`, are left alone.
- **Everyone else's email.** Every other email address becomes `[REDACTED:email]`, except addresses that are public by design or placeholders: GitHub noreply addresses, `noreply@anthropic.com`, `git@github.com`, and the `example.com`, `langfuse.local` and `localhost` domains.
- **Credential formats.** Anthropic, OpenAI-style `sk-`, Langfuse, GitHub, GitLab, AWS, Google, Slack, npm, Hugging Face, Stripe and SendGrid keys, Slack and Discord webhooks, JWTs, private keys, bearer and Basic authorization headers, passwords in URLs (`scheme://user:password@host`) and in `curl -u`, and the value of any `KEY=VALUE` or `"key": "value"` pair whose key says it is a secret (`PASSWORD`, `SECRET`, `TOKEN`, `API_KEY`, `_AUTH` and the like). Templates such as `${VAR}` or `<placeholder>`, expressions, paths, flags, and values shorter than 8 characters are left.
- **Your own list.** Extra literals in `~/.config/llm-traces/redact.txt` are applied, one per line, as `literal` or `literal => replacement`.

Every rule leaves its own output alone, so redaction is idempotent and `check` can run the same rules over a finished log: anything they would still change is reported as `unredacted`, and the upload refuses such a log. A policy change therefore also audits the logs that are already published: what the new rules find in them is reported as a warning, not an error, because the only remedy is `unpublish --reason` and whether a finding is worth that is a person's call. Once a person has decided to keep a log up, its hash goes in `ACCEPTED_LOGS` and the warning becomes a note. Acceptance is by hash, so a later policy that flags other published logs warns about them.

The rules live in `tools/redaction_rules.py`, which ends with a stamp: a hash of the file above it and the date the rules were last applied to everything. A transcript or log older than that date counts as checked, so `check`, `scan`, `review` and `sync` don't scan it again. `sync` reuses the log it stored, and any findings in that file are no longer reported, which `check` says in a note. Editing the rules voids the date, so every file is scanned until `sync.py stamp` has rescanned them and recorded a new one. It refuses while errors are open, because they would stop being reported. An open warning does not hold it up: it is added to the allow list as a proposal (without its value), and `check` warns about the proposal until a person approves or drops it. An edit that changes no result, such as a speed-up, keeps the old date instead: `sync.py stamp --equivalent` compares the edited rules with the stamped ones committed at `@-` on every distinct line of every transcript, stored log and published file (redaction, and findings before and after redaction), and writes the new hash with the old date only if nothing differs. The date then still says which files have been checked, because the edited rules would have found the same in them. `upload` still scans each log it sends, as the last check before a log goes public, but takes the result from the scan cache when `check` has already scanned exactly that content under the same rules. A log older than the stamp, which `check` leaves out, is scanned here all the same.

`check` reports three levels. An `ERROR` must be fixed and fails the command. A `warn` is for a person to judge and does not fail it. A `note` needs no action, and is grouped per session rather than printed per log.

**Reviewed false positives.** A finding that a person has judged harmless would otherwise come back with every new log snapshot, so `llm-dlc/reviewed-findings.json` records it. An entry covers one kind and one exact value, named by a hash, with the reason, who decided and when. The same value is then left out of `check`, `scan`, `push` and the upload refusal wherever it appears, including in future logs, and a different value of the same kind is still raised. `check` notes how many findings it left out, and fails if an entry has no reason, no author or no date. This works for errors as well as warnings, except for `local-secret` and `account-id`: a match there is this machine's secret or account by construction, so no entry can waive it. `ACCEPTED_LOGS` is different: it accepts whole published logs whatever they contain, and is kept for the 13 logs reviewed that way.

```bash
python3 llm-dlc/tools/sync.py review                               # open findings, masked, with ids
python3 llm-dlc/tools/sync.py review accept <id>... --reason "why"  # a person, at a terminal
```

Listing is open to anyone. Accepting is a person's decision: the command shows the real value, asks for a typed confirmation, and refuses a shell with no terminal or one that Claude Code started. The project settings also deny agents direct edits to the list. These stop an agent acting by accident, not one set on getting round them, so the record that counts is the file's history: the list is published, and each change to it is in a commit with its session. The first four entries were authorized in chat by the maintainer on 2026-10-31, before the command existed, and say so.

**The allow list.** Accepting by id means finding the value again, which takes a scan of every file newer than the stamp, and a class of false positives (version numbers that look like addresses) used to be settled by a new rule, which voids the stamp and rescans everything. `llm-dlc/allowlist.json` settles them by value instead, without touching the rules. An agent that judges a finding a likely false positive proposes it by id, with a reason; the proposal holds the kind and the masked value, never the real one. A person approves proposals at a terminal: the command shows each real value with its count and where it occurs, asks for one typed confirmation for all of them, and writes the value into the entry. Values come from a cache of the last scan's findings (`~/.local/state/llm-traces/finding-values.json`, readable by its owner only), so neither proposing nor approving scans unless an id is not in it. Approved values are left out the same way as reviewed ones, and since the list is data, not rules, the stamp stays valid. A person can also add a value before anything finds it.

```bash
python3 llm-dlc/tools/sync.py allow                                       # entries: approved values, proposals masked
python3 llm-dlc/tools/sync.py allow propose <id>... --reason "why"         # anyone, an agent included; commits it (--no-commit)
python3 llm-dlc/tools/sync.py allow approve [<id>...] [--no-commit]        # a person, at a terminal; commits it
python3 llm-dlc/tools/sync.py allow vouch                                   # a person, at a terminal: see below
python3 llm-dlc/tools/sync.py allow add <value> --kind <kind> --reason "why" [--no-commit]  # likewise
python3 llm-dlc/tools/sync.py allow drop <id>...                           # remove entries
```

A decision in `allowlist.json` (an approved entry) or `reviewed-findings.json` is a person's. The commands that write one refuse an agent's shell, and they record each decision they wrote on the machine (`person-decisions.json` in the state folder: the entry's digest, never its value). `check` reports as an error a decision in either file that is neither in the file as published (at the newest immutable ancestors of `@`) nor in that record, so an entry written by a patch, by an agent of any client, is found at its next commit and before a push. The published commits are asked only when the two files change. A person who did take a decision the record lacks (made with an earlier version of the tool, or on another machine and not yet pushed) says so with `allow vouch`, which changes neither file. Until it is settled, such a decision waives nothing: the redactor is given only the decisions that are published or recorded, so the finding stays raised. `sync.py decisions [--at REV]` asks the same of this working copy or of a commit (status 1 when there is one), and `land` asks it of a workspace's line before merging it. The record is a file an agent could write too: it catches a decision made by mistake or by habit, not one forged on purpose.

The list is published with its values, so it takes only the kinds that the redactor leaves in a log and that are published anyway once accepted: `public-ip`, `ipv6`, `mac-address`, `other-home-dir`, `auth-header` and `long-token`. A finding of a kind the redactor removes would be published by the list itself, so it goes through `review accept`, which keeps only a hash. An approval or addition commits itself, so the decision never waits in `@` (where `push` would refuse it): with nothing else changed in `@`, as `sync.py commit` does, trace lines and check included; with other work in `@`, the allow list alone (`jj commit PATH`), leaving that work in place. A described `@` is left alone, and `--no-commit` leaves the decision uncommitted. `check` warns while proposals wait for a person, and fails if a proposal holds a value, an approved entry's id does not match its kind and value, the rules would not find the value as that kind, or the value holds something the redactor removes.

Not everything can be a rule. **Read a log before you upload it.** `sync.py scan` previews what a push would publish for each session: the redaction markers by kind, and *warnings* about things no rule removes and a person should judge: public IP addresses, home directories of other users, authorization and cookie headers, long mixed-case tokens of unknown format. A four-part version number looks like an IP address, so one is skipped only when its surroundings say it is a version, such as `openjdk version`, `java.base@`, or an SDK listing row; `root@<ip>` still warns. `check` prints the same warnings for logs that are not yet uploaded, and `push` prints them for each log as it goes up. Output is masked, because it lands in the transcript of the session that runs it.

The agent itself is a common leak vector: while building or testing a redactor it tends to grep its own transcript, or to paste a real identifier into a test. Use made-up values in tests, and keep raw transcripts and `~/.claude.json` out of tool output.

**Delegated decisions.** A person can let the watcher of one run take the routine decisions, so that a run's findings do not wait for them ([`tools/delegation.py`](tools/delegation.py)). It is off until a person turns it on, and they turn it off again whenever they choose:

```bash
python3 llm-dlc/tools/sync.py delegate status                # on or off, for which watcher, and whether the record verifies
python3 llm-dlc/tools/sync.py delegate request --run NAME    # the watcher asks; prints a code
python3 llm-dlc/tools/sync.py delegate on CODE [--fresh]     # a person, at a terminal, grants that request
python3 llm-dlc/tools/sync.py delegate off                   # anyone
```

- **Who the watcher is.** The client process (Claude Code's or Codex's) that made the request, by its pid, start time and the machine's boot. A command is the watcher's when the nearest client process above it is that one. A variable in the environment or a file in the checkout says nothing, a worker the watcher started is not the watcher, and a watcher that ended decides nothing more. No command of the watcher asks for a terminal or pretends to be a person.
- **What it may decide.** `delegate approve ID... --evidence KIND:DETAIL --reason TEXT` approves allow-list proposals whose origin the command itself checks: the value is in a file `main` already publishes (`main-file:PATH`), in a committed fixture (`tracked-file:PATH`), is a digest of a committed file (`content-digest:PATH`), the id of an object of this repository (`git-object`) or the name of a log (`trace-log`). `public:URL` records a stated origin without checking it, and is refused for a `long-token`, whose shape alone establishes nothing. The kinds the redactor removes are refused as they are for everyone, and there is no approval by category: each id is named. `delegate withhold SESSION SHA256` keeps a log that is not uploaded out of publication for good: it is sealed in the restricted archive, removed from the workspace and marked `withdrawn` in its manifest, so a trailer that points at it resolves truthfully. `delegate mask ID...` adds an ambiguous value to this machine's own redactions (`~/.config/llm-traces/redact.txt`), so every later log omits it, and withholds the logs not yet uploaded that hold it. None of these prints a value.
- **What stays a person's.** Accepting a finding the redactor removes (`review accept`), taking a published log down (`unpublish`), anything that would broaden what is public, and a credible live credential. For those the watcher contains what it can and writes one masked escalation (`sync.py review escalate ID... --reason TEXT`, open to any agent): `check` warns of it until a person closes it (`review close`). A masked value that a published log already holds is escalated by the command itself.
- **The record.** One line a decision in `~/.local/state/llm-traces/watcher-decisions.jsonl`, outside every checkout: the actor, the run, the session, the finding's id, a digest of the entry as written, the action, where it applies, the redaction policy, the reason and the evidence with a digest of the bytes it rested on. Each line names the hash of the one before and is signed with a key kept beside the archive's tokens, and the file is sealed into the restricted archive as it grows. It holds ids and digests, never a value.
- **When a decision counts.** `check`, `land`, `checkpoint` and `promote` take a decision in `allowlist.json` as taken when it is in a commit a promotion put on `main`, or recorded as a person's, or recorded by the watcher with exactly the bytes the file now has, under the redaction policy in force, while the delegation is on. So an entry written into the file by hand fails, as do an entry edited after the decision, a line added to or changed in the record (nothing from that line on counts), and a decision taken under an older policy. A commit that is only on `develop` confers nothing: a checkpoint asks this question first.
- **Turning it off.** `sync.py delegate off` takes effect at once. The watcher's decisions that are on `main` stand; those that are not stop counting, `check` names them, and a person approves or vouches for them (`allow vouch`) or drops them. `delegate on CODE --fresh` for a new watcher does not carry earlier unpublished decisions over. Turn it off when the machine gains other contributors: every agent here runs as one user, so the record is evidence against a mistake or a careless edit, with the archive's copy as the one a forger would also have to change, and not a boundary between hostile processes.

## Local caches

Four files in `~/.local/state/llm-traces/` keep `commit`, `check`, `scan`, `review` and `stamp` from repeating work, and never change what they produce or report:

- **`transcript-cache.json`**: for each transcript, how many bytes of it were redacted into which stored log. Redaction works line by line, and a cut right after a newline byte divides the transcript, its decoded text and its lines at the same place, so the log of a longer transcript is the stored log's first part followed by the redaction of what was appended. That part is reused only if the transcript's first bytes still have the recorded SHA-256 and the stored log still holds the content its name says; an unfinished last line is redacted on its own each time.
- **`scan-cache.json`**: for each stored log, by the SHA-256 of what it holds (computed by `check` as it reads it, not taken from its name), what scanning it found: per kind, finding ids, masked values and counts. `check` scans a new snapshot only past the end of the longest earlier log of its session that is a prefix of it, and adds the counts. Reviewed false positives and the allow list are applied afterwards, as for a fresh scan, so deciding on a finding needs no rescan.
- **`check-cache.json`**: what `check` worked out from content besides scanning, each under the SHA-256 of exactly the content it came from. For a stored snapshot, keyed by the SHA-256 of its `.gz` bytes: the SHA-256 and length of what they decompress to, which decompression always gives the same way, so a snapshot read before is verified against its name without being decompressed again, and one whose bytes changed in any way is decompressed and hashed afresh. For a log, keyed by its content: the SHA-256 of its first n bytes for the lengths of earlier logs, for the prefix check. For a session's `metrics.json`, keyed by the content of its logs, its manifest, the file itself and `pricing.json`: whether the file is what they give.
- **`sync-cache-WORKSPACE.json`**, one per workspace (WORKSPACE is the first 16 hex digits of the SHA-256 of the checkout's path; until 2026-11-25 all workspaces shared one file and emptied each other's entries, VF-069): for each session, its state right after it was last synced: the size, modification time and inode of its transcript and subagent transcripts (taken before they were read, so any later write shows), the SHA-256 of its manifest, summary, metrics and note, the names of its stored logs, its status, and every change that the sync stamps or lists for it: those carrying its `LLM-Trace` line and the mutable ones authored within two minutes of its span (each with its description, emptiness, whether it is `@`, and its git SHA once immutable), read for all sessions in one `jj log` (read again after a session only when its sync described a change). A sync without session names skips a session whose state is the recorded one, since syncing it again would write the same files and descriptions; anything else, including a sync during a publish, which records git SHAs, means it is synced. `sync --all` syncs every session.

Every entry sits under a fingerprint of everything besides the content that decides its result: the source of `redaction_rules.py` and `redactor.py`, the Python version, and this machine's redaction literals (only their hash is stored). `redactor.py` holds the redactor, these caches and the helpers they use, and imports nothing from `sync.py` or `metrics.py` (a test keeps it so), so the rest of `sync.py` cannot change a redacted log, a scan or a verified snapshot, and an edit to it keeps those three caches. What depends on more adds a digest of the source of `sync.py` and `metrics.py`: `sync-cache.json`, whose fingerprint also covers the summary template, `pricing.json`, the reviewed findings and the repo's remote URL (not the allow list, since 2026-11-26: an approved entry changes only what is reported, never a manifest); the key of each `metrics.json` entry in `check-cache.json`; and the end-of-turn hook's cursor. A different fingerprint empties the cache, so an edit to the rules or `redactor.py`, or a new literal, means one full pass. None of them holds a finding's value or any log content. `--full` on `sync`, `check`, `scan`, `review` or `stamp`, or `LLM_TRACES_FULL=1` for any command, trusts no cached result and records fresh ones: the full audit.

`scan`, `review` (with `review show`, `review accept` and `allow`) and `stamp` read the same caches. A transcript is redacted only from where the log `sync` last stored for it ends, by the transcript cache, which they read but never save, since the log they make is not stored; that log, each stored log not yet uploaded and each session file is then looked up in the scan cache by the SHA-256 of what it holds, and scanned only if it is not there, or only past an earlier log of the session that is a prefix of it. A stored log is named by its `.gz` bytes through the check cache, as in `check`. What they scan is added to the scan cache, and `check` later drops what it does not need. Reviewed and allowed findings are applied afterwards, so the results are those of reading everything, which `--full` does. Since the scan cache holds no values, a command that needs a finding's real value (`review show`, `review accept`, `allow propose` and `allow approve`) takes it from what this run scanned or from `finding-values.json`, checked against the finding's id, and reads everything again if one is not known there.

A cold pass, when these caches are empty or do not apply (an edit to the rules or `redactor.py`, `stamp`, `--full`, a new machine, a new session's first transcript), is split across processes, one per CPU (`LLM_TRACES_PROCESSES`; 1 keeps it in one process). Redaction and scanning work line by line, so each worker builds the same rules from the same literals and returns what one process would: a redacted line, or a line's findings, which go into the redactor's per-line memo as if it had scanned the line itself. A worker whose rules or `redactor.py` differ from what the command read when it started (an edit in between) takes no work, and the command does it itself. The workers start only for at least 4 M characters not yet done, so a commit's new lines never start them; once started, they also take texts of 250 k characters or more. They read and write no file.

Within a process, the rules skip what cannot match. Each rule that has one carries a gate in `GATES`: words, one of which every match of the rule holds (compared as `re.I` compares, for a case-insensitive rule), or an assertion-free pattern that matches inside every match, or both. A gate is tested once per line, on the line's JSON strings joined by `\0`, and a rule whose gate fails is skipped on every string of that line; a rule also skips any string shorter than its shortest match. Redaction applies the rules one after another, so a gate there holds for a string only until a rule changes it; after that, every later rule runs. The results are those of the rules without gates, which `stamp --equivalent` checked on every stored line when the gates went in. That comparison runs in one process per CPU too, each loading both versions of the rules from their source text; it stamps only if the rules file still holds the text it compared.
