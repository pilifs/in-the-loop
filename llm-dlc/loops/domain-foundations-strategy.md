After the queued plumbing and `lib` architecture work, return to features with **Avro byte conversions**. Use #3878 to establish which facts about ordinary startup, object construction and buffer behavior the checker can prove once. Then give those facts to a different feature, Avro #729, and measure how much work its proof still requires. Use JavaParser to test whether the startup technique travels across domains. Treat receiver construction as a separate feature opportunity.

For each subsequent domain, start with an actual change and name a second consumer. Trace backward from their public observations, find the shared construction or semantics, and prove just the part both need. Give the next agent a runnable entry, an independently checked fact and an example of when it stops applying.

The second change introduced different read schedules and a different regression. That is the desired unit of progress here: after solving one hard change, a later agent can spend its effort on what changed in the next one.

## An initial dependency analysis for Avro

The fixed converter constructs `Schema.create(BYTES)` and saves it as `mSchema`. Its `convert` method reads the writable’s backing array and logical size. Another method, `getWriterSchema()`, actually reads `mSchema`. The frozen adapter allocates a byte array of capacity 0–5, fills it, and calls `setSize(length)` with `0 ≤ length ≤ capacity`. On these inputs Hadoop’s growth branch is unreachable. The parent wraps the whole backing array. The fix passes offset zero and the logical length to `ByteBuffer.wrap`. These source observations identify a small candidate proof on the original bytecode. [Converter and factory][converter] · [Hadoop writable][writable] · [Frozen adapter][adapter]

The factory exposes the more interesting boundary. Its public `create(BytesWritable.class)` eagerly calls `getNumReduceTasks()`. The resulting flag selects behavior inside the `AvroKey` and `AvroValue` branches, neither of which the exact input class takes. **The integer can be irrelevant while the call that produces it is essential.** It runs before dispatch and can observe configuration, mutate state or throw. A proof can abstract the returned integer once it establishes that the lookup completes with effects the continuation tolerates. [Factory dispatch][converter] · [JobConf][jobconf] · [Configuration][configuration]

## The first run after architecture

**Commission a half-day investigation on the VM.** Start from the measured checker and compare it with the post-architecture head. Reuse the normal planner, qualifier, provenance and execution receipts. The agent can choose instrumentation, bytecode slicing, symbolic execution, small proofs or another technique. The deliverable is a decision on the cheapest sound route for each family, backed by artifacts a feature agent can rerun. The half day is a proposed discovery budget. Reserve any larger implementation brief until the traces show which producer obligation is worth tackling.

The successful conditioned factory job, its fresh witness receipts and the JavaParser companion job are referenced by the scorecard. Locate those on the VM and record the new checkout, classpaths and tool fingerprints. If a receipt is unavailable, retain its reported result as historical and mark the independent replay pending.
2. **Build the missing dependency table.** On parent and fix, enumerate the static fields written by the four roots and their relevant initializer closure. Include cross-class writes, class-init status and opaque effects. Link each to constants, process inputs, class loader/resources or an unresolved origin. For each of the seven frozen rows, mark reads affecting returned values, dispatch, alias/mutation, possible exceptions and whether the method is reached. Give bytecode locations and the first unknown. Use observations under alternate processor counts, directories, properties and resource setups to find missing dependencies. A finite grid can falsify a proposed invariant.
3. **Try one proof that could change the decision.** Start with `direct-limit-fix`, preserving its 21 selectors, original artifact, strict mode, unwind 64 and max array length 128. Determine which environments and startup outcomes the saved statement admits. Record any ambiguity explicitly. A useful intermediate result is a checked continuation plus one named producer obligation, such as successful schema construction. If ordinary verification succeeds, rerun the fresh parent witness and the changed-observer control below.
4. **Test a different dependency.** Trace JavaParser’s actual `System.getProperty("line.separator")`. The pinned enum reads it twice and calls `replace` on the second result. If the property can be absent in the admitted setup, there is a real exceptional edge. Preserve correlation across reads subject to modeled writes. An enum-only capture already advanced the checker to `HashSet(Collection)` in printer setup. Determine what successful printer setup must guarantee for traversal of the two frozen trees. Preserve node identity, child order and iterator exhaustion. [LineSeparator][line] · [Node][node]
5. **Report the decision and resume feature work.** For Avro and JavaParser separately, return the strongest checked statement, remaining assumptions, a replay or refusal, and the cost of the next experiment. A small proof obtained during the investigation is a deliverable in its own right.

### How to choose a startup strategy

| Route | When to spend on it | Evidence that qualifies it |
|---|---|---|
| **Prove a small guarantee about ordinary startup** | First choice for the unused schema value and reducer count. Execute cheap initializers normally. Abstract a costly producer when the consumer demands little from it. | For every startup allowed by the original claim, establish how initialization completes, which live state and aliases it creates, and which effects can reach the observer. Prove that these guarantees imply the continuation’s requirements. If comparing two states, vary the discarded state independently and preserve input and object correspondence. |
| **Make the remaining inputs symbolic** | A property or resource genuinely controls a relevant branch. Start with the actual key or semantic distinction, such as separator present/absent or a relevant configuration value. | Verify all admitted values, or prove a finite partition exhaustive and check every class. Include exceptions, correlations and effects for repeated reads. If the verifier encounters unrestricted callbacks, resource contents or mutation beyond the model, return that dependency. |
| **Keep a named initialization contract** | A deployer can supply stronger configuration guarantees, or native proof of the producer is currently out of reach. | Publish the producer assumption and conditional consumer result. JVM profiles test the contract and can expose violations. A producer proof or an already-declared premise of the original claim can justify promotion. |

“Every startup” is relative to the original entry, selected classpath/JDK, input guard, bounds, allowed external settings and verifier execution semantics. Write down how exceptions, initialization failure, recursion and relevant concurrency or nontermination are handled. A new requirement that setup succeeds narrows a statement that previously observed its failures. An overapproximation can establish a universal property if it covers every admitted execution. A counterexample arising only in that overapproximation needs an original-entry replay or proof of reachability. JBMC’s static-value import and nondeterministic-static option illustrate two modeling choices. Java’s initialization rules explain why coverage of the startup effects remains a separate proof obligation. [JBMC manual][jbmc] · [JLS §12.4.2][jls]

## What a domain foundation contains

Build the smallest reusable result that a second feature can consume. For Avro, the first candidates are **successful construction of a bytes schema with specified effects**, **the relationship between a writable’s logical size and backing array**, and **the behavior of a heap buffer over a bounded byte range**. Factory selection on a fresh `JobConf(false)` is a distinct Avro/Hadoop fact. JavaParser has its own facts about constructed nodes and traversal. A common technique for tracking initializer effects can support both projects without giving them the same domain model.

For each reused fact, the feature agent needs to answer four questions from existing proof artifacts:

- **What exactly is available?** Name the bytecode entry, admitted state and inputs, guaranteed results or exceptions, relevant heap changes and object identities. Distinguish a proved fact, a captured example and a supplied contract.
- **Why does it apply here?** Link the producer proof. At the actual call site, discharge its preconditions and show that its guarantees imply everything this consumer observes. Check each revision independently. A new observer or stronger claim can require more. On an unrelated edit, demonstrate a valid reuse. Change the selected callee or an initializer and show that stale evidence is declined or revalidated.
- **When must it be recomputed?** Bind the summary to its transitive dependencies, including resolved class bytes and order, relevant JDK implementation, model versions, initialization order, environment assumptions and bounds. Start conservatively. After a dependency changes, reprove the affected fact or supply a checked equivalence argument. Run 7’s selected JDK models are qualified on specific Temurin builds.
- **What would falsify misuse?** On Avro, switch from `convert` to `getWriterSchema()` and observe the schema type. That consumer requires a schema guarantee. Introduce a controlled initializer that throws on one admitted input while the conversion arithmetic is identical. On JavaParser, add a consumer that reads the separator itself. Each test must produce the new dependency, the genuine violation, or evidence that discharges it.

Use the existing native proof cache and its proved-callee dependency mechanism where applicable. The current read-footprint helper handles a restricted class of methods, and the cache documents its regression-check scope. Generalizing either to startup or property proofs is a possible implementation choice. A domain agent owns the change end to end and can work in whichever layer exposes the bottleneck. Keep a promising experiment beside the example. Promote it when a second consumer needs it. [Existing proof cache][cache] · [Read-footprint implementation][footprint]

## Make the next feature pay for the foundation

**Choose merged Avro #729 as the first new adoption case.** Its decimal conversion used to read directly from the caller’s `ByteBuffer`, advancing the caller’s position. The fix reads through `duplicate()`. The upstream test, `TestGenericLogicalTypes.testDecimalToFromBytes`, creates a bytes schema and converts the same buffer twice. This changes the method, observer and historical classpath while retaining recognizable schema and buffer semantics. The landed change is `ce9032a4123e262341a3e746e6eb2b8476eae1ae`. [Upstream PR and tests][decimal] · [Landed change][decimalcommit]

Freeze the original parent and landed bytes, public conversion entry, test fixture and small nonempty buffer windows before modifying the checker. Include a nonzero starting position and backing bytes outside the window. Check the caller’s position and limit after the first conversion, then check both decimal results against an independent unscaled-integer and scale oracle. Keep the upstream parent failure and a deliberate wrong-result control. A cursor-only proof and a full decimal-result proof are separately reportable. `duplicate()` introduces a distinct cursor with shared content, and decimal construction introduces new arithmetic and exception behavior. Credit only the facts that actually validate on this classpath. #729 tests schema and buffer reuse. A second public Hadoop factory consumer would be needed to demonstrate reuse of `JobConf` work.

Measure the same frozen claim with the same checker and budgets, first with foundation reuse disabled, then with a cleanly built foundation, then with verified reuse enabled. Count setup and recertification, validation at the call site, proof time, total workflow time, peak RSS, agent effort and any core edits. Record missing effort measurements as unknown. A newly decided same-scope claim is a capability gain even when the old route refused. Report a speedup only when both routes decide the same claim. A repeat of an identical claim is an exact cache hit. A new PR consuming an earlier proof is stronger evidence of leverage.

If the one-time cost is B, a fresh later proof costs D, and a later proof using the foundation costs R including validation, break-even is the smallest number of later changes for which their cumulative savings cover B. Under comparable costs and D > R, this is ceil(B / (D − R)). Report actual costs and incremental work as each PR lands. A single successful adoption warrants trying another. A result that only transfers the implementation recipe should be labeled as such. Keep returning to feature changes while the foundation earns its cost.

Retain cases involving external collaborators or effects to test that an invalid substitution is refused. Recheck normal initialization order, dynamic type and dispatch, aliases and raised exceptions. The current code already allows an explicit constructor in a construction plan and restricts arbitrary factory construction. Preselect examples across at least two dependency families, then rescore all 32. Report how many of the 23 advance past their first refusal, reach the changed operation, and gain an original-scope verdict. As a proposed threshold for expanding this work, aim for four new original-scope decisions among the 23 across two families. Preserve all 23 in the denominator. The eight historical transfer cases have been disclosed. Use fresh separately selected changes for any later blind evaluation. **The two unsplit timeouts are performance work.** The campaign scorecard locates them in *two different examples*. Commons Lang 354 `truncate-fix` used 60.8 seconds, including 54.6 in SAT. Its exact native fallback covered 1,515/1,515 selectors in 71.4 seconds end to end. Eclipse Collections 359 `contents-fix` used 60.1 seconds, including 55.8 in SAT. Its fallback covered 2,865/2,865 in 121.4 seconds. Both obligations already have original-scope native decisions. To investigate, run one larger-budget unsplit diagnostic at the same bounds and solver, then compare SAT time, peak memory and coverage against grouped selectors. The gain to record is cheaper equivalent coverage or an unsplit proof within 60 seconds.

**Decision at the end of the pilot.** Keep the 39/46 primary and 2/8 JavaParser baselines visible, alongside counts for conditional, finite, refused and newly discharged claims. Try for all seven Avro and all six JavaParser lifts, and name the first outstanding producer obligation for any shortfall. Expand a reusable domain fact when another change consumes it, a negative control catches overreach, and the saved work or newly reachable behavior is visible. If Hadoop remains expensive but #729 advances cheaply, keep shipping Avro features that use the cheaper facts. A difficult factory can stay an open research finding.
