# A verification workflow for refactors and major Java upgrades

**Strategy for `pilifs/in-the-loop` · 22 November 2026 · [develop at 2fff2b0d][head]**

Make one proposed change the unit of planning and one caller-visible claim the unit of proof. Persist the relationship between them. For each old and new application environment, the verifier should tell a maintainer which behaviors it identified, which ones the change could affect, what it established or refuted, and what could still matter. A second commit should reopen precisely the obligations whose justification has changed, wherever the verifier can establish that dependency boundary.

I would fund the connection between the application comparator and the example runner first. Both already do substantial parts of this job. Keep general-purpose solver replacement behind a workload-specific experiment. Give the queued checker, Spring and kernel work actual callers of the capabilities they produce.

## Join the two workflows that already exist

The early approach document proposed grounding the claim in a real harness, proving the artifact that ships and reusing proofs for shared library code. The November foundations work added a more specific design for application changes. It anchors inputs, compares old observations, asks about ambiguous intent and tracks proof dependencies. Its joint application fixture caught a missing effect, a duplicated effect and a reference alias replaced by a copy. [Original approaches][approaches] · [Foundations and joint results][foundations]

Today `jvmcontract compare` compares entry observations and effects, aligns changed method pairs, uses native proof reuse and reports decisions requiring a person. Its application effect check is invoked with an empty additional classpath slice. The separate upgrade discovery code inspects direct dependency calls in a supplied client and includes some service-provider heuristics. The target runner already knows how to freeze claims, prepare revision-specific inputs, retry tasks and qualify multiple evidence routes. The branch also has a shared proof-output reader and a binding for the class bytes selected by the JVM. Those are the implementation seams. [Comparator][compare] · [Upgrade discovery][discover] · [Target runner][runner] · [Shared evidence and binding][shared]

| Step | What to add to the existing path | What the change report can say |
|---|---|---|
| **1. Resolve both applications.** | Give the comparison each side's built client, ordered runtime classpath, selected JDK/classes, resources and declared environment. Reuse source preparation and class binding. Track changes in transitive dependencies, service descriptors, classpath precedence and configuration. Bind test and production launches separately. | Which original client binary still links under the new graph? Does unchanged source rebuild? If migration edits are required, which observations agree between the old client and the migrated client under their intended deployments? These are three distinct questions. [JLS §13.2][jls] |
| **2. Inventory caller observations.** | Start at production entries, public calls used by the consumer, message or service handlers, and user-designated workflows. Use upstream tests, release notes and traces to propose expected behavior and controls. Intersect conservative reachability from those roots with changed code, dispatch targets and resources on **either** side. Include added/removed entries and unknown dynamic edges. | For each declared capability, list preservation, intended difference, or an open question about intent. Include observations such as returned bytes, exception, alias, mutated state and callback order only where a consumer can distinguish them. Give every discovered candidate a disposition, including excluded or unanalysed with reason. State how the inventory was obtained. |
| **3. Plan dependencies between claims.** | Retain the existing frozen claim ID and bind each execution to its concrete artifacts. Add edges saying *why* a parent depends on a child, for instance, receiver construction, an effectful helper contract, exhaustive input partitions, or a specific startup invariant. ### What makes composition sound enough to use

- **Exact reuse and contract reuse answer different questions.** An exact hit needs the existing full claim key, including observations, domain, code closure, models, tool settings and assumptions. A changed helper can still support an existing caller argument if its contract is re-established on the new bytes and the caller proof genuinely depends only on that contract. When a caller was proved by inlining the helper, recheck it. A closure marked unchanged by `impact` establishes only the code portion of the key. [Closure impact][impact] · [Native cache][cache]
- **Every summary has a proof of applicability.** Check the receiver's origin, input precondition, alias layout, reads/writes, exception behavior, initialization and relevant effects at the call site. If the caller uses more than the summary promises, inline the body, prove a stronger summary or leave that edge open. For cycles, prove a joint invariant or use the existing bounded route with the bound in the statement. A group of mutually assumed summaries cannot establish itself. [Current read-only summaries and cache restrictions][reuse] · [Function contract semantics][contracts]
- **Partitioning must cover the parent claim.** If the frozen domain is split into guards, check that their union covers it and that each positive result proves the same observation under compatible assumptions. One missing partition keeps the parent open. One admitted witness replayed at the original entry can refute the parent immediately. A sample or recorded startup state can guide search. Lifting a positive result requires proving the captured state covers all permitted entry states, or proving that the observation is independent of their differences. [Native selector validation][selectors] · [Real startup and partition results][domain]
- **Keep preparation, proof reuse and solver state independently keyed.** Whole builds and parsed artifacts can be shared per exact launch. Reuse a proof across different full classpaths only when its actual dependency boundary is established, including dynamic dispatch, relevant resources and lookup failures. For unknown dependencies, use the full relevant classpath/environment or leave impact open. Learned clauses and assumptions belong to their compatible encoding and solver session. The current property cache explicitly refuses several inputs, including observed initializers, induction/lemmas and write effects. Admit one family at a time with a key and an invalidation control. [Property option handling][reuse] · [Incremental SAT implementation][sat] · [Fine-grained verification caching][boogie]

This gives a small refactor a short path. Re-identify the affected caller roots, reuse their eligible proofs, recheck the changed leaves and replay any relevant witness. A major upgrade follows the same rules with more roots, more changed providers and more uncertainty. Ask a person when an observation may intentionally change, a mapping is ambiguous or the environment must be narrowed. Algorithms and agents can choose the tactics.

## Solver policy

| Shape of the remaining question | First route | Escalation or stop condition |
|---|---|---|
| Small, completely enumerable caller domain | Run the original JVM on the entire certified domain, or use the existing native selector route. Reuse the old-side observations across candidate builds when their identity is valid. | A sample answers only for sampled inputs. A formal bounded claim needs a coverage argument, a controlled environment and all relevant nondeterminism accounted for. When initialization or scheduling varies, quantify it or state the condition. |
| Bounded heap, control flow, ordinary integer operations | Strict native BMC with bundled CaDiCaL 1.9.5. Use the existing phase timings and incremental queries. Test grouping claims that share an entry and symbolic prefix, using independent assertion checks and reachability/coverage per claim. | Branch to exact partitions when one search is expensive and the original guard can be covered. Use an alternate checker such as JBMC where its Java modeling covers a real gap. Match classpaths, runtime models, exceptions, unwind completeness and observation before crediting the answer. Record disagreements for adjudication. |
| Word arithmetic dominates measured solving | Compare the existing Bitwuzla word-level or finite-domain route against native on the same pinned claim, settings and machine. Keep witnesses and compare all-in costs. | In the recorded five-workload experiment the best tuned word-level gains ranged from **1.00× to 1.93×**, with the same five verdicts. The encoding and CaDiCaL version also differed. Use the Eclipse transfer and another hard caller to decide whether further solver work pays. [Solver comparison][solver] |
| Unbounded loop or recurring heap invariant | Try a supported bytecode-bound induction rule, such as the current Z3 array proof, or prove a relational contract for the old/new procedure pair. Discharge initialization, frame, preservation, exits and termination where claimed. | Propagate only the theorem the consumer can apply. Reach for bounded schedule exploration or protocol models when the observation itself is about histories or interleavings. Credit an abstract protocol result to the Java caller only with a refinement argument. [Array induction][induction] · [Differential assertion checking][dac] |
| Receiver, factory, dynamic dispatch or startup missing | Investigate how the real public caller reaches the state. Turn a shared missing premise into its own producer obligation and connect its consumers. A JVM trace supplies candidates and replay. | An ordinary-entry positive result requires a justified producer or independence argument. A longer SAT timeout cannot supply missing Java semantics. |

## Execution order and acceptance

1. **Start now with example 345 and Retrofit/Wire.** Run the current workflow as baseline. On 345 reproduce all 12 primary claims and four controls on the existing four configurations. For Retrofit supply the pinned artifacts and consumer module to the planner, and use the historical request/response records as grading evidence. Require the inventory to surface both converters, preserve the two known read observations and reproduce the write-side failure at its public caller. Record an uncovered direction as a discovery miss. Add the request as a new obligation and preserve the historical denominator.
2. **Make the second commit cheaper.** On the same cases run a cold baseline, an exact rerun, an unrelated edit, a reachable helper or resource change, and a change in startup/dispatch or classpath ordering. Include an interaction control where two dependency changes together alter the final caller result. Compare every incremental verdict and scope to a clean recomputation. Require a relevant edit to invalidate every consuming proof that depends on it. Keep positive and negative reuse controls. The cold path may be faster when run directly. [345 cost and interaction matrix][345] · [Existing cache economics fixtures][economics]
3. **Feed queued work into the same plan.** Run the 15 Java semantics cases and then the receiver/property-discovery brief in their queued order. Have each improvement retry a real root or explain which narrower obligation it settles. In particular, retain generated check-site reachability separately from whether that check could fail. Use the additional Spring Boot examples as clients. Binding, metadata and formatter examples on the reviewed branch already delivered 16/16 finite Spring decisions, with 0/16 on ordinary native startup. Choose a Boot caller where a shared construction or startup result could lift at least two observations. Run the independent-kernel experiment in parallel on Guava 336 → 346, with its Rust/Lean and SAT-certificate comparison. Record independent checking per node and the trusted assumptions it removes. Let its own transfer and effort criteria decide adoption. [Spring results][spring] · [Queued semantics][queued-semantics] · [Queued entry/discovery][queued-entry] · [Queued kernel][queued-kernel]
4. **Graduate to a held-back application migration.** Pre-register a genuine consumer upgrading across a major version, its production workflows, independent acceptance examples, budgets and allowed changes. One candidate family is a Spring Boot 2.7.x → 3.0.x application. Pick the actual upstream migration before unsealing expectations. Use a shared Java 17 deployment where feasible and separately label any JDK migration. Test build/link/startup, public binding and validation results, and an observable output or effect on one real application path. Boot 3 changes the Java baseline and moves applicable APIs from `javax` to `jakarta`, so retain both the binary compatibility answer and the adapted-application answer. Test additional library combinations only to attribute a divergence where the combination forms a valid deployment. [Spring's migration guide][boot]

**Decision to expand.** Freeze the denominator of intended production workflows and report discoveries added later separately. Track original-scope decisions per workflow, missed important operations, contradicted assurances, open roots per shared blocker, and how many claims required a human to supply intent or construct an adapter. Measure cold/warm wall time, aggregate CPU, peak memory, setup, JVM replay, solver time, and inference/human effort where attributable. Compare at equal scope and include failures. The immediate win is a clean-equivalent rerun that skips verified unaffected work and a major-upgrade report that captures both known Wire outcomes. A claim of general improvement requires the held-back client to gain original-scope coverage or reduce end-to-end cost at the same coverage, with zero contradicted assurances. The frozen V3 historical gate of 8/12 is a separate existing target. [Evaluation protocol and results][external]

The implementation can stay behind today's internal runner while the public UX evolves. One durable plan and a set of checked rules for composing results are enough to start. The opportunity is to make each future example either answer a maintainer's question directly or produce evidence a second caller can actually consume.
