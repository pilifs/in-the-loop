# Engineering brief · Publish code promptly and preserve the original evidence

**21 November 2026** · `pilifs/in-the-loop` · Public `main` at [`cfe2dc91`][head].

**Outcome.** A watcher can put a coherent change on remote `develop` while another agent is still working, the object store is unavailable, or the default suite is running. An agent starting on a different machine can find a particular attempt, recover its exact original outputs, and run the existing evidence checks. `main` identifies which code passed the default suite and which evidence was available for that promotion.

Use this as one sequenced implementation brief. It can be supplied directly to the repository’s single-agent watcher as its `--brief`. Start with the VM inventory. Use example 359 for recovery and a dirty workspace with a stalled uploader for the first code checkpoint. Scope this run to development plumbing. The next brief owns capability boundaries and the top-level directory restructuring.

## 1. Give code checkpoints and promotion different jobs

| Event | What the watcher does | What callers can rely on |
|---|---|---|
| Feature commit | Run tests for the changed behavior, using `python3 lib/tools/test_costs.py run --changed` and the existing example-specific checks as applicable. Record the finished files with `sync.py commit --only PATH …` in a shared workspace. Seal trace provenance and a compact capture intent. | An identifiable commit with an explicit evidence status. Targeted test failures stay visible. Agents can run the full suite locally whenever it answers a development question. |
| Checkpoint to `develop` | At a completed slice, stream landing, pause, or request for a planning snapshot, push the latest eligible committed head. Coalesce adjacent checkpoints. The watcher owns this operation under standing authority on this VM. | A remote commit SHA suitable for planning. No default-suite call, wait for proof jobs, bulk rendering, public log upload, or wait for the private uploader. Receipt distinguishes `pending` from remotely available evidence. |
| Promote to `main` | At the close of a brief or an explicit promotion request, freeze a candidate and evidence cutoff. Assemble compact publication metadata, reconcile the selected archive, run `python3 lib/tools/test_costs.py run` (unit and tool tiers) or reuse a covering pass, then advance `main`. Allow subsequent work on `develop` throughout. | A tested revision with a recoverable, bounded inventory and truthful public links. A failed promotion leaves the last successful `main` visible and records the reason. |
| Release | Keep the existing release gate and its pinned tree. Proof-tier work continues through the job queue with the existing status semantics. | Runtime checkouts keep their current plain-commit behavior. A develop checkpoint does not confer release or proof status. [Test policy][policy] · [Default-run implementation][default-run] |

Implement two narrow commands in the existing development tooling, for example `sync.py checkpoint --rev REV` and `sync.py promote --rev REV`. These names are proposed. Bind the first to the configured origin’s **exact** `develop` bookmark and the second to its exact `main`. Preserve the existing `push --bookmark main` and `/publish` as deliberate promotion entry points with documented semantics. The checkpoint path must reject multi-ref, wildcard, alternate-destination and force updates. Retain user-only override rules separately. Ordinary checkpoints follow their own test policy.

**Checkpointing with uncommitted work.** Select a committed ancestor or an integrated stream head, resolve it once and work from that revision in a separate jj workspace if needed. Leave other sessions’ working changes in place. Do the checkpoint bookkeeping in the isolated workspace. For useful partial work, let its owner make a clearly labelled, path-scoped checkpoint. The watcher reports uncommitted work as local only. Read the actual outgoing Git objects and messages, including merge ancestry, to reject raw payload paths, unsafe filenames or content, unresolved conflicts and unintended oversized objects. Cache eligibility by object ID and policy version so work scales with newly exposed bytes. A file deleted at the tip still travels in any outgoing parent that contains it.

**Promotion transaction.** Record the expected remote `main` (P), the selected `develop` commit (D), and a sealed ID for the inventory covered by this promotion. Resolve provenance over `ancestors(D) − ancestors(P)`, including merged side branches. The existing `::target ~ ::remote_bookmarks()` expression would skip everything already sent to `develop`. Use a clean candidate workspace, add the reviewed summary referring to that frozen inventory, then test its final tree or reuse an existing pass under the tested input equivalence in `default_run.py`. Store the gate attempt, any test-generated artifacts and the successful test receipt outside the tested tree, keyed to its tree and promotion ID. Verify custody for those artifacts before advancing the ref. Record the observed remote commit in the linked receipt after the push. This avoids requiring the test to produce a receipt that already had to be in the tree when the test started. Recheck the gate against the actual outgoing revision. Executables, schemas, policies and test inputs require coverage. Prove any new summary-only exemption narrowly. Later unrelated work belongs to the next cutoff. [Publication gate][pub-gate] · [Tree coverage][default-run]

Advance `main` only if P still matches. Never force a published bookmark. On a concurrent promotion, refresh the base, build the resulting merge tree and recheck it. If `develop` advanced, publish the frozen candidate and integrate the promotion metadata forward with an ordinary merge, preserving later work. Record D, resulting tree and final remote SHA without requiring a commit to contain its own hash. If the push response was lost, read the remote ref before retrying. Use the existing VM watcher and test runner.

Give the watcher one review view per promotion. Lead with the source diff from P to the candidate, grouped by finished change, the default-suite receipt, unresolved decisions and artifact counts. Put generated summaries in a separate commit and offer drill-down by run or job. A human can review the code remotely while uploads run and can inspect an exception without paging through thousands of generated files.

Update the normal entry points together, including `CLAUDE.md`, `llm-dlc/{README,specification,operating-notes}.md`, the brief template, the publish and review skills, the single- and multi-agent watcher instructions, jj aliases/hooks, transfer helper and relevant Claude/Codex permission rules. Remove mandatory defaults at example completion, routine stream landing and hourly development merges. Keep changed tests and optional full runs. A command-line fast path is of little use if the watcher still pauses the run waiting for the old checklist. ## 2. Take custody of originals before producers release them

**Recommended layout.** Use the existing R2 account. Give project originals a private bucket with no binding to the public Worker, no public domain and no public development URL. Receive unclassified bytes into restricted private custody. Enforce restricted versus ordinary reads using separate private buckets or an authenticated broker that checks every read and keeps its backing credential from ordinary agents. A prefix alone cannot isolate data from a bucket-wide reader. Retain today’s public route for approved redacted traces. Put compact, publishable promotion summaries under `llm-dlc/artifacts/YYYY/MM/DD/`. A code checkpoint needs only stable occurrence IDs and safe provisional metadata. The private archive must be discoverable before any promotion. [Current public route][worker] · [R2 access controls][r2-access] · [Bucket-scoped credentials][r2-tokens]

1. **Inventory the producer’s output.** Assign a unique occurrence to each run, job, attempt and artifact kind, including failed, cancelled, partial, superseded and no-commit runs. Seal finalized bytes before a retry reuses a path. For append-only sessions, checkpoint immutable segments with byte offsets, lengths, predecessor and digest, or immutable whole-file versions initially. Record rotation, replacement and truncation as new versions. Restore an exact historical prefix in either format. A timestamp or filename alone cannot identify an occurrence.
2. **Capture once on disk.** Place originals and a manifest in an append-only spool on persistent disk outside the checkout, runner workdirs and `/tmp`. Stream large files. Write temporary data, fsync, atomically install it, and commit the intake record durably before acknowledging local capture. A shared VM-local SQLite journal with transactions and worker leases is sufficient. Make sealed files discoverable after a crash between file installation and journal commit. Capture the producer’s inventory independently of the uploader so a silently omitted file can be detected. For an interrupted producer, seal the bytes actually present with a partial status and record which expected outputs never materialized. A link to a mutable file is insufficient.
3. **Preserve each byte and its meaning.** For one blob, record byte length and SHA-256 of original bytes. For a tree, use a deterministic lossless bundle with a full private member manifest of relative paths, types, relevant modes, lengths and hashes. Record encoding, stored size and stored digest separately. Bundle thousands of siblings into bounded chunks and hash the inventory itself. Record empty files, deletion records and application conflicts explicitly. Reject escaping paths, unsafe links and ambiguous members on extraction. Unknown file types get an opaque lossless representation. A failed summarizer leaves the original intact.
4. **Upload as soon as a capture seals.** A restartable worker streams from the spool, deduplicates by content within the same access class and uses create-if-absent or equivalent immutable writes. Overlapping watchers may report separate occurrences for identical bytes. Commit an attempt before transfer. Reconcile an ambiguous outcome by reading the existing object. Mark it `remote_verified` only after checking original digest and length from authenticated remote bytes, plus the complete recoverable manifest. An ETag, HEAD, successful PUT or self-supplied metadata alone cannot establish that. Finalize remote, immutable occurrence receipts and manifests so another machine can rebuild the catalog without VM state.
5. **Make custody visible.** Track `expected → locally_sealed → transferring → remote_verified` per occurrence, with retryable error, missing input and integrity failure as explicit states. Track public redaction/publication separately. The watcher shows bytes/counts by state, oldest unverified age, disk headroom, retries, last remote verification and the affected run IDs. Retry with backoff. On low space or lost custody, pause only new work that would overwrite evidence or exhaust the spool. Keep eligible code moving. After sealing, the collector may release working directories backed by a verified receipt or by replicated staging. On a single-disk VM, pin the sealed bytes through outages and report the remaining VM-loss exposure until the remote manifest and receipt verify. Extend the recovery checks in `prune_workspaces.py` to recognize verified receipts and outstanding pins before a workspace can be removed. Disable automatic raw expiry and remote deletion for this rollout. Review bucket lock/retention separately from existing public-log withdrawal. [R2 retention controls][r2-lock]
6. **State the loss boundary.** A local spool and its original on the same VM can both disappear before upload. The checkpoint receipt must say `local only` during that window. Treat irreplaceable evidence as requiring off-VM custody. Use replicated staging or finish the verified off-VM transfer before the producer declares the artifact durable and releases its last source. If losing the VM even during acquisition must be survivable, stream to an independent durable destination during production and acknowledge only replicated checkpoints. Transfer starts during the run either way. Waiting for a merge as the first opportunity to copy off-VM leaves the most valuable outputs exposed for the longest time.

**First capture adapters.** Wire the pipeline’s full step logs before `keep_log`, generated or changed outputs before collector apply/cleanup, full available diffs, result JSON before compaction, and failed workdir evidence. Include example-local records and selector bytecode/case files, private run/loop records across jj workspaces, watcher decisions and interrupted streams. Preserve trace snapshot IDs and the approved redacted CDN representation. Inventory project-scoped source transcripts separately from their redacted snapshots and apply restricted private custody to sensitive originals. Do not sweep unrelated user sessions, credential stores or linked dependency caches. Classify any unrecognized project-produced output as retained pending classification. If an existing output never existed or was already lost, record its identity, available derivatives and the gap. [Runner lifecycle][runner] · [Trace finalization][finalize] · [Workspace pruning][prune]

### Typed summary and agent read contract

Version a small common JSON Schema with kind-specific payloads. A summary describes the evidence and how to verify it. A checker’s verdict still comes from its established validator. Keep unbounded rows, paths, tool text, case lists and long metrics tables in digest-addressed objects. Use the existing job/result schemas and trace manifest identifiers as inputs.

| Record | Essential fields |
|---|---|
| Occurrence and custody, private | Schema version, occurrence ID, kind, run/session, job and attempt, producing jj change ID where available, exact source Git commit/tree, logical output, capture time, complete/partial status, raw byte length/digest, encoding, member inventory digest/count, read locator, access class and verification receipt. Preserve distinct parent/source/collector revisions. |
| Reviewed publication summary, Git | Safe occurrence ID and source references, kind, bounded typed fields, evidence availability, safe archive reference, publication/withholding disposition and policy version. Keep access credentials, expiring URLs, literal findings and sensitive filenames out of it. Start with proposed caps of 64 KiB per new summary and 256 KiB per catalog page. Spill details to a verified object and paginate before hitting the cap. Measure the canaries before adjusting either budget. |
| Example-specific fields | A job carries status, exit, declared/applied/conflicted counts, wall time and peak memory. A selector set carries admitted/checked counts, route, disposition, first blocker if publishable and full evidence ref. A trace segment carries session, capture boundary, event/token counts, digest of the redacted derivative and a public URL only after verification. Unknown kinds carry a generic summary immediately. |

Provide the following **proposed** operations through one internal CLI, backed by the private remote catalog as well as local state. The names illustrate the user experience.

- `artifacts list --run RUN --include-attempts` and `artifacts show ID` let any project agent discover ordinary objects before or after promotion, including failures, and distinguish pending, verified, restricted and missing.
- `artifacts fetch ID --to DIR` streams the object with bucket-scoped read credentials, verifies bytes and members, and reconstructs the historic logical layout in a private cache. A subsequent normal reader can operate offline on a verified cache hit. Resolve by digest, job, attempt, session or source revision. Missing or corrupt evidence yields a specific unavailable/ineligible result. Reading an artifact never enqueues a proof, applies an output, uploads a derivative or changes a verdict.
- Give all established project agents standing read access to the ordinary project archive from the VM or an equivalently trusted agent environment. A read API or command may mediate this without handing each agent a writer credential. Permit watcher-mediated **private analysis** of restricted originals under the access policy. Analysis tools must keep raw bytes and secrets out of publishable session transcripts, Git, public command output and dashboards. Log IDs and purpose, and return safe derived facts. There is no per-object human review for ordinary research.

## 3. Delegate redaction decisions to the watcher

Keep deterministic redaction, full audit mode, policy-stamp invalidation, and a final scan of the exact outbound bytes. Extend existing decision commands and their validators with an explicit watcher actor. Continue to recognize historical human decisions and withdrawals. Worker agents can propose and investigate findings. The watcher can decide all routine redaction work, including a conservative mask, private-only disposition, isolated re-render, or a narrowly supported false positive. [Redaction specification][redact] · [Decision ledger][authority] · [Rules][rules]

| What the watcher finds | Autonomous action | When the human is needed |
|---|---|---|
| Known benign digest, version, public identifier or fixture with evidence of that origin | Record a narrow decision with the finding ID, evidence digest, scope, policy version and rationale. Batch exact matches. Use hash-only records wherever possible. | None. |
| Ambiguous token or identifier that can be removed without changing the published meaning | Mask or omit the value, regenerate the derivative and rescan. Save the original privately. A private-only derivative can close the review if Git carries an accurate disposition. | None. |
| Credible live credential, personal information or unauthorized destination with residual exposure, evidence already published, or an exception that would broaden access | Immediately contain the affected output, use the existing withdrawal/purge process where applicable and preserve original custody. Open one masked decision identifying affected IDs, scope, containment and the choice that remains. Continue unrelated safe checkpoints and analysis. | Only for unresolved high risk, such as credential rotation under the owner’s control or a proposed disclosure the watcher cannot safely resolve. |

Do not let a watcher impersonate a human via a TTY or bypass the checker. Bind authority to the designated watcher launch/run on this VM, outside a worker-controlled environment variable or editable checkout. Validate decisions on landing, checkpoint and promotion against a trusted ledger or attestation. Record actor, run, finding digest, action, destination, scope, policy, rationale and supersession. A pushed `develop` commit or jj `immutable()` ancestor alone cannot confer review authority. Narrow repeatable rules can amortize frequent known cases, but a match on `long-token` alone establishes nothing. Preserve existing non-waivable redaction categories. If reviewer identity or policy changes, clear cached trust and re-evaluate affected derivatives. Document how to turn this delegation off if the VM gains other contributors or the trust boundary changes. [Current human-only enforcement][authority] · [Pre-land check][land]

## 4. Reduce churn and keep historical evidence usable

**Trace capture.** Add a tested delta cursor over processed commits and session offsets, scoped to a workspace/line with jj change identity and Git revision. On divergence, rewritten mutable history, new merge parents, changed policy, or invalid cache, reconcile affected history from a known point. Preserve subagent, no-commit, late session and post-last-commit records. Never restamp a commit already visible on `develop`. New commits should carry a stable provenance ID that remains valid while evidence is queued. Resolve it through a receipt or session catalog. The current summary trailer hardcodes `main` and the log trailer assumes a future public URL. Teach readers the new pending representation while retaining all historical three-trailer links and withdrawal semantics. [Trailer construction][trailers] · [Trace contract][trace-spec]

Render full session details, global indexes and human-readable rollups once per promotion or on demand. Update only affected partitions and keep growing event journals out of Git. Keep exact full-fidelity metrics accessible remotely. At promotion, preserve the existing public aggregate paths and documented reader fields with a compatibility view or a versioned manifest plus updated readers. A remote planning reader should ask for a specific `develop` SHA and see freshness, safe counts and pending IDs. A historical `main` dashboard should still render without credentials for private raw data.

**Pipeline layout.** Keep `verification/pipeline.py` and historical paths. New jobs and compact result receipts can use UTC submission-day shards under `verification/{jobs,results}/YYYY/MM/DD/`, with a bounded overflow shard if needed. Preserve job IDs, job-spec hashes and source pins. The runner currently chooses the last commit touching the job path when no explicit revision is given. Moving a pending job can silently change the code tested. Dual-read old flat records and new sharded ones via a shared ID resolver. Resolve identical duplicates consistently and report conflicting records for one ID. Recognize results already recorded on other jj heads. Keep collecting genuine source outputs under the current apply/conflict rules. Pure machine evidence can be hydrated into the old layout on demand. [Job resolution][jobs] · [Cross-head detection][heads] · [Collector][collect]

Migrate normal readers before changing writers: submit, prioritize, resubmit, collect, commit-paths, status, report, validation, loop statistics, watcher/conductor, cost inventory, example acceptance and claim history. Fix relative schema references at new depths. Bound new receipt arrays and partition the result index. Make the old complete index reproducible at a documented point for existing consumers. Leave old jobs and their links in place. The future refactor can move pipeline orchestration, domain evidence and rendered reports after these interfaces stabilize. ## Sequencing, cutover and rollback

After the inventory, implement the checkpoint command and archive adapter in parallel if two agents are available. One owns jj/push, review and test-gate changes. The other owns capture, retrieval and reader compatibility. Agree on occurrence IDs, pending/verified semantics and the promotion receipt first. Enable code checkpoints as soon as the outgoing-history checks pass and the pilot’s raw outputs are protected. Broad historical backfill, final dashboards and the directory migration can continue in the background.

1. **Inventory and protect the current VM.** Compare its actual `origin/main`, local jj heads, working copies, ignored/untracked outputs, runner state, upload journal and existing CDN refs. Identify the only remaining copies, including earlier versions reachable only from local Git/jj history, and pin those heads. Record private path/count/digest inventories for runs 5–7 and the paused attempt where available. Capture or independently snapshot unique data before any prune, reset, rewrite or garbage collection. Inspect outgoing ancestry for large historical blobs. If it is unpublishable, retain its original references privately and construct a clean forward commit from the published base with explicit provenance mapping. Reconcile what has already landed to avoid a second import.
2. **Make custody and reads work in shadow mode.** Keep the current producer/collector output while dual-writing manifests and objects. Pilot a full log that would be shortened, a failed/retried attempt, a reused session and example 359. Exercise the real authenticated store on a small project-owned canary and use a fresh empty cache for recovery. Record private coverage as expected, restored, pending or historically missing. Advance each producer only when its available original bytes restore exactly and its existing consumers agree.
3. **Enable the fast checkpoint alongside shadow capture.** Bootstrap `develop` from the verified current remote `main` with a normal forward operation. Use an isolated local bare remote first to test both bookmark paths, then a normal scoped checkpoint when the new workflow is adopted. Cut over watcher commands, eligibility scans and trust checks together. Enable the private queue on the same run. Leave pending or quarantined payloads off public branches.
4. **Promote one real batch.** Run the delegated reviewer and new gate. Compare the old/new counts, classifications, trace lookups and evidence validator outputs before publishing. Reconcile every newly expected occurrence, including unknown kinds and failed, partial or private-only attempts. Every original produced needs verified private custody and a complete recoverable remote receipt. Withholding a public derivative can close its disclosure review only. A missing or unverified new original blocks that candidate while `develop` continues. Distinguish a recorded output that never materialized on a failed attempt from bytes known to have been produced and subsequently lost. Disclose any pre-cutover loss as a historical gap. Once restore parity holds, switch new writes to bundles, compact summaries, day shards and deferred rendering. Capture pre/post timing for both the fast checkpoint and promotion.
5. **Rollback without disposing of evidence.** Disable the new writers or bookmark advancement, retain the journal/spool, immutable objects, receipts and local source refs, and resume legacy publication from the last good `main` in a compatible workspace. Ship backward-compatible readers first so newly archived evidence remains readable. Reconcile any ambiguous public uploads or ref changes before retry. The rollback is a forward change. Historical Git cleanup, remote deletion and a top-level rename are separate decisions.
