# Discover and verify the public Java entry on the shipped class path

**Implementation brief for the single-agent run.** Reviewed on November 26, 2026 against [develop at `00800750fc71`][head]. Build this capability into the path that prepares and proves an ordinary Java change. Keep the watcher and single-agent workflow. The first deliverable is a run of Log4j #1173 that reaches the original public method with API first and core second, without an agent supplying the provider index.

## What the product should do

Given both revisions’ resolved deployment artifacts, their order and their JVM profiles, produce an answer an agent can act on: **which public call exercises this change, which class file will each side actually use, and how do we know the verifier will inspect those bytes?** Accept a changed method or an already approved public entry when supplied. Otherwise derive candidate changed declarations from the compiled revisions and propose public callers from the available evidence. A prepared PR should carry this answer through setup, proof, replay and reporting without asking a user to interpret a JAR list.

For Log4j, the answer should identify `org.apache.logging.log4j.core.appender.rolling.PatternProcessor#getNextTime(JIZ)J` in the second provider on each revision, retain `[log4j-api, log4j-core]`, and name the original-JVM observation behind each binding. The explicit-zone and omitted-zone questions share that entry binding and retain separate claims. A strict proof that subsequently stops at `TimeZone.getDefault()` should report that boundary. This is a successful binding with an open proof. [Original run and outcomes][log4j]

## Implement in this order

### 1. Close the Log4j failure through the product

Start with the existing prepared old/new manifests and frozen public questions. Separately run candidate discovery with the two deployments and the change, withholding those registrations until scoring. Reproduce the first open reason through `python3 examples/tools/build.py --change-plan application`. Keep the release order intact. Fix inventory, planner and replay together. Compare the resulting entry observation, zone histories and same-path substitution against the independent campaign evidence. Then exercise a proof recipe with the two-JAR order control in exercise 2. This catches a fix that works for a JVM replay and silently changes what the checker proves. [Product entry points][build] · [Frozen Log4j inputs][log4j-inputs]

### 2. Describe the deployment the claim actually runs on

For each revision and each supplied launch profile, record the ordered roots, pinned JDK, loader identity or delegation policy, and whether it is a production, test or original-client deployment. Derive the effective local class path for the supported loader. Resolve manifest URLs relative to the containing artifact’s **deployment location**. Track insertion order, transitive references, cycles, duplicate URLs and the path by which each provider entered the search. Preserve the original relative layout or a verified mapping when a cache renames artifacts. Where two manifests produce different effective orders from the same declared roots, report both. A matching filename or Maven coordinate alone cannot recover a lost layout. [Current manifest classifier][manifest-code] · [JAR specification][jar-spec]

“Every loader order” means every declared or directly evidenced deployment order for both revisions, including distinct loader scopes and original-client variants where applicable. An intentionally reversed path belongs in the controls. With an unordered bag, show the ambiguous winner and identify the missing launch evidence. For custom loaders, report what was observed for the particular invocation and which delegation or lookup remains unknown. Do not enumerate arbitrary permutations or promote one to production.

Extend the existing `bound / absent / unresolved` manifest handling. A known absent optional entry on a captured layout is usable negative evidence. A newly present, pinned local artifact with a verified deployment position can be included automatically. An unpinned artifact, unavailable original layout or unknown loader rule leaves the affected launch open. Preserve the existing absence checks around execution and deferred cache publication. If affected claims cannot be isolated soundly, keep the whole affected profile open. [Manifest appearance experiment][manifest-control]

### 3. Select an entry the caller can really use

1. For each changed selector, list the binary owner, JVM method name and full descriptor, physical provider, class digest, entry path and release variant on both sides. Record added, removed, moved, changed and shadowed definitions. Retain access, static, synthetic and bridge flags. A changed method inside a shadowed copy may have no effect on this launch.
2. Bind the owner in the named loader **before** resolving the member. Check access, descriptor, inheritance and invocation kind as applicable. A missing method on the winning class cannot be supplied by a shadowed copy. Record the runtime receiver and implementation when virtual or interface dispatch determines which body ran. Where linkage cannot be established, preserve the exact open edge or observed linkage error. [JVM resolution rules][jvms]
3. Prefer an approved or requested public entry whose path to the intended change can be checked. Otherwise rank accessible public callers by evidence: an original caller reaching the exact changed body, a statically supported call chain that can be exercised, then weaker candidates with their missing evidence. Consider constructors, public façades and factories that make an otherwise inaccessible receiver. Show competing candidates and their reasons. A shortlist may be capped for display or probing, with total counts and truncation recorded. A cap must never silently select a winner.
4. Use a fresh original JVM per revision/profile to check the defining loader, code source, physical class bytes and exact member. For an indirect entry, retain invocation or trace evidence linking it to the changed method on the applicable input. A non-initializing lookup establishes class identity. A witnessed call establishes reachability for that input. Resource claims also need the actual lookup mechanism, key, initiating loader and ordered resource origins where order matters. Class origin alone cannot establish which resource a caller consumed.
5. If two public entries express materially different behavior and available evidence cannot select between them, carry both into the existing claim-design review with one precise question about intent. Keep frozen approved claims intact. Stage 2 may propose a candidate using the upstream change’s intent or tests. Record that input as assisted discovery when comparing against a binary-only run. A unique, qualified entry should require zero user-supplied JAR indices, package hints or loader overrides.

### 4. Carry the evidence into setup, execution and reuse

Stage 2 can propose the caller before compiled artifacts exist. Stage 3 binds it when the revisions have been prepared. Produce **one versioned binding record per entry, revision and deployment profile**, referenced from the existing plan, scaffold, execution receipt and report. Reuse the existing sidecars and schemas where they fit. The ordinary `/prove-java-change` path and its `--scaffold-only` mode should surface the outcome. A plan-only or historical receipt reader should work offline from saved evidence. [Product stages][skill] · [Plan contract][plan-schema]

The record must let another process reconstruct the ordered graph and independently check the decision. Include revision and JDK identity, ordered roots and manifest edges, relevant absences, loader scope, all candidate origins (including byte-identical duplicates with different code sources), the selected artifact and class hashes, physical entry, exact member, shadowing reasons, caller-to-change evidence, and references to the JVM and checker observations. Reference the shared graph by digest across claims. For a refusal, name the side, first unsupported edge or disagreement, relevant candidates and the smallest missing fact that would settle it.

Build the physical index once per distinct artifact digest. Resolve effective views by deployment and JDK, batch requested owners and descriptors, and probe the shortlisted public routes. Avoid rescanning every dependency for every claim. Retain the index’s coverage and the reason any member was skipped.

Use the actual checker and replay arguments to verify both sides of the handoff. Record different per-revision class observations even when the binary name is identical. Qualify each backend separately. The historical 283-class audit compared a JVM with the measured native checker during a JBMC comparison campaign. It does not certify that stock JBMC selected the same bytes. [Historical audit implementation][origins-code] · [Recorded bindings][origins]

Bind reuse to the side’s effective order, loader and JDK profile, member and artifact identities, resource or manifest inputs, and resolver/observer version. Keep claim intent and verification bounds on their existing keys. Start with conservative whole-deployment invalidation within a side. Require warm/cold agreement, independence of the unchanged side, and rechecking of any assumed absence before a cached conclusion is published. Old single-JAR manifests and receipts remain readable. If an older record lacks evidence required for reuse on a new deployment, mark the binding for requalification.

For a reproducible first run, rehydrate the pinned inputs and verify their recorded digests. Some archived manifests name a prior agent’s absolute cache directory. Rebase only the storage paths and preserve the original deployment-relative names, order and hashes. In the existing application command, supply `--before`, `--after`, `--jdk`, `--workflows`, `--output` and `--run`. Use `--cache` and `--previous` for the resumed comparison and a fresh cache for its control. The existing resource discovery entry point is `python3 examples/tools/build.py --discover-resource-workflows` with both manifests, the JDK and a fresh output directory. Keep the normal product demonstration independent of these diagnostic invocations. [CLI and argument definitions][build] · [Application command][plan-cli]

## What the agent must hand back

- **A product demonstration.** Show a normal setup or scaffold-only run, a resumed proof or replay consuming its binding, and a compact per-side explanation for Log4j. Include the actual JAR order used, the two entry origins, and the unchanged claim IDs. An example-specific provider override, patched harness order or hand-written answer file does not satisfy this demonstration.
- **A machine-readable scorecard.** One row per case, revision, profile and question where applicable. Record input mode, inventory coverage, proposed and selected entries, JVM/checker agreement, public-call and changed-body reach, first open dependency, final claim status, cache action, and manual binding interventions. Distinguish supplied-entry qualification, cold entry recovery and alternate observations. Give numerators and denominators, including open and unexecuted rows.
- **Release evidence.** Gate the core capability on both Log4j bindings without manual repair, automatic handling of the ten manifest questions on the captured layouts, zero false admissions on the negative controls, matched cold/warm/clean outcomes, and a checked account of all 283 historical bindings. Run the frozen Parquet transfer once before tuning. Preserve its first result, including a miss. Count archive scans, checker batches and JVM probes on that graph so subsequent work can reduce repeated work without weakening qualification.
- **Evidence of automatic public-entry discovery.** Recover the façade in exercise 7 and the nominated Annotation Indexer entry in exercise 9 without supplying either selector. Move the discoverable resource entry into provider two of a controlled deployment and repeat with neutral provider names. For Log4j and Parquet, publish the first unaided ranking and the evidence for the chosen entry, even where the supplied-entry replay succeeds. This makes the improvement beyond accepting a known method measurable.
- **Next unresolved case.** Name the first remaining obstacle after binding succeeds, with a reproduction and the claim it affects. Distinguish missing deployment evidence, uncertain public intent, an unsupported loader/dispatch mechanism, and a downstream checker limitation. Keep solver-model expansion for its own brief.

Follow the repository’s existing changed-test and queued-proof conventions. Use small generated layouts for the controls and the existing campaign inputs for real-world qualification. Keep the historical registrations and result packets available as oracles. The implementation belongs in shared code that the next ordinary change will invoke.
