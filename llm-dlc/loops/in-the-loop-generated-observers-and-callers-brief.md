# Generate Java callers and observers from a registered prediction

**VF-063 implementation brief for the existing single-agent workflow**  
Reviewed November 26, 2026 against [`develop` at `32d3a22cfbae`][head].

Given a changed Java method, two prepared revisions and an approved prediction about public behavior, generate the caller that exercises the change and the observer that records what happened. The first milestone is Spring Framework #37434. Starting with the private number-parsing changes and the registered inputs, ordinary setup should produce a public caller that captures the actual number type, value or exception on each call. A wrong expected value must survive setup and be exposed by replay. [Registered Spring questions][spring] · [Upstream change][spring-pr]

## Why this is the next product capability

The 20-PR product campaign supplied 20 observers and their scopes. With that preparation, the verifier decided 43 finite questions over 85 histories, including one incorrect Lucene prediction. The earlier composition campaign explicitly records one Java observer, two production manifests, two registered scopes and one helper table per primary. Both campaigns could report zero **user**-written harnesses while agents still authored the instrumentation case by case. Those files are now a valuable independent evaluation set. [Product campaign][product-results] · [Construction accounting][composition-results]

The latest Spring P01–P30 campaign adds 94 registered merged-side predictions over 30 PRs. Three were refuted. Its numbered callers provide further checks on whether generation can reproduce an inconvenient result. [Spring P01–P30 results][spring-p]

VF-063 covers a larger problem. On its original blind draw, the product reached a public operation on both revisions in 12 of 16 projects and recovered zero registered primaries. Among those 12, four needed operation histories, four a complete reader or writer, three grammar inputs and one typed metadata. On a second draw, 44 candidate callers across 13 original distribution graphs again recovered zero primaries. **This brief measures recovery when the prediction is given.** Cold discovery of the prediction from a PR has its own denominator. Keep both results visible. [VF-063][finding] · [Second-draw callers and misses][successor]

## Product contract

| Input from the normal workflow | What the generator owns |
|---|---|
| Pinned old/new deployments and JVM profiles. Changed owner, name and descriptor on each applicable side. Public entry binding or candidate route, with its evidence. | Consume existing preparation and emit the two runner manifests with their real ordered artifacts, environment and provenance. When entry binding is unavailable, retain the missing fact. An established single-JAR binding is enough to start this work. [Companion entry-discovery brief][companion] |
| Frozen claim ID, side or relation, intended public observation, semantic input/domain, preservation boundary, assumptions, controls and expected predicate or independent oracle. For example, “parse this string as a Byte” is an input; the opaque case label `width` alone does not specify one. | Resolve public construction, calls, state retention, fixture data, input partitions and observable fields. Use a registered fixture by digest when the claim specifies one. If two interpretations produce materially different experiments, surface the smallest unresolved choice in the existing review. |
| The unchanged claim and its bounds. Expected values may come from the approved prediction, a separately pinned reference model, or a registered metamorphic relation. | Emit inspectable Java or bytecode, fixture recipe, workflow/scopes and a typed observation mapping. Persist generator version, evidence used, source and compiled hashes, and first unsupported step. The executable caller receives inputs and fixture data. The evaluator owns side-specific expectations and comparison. |
| An optional claim that a checked helper contributes to this public history. | Generate a helper declaration and table for supported helpers, with independent expected values and live-consumption evidence. A complete ordinary public observation can stand when this stronger derivation stays open. |

**Authorship rule.** Product-managed model synthesis is a valid implementation choice. A clean checkout must be able to perform it via the same maintained entry point and policy for every case. Persist its resulting source and replay those bytes. Count a campaign agent writing Java, translating a case into a private script, pasting an old caller into a fixture, or manually spelling out an executable plan as assisted work. Also record agent repairs and user interventions separately. The user-facing input can remain a short behavioral claim.

## First vertical slice

Spring’s two changed private helpers are `NumberUtils.isHexNumber(String)` and `decodeBigInteger(String)`. The customer observes `NumberUtils.parseNumber(String, Class)`. The implementation should be able to generate this experiment from the existing registration, with the historical `PublicCaller.java` and actual outcomes withheld. [Upstream diff][spring-pr] · [Registered inputs and falsifiers][spring]

| Frozen experiment | Measurement emitted by the caller | Evaluator check |
|---|---|---|
| Parse `+0x7f` as `Integer` and `BigInteger`. | For each public invocation, record normal return with actual runtime class and numeric value, or the exception type thrown at that call. Catch per invocation so the second call still runs. | Parent rejects both. Fix returns 127 in each requested type. |
| Parse `-0x7f` as `Integer` and `+127` as `BigInteger`. | Use the identical observation code with different inputs. | Both revisions preserve the signed values and types. |
| Parse `+0x80` and `+#80` as `Short` and `Byte`. | Return all four outcomes in input order. | The fix returns `Short(128)` and rejects both Byte cases. Keep this challenge scoped to the registered side. |

Run the same compiled observer against an outcome-changing subject control. Then change only the evaluator’s fixed-side expectation from 127 to 126. In the first run the raw observation must follow the subject. In the second, the caller, fixtures and canonical typed observation must retain their hashes and the evaluator must identify the wrong expectation. A method-entry trace alone would accept a caller that discards `parseNumber`’s result and prints 127.

## Implementation sequence

1. **Connect claim review to ordinary setup.** Stage 2 owns the reviewed meaning and controls. Stage 3 owns materialization after artifacts are available. `scaffold_example.py` already writes approved claim files and tasks. `verification/product-behaviour/register.py` already converts registered questions and bindings into scopes, allowed changes and `caller-workflows/v1`; it expects a case-authored `UpgradeProbe.java`. Extract or reuse the portable materialization logic at this seam. Keep campaign registries and their stored expectations behind the evaluator. Demonstrate `/prove-java-change --scaffold-only` and a resumed run that consumes the saved caller without regenerating or editing it. Keep existing authored callers usable and label their provenance. [Product stages][runtime] · [Plan schema][plan] · [Scaffold writer][scaffold] · [Registration materializer][registration]
   A typical application bundle contains an old and new prepared manifest, `workflows.json`, the per-question scope files, one `UpgradeProbe.java` shared across related questions, and any required fixtures. Exercise it through `python3 examples/tools/build.py --change-plan application --before OLD --after NEW --jdk JDK --workflows WORKFLOWS --run --output REPORT`. Keep example-specific paths and historical caller files out of the producer. [Existing command entry point][build]

2. **Generate the smallest public history that can distinguish the prediction from its control.** Resolve exact signatures using the bound deployment. Derive receiver construction, arguments, named object identities, aliases, callbacks, environment, action order and the points at which fields must be sampled. Permit the same receiver or buffer to survive multiple calls. Generate grammar inputs and complete write/read pairs when the observation demands them. Cap candidate search and record rejected candidates and the first missing operation. A successful call to an unrelated getter has zero coverage of the registered question. The benchmark already emits simple constructor–operation–getter candidates. Rust `construct` finds public producers for a *supplied* observer, and two shared generators already handle resource lookup and signed integer codecs. Build on these pieces. [Candidate generator][auto] · [Receiver construction][construct] · [Resource generator][resources] · [Integer-codec generator][codecs]
3. **Measure public behavior without encoding the answer.** Generate raw typed outcomes for the fields the claim names. Preserve distinctions such as returned null, absence, exception before entry, exception from the call, and error after a partial stream. Track ordering, multiplicity, callback count, object identity and caller-owned state where registered. Give each field a source in an invocation, a public read, a listener event or an independent readback. Store any wire encoding and field mapping so an evaluator can re-score the raw observation. The current `UpgradeProbe.observe(String[])` can carry a deterministic encoding; reuse the existing finite-field and correspondence facilities where they fit. Keep expected values, oracle calls, revision labels and historical actuals out of the measurement path. [Replay contract][replay] · [Typed finite observations][finite] · [Correspondence checks][qual]
4. **Qualify the generated caller on the original deployments.** Compile once against the older public API and reuse the same compiled caller when the claim concerns an existing client. Record separately any intentionally per-side compilation and its scope. The application replay already checks call sites, dispatch, entry origin and repeated fresh-JVM observations. Use that route when applicable. For a private, added or removed changed method, qualify the public call on each original side and record changed-body reach where that body exists. Keep deferred, asynchronous or pre-entry failures distinguishable. The numbered public-comparison runtime now supports `compileAgainst`, `compilePerSide` and paired per-side adapters. Declare the compilation policy and show any adapter source in the authorship record. A qualified finite observation and a symbolic proof each retain their own receipts and domain. [Original-classpath replay][replay] · [Numbered public comparisons][public-comparison] · [Evidence composition][compose]
5. **Generate one helper table through the product.** Start with Commons IO’s `Math.min(II)I` at `CharSequenceInputStream.read([BII)I`. Freeze the public question and caller. Discover candidate arguments from real marked calls; derive expected results from an independent minimum operation. Feed the generated declaration to the existing helper checker, bind its class and bytecode per side, and verify the actual consumer site, arguments and returned value before claiming use. Trace values alone describe an execution. Publish uncovered tuples or unsupported effects as open. Withhold one used row, change one expected result, and change the helper binding. Each must invalidate the affected helper derivation; rerun the ordinary observer independently. [Six registered pairs][io-helper] · [Shared helper checker][helpers] · [Original public experiment][io-results]
6. **Keep the workflow reproducible across retries.** Store the frozen registration, generation inputs, generated sources, fixture and compiled digests, verifier/observer identities, effective bindings and profile. A change to the oracle requires fresh scoring; a change to the caller, fixture or deployment requires requalification of the affected side. Preserve the project’s existing safe reuse policy. Compare warm, cold and empty-cache results. A page of generated source or a successful compile is an intermediate artifact. The deliverable is a qualified, repeatable observation or a reason it stopped.

## Qualification and scorecard

**Run the authorship experiment in isolation.** Give the operator production artifacts, changed selectors or diff, registered input meanings, observation and permitted evidence such as public API declarations. Freeze the allowed source policy, generator version, model configuration if used, candidate budget and transfer set before running it. Keep historical Java callers, per-case generator scripts, helper tables, observations, receipts, retrospective explanations and upstream tests that give away the full caller in the evaluator workspace. If an upstream test or old adapter is intentionally used, report a separate assisted attempt. Disclosed cases in this brief are historical transfer tests. A claim about fresh generalization needs an independently chosen set of new projects with registrations sealed before generation.

**Require falsifiers for the mechanism as well as the PR.** Alongside the wrong-prediction and changed-subject tests, plant a caller that executes the right method then returns a canned literal, one that reads a fresh receiver after mutating another, and a fixture that throws the expected exception before entry. Require all three to lose qualification. For generated helpers, remove the marked application while retaining the correct final public output. The helper-dependent claim must lose its evidence. Freeze the proposed history, projections, fixtures, expected relation and controls before inspecting qualifying old/new outcomes. Permit explicitly logged exploratory runs to resolve API or fixture construction. A repair informed by observed behavior gets a new attempt and retains the failed first result. Keep compiler failures, missing fields, nondeterminism and unsupported call paths in the denominator.

**Report each frozen question independently.** Record input mode and permitted hints; changed selector and bound public entry; caller/manifest/scope/helper provenance; compile and entry reach per side; coverage of all registered inputs, fields and controls; actual observed counterexample or first open step; finite and symbolic outcomes; custom code, manual repairs and user interventions. Include eligible denominators for helpers. Present successive counts for generated, compiled, reached, fully observed and correctly adjudicated. Compare against the historical authored callers at the same scope. A wrong old baseline stays open under `change_evidence.compose`; a qualified wrong new expectation with a valid baseline can refute. Preserve the underlying prediction discrepancy in either case. [Composer semantics][compose]

**Proposed acceptance bar.** Land the first product slice when examples 458 and 445 pass ordinary setup and resume with zero bespoke caller, manifest or scope edits, and the planted false greens are rejected. For the full campaign, target at least six of eight development cases fully observed, including Commons IO with a generated, consumed helper table and one complete write/read or reopen case. Target at least three of five retrospective transfer cases fully observed on the first frozen attempt, and zero false qualifications across all cases. Publish every first result even if a target is missed. Report fresh URL-to-prediction performance only from a separately measured cold run.

Hand back the shared implementation, one ordinary scaffold-only and resumed-run demonstration, the per-question scorecard with receipt references, and the smallest remaining unsupported caller with the exact missing operation. Keep the existing watcher, single-agent run and queued-proof conventions.
