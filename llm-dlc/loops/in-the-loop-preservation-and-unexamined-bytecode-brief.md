# Show what a Java change leaves unexamined

**Product implementation brief for `in-the-loop`** · Reviewed against [`develop` at `5f0b23893448`][head]

A reviewer opens a completed run. The selected return-value claims passed. Can she tell whether a callback now fires twice, a rejected update leaves an object unusable, or an entire changed method had no relevant check? The product should answer four questions on the first screen of the watcher report.

1. What was allowed to change, on which inputs, and who or what supplied that intent?
2. What behavior was checked for preservation, with which observations and evidence?
3. What unexpected differences or violations were found, and can they be reproduced?
4. Which changed bytecode and potentially affected public behavior still lack evidence?

Deliver this in the existing change plan and single-agent watcher. First expose the evidence the product already has. Then generate missing preservation checks from the change itself. Finally ensure the checker route and the intended-change policy preserve the precise meaning of each check. The first milestone can ship before the last two.

## 1. Make the existing run legible

**First acceptance case — Spring Petclinic.** Render this from the committed plan through the ordinary watcher, with links from each number to the underlying rows. This example is especially useful because every number below is correct at the same time. [Petclinic plan][pet] · [Original evaluation][app-results]

| Reviewer’s question | Answer recoverable from this run |
|---|---|
| Did the selected workflows work? | The adapted application established all three workflows. The old application also established all three on its own runtime. The old binary on the new runtime failed its startup claim, leaving its two business workflows open. |
| How far did those claims extend? | Four of 17 HTTP entries participated in the registered workflows. The other 13 are listed outside that scope. |
| What was preserved? | The framework comparator classified 51 observation declarations as preserved and ten as unresolved. All **61 behavioral obligations remained open** in this plan. Declaration matching alone cannot establish a runtime result. |
| How much changed bytecode escaped analysis? | This saved plan does not contain an adequate changed-method denominator. Display **unavailable from this run**. A fresh inventory can populate it. Never backfill a zero from the three passing workflows. |

**Second acceptance case — Retrofit/Wire.** Start with the selected response-conversion claim. Both deployments decode both phone inputs correctly. The planner also found the request direction. On both inputs its original public method writes the expected message on the old runtime and throws `NoSuchMethodError` on the landing runtime. Reordering Okio restores writes in the attribution control. Show the passing claim, the additional regression, and the three remaining factory operations that still need domains and observations. This is an existing discovery and replay the product can surface immediately. [Wire receipts and inventory][wire]

### What the plan must carry

Extend the Stage 2 plan’s preservation boundary into structured records the proof loop can consume. Reuse the existing preservation contract, observation types, claim keys, framework obligations, registered/additional/control cohorts and receipts. Give each preservation obligation a stable identity. Carry its source (selected claim, inferred default, independent invariant or user decision), entry or changed item, relevant revisions, input/history and assumptions, observation and comparison policy, allowed difference if any, status, and evidence or first blocker. Let an author review an inferred obligation without silently changing the original prediction. A renamed route, disputed correspondence or unclear business intent can remain an explicit question. [Plan schema][plan-schema] · [Preservation types][ir] · [Change planner][plan] · [Application comparator][compare]

Render the same records in the planning preview, the live `single_run.py` summary and the final result. Reuse that projection in the proof-workflow watcher. Keep registered claim outcomes intact when an additional check fails. Put a reproducible unexpected difference on the first screen alongside the original result. Offer a drill-down for the first missing observation, its importance and the cheapest action that would change its status. During an incomplete run distinguish pending, blocked, not selected and unavailable. Old records remain readable with explicit unknowns. ### Account for the changed bytecode

Use the effective old/new classpath and JDK for each deployment pair. Begin with the method fingerprints and origin records in entry discovery. Use the impact report to link changes to claims whose code dependencies they invalidate. The planner’s archive scan count, the number of candidate entries, and the count of decided claim subjects each answer a different question. [Entry discovery][entry] · [Change inventory][inventory] · [Impact and cache semantics][impact]

| Reported unit | Counting rule and what the reviewer can infer |
|---|---|
| Effective changed methods | Count each localized changed owner, name and descriptor once per deployment pair. Distinguish modified, added and removed. Retain both sides’ class identity and provider. Separate application changes from dependency changes. A proposed rename needs its own correspondence record. |
| Links from methods to evidence | For each changed method record, independently, a static link to a claim, a qualified body hit on each applicable side, and a **qualified check of a named observation** that can be tied to that method and scope. Identify the tie, such as a direct checker target, checked composition, or a witnessed operation with validated readback. Static reach, an instrumented selector request or an isolated body hit cannot establish the observation. A proof can supply a direct tie without a runtime trace. |
| Residual changed methods | Headline **“X of N localized changed methods have no qualified check tied to an observable.”** Show how many of X have only static or execution evidence and how many have none. Deduplicate overlapping claims. A refutation counts as a check with an adverse result. For each of the other N−X, keep missing projections, inputs, history depth and environment visible. Checking one return still leaves a callback open. |
| Additional change and uncertainty | List class-level changes whose affected members are uncertain, including handlers, bootstrap data and metadata. Keep resource changes, provider moves and shadow-only changes visible in their own units. Identify unreadable inputs, truncated discovery, unresolved dispatch or reflection, and unknown deployment layouts. Show whether the denominator is complete for the declared artifact set, partial, or unavailable. Zero identified changes and no usable inventory must display differently. |
| Public behavior at risk | Count affected or potentially affected entries and their open preservation obligations separately. A method reachable by five public routes counts once in the method inventory. The five routes may need different observations. Name the open entries or effects. No count of opaque edges can bound the number of behaviors behind them. |

Start with method counts. For a large upgrade, a secondary **size measure** can report old/new instruction totals *in localized changed methods lacking a tied check*, if the decoder and scope are qualified. Label that as the size of those bodies. Measuring exact changed or executed instructions requires an aligned instruction diff or instruction-level evidence respectively. Keep the two sides separate.

**Audit fixture.** The saved Log4j first ranking has eight effective changed classes, six localized selector rows, four potentially overlapping class-level uncertainties, zero changed resources, and 22 ranked entries. Reproduce those counts without summing the overlapping units. Use a small controlled deployment to check a changed method with two claims, an uncalled changed method, a call whose result alone is observed, a removal and addition, and a change confined to a shadow JAR. Add a handler-only or bootstrap-only edit and an unavailable-inventory run. Adding a second claim on the same deployment pair must leave the denominator unchanged. Reversing JAR order can change the effective denominator and must produce a separately identified report. [Log4j inventory][log] · [Member fingerprints][entry]

**Worked counting control.** Plant four modified methods on one effective classpath. Give A two valid return checks, B a body hit with no readback, C a qualified callback-count refutation and D no link to any claim. The report should say “2 of 4 changed methods lack a qualified observable check” and name B and D. A still has unexamined post-state. If a third claim on A makes that fraction improve, the accounting is wrong. Make this a tiny fixture with a known answer, separate from the historical Log4j measurements.

## 2. Discover side effects and general error patterns

**First new end-to-end capability — example 324.** Give the planner the original `Optional` deployments and the return-only claim. Withhold the historical callback claim, authored observer and expected counts from the producer. Have it nominate callback count from the changed fallback construction, generate the observation, bind the actual supplier, and run both revisions. Across four inputs all return values agree. The eager implementation makes an extra call on each of three present inputs. The lazy and explicit-branch controls preserve both values and counts. The watcher must show the valid return proof, the discovered callback difference, and the concrete present input together. The archived oracle and strict native result are independent scoring references. [Optional fixture and public results][optional]

Use a small shared set of triggers. Writes to a receiver, argument or aliased view suggest a post-state comparison on normal and exceptional exit. Calls moved across a guard suggest count, order and argument checks. Catch/finally, cleanup and retry paths suggest the escaping exception, committed prefix and what the next legal operation observes. Changed arithmetic at a bound suggests a boundary input and an independently justified range or monotonicity check. A changed method call or provider can suggest a public linkage or startup check. Existing Spring observation and failure analysis can supply candidate boundaries. Rank candidates by evidence of a changed operation on a public path, what a caller could observe, and whether a discriminating check is available. Include a cheap preservation control. Record the triggering site, the proposed oracle, the cost and why the candidate was selected or deferred. [Effect model][effects] · [Exception and handler inventory][failures] · [Generated observers][generator]

Use two ways to test a candidate. **Differential preservation** compares the two revisions at the same public boundary. **An independent property** checks each revision against a contract, a valid metamorphic relation, or an independently implemented reference. Record the source, domain and preconditions of that property. If both versions violate it, show a reproduced **pre-existing issue**. A landing-only failure is a regression. A parent-only failure is a repair. A changed behavior with unclear intent is an observed difference pending review. A suspicious opcode, a documented exception on invalid input, or an unstable measurement stays a candidate until the relevant claim has evidence.

### Worked campaign

Run each exercise initially with the revealing observation withheld. Use historical callers and tables on the evaluator side to score the generated or newly selected projection. Distinguish these masked historical recoveries from prospective discovery. Use the immutable deployment pairs, the same caller bytes on both revisions where applicable, and a fresh independent replay for an adverse finding.

| Exercise | What the product must discover or distinguish | Control that can falsify the observation |
|---|---|---|
| **197 · Shared array post-state** | Returns agree on all 71 input heaps. Checking only the right root finds 3 disagreements. Checking both finds 21. For shared `[0]`, the right root finishes as `[1]` versus `[0]`. Report all three scopes independently. | Clone a shared input or observe the other root. The caller must lose qualification. Distinct equal-content arrays are a separate control. [Example 197][arrays] |
| **314 · Partial writes before a throw** | Both implementations throw `ArrayStoreException` on the same 25 of 40 inputs. Twelve destination post-states differ. Capture the destination after catching the exception. One prefix is `[A,x]` versus `[x,x]`. | A normal-exit-only read or a new destination cannot discharge exceptional-state preservation. [Example 314][copy] |
| **538 and 539 · Rejection followed by reuse** | On the map, identical failure, size zero and empty iteration hide a retained key and a failing retry on the parent. On the indexed collection, identical rejection and key lookup hide a changed caller-owned list and a failed rebuild. Generate a bounded “fail, inspect, retry” history that transfers between projects. | Include ordinary updates, unequal colliding keys and an independent view/rebuild. Preserve which revision contained the defect. [Map][map] · [Indexed collection][collection] |
| **551 and 318 · Short histories** | An overwrite leaves identical five bytes with cursor 0 versus 3. A following write distinguishes them. For the queue, all 13 shorter-than-three histories agree. Three offers of A change the acknowledgement while leaving the same final queue. | Compare step-by-step events as well as terminal state. Cap depth and report histories beyond the cap as unexamined. Preserve a split-write or ordinary queue control. [Cursor][cursor] · [Queue][queue] |
| **322 and the shop fixture · Ordered effects** | Reversing resource acquisition changes close order on all 8 failure masks, while every tagged failure has the same exception class. In the shop, a bulk quote can drop or duplicate an event while preserving the response. | Check the nested-equivalent close implementation and an ordinary shop order. Record events at call time with order and payload. A modelled send supplies evidence about an attempted send. [Close order][close] · [Shop controls][shop] |
| **457 · Durable state** | Two failed Spring reservations surface the same public exception. A separate MySQL connection sees 98 after rollback and 100 after a successful commit followed by restoration failure. Compare retry, returned IDs and persisted rows. | Pin the real sidecar and isolate each run. An attempted SQL call or an in-memory mock cannot discharge the durable-row obligation. [Transaction readbacks][db] |
| **016 and 451 · General errors that need an oracle** | Derive a backoff boundary challenge from changed shift arithmetic and check the module’s stated delay bounds. Separately compare a reused clipped polygon’s bounds to its measured vertices and a fresh output. The latter invariant fails on **both** revisions. | Keep an in-range delay and a fresh polygon. Integer wrap by itself is legal JVM behavior. Attribute a failure to the PR only with matching parent evidence. [Backoff property][delay] · [Polygon readbacks][polygon] |

**Limit noise as part of qualification.** Freeze the trigger policy, ranking and per-case budget before scoring. For a first release, try at most three additional obligations per change in the default pass. List lower-ranked candidates and reasons for deferral. Reserve examples 539 and 551 for transfer after the pattern implementation is frozen. Keep their answer-bearing files outside the producer view. Publish detected eligible cases over all attempted cases, clean controls that raised a false finding, stops by reason, additional launches, and new case-specific inputs or hooks. An informative open row earns diagnostic credit. A fabricated witness or a clean control published as a confirmed regression fails the release gate.

## 3. Keep observation meaning consistent across routes and intent scopes

Use one reviewable contract for the observable, input and heap domain, exit kind, sequence depth, equality or identity rule, environment, and allowed changes. At dispatch, each route must identify precisely which obligations it implements. At result import, compare the requested statement with the returned one. Preserve the route’s actual quantifier, bounds, assumptions, gap treatment, vacuity and witness. A strict bounded proof and a finite JVM replay may corroborate the same projection while covering different input sets. A disagreement on matching statements stays disputed until the original deployment adjudicates the witness or the reason for disagreement is established. [Proof statement][statement] · [Public proof wire][wireformat] · [Claim history][history]

| Qualification pair | Required behavior |
|---|---|
| Ordinary equivalence, generic paired execution and explicit array roots | The ordinary regression harness can compare array post-state. Generic pairing and explicit bounded `int[]` roots have different observation policies and supported options. Reuse 197’s existing native and JBMC evidence for the full two-root profile. Request return-only, right-root and both-root separately on each eligible route. A weaker fallback or a smaller heap domain leaves the stronger obligation open. [Equivalence][equiv] · [Paired execution][paired] · [Explicit roots][roots] |
| Exception and effect semantics | Distinguish class/category, cause or message, suppressed sequence, frame on exceptional exit, and durable effects. Use 322, the existing write-before-throw and alias frame controls, and 457. A class-only equality may pass while suppressed order differs. A message-sensitive check needs a reproducible JDK/launch policy. [Frame controls][frame] · [Exception-message measurements][messages] |
| Allowed changes in only one region or field | Express approval as input predicate × observable × allowed relation. Check all affected observables outside the region and all unaffected ones inside it. Reuse 007’s confined change, 008’s below-tier price leak, and 144’s vacuous complement at the default array bound. Add a small case permitting a return change on one input while a callback doubles or an argument is mutated on that same input. The sibling effect must still be reported. An all-excluded domain is vacuous. [Confined change][inside] · [Leaking change][outside] · [Vacuity][vacuous] |
| Existing per-input approvals and unsupported combinations | Preserve the historical meaning of finite `allowedChanges` and `--unchanged-unless`. The former currently admits an `expectedNew` per input. The latter can exclude whole inputs. Add field-specific approval explicitly. The selected-array route presently refuses `--unchanged-unless`. Deliver a qualified lowering or retain the named refusal on that combination. A reviewer’s later approval creates a new assessment with its own identity while retaining the original finding. [Finite composition][compose] · [Array route][roots] |

## Release and independent verification

Start with the existing commands. In a prepared checkout, `python3 examples/tools/build.py --plan 197` lists the array checks. `python3 lib/benchmark/change-verification/wire_matrix.py --baseline-only --output "$TMPDIR/wire/summary.json"` reproduces the Wire evidence. The application change-plan command already supports a plan-only run, `--run`, and `--previous` for a delta. Use the same records through all three transitions. [Reproduction guide][run]

1. **Ship the report first.** From a fresh checkout, produce the Petclinic, Wire and Log4j figures above through the normal plan and watcher. Verify that every aggregate reconciles to stable rows, every finding links to evidence, and an old or supplied-only run with no inventory reports an unavailable denominator. The user must be able to name one passing claim, one unexpected difference and one material omission directly from the reports.
2. **Ship shared discovery and observations.** Recover the hidden callback in 324, the exceptional write in 314 and a same-on-both invariant failure in 451. On the two masked transfer cases require the relevant 539 view/rebuild and 551 cursor/follow-up differences without per-case observer code. Publish every miss before repairs and preserve the passing controls. Rerun the authentic Wire and MySQL deployments to verify the difference between a modelled boundary and an externally measured failure or effect.
3. **Ship route and scope qualification.** Exercise 197 and the scoped sibling-effect case across available routes. Require an equivalent statement with evidence or an explicit unsupported outcome for every requested projection. No green credit for vacuous complements, out-of-domain input, attempted-but-unmeasured effects, stale receipts or a fallback that drops a field.
4. **Keep it correct on resume.** Repeat warm and from an empty cache. Changing only the predicate may rescore retained raw fields if they suffice. Adding a missing getter, changing receiver identity or sequence, sidecar, provider bytes, model or bounds must invalidate the affected evidence. Keep provenance for additional JVMs and any user-supplied intent. Report how many rows moved from unexamined to qualified and which observations still could change unnoticed.
