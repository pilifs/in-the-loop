# Can the verifier help a maintainer review a Java dependency upgrade?

**Execution brief for `pilifs/in-the-loop` · 20 November 2026**

**Evaluate the verifier on 24 external upgrades, check whether improvements transfer to eight unseen upgrades, and run an advisory pilot with three Java teams.** Start the CompSuite and routine-upgrade calibrations now, alongside the current importer and array campaign. Once its accepted changes are in the repository, pin that commit as V0 and use the team’s existing verification workflow for the scored runs.

The unit of success is **one maintainer decision on one client upgrade**. The tool receives a dependency change and identifies a consequential behavior of the application that consumes it. It returns a scoped preservation result, a client-visible counterexample replayed on the JVM, or an honest explanation of what remains open. Six correct claims about incidental methods still leave the PR unanswered if the changed behavior was pagination, rounding, or the contents of a returned list.

## Assignments and exit evidence

| When | Accountable party | Deliverable |
|---|---|---|
| Now | Evaluation curator and an independent reviewer | Run the open calibrations below. Pre-register eligibility, budgets and scoring. Seal 12 breakages, 12 routine upgrades and eight transfer cases, with independent expected observations and a candidate/exclusion ledger. |
| After freezing V0 | Product operator with a reviewer who has not seen the answers | Run each upgrade from the pinned checkout. Save its first report for every case, including failures to build, timeouts and irrelevant claims. |
| After all 24 reports are sealed | Curator and verifier team | Score V0. Use recurring misses from the 24 to improve the product. Compare V0 and V1 on the same eight untouched upgrades. |
| After a useful retrospective result | Pilot owner and three consenting maintainers | Collect consecutive upgrade decisions in advisory mode. Report additional value over normal CI, review effort, latency and voluntary repeat use. |

One implementation team can own the product end to end. Use a separate person or isolated session for curation and adjudication. The operator and claim reviewer should have only what an ordinary maintainer would know at the time of the upgrade.

## 1. Open-book examples for calibration

**Start with rxjava-jdbc and Commons Text.** The first has a developer-written expectation about a returned sequence. The second is a merged, dependency-only change with a small independently enumerable claim. Get both through intake and adjudication before scaling to 24. Use Rocker and AWS to calibrate the human relevance rubric. All named examples in this section are disclosed and excluded from the scored and transfer sets.

The source assertions, version pairs and dependency-only changes below were inspected for this brief. ### Run a CompSuite calibration as the evaluator

```sh
git clone https://github.com/compsuite-team/compsuite.git
cd compsuite
git checkout --detach 6e6d738c8b0ca6ecbba6220b1fd549b2ae14a05d
python3 main.py --info i-87
python3 main.py --incompat i-87
```

CompSuite documents Java 8, Maven 3.6.3 and Python 3.11 as its reference environment. Its actual CLI spells the individual new-side flag `--testnew`. The runner uses Maven `-fn`, permits zero tests in its default test command, and inspects logs for a failure marker. **Verify the named test actually executed.** Resolve and record both tags' commit SHAs, effective POMs, JAR digests, runtime image and ordered dependencies. Repeat the named test in separate clean workspaces with fresh reports. Inspect the matching Surefire/Failsafe testcase, or equivalent records for a custom command. Verify old-side pass, new-side behavior and the exception or assertion that actually decided it. A skipped test, early linkage error, stale XML, missing resource or green wrapper exit gets its own disposition. Record the subject JDK separately from the JDK that runs the verifier. ## 2. Choose the 24 and seal the answers

**Eligibility.** Admit non-CVE Java/Maven production dependency upgrades with an identifiable consumer entry and a reproducible before/after build. The grade concerns ordinary functional behavior. Classify compile-only, dependency-resolution, build-plugin, policy, and test-tool failures during screening. Check for zero production-client source changes between sides, including generated code. Record transitive changes. When the resolved classpaths differ more widely than one artifact, attribute the observation to the upgrade closure until a controlled substitution isolates the cause. Record whether the case is an actual upstream PR or a benchmark-curated pair on real client code.

| Stratum | How to select | Evidence the curator seals |
|---|---|---|
| **12 known behavioral changes** | Screen undisclosed CompSuite cases first, then eligible BUMP cases. Both sides must reach the relevant consumer operation. Seek several kinds of behavior, including returned content, exceptions, and state or sequences of calls. | Exact loaded artifacts and entry, a developer test or independent discriminator, independently reproduced old/new observations, one preserving companion where feasible, and the user consequence. |
| **12 ordinary upgrades with a preservation claim** | For each behavioral case, seek a dependency-only merged PR in the same client or library family, choosing the nearest eligible PR in time under a predeclared rule. If unavailable, use a matched ecosystem, upgrade size and comparable build. Follow a fixed PR order. | One meaningful caller observation, frozen inputs, and an independent basis for expecting preservation across that scope. Use an exhaustive finite oracle, a separately justified contract or independent proof. A green merge is a sampling lead. If the two sides differ, record the discovery and continue screening before lock. |
| **8 reserved transfer cases** | Reserve four changes and four scoped-preservation cases **before V0 is scored**. Split each stratum evenly between a new client of a library represented in the 24 and an entirely new library family. Keep the eight sealed through engineering on the 24. | The same independent reference material, conditions and grading rubric. Also seal the family relationship to the 24. This permits separate measurements of reuse within a library and transfer beyond it. |

Freeze selection rules before seeing product outcomes. Dedupe by client, dependency, version pair, trigger and shared incident. Aim for at most two cases per client and library family within each 12. Record relaxations or shortfalls explicitly. For reproducible selection, the curator saves the candidate list and a seed commitment, sorts eligible candidates in each stratum by the SHA-256 of the seed plus their stable IDs, and follows that order subject to the matching/diversity rules. Log every exclusion with evidence. Keep the published examples, their duplicates and known in-house training fixtures outside the score. Flag prior exposure to a client or library separately. After lock, failed intake, exhaustion of the budget and unsupported cases stay in the denominator.

**Two packets per case.** The operator packet gets a neutral ID, the review-time consumer change, dependencies, ordinary historical context and the common prompt below. The curator packet also gets the hidden assertion, test method and fixtures, expected result, failure logs, later fixes, companion, scope and the signed reference observation. Keep the second packet out of the operator's context, accessible history, compiled test classes, runner logs and searchable working tree. Give the operator a neutral, read-only pair of revisions if the dataset fork name or commit history reveals the answer. Retain checksums tying the production bytes and dependency coordinates to the originals. If the pinned workflow cannot process the supplied pair, record an intake failure. Track any result obtained with case-specific assistance separately.

Use review-time tests in the product run except the sequestered trigger and any duplicate that discloses it. Separately run the full client CI that a maintainer actually had and record whether it already included the trigger. Rediscovering an existing CI failure can establish diagnostic value. Credit an additional finding only if it adds an independently validated observation beyond the original CI. Public cases are held out from this campaign's engineering, and model pretraining exposure remains unknown.

## 3. Run the pinned verifier and its baselines

Record the repository commit and the team’s invocation during calibration. Pin the checker binary digest, model IDs/settings, library models, prompts, JDK images, solver, hardware, cache policy and limits. Suggested pilot default per PR is **4 vCPU, 16 GiB, a two-hour end-to-end budget from case intake, and up to 15 human review minutes**. Record first useful evidence at 15 minutes as well as the final result. Use the open calibrations to set one affordable model/token cap and confirm these defaults before the cohort is locked. Give comparable systems the same stated machine and wall budget, with their own setup work visible. Record shared environment preparation once and identify runs that resolve dependencies from a cold cache. Count case-specific preparation, claim approval, queuing and replay in the end-to-end result.

Use a fresh working area per case. Give the operator the revision pair and the same neutral request each time. Have a reviewer who has not seen the answer assess the proposed claims. Record each clarification, edit and minute of human work. Supplying the hidden observer or a new domain oracle moves the result into an assisted column.

> Identify which behavior of this application could change for its caller. Check the most consequential preservation or change claim you can justify with the pinned verifier. Record the result as open at the first unsupported operation.

During scored runs, confine changes to case inputs, harnesses and evidence. Case-specific setup may construct the actual receiver, invoke the consumer and read its result. Audit adapters for correspondence and non-vacuity. A fixture that supplies the dependency result, an injected expected answer, or a handwritten replacement for the client's application path changes the scope. Verify the checkout, checker and model hashes afterwards. Preserve any attempted engine edit as a diagnostic for the later engineering pass.

**Baselines answer different questions.**

- **Original client CI** is the operational baseline on all 24. Record whether it flagged the same issue, elapsed time, and any additional diagnosis supplied by the verifier. An API-diff tool such as japicmp or Roseau can explain binary/source compatibility where relevant.
- **CompCheck** is a client-specific regression-discovery baseline. Run it on supported cases. Record the call site and other inputs an operator had to supply. Joining the published registries gives **13 of 123 CompSuite entries** with the same client, library, old version, new version and developer test in CompCheck's knowledge base. Report its out-of-box result and a sensitivity run excluding prior knowledge of that same client/incident. Retain applicable knowledge from other clients. Mark uncovered cases and publish the applicable denominator. - **JBMC** is a secondary engine comparison on a declared subset. Supply the same entry, before/after bytes, input domain, observer and resource limits. ## 4. Grade the PR, then diagnose the miss

Have the operator seal its claims, report and artifacts before revealing the reference. The curator and a reviewer independently grade relevance and evidence. Resolve disagreements with written reasons. Grade **what changed**, **whether the evidence supports the stated scope**, and **whether a maintainer should act** separately. An intended improvement can be a correctly detected behavioral difference. A correct result about a different observer earns its technical claim verdict and a miss on the primary PR question.

| Measure | Decision rule |
|---|---|
| **Relevant change found / 12** | On the original client and artifact pair, the reported counterexample independently replays and exhibits the sealed behavior or an adjudicated equivalent. A different valid finding is recorded separately. |
| **Relevant preservation established / 12** | The original observation and admitted domain are covered with a non-vacuous, appropriately qualified result. Record native proof, other proof engine, and exhaustive finite-JVM decision separately. Finite sampling or a smaller domain earns its own scope. |
| **Contradicted assurances / 24** | Count PRs with any accepted claim contradicted on its stated artifacts, domain and observer. Reproduce and investigate immediately. A missed behavior with an honestly bounded result is a relevance miss. A summary that calls the whole upgrade safe also gets a reporting fault. |
| **Open, irrelevant or unavailable / 24** | Assign a primary reason such as wrong claim, build/setup, first unsupported JVM operation, missing environment assumption, timeout, or evidence rejection. Preserve intermediate verified claims. |
| **Review cost and incremental utility** | Per PR, record cold/warm state, elapsed time to first actionable result and final report, elapsed time for unresolved cases, human minutes, tokens/compute cost, and whether original CI already supplied the finding. Tabulate false alerts on the 12 scoped routine upgrades separately. Report exact counts with denominators. |

Save one operator record and one adjudication record, joined by a neutral case ID. At minimum keep `case_id`, client/revision pair, artifact digests, primary claim/observer/domain, scope qualifications, tool/configuration digest, result route, direct replay or proof receipt, CI result, human minutes, time, cost, and the grade with reason. Keep links to retained evidence and per-attempt timings. For registered examples, capture the existing exports with these commands.

```sh
python3 examples/tools/targets/workflow_handoff.py handoff NNN --markdown
python3 verification/pipeline.py report --format json
```

Use the following five lines for the report a maintainer sees. For an open result, put the first unverified step on the evidence line.

```text
Upgrade <client> · <old dependency> → <new dependency>
Caller-visible behavior <entry point, observation and why the application uses it>
Result <before/after replay, scoped preservation, or open> · <link to evidence>
Scope <input domain, environment and assumptions that affect the decision>
Review action <specific action, reason and any remaining uncertainty>
```

Treat the intentionally balanced 12+12 as a comparison set. Estimate how often alerts appear in routine work from the prospective pilot. ## 5. Spend the next engineering cycle on what the misses cost

Group misses by **distinct affected client upgrades**. Prioritize a common blocker when a fix would change multiple PR-level outcomes. If claim selection repeatedly misses caller-visible values, improve how the planner identifies consumer entry points and observations. If the right claims repeatedly stall on the same operation, extend the verifier there. If correct answers arrive late, inspect preparation, queuing and invalidated summaries before changing the solver.

For each chosen improvement, record first-case engineering time, the general change, the controls that challenge it, and the second client that can consume it. Replaying the original 24 after fixes measures recovery. Freeze a new V1 before revealing the reserved eight. Run V0 and V1 independently on the **same eight** at matched budgets and cache conditions. Keep the second runner blind to the first report. Publish both correct, V1 only, V0 only, and neither, with regressions, availability, costs, and the same-family/new-family split. If the implementation team saw a transfer answer, retire that case from the held-out claim and report the exposure.

## 6. Run with three teams and make the investment decision

Recruit three consenting Java/Maven teams with ordinary upgrade traffic. The pilot operator runs the pinned verifier on the **first five eligible consecutive dependency upgrades per team** and delivers an advisory report to each maintainer for review. Log all arrivals and exclusion reasons. Before showing the report, collect the maintainer's usual action and the CI evidence they had. Afterwards record the actual decision, including merges as planned, deferrals, changes to the pin, added tests and requests for information. Record whether the report arrived before the decision, total human minutes, and whether they voluntarily request another review. Extend the observation window if traffic is slow. Keep unpublished code and results within each team's agreed environment.

**Proposed investment gates.** Agree or amend these before opening the scorecards.

- **Start the prospective pilot** when V0 or a clearly identified repaired build independently replays at least **8/12 relevant historical changes**, establishes **8/12 original-scope routine claims**, and has **zero unresolved contradicted assurances**. Label recovery scores on the original 24 as such. If a gate is missed, use the largest group of misses to choose the next repair and keep the cohort totals visible.
- **Count a repair as transferable** when V1 gains a relevant outcome on an untouched client, the case uses the improved capability, and matched V0 missed it. Publish every regression alongside every gain. A gain confined to a library already seen justifies reuse within that family. Expansion to another family needs a corresponding new-family result.
- **Expand advisory use** when at least **two of three teams voluntarily choose another run**, there is a documented instance of the report improving a real review beyond existing CI, and there are zero unresolved contradicted assurances. Report how many results arrived in time and what the useful review cost. These thresholds guide the next investment. The prospective sample is too small to estimate market-wide demand.

Put V0's results on 24, the paired V0/V1 results on eight, and the maintainer decisions on up to 15 consecutive PRs on the first page of the final report. Include one independently reproducible changed behavior, one meaningful preservation result, and one miss that identifies the next engineering priority. Lead with what a client team learned beyond its existing review process.
