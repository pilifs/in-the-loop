# The Python architecture around `jvmcontract`

**Recommendation.** Keep Python for planning proofs, preparing artifacts, running controls, and qualifying evidence. Refactor the point where a declared claim becomes an executable `jvmcontract` invocation. Make that translation inspectable before a run and check the effective statement against the claim before accepting a result. This addresses a concrete defect and gives agents a simpler way to author the next example.

**Scope.** Review of `pilifs/in-the-loop` at `2fd3369f`, covering the ordinary Java target route, selected example drivers, the Rust CLI boundary, evidence ingestion and queue submission. I exercised the Python planner and command builder with the real example 307 packet and stand-ins for prepared artifacts. I inspected six example drivers. I did not run a solver, produce a receipt, or benchmark the queue. The migration below is designed to follow the foundation work already underway.

## Where the architecture works

| Boundary | What already works | What I would change |
|---|---|---|
| Example authoring | A task identifies a property or revision pair. The sidecar and claim file already express the method, inputs, observations, bounds and controls. | Keep the existing JSON authoring path. Give authors a way to see which parts the selected proof strategy can honor. |
| Proof lifecycle | The 74-line `route.py` coordinates planning, preparation, controls, verification and ingestion. Frozen Python types distinguish a task plan, prepared target, raw execution and receipt. | Extend that existing sequence with an explicit translation from the planned claim to an invocation. Preserve stage-specific refusals. |
| Rust checker | The binary exposes property-file execution and structured descriptions of assumptions, observations, bounds, models and vacuity. | Use those fields as evidence of what was checked. Add narrow output fields where Python otherwise has to infer scope. Keep JVM semantics in Rust. |
| Verification queue | Task submission reuses the proof planner. The queue owns a pinned checkout, resource limits, retries, logs and conflict-aware collection. It also runs other kinds of jobs. | Let the queue carry proof and attempt references. A retry gets an execution identity so the earlier attempt remains discoverable. |
| Evidence and reporting | Acceptance already checks details such as artifact identity, replay and provenance. | Move result decoding out of the CLI. Keep the decision to accept a claim independently checkable. |

## The failure that changes my recommendation

Example 307 declares equivalence of two revisions of a Java method under a specific input assumption. Its salt argument is restricted to seven values, including null. The claim also declares two nullable parameters, an array-length bound of 80 and an unwind bound of 513. The planner freezes that assumption into the claim. The ordinary equivalence command forwards nullability and both bounds, and silently omits the assumption. The example’s own driver explicitly passes it. Rust exposes the corresponding option. [307 preservation claim](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/307-spring-security-fe9e4549-bcrypt-standard-charset-utf8/claims/hashpw-preservation.json) · [Claim planner](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/workflow.py#L209) · [Ordinary invocation](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/runtime.py#L1581) · [307 driver](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/307-spring-security-fe9e4549-bcrypt-standard-charset-utf8/proofs/prove.py#L78) · [Rust equivalence interface](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/lib/src/main.rs#L491)

I varied the claim in three schema-valid ways using the same revisions, prepared-artifact descriptors and work path. The variants covered a return-only observation, adding an input assumption and adding a poststate observation. The planner produced **three distinct frozen claim keys**. The ordinary builder emitted **one identical complete command**. The property-proof branch of the same builder does forward an assumption. The defect is specific enough to fix and test. [Claim schema](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/schema/target-claim.schema.json) · [Claim planner](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/workflow.py#L209) · [Ordinary invocation](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/runtime.py#L1581)

The consequence depends on the direction of the verdict. A difference found outside the seven admitted salt values cannot refute 307’s claim. A proof over a larger domain can establish a narrower property when the observations, other assumptions and bounds justify that inference. Likewise, identical commands for two observation sets can be legitimate if checker defaults cover both and acceptance handles the direction correctly. The experiment establishes a translation gap. It does not establish an incorrect published verdict. In particular, 307 has a bespoke driver that passes the assumption.

The first regression fixture should be much smaller than 307. Use two methods that agree on all nonnegative inputs and differ on a negative input. Run with and without `assume x >= 0`. The unconstrained case should expose the difference. For the constrained case, require an appropriate established result on a supported route, or a precise unsupported result. A negative witness must be ineligible for that claim. A second fixture should return the same value in both revisions while mutating an array differently. It tests whether acceptance understands the difference between return-only and return-plus-state claims. Check the resulting evidence as well as the generated command.

## What should become declarative

I would introduce one small Python component that consumes the existing task plan and a selected **proof recipe**. The recipe describes how a verifier can check a claim. Its first implementation can be a typed Python function for direct-method verification. Give authors a new JSON field only when there is a real choice to express. An adapter recipe becomes justified by the second pilot.

| Concept | What belongs there | Example |
|---|---|---|
| **Claim** | What is asserted, about which revisions and method, over which domain and observations, with which semantic bounds. | The two revisions agree on result and exception class for the seven admitted salts. |
| **Proof recipe** | Which method the checker actually enters, how it corresponds to the subject, how each side’s ordered classpath is built, how assumptions and observations are enforced, which models or lemmas are required, and what replay qualifies the result. | Direct verification of a method from pinned source slices, or verification through a named adapter with an explicit scope. |
| **Attempt policy** | Operational choices such as wall-clock budget, resource limit and retry. Attach the actual choices and measurements to each attempt. | Raising a timeout can retry the same obligation. Reducing the array bound changes the scope the attempt can establish. |
| **Evidence** | Checker-reported statement, actual byte identities, verdict, qualifications and replay where applicable. | A refutation is eligible when the replayed witness satisfies the claim’s precondition and differs on a declared observation. |

The recipe should implement each semantic field through an explicit argument, a pinned harness, or an independently verifiable checker default. For anything else, return the existing `Unsupported` type with the uncovered field. For example, the ordinary builder already refuses hashed model files it cannot supply. A named Rust model and a file with a digest are distinct inputs. Preserve that distinction. Classify engine, model and gap-handling changes by their effect on the checked statement and its qualifications before treating two attempts as comparable. [Ordinary invocation](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/runtime.py#L1581) · [Workflow interfaces](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/interfaces.py#L45)

Expose that mapping in the existing `--plan` output. Planning can immediately explain which inputs it will enforce and which need prepared artifacts. Preparation binds the actual bytes, entry point and ordered classpaths before starting the solver. Ingestion then reconciles the Rust statement, artifact identities and witness or independent controls with the frozen plan. An echoed plan digest proves which plan was requested. It supplies no independent evidence that the verifier enforced it. ## Why the custom drivers matter

In examples 286–290 and 307, **19 of 26 proof tasks declare `besideRoute`**, which sends them through an example-specific proof path. The counts are 4/6, 4/6, 1/4, 4/4, 4/4 and 2/2 respectively. I selected these six because they exercise demanding real-world cases. The counts describe their checked-in task declarations, not a repository-wide rate or a tally of accepted proofs. All six drivers already use the shared `beside_route.Run`. Another generic run helper would leave the most important duplication intact.

The ordinary route deliberately verifies the original bytecode entry. A driver can instead enter an adapter, select an environment model or calculate a claim-specific unwind. Those choices change what a verdict can support. A declarative recipe earns its place when it makes the checked entry and its relationship to the claimed method visible **and** removes hand-written invocation assembly from the next example. Keep specialized Java adapters, independent oracles, and unusual stand-in compilation in code. Agents need room to discover a new strategy before it has a reusable representation. ## Implementation order

| Order | Change | Acceptance criterion |
|---|---|---|
| **1. Fix the known gap** | Add the two benign fixtures. Audit each existing claim field across property and equivalence paths. Forward equivalence assumptions on supported paths and refuse unsupported combinations. | Each semantic field has an explicit implementation or diagnostic. For both fixtures, test which verdict and witness are eligible. Detect statically known gaps before expensive preparation. |
| **2. Introduce the invocation model and migrate 307** | Use the existing `TaskPlan` to generate a typed invocation for both 307 tasks. In shadow runs, compare the common path with the example driver on the same frozen inputs and budget. | Match the original entry and slice bytes, ordered dependencies, seven-salt restriction, nullability and bounds. Preserve replay’s digest check for each revision. Compare verdict, witness or reason unresolved, and downstream acceptance for both preservation and its mutation control. Investigate discrepancies before switching the route. |
| **3. Exercise the adapter boundary on 289** | Declare the checked adapter entry and claimed upstream method separately. Preserve the current relation between input length and unwind. Record the adapter identity and what qualifies transfer of the result to the upstream method. | A scope mismatch is visible at planning and rejected at acceptance. A second example with the same proof shape can be added without a new `prove.py`. Where transfer cannot be justified, publish the narrower adapter result. |
| **4. Extract decoding and make attempts comparable** | Move shared Rust-result decoding and classification primitives from `build.py` to an importable module. Give the existing ordinary route an explicit timeout policy. Connect the recipe to the foundation’s claim and attempt records. | Existing CLI consumers and historical receipts remain readable. A timed-out attempt and its successful retry are independently discoverable. A multi-claim run records separate dispositions and evidence per claim, including partial completion. |

Example 307 has an unusually cheap starting point. It already calls the common planner and preparer and explicitly checks that it is proving over the same JAR bytes the replay ran. Example 289 then forces a genuinely different decision about scope. Examples 286 and 290 can remain custom while the pilots establish which parts of stand-in compilation, model selection and initialization recur. The next structural cleanup belongs at the evidence boundary. Receipt ingestion currently imports `build.py` for classification functions. Some acceptance checks rely on a literal generated Java guard or a phrase in human-facing output. Introduce one version-aware decoder for the wire format. Replace textual signals individually when structured evidence and an independent behavioral check cover the same guarantee. A shared decoder can tell consumers what Rust reported. Eligibility for a particular claim still requires a separate decision. ## Fit with the foundation work

Keep the existing distinction between the source claim key and its binding to prepared artifacts. Link the recipe, actual invocation, operational budget and stage reached to the durable attempt. A retry on the same obligation should let an agent discover that preparation succeeded, the solver exhausted its budget, and a later approach changed strategy. A narrower semantic bound or adapter scope must remain visible. Historical results retain their original meaning. Several claims can share preparation or one invocation, while each claim keeps its own verdict and evidence links. Rust already supports multi-property runs, so the Python design can support such batching where the selected backend and claims are compatible. [Workflow interfaces](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/interfaces.py#L45) · [Claim planner](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/examples/tools/targets/workflow.py#L209) · [Rust property-file interface](https://github.com/pilifs/in-the-loop/blob/2fd3369fb9c884f6bdcbb6549426382d762b1c4f/lib/src/main.rs#L973)

I would leave the foundation brief in flight and make the 307 migration the first consumer of its records. Measure progress by asking three questions. Can an agent tell what will actually be proved from `--plan`? Does acceptance reject an out-of-domain or wrong-observation witness? Can the next example of a supported shape land without a new driver? The answer to those questions is a better signal than line counts, the number of configuration fields, or a wholesale switch of orchestration frameworks.
