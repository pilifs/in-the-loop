# jvmcontract

Formal verification of JVM bytecode, as *contracts* derived from the compiled code and checked in next to it.
The build fails when the code no longer matches its contract. A developer who changes behaviour on purpose regenerates the contract, and the pull request then shows reviewers exactly which behaviour changed, and only that.
Nobody writes a specification.

This is the Rust library and command line behind the [examples](../examples/README.md) of this repository.
It started as a port of the Java proof of concept in [`examples/tools/contracts`](../examples/tools/contracts/README.md) and the Python scripts around it, and goes further: it runs without a JVM, its purity proof is complete over the executed domain, it needs no Java compiler for its symbolic proofs, and it adds contract kinds and views the original did not have.

| Contract | For | The contract is | Proved by | Approach |
|---|---|---|---|---|
| **Behavioural** | A pure method with finitely many inputs (enums, booleans, records, sealed types), static or an instance method of such a type | The outcome of every input | Purity from bytecode, then every input executed in the built-in interpreter under an effect monitor | [B8](../examples/approaches.md#b8-behavioural-contracts-poc-in-toolscontracts) |
| **Regression** | A method with unbounded inputs (`long`, `int`, ...) | The previous version, outside the inputs the developer declares as changed | Both versions in one program, a generated bytecode harness, bounded model checking with JBMC, the counterexample replayed in the interpreter | [B9](../examples/approaches.md#b9-regression-verification-poc-in-toolscontracts) |
| **Property** | A method with unbounded inputs | A statement the developer makes about it, committed next to the code: a postcondition (`result >= baseMillis && result <= capMillis`) or a law (`result == merge(b, a)`) | A generated bytecode harness that assumes, calls and asserts; JBMC proves it over every input or finds one, replayed in the interpreter | [B11](../examples/approaches.md#b11-property-proofs-in-lib) |
| **Capability** | A module, or a dependency jar | Every JDK capability (clock, network, reflection, ...) and library its bytecode can reach | A closed-world walk over every call site | [B10](../examples/approaches.md#b10-capability-contracts-poc-in-toolscontracts) |
| **API** | A module | Every public type and member, with its exact signature | Read from the class files | |
| **Boundary** | A Spring Boot module | Where the framework enters it (routes, listeners, schedules, bean definitions), the advice on each bean (transactions, security, validation, caching, retries), the places where an annotation does not do what it says, the configuration keys (what the classes read, what `application.yaml` sets, what the class path's metadata declares, cross-checked), the wire types (the JSON shape of each request, response and message) and the stored types (the shape of each MongoDB document, with the query strings that name a field it does not have), and under each entry point what it reaches: the documents and tables it reads and writes, the topics it sends to, the HTTP calls it makes, the events it publishes | Read from the annotations in the class files and the application files, with a closed-world walk over the module's own calls | [B12](../examples/approaches.md#b12-boundary-contracts-in-lib) |
| **Protocol** | A distributed system | A TLA+ operator generated from a behavioural contract, inside a model checked by TLC | TLC, over every interleaving within bounds | [D1](../examples/approaches.md#level-d-distributed-systems) |

Every verdict is one of three. *Verified*: the code behaves exactly as its contract says, for every input. *Violation*: behaviour changed and the developer did not say so, with a concrete witness. *Unverifiable*: the tool refuses to give a verdict, because "we could not check" must never read as "fine".
Every verdict can be written as SARIF for GitHub code scanning and SonarQube.

## Install

```bash
cargo install --path lib          # from this repository: puts `jvmcontract` on your PATH
cargo build --release -p jvmcontract --manifest-path lib/Cargo.toml   # or just build it
```

It needs nothing else to derive behavioural, capability and API contracts: no JVM, no `javac`.
It reads the JDK's own class files from the `lib/modules` image of the JDK found through `JAVA_HOME` or `java` on the `PATH`, to know the shape of JDK types (a built-in table of `java.base` facts covers the common ones when no JDK is found).
Regression and property proofs need [JBMC](https://github.com/diffblue/cbmc) on the `PATH`, except where the tool's [own checker](#the-tools-own-checker) applies (`--engine native` or `auto`: methods over integers, arrays and records of them); the models of the JDK classes JBMC has no bytecode for ship with the tool ([`models/`](models/README.md)), and so does the SAT solver the checker uses (CaDiCaL, compiled by `cargo build`, which therefore needs a C++ compiler). Model checking needs TLC (`~/tools/tla2tools.jar`, `$TLA2TOOLS_JAR`, or `tlc` on the `PATH`); `$JVMCONTRACT_JAVA_OPTS` passes JVM flags to it, such as a heap size for `--coverage` on a large model.

Each JBMC run is limited to 3 GiB of address space, so a proof that runs away ends as "cannot be verified" rather than exhausting the machine. `JVMCONTRACT_JBMC_MEMORY_MB` changes the limit, and 0 turns it off. JBMC is read through `--json-ui` ([`src/jbmc.rs`](src/jbmc.rs)): its property results, the trace of the failed one, whose input values are read from their bits, and its overall `cProverStatus`. Only `success` with every property holding counts as a proof: a solver that gives up leaves no property failed and the status `error`, which is no verdict. Each run says how it ended, with the kinds of no verdict apart: an unwinding failure, another property failing, a timeout, memory exhausted, a kill, a solver failure, JBMC refusing the program, or output it cannot read. The console text was read before step 4b of `llm-dlc/loops/sound-verdicts.md`; that reader was removed once both readings had agreed on every run of every recorded JBMC example (88 runs, pipeline jobs 20261106-073804 and 20261106-123940).

JBMC's own approximations are gaps, in the same modes as the own checker's ([`src/jbmc_gaps.rs`](src/jbmc_gaps.rs), step 4c of the brief). Before JBMC's proof, the tool lists JBMC's goto program on the harness (`--show-goto-functions`, which converts what the proof would and solves nothing; `jbmc-goto.txt` in the work directory) and walks JBMC's own call graph from the harness. A method reached with no bytecode on JBMC's class path is JBMC's stub, which returns any value of its type (`null` or a new object for an object) and does nothing else: a JDK one has the own checker's id (`jdk-constructor:java.util.ArrayList.<init>(I)V@jdk-...`), any other is `missing-body`. An `invokedynamic` JBMC links to no class of its own making takes the value zero or `null` (`invokedynamic`: a string concatenation, a record's `equals`, `hashCode` or `toString`, a lambda for an interface JBMC has no class file of). And a method that synchronizes is a `monitor` gap, since JBMC drops monitor instructions, so `synchronized (null)` throws nothing there. The stubs JBMC's stub reproduces exactly (the constructors of `Object`, `Record` and the JDK's exceptions, and a JDK constructor that only calls one of them) are no gap, and nor are the stubs only a JDK class's initializer reaches, which the statement's engine assumption covers. The call graph takes every branch, so when it reaches a stub the preflight also runs JBMC's symbolic execution of the proof (`--program-only`, with the proof's bounds and over every input, solving nothing; `jbmc-symex.txt`), whose formula is what the proof solves, and a stub none of its steps comes from is on no path within the bounds and no gap (the note names it: `never enters`). The model of `List.copyOf`, for one, calls the stubs `Collection.isEmpty` and `toArray` only for a collection other than the lists `List.of` makes. The steps are read by the listing's location numbers, each checked against the listing's comment for it; a run that does not finish within the preflight's minute, or does not match, leaves the call graph's gaps. Symbolic execution drops a branch only when it simplifies the condition to false, so a stub behind a condition only a solver decides (one an `--assume` closes) is still entered. For those, the preflight runs the proof once more, with its bounds, solver and every input, and a probe before each call site of each stub (`jbmc-probes/`, its output `jbmc-probes.txt`). The probe is a method of `jvmcontract.StubProbe` that the call site is rewritten to: on a branch `CProver.nondetBoolean()` chooses, it fails an assertion of its own, and otherwise it makes the call, so no path is cut and a stub reached after another's probe is still reached. A stub whose every probe holds, in a run with every unwinding assertion holding, is no gap (the note: `its solver shows no path`). A run out of the preflight's minute or with no verdict, or a call site no probe can be placed at (no bytecode index in the listing, a caller with no class file), leaves the stubs gaps. Call sites JBMC does not link, monitors and defects stay the call graph's. Under `--gaps strict` a JBMC proof that reaches a gap is no verdict, and a counterexample stands when the interpreter replays it; under `--gaps assume` the verdict names each one (`assuming 1 behaviour JBMC does not implement`). Under `--gaps advised` JBMC applies the contracts for its gaps ([`src/jbmc_contracts.rs`](src/jbmc_contracts.rs)): a gap its program reaches with no contract stops the run with the advice, as the own checker's do, and each contract is checked (proved, tested on a JVM, or trusted, or the library's record) as for the own checker. JBMC applies one by running the same contract method: each call site of the gap, in the harness and the application's classes, is rewritten into a call of it (`jbmc-contracts/` in the work directory), and the intrinsics it calls are JBMC's `org.cprover.CProver` (`nondetInt`, `assume`), with an input outside the contract's `assume:` a failed property of its own, which is no verdict. A call site whose JDK method an application class overrides is left as it is, and its gap stays open. What no contract closes under JBMC (a monitor, an `invokedynamic`, a missing body outside the JDK) is listed in the advice as approximated whatever the contracts, and refused as under strict. `build.py` runs a recorded example JBMC proves in `assume` too.

The same preflight names where JBMC runs bytecode it has otherwise than the JVM, whatever its class path: a *defect*, not an approximation ([`tests/fixtures/jbmc-defects/README.md`](tests/fixtures/jbmc-defects/README.md), step 3 of `llm-dlc/loops/engine-priorities.md`). In the first two kinds a runtime exception gets past the handler that catches it on the JVM and escapes the method. `return-past-handler` is a `return` inside a try block of a value whose computation may throw what the handler catches (`return 10 / n;`, `return a[i];`, `return o.f;`): javac ends the handler's range before the return instruction, and JBMC 6.11.0 computes the value at the return, after the range has ended. `stubbed-handler` is a handler of a JDK class JBMC has no class file of (`catch (RuntimeException e)`), where the program may raise an exception whose class extends it on the JVM: JBMC's stub of a class has no superclass, so the exception escapes. `unmasked-shift` is a right shift (`>>`, `>>>`) by a distance not known to be within the type's width: the JVM shifts by the distance's low five bits (six for a `long`), and JBMC 6.11.0 by the whole distance, so `x >> 33` is `x >> 1` on the JVM but `0` or `-1` in JBMC. `extra-initializer` is a `new`, `getstatic`, `putstatic` or `invokestatic` at which JBMC's goto program runs the `<clinit>` of an application class the JVM does not initialize there (JVMS §5.5): JBMC 6.11.0 initializes the class the instruction names, where the JVM initializes the class that declares the field or method (`Sub.value`, declared by `Holder`, initializes `Holder` alone), and with a class it initializes every superinterface, where the JVM initializes only those that declare a default method. A JBMC proof that reaches a defect is no verdict under every `--gaps` mode, since no statement could assume it. A counterexample is replayed as any other, and when it does not reproduce, the message names the defect (`jbmc defect:` in the notes).

## Commands

```bash
# Behavioural, capability and API contracts of a module, as a build step (exit 1 on any drift).
jvmcontract verify --contracts src/contract --classes build/classes/java/main \
    --sources src/main/java --base . --report build/reports/contracts --module ticketing-domain
jvmcontract update --contracts src/contract --classes build/classes/java/main --module ticketing-domain \
    --add 'net.example.OrderLifecycle#decide' --add capabilities --add api --add boundaries   # add contracts, or rewrite after an intended change

# One contract, printed (add --json for tooling, --cost for the execution cost).
jvmcontract derive 'net.example.OrderLifecycle#decide' --classes build/classes/java/main
# A target is `pkg.Class#method`; an overloaded method is named with its parameter types, in Java's spelling.
jvmcontract derive 'net.example.Pricing#discount(Tier, boolean)' --classes build/classes/java/main

# A regression proof between two builds, for a method whose inputs are not finite.
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.HoldPolicy#totalCents' \
    --unchanged-unless 'seats >= 8' --report build/reports/contracts
# The same for a method over arrays (symbolic, up to --max-array-length elements): what each version returns, throws
# and leaves in the arrays is compared, and the differing input is shrunk before it is reported.
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.Utf8#encodeInto'
# Across a signature change: the previous version, renamed or moved, is named, and its arguments are expressions
# over the new parameters; the proof is of new(x) against old(f(x)).
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.Writes#winner' \
    --before-target 'net.example.LastWriterWins#winner' --before-arguments 'tsA, nodeA, tsB, nodeB'
# A result that changed its type or meaning (a boolean that became the time left) is related to the previous one by
# a boolean expression over the new parameters, `previous` and `result`, which takes the place of equality.
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.Expiry#remainingNanos' \
    --before-target 'net.example.Expiry#isExpired' --results-agree-when 'previous == (result <= 0)'
# Which new method corresponds to each old one that changed or is gone, proposed statically (names, descriptors,
# body shapes, callers) and ranked, each with what ties it; then, for each pair, the mapping of its arguments,
# records and result: the flags above, inferred. An input the contract fixes (with --contract, a JSON
# PreservationContract; otherwise a parameter both versions take by name and type) is mapped to itself and nothing
# else; only internal ones (a parameter gathered into a record, a record that gained a component) and the result
# (equal, widened, wrapped, compared on the old components, or a changed meaning put as a question) are proposed.
# An object whose class changed shape is related field by field (old.q.cents == new.q.amount.cents), from how each
# version's constructors store their parameters in fields, straight or inside a value object they make with
# new Money(cents), or through the class of a field that changed shape in turn (old.q.line.cents ==
# new.q.line.amount.cents); a field set any other way is named, never guessed. A method moved into that value object
# (Quote#cents to Money#cents) takes it in place of the old object when the old method only reads fields it keeps
# (old.this.cents == new.this.cents), and the fields it never reads are named. A result of such a class is compared
# field by field the same way (old.result.cents == new.result.amount.cents), its primitive fields only; where an
# input of the same class is related by the same equations, the regression check compares the result under them
# itself, and the correspondence has no output relation for it, which would wait for a person's approval. A method
# whose code is unchanged but which takes or returns such a class (Pricing#withQuantity(Quote, int)) is reported as
# reshaped, not unchanged, and mapped onto itself the same way.
# --hints writes them to a hints file as proposed, their evidence unchecked, keeping every hint a person stated or
# approved. Proves nothing.
jvmcontract align --before base/classes --after head/classes --hints build/alignment-hints.json
# --prove checks each complete mapping by the regression proof (equivalence with the flags it amounts to, under
# --engine, --unwind and the scope --unchanged-unless): proved mappings the contract can't tell apart (the same
# relation, or the same inputs) are one candidate, with what tells their relations apart (a new result no input
# produces: -1 for result > 0 against result != 0); one proved gets evidence "proved for claim key K", its intent still
# proposed (for a standalone method, the relation holds and whether it is the intended one is unconfirmed); several,
# with different inputs and relations, are a question, with an input that separates two of them where a proposal
# tried shows one; none lists each mapping tried with its counterexample. A vacuous proof counts as none. Runs proofs:
# queue it as a job.
jvmcontract align --before base/classes --after head/classes --prove --subject 'net.example.Expiry#remaining' --hints build/alignment-hints.json
# align ends with its questions: each decision that is a person's (several candidates and none ahead, a lone one
# matched on type alone, a result whose meaning changed, or what a proof left open), what to decide, each candidate
# with what approving it would mean and its evidence (a counterexample where a proof refuted it), and the line that
# approves it. Approving sets the intent state only; the evidence comes from a proof under the current claim key:
# each run with --hints gives a decision a person made the evidence of its proof in that run, keeps proved or
# refuted evidence whose claim key the current builds and settings still give, and marks the rest stale. A decision
# that isn't proved is listed with its evidence, not asked again. A hints file whose decisions are all approved and
# proved asks nothing and lists nothing.
jvmcontract approve --hints build/alignment-hints.json --kind correspondence --subject 'shop.Pricing#total' --rank 1

# A property of one method, proved over every input, or refuted with a witness.
jvmcontract prove 'net.example.Backoff#delayMillis' --classes build/classes/java/main \
    --assume 'attempt >= 0 && baseMillis > 0 && capMillis >= baseMillis' \
    --assert 'result >= baseMillis && result <= capMillis && (attempt == 0 || result >= delayMillis(attempt - 1, baseMillis, capMillis))'
jvmcontract prove --properties src/contract/properties.contract --classes build/classes/java/main   # every property of a module, as a build step
jvmcontract prove 'net.example.LookupSwitch#find' --classes build/classes/java/main --max-array-length 8 \
    --assume '(\forall int i; 0 < i && i < matches.length; matches[i - 1] < matches[i])' \
    --assert '(result == -1 && (\forall int i; 0 <= i && i < matches.length; matches[i] != key)) || (result >= 0 && result < matches.length && matches[result] == key)'
jvmcontract prove 'net.example.StackMapTable#offsetOf' --classes build/classes/java/main \
    --assume '0 <= k && k < offsetDelta.length' \
    --assert 'result == k + (\sum int i; 0 <= i && i <= k; offsetDelta[i]) && (k == 0 || result > offsetOf(offsetDelta, k - 1))'   # a refuting input is shrunk before it is shown
jvmcontract prove 'net.example.Arithmetic#idiv' --classes build/classes/java/main \
    --throws 'ArithmeticException when divisor == 0' --assert 'divisor != -1 || result == -dividend'   # the exceptional path, proved with the normal one
jvmcontract prove 'net.example.Backoff#delayMillis' --classes build/classes/java/main --engine auto \
    --assert 'result >= 0'   # the tool's own checker where the method is over integers, JBMC elsewhere (--engine native: the tool's own only)
jvmcontract prove 'net.example.Pool#size' --classes build/classes/java/main --engine native \
    --assert 'result > 0' --gaps assume   # a JDK call the own checker does not implement (a gap) is assumed and named in the verdict, not refused

# A capability contract of each dependency, from the jars.
jvmcontract capabilities --each build/libs/*.jar

# The boundary contract of a Spring Boot module: routes, listeners, schedules, bean definitions, the advice on each
# bean, the `!` lines where an annotation does not do what it says (a @Transactional method called on `this`, advice
# on a private or final method, a checked exception that commits, an @Async result lost), the configuration keys
# (what the classes read, what application.yaml sets, what the dependencies' metadata declares, with `!` lines for a
# key nothing binds, a deprecated key and a value of the wrong type), the wire types (the JSON shape of each
# request, response and message, as Jackson encodes it), the stored types (the shape of each MongoDB document,
# with a `!` line for a query, update, index or sort string that names a field the document does not have) and,
# under each entry point, what it reaches: `reads`, `writes`, `sends`, `calls`, `publishes` (a GET that writes is a `!` line).
jvmcontract boundaries build/classes/java/main --classpath "$(./gradlew -q :ticketing-service:printRuntimeClasspath)" \
    --resources src/main/resources --module ticketing-service

# The observation spec of each entry point: its external inputs and how each is bound, what a consumer observes (the
# result, the exception, a route's status per outcome, each effect with the payload paths it snapshots), the
# environment model of its effects, and what the analysis can't see (add --json for the shared IR's EntryPointSpecs).
jvmcontract observations build/classes/java/main --classpath "$(./gradlew -q :ticketing-service:printRuntimeClasspath)" --base ..

# Two builds' specs compared into obligations: save the old build's with --json, then compare the new build against
# it. Each old observation is preserved (to prove), changed, removed or unresolved, with what each would need.
jvmcontract observations build/classes/java/main --classpath "$CP" --base .. --json > before.json   # on the old build
jvmcontract observations build/classes/java/main --classpath "$CP" --base .. --against before.json  # on the new one

# The obligations discharged: each entry point of the old build checked against its counterpart in the new one by
# the effect trace (below), under the claim its own spec makes: the result, the exception, the status and each
# effect's attempts in exact order. Exits 0 only when every entry point checked is verified; one the narrow case
# can't model is reported as unsupported. Add --entry 'POST /quotes' for one, --trace-bound N, --cache DIR, --json, --report DIR.
jvmcontract effects old/classes new/classes

# Two builds of an application compared with nothing written by hand (below): each entry point as effects checks it,
# and each changed kernel method under the correspondence align proposes for it, with the proof cache when given one;
# then the obligations, what was reused, and every decision a person made or is asked to make. Add --json, and
# --report DIR (with --sources and --base) for compare.sarif: a finding per refuted entry point and kernel pair;
# --environment FILE for the modelled calls, --domains FILE for a kernel subject's domain (a construction plan, say).
jvmcontract compare old/classes new/classes --cache build/proof-cache

# The protocol model: a TLA+ operator from a contract, then TLC.
jvmcontract tla src/contract/OrderLifecycle.decide.contract spec/OrderLifecycleContract.tla
jvmcontract tlc spec/BoxOffice.tla --json
jvmcontract tlc spec/ClassInit.tla --deadlock    # also report a reachable state in which no action is enabled
jvmcontract tlc spec/TwoPhaseCommit.tla          # the configuration's PROPERTIES (liveness, refinement) are checked after the invariants
jvmcontract tlc spec/RaftElection.tla            # an action property [][A]_v among them is reported by name, with the run up to the offending step
jvmcontract tlc spec/RaftElection.tla --config spec/RaftElectionInductive.cfg   # another configuration of the same model: here INIT is an invariant, and a counterexample is one step from a state it admits
jvmcontract tlc spec/RaftElection.tla --coverage   # and what the verdict rests on: the rows of each generated operator a step of the model takes, and the rows none does

# Views: the state machine a contract describes, a class file's structure, and the models of the JDK the proofs use.
jvmcontract statemachine src/contract/OrderLifecycle.decide.contract --format mermaid
jvmcontract inspect build/classes/java/main/net/example/OrderLifecycle.class --code
jvmcontract models                               # what is modelled and why; --write DIR writes the class files out

# The gaps of the tool's own checker a method reaches: what it approximates rather than implements, found from the
# bytecode alone (a JDK constructor or instance method, a class initializer, a string conversion), each with a
# stable id; add --json for tooling.
jvmcontract gaps --classes build/classes/java/main --target 'net.example.Pricing#total'
# The own checker's solver calls, recorded (any command; one file per check) and run again on the bundled CaDiCaL.
JVMCONTRACT_TRANSCRIPTS=build/transcripts jvmcontract equivalence --engine native ...
jvmcontract transcript build/transcripts/4711-1.icnf    # --json for every call; exit 1 if an answer differs
jvmcontract transcript --solver bitwuzla build/transcripts/4711-1.icnf    # the same calls on Bitwuzla
```

The contract file formats are those of the Java tool, so existing contracts verify unchanged, and `verify`/`update` take the same options as the Java tool's `Main`, so the [`boxoffice.contracts`](../examples/apps/boxoffice/build-logic/src/main/kotlin/boxoffice.contracts.gradle.kts) Gradle plugin can run either. A Gradle task for the Rust tool is an `Exec`:

```kotlin
tasks.register<Exec>("verifyContracts") {
    group = "verification"
    dependsOn("classes")
    commandLine("jvmcontract", "verify", "--contracts", "src/contract", "--module", project.name,
        "--classes", sourceSets.main.get().output.classesDirs.asPath,
        "--sources", "src/main/java", "--base", rootDir.path, "--report", layout.buildDirectory.dir("reports/contracts").get().asFile.path)
}
tasks.named("check") { dependsOn("verifyContracts") }
```

## How a behavioural contract is proved

The contract of [`OrderLifecycle#decide`](../examples/apps/boxoffice/ticketing-domain/src/main/java/net/terminalvalue/boxoffice/ticketing/domain/OrderLifecycle.java) is [36 lines](../examples/apps/boxoffice/ticketing-domain/src/contract/OrderLifecycle.decide.contract): every (status, input) pair and what the method does with it.
The tool derives it in three steps, each of which can refuse, and a refusal fails the build:

1. **Purity, from bytecode** ([`purity`](src/purity.rs)). It walks every application method the target can reach, following virtual calls through sealed hierarchies and rejecting calls whose implementations it cannot enumerate. It rejects writes to static fields, reads of mutable static fields, writes to fields outside constructors, native methods, and any JDK call outside the short list in [`trusted.rs`](src/trusted.rs). That list is the trusted base, and each run prints the entries it relied on.
2. **A finite domain, from types** ([`domain`](src/domain.rs)). Enums, booleans, records of finite types and sealed interfaces have finitely many values. Each reference parameter also takes `null`.
3. **Execution of every input** ([`interp`](src/interp/mod.rs)). A pure method with finitely many inputs is fully described by its outcomes on all of them. The interpreter executes the application's bytecode as written and models the JDK natively; it has no clock, no randomness and no I/O, so every execution is deterministic by construction.

The interpreter carries a **dynamic effect monitor**. Every heap object remembers the epoch it was allocated in, and a write to an object from an earlier epoch (an argument, an enum constant, a static array) stops execution and makes the verdict *unverifiable*. Because the domain is executed completely, this check is a complete proof that the method changes nothing that existed before the call, which closes the gaps a static analysis leaves: the Java tool documented that stores into arrays and collections passed in were not tracked; here they are caught. The static analysis remains the first step, because it refuses early with a precise message, and because its trusted list is what a reviewer audits.

Anything the interpreter does not model stops execution with an *unverifiable* verdict rather than a guess. The model covers what pure domain code uses: strings and `StringBuilder`, boxed primitives, `Math`, `Objects`, `Optional`, immutable and mutable collections, enums, records (including the generated `equals`, `hashCode` and `toString`), exceptions with the messages the JDK gives them, string concatenation, pattern-matching `switch` over sealed types and enums, lambdas and method references. Locale-dependent methods (`String.format`, `toUpperCase(Locale)`), regular expressions, streams and reflection are outside it.

On the Box Office domain module, deriving the 36-case contract takes about 15 milliseconds, JDK image included (only its index is read; classes are fetched on demand). The Java tool needed a Gradle build and a JVM start.

## How a regression proof works

[`HoldPolicy#totalCents(long, int)`](../examples/apps/boxoffice/ticketing-domain/src/main/java/net/terminalvalue/boxoffice/ticketing/domain/HoldPolicy.java) has 2^96 inputs. The statement proved is "the new bytecode behaves as the old bytecode on every input, except the inputs the developer declared as changed":

1. The old classes are copied into a `before` package by rewriting their constant pools ([`relocate`](src/relocate.rs)), so both versions load side by side.
2. A harness class is **generated directly as bytecode** ([`harness`](src/harness/mod.rs)): it calls both versions on the same arguments, catches what each throws, and asserts that the results and exception types agree. The exception types it tells apart are a fixed list of unchecked ones (`harness::EXCEPTIONS`, `RuntimeException` and `Error` last), then the checked exceptions either version declares in its `throws` clause, most specific first, then `Exception`: so a checked exception thrown on other inputs, of another class, or by one version alone is a difference, and one that both throw alike is the same outcome (VF-015, where a checked exception left the harness uncaught and no such method could be verified). A method without a `throws` clause gets the harness it had. An array parameter is copied first, exactly as long, so that the version before writes into the copy and the version after into the array, and the two are compared element by element after the calls, as an array result is; two `NaN` results count as agreeing. The `--unchanged-unless` expression is parsed and type-checked with Java's rules ([`harness::expr`](src/harness/expr.rs)) and compiled into the harness, so no Java compiler is needed; JML's quantifiers may range over an array parameter in it. A statement that skips inputs before the calls (a scope, a record whose constructor may reject an input, previous-version arguments that may throw) may skip every input in the domain, and a scope every input satisfies, or one over an array's length that the bound on the arrays never reaches (`matches.length <= 8` at the default bound of eight), is proved vacuously: the verdict is still *verified*, since the statement is true, and a line `vacuously: no input in the domain reaches the calls, ...` says it covers nothing. The tool finds this by proving a probe, the same harness with the two calls replaced by the assertion's failure, with its own checker (an input that reaches the calls violates the probe), whichever engine proved the statement; `prove --assume` is probed the same way ([examples 144 and 145](../examples/README.md#tag-vacuous-proof)). The probe's answer is a status in the statement (`stated.vacuity`): `non-vacuous`, with the probe's witness under a line `not vacuous: f(...) reaches the calls`; `vacuous`; or `unknown`, with a line `vacuity unknown: ...` naming why the probe gave no verdict (a gap the own checker refuses in a record's constructor, a timeout). A statement that skips no input before the calls is `non-vacuous` by the harness, and identical bytecode by being identical. Only a *verified* statement has a status, and a vacuous or unknown one still exits 0. A statement over a record built through its constructor says, in a line `constructors: ...` and among its assumptions, that it is about the records both versions' constructors accept: whether the constructors accept the same inputs is another obligation, which this proof does not discharge. The previous version need not have the target's name or parameters: a method renamed or moved is named with `--before-target`, and one whose parameters were reordered, added, removed or retyped is called with the arguments `--before-arguments` gives, expressions over the new parameters (`tsA, nodeA, tsB, nodeB` for a reordering, `start, (int) (end - start), failed` for a size that became an end offset, an array passed by name), compiled into the harness in the same way; the statement proved is then "new(x) agrees with old(f(x))" for the stated relation, and the report shows a counterexample as both versions received it ([example 121](../examples/121-tie-break-parameters-grouped-by-kind-proved-under-the-reordering/README.md)). An input for which an argument expression throws (a division by zero) is outside the relation and skipped, as an input in the scope is. A result that changed its type or meaning is related to the previous one by `--results-agree-when`, a boolean expression over the new parameters, `previous` (the previous version's result) and `result` (the new one's), which takes the place of equality whenever both versions return (`previous == (result <= 0)` for a boolean that became the time left, `result == previous * 1000L` for seconds that became milliseconds); the versions must still throw alike, and a relation that throws on a pair of results does not hold ([examples 122 and 123](../examples/README.md#tag-signature-change)). Without it, differing return types are refused. The same statement is written out as Java source for readers.
3. The two versions' bytecode is compared before any solver runs ([`shared`](src/shared.rs)). A target identical in both, together with everything it reaches (constant pool references resolved, so renumbering does not count, and a dynamic constant through its bootstrap entry, where an enum case of a pattern switch lives), is verified with nothing to prove. A callee both versions call unchanged, that is a pure function of its primitive arguments (no fields, no arrays, nothing of the JDK beyond its arithmetic and the building of an exception), is taken as *one function in both versions*, as relational verification does with an uninterpreted function: a generated stub class keeps a memo table per such callee, giving arguments seen before the outcome they got and new arguments an arbitrary one, a result or an exception of a type the callee can throw, and the call sites of both versions are redirected to it. The solver then relates how the two versions use the callee and never its arithmetic, which is what makes a refactor around a 64-bit division cost a second instead of a time-out. The abstraction is sound for a proof, since the stub behaves as every function the callee could be; a counterexample found with it is replayed through the bytecode as written and, when it does not reproduce, the proof is run again with the callees whose stubs it rests on as written, the others still one function. Which those are is read off the counterexample (`shared::spurious`): the stubs' memo tables, as JBMC's trace leaves them, say what each stub answered on which arguments, and the two versions are replayed on its input with a stub class that gives those answers again, once as found (which must show the disagreement) and once per callee with that one computed as written instead. A callee whose real answers make the versions agree is one the counterexample rests on. When the replay as found doesn't reproduce, or no one callee's answers undo the disagreement, every callee is computed as written, as before. Whatever the choice, the next run is sound for a proof, and its counterexample is replayed in turn, so the choice decides how much is computed again, never a verdict. The own checker never takes these stubs (a changed helper proved equivalent is shared there by substitution, which needs no refinement), so this is JBMC's, under `--engine jbmc` and `auto`. A callee of a few instructions without a loop, a multiplication, a division or a remainder (`Math.min`, `Math.abs`) is computed as written in both versions rather than shared: as one function its result on different arguments in the two versions is unconstrained, so a counterexample through it rarely reproduces and the rerun costs more than the comparison it stands for. `--no-shared-callees` skips both.
4. JBMC turns the harness into a satisfiability problem over bit-vectors ([`jbmc`](src/jbmc.rs)). By default it is asked once, over the whole domain, and a counterexample is made readable by shrinking it in the interpreter ([`shrink`](src/shrink.rs)). Under `--jbmc-staging staged`, small inputs are searched first (`[0:20]`, then `[-100000:100000]`); the last stage is the proof over the whole domain. A stage runs only where its interval leaves out a value of some primitive input of the harness: JBMC's `--java-assume-inputs-interval` does not bound the elements of an array, so a harness over arrays alone runs once, and one over bytes skips the second stage ([`deadline`](src/deadline.rs)). The whole check, the own checker and JBMC's stages and fallback and the vacuity probe, has one deadline, `--timeout`: a preliminary stage gets at most an eighth of it and hands on to the next when that runs out, the own checker under `--engine auto` gets all but the quarter kept for JBMC, and the last stage what is left. Which stages JBMC runs is its staging policy, `--jbmc-staging`: `full-range`, the default, runs only the last stage, its counterexample shrunk in the interpreter instead; `staged` is the search just described; and `tight` runs `[0:20]` on at most a fortieth of the check, then the last stage. `full-range` is the default on the evidence of benchmark job `20261106-201041`: the same proofs as `staged` in less time, half of it on the hardest, its counterexamples in a third, no shrunk witness larger ([`benchmark/README.md`](benchmark/README.md#jbmcs-staging-policies-step-2b)). Each keeps the bounds, the models and the deadline, and only the last stage proves. The own checker's stages don't follow it. `--confirm` is a second check with a deadline of its own. The real bytecode of `java.lang.Math`, `StrictMath` and the integer wrappers (`Integer`, `Long`, `Short`, `Byte`), taken from the JDK image, is on JBMC's class path, so `Math.multiplyExact` and `Integer.numberOfLeadingZeros` are analysed as written.
5. A method of a record whose components are primitive, or one that takes or returns such a record, is proved on the components ([`harness::Layout`](src/harness/mod.rs)): they are the harness's symbolic parameters, named `this.component` for the receiver's and `other.component` for a parameter's (a scope may write the receiver's as the method does, `baseMillis`), the record is built from them in each version through its canonical constructor, an input a constructor of either version rejects is outside the statement (the record's invariant is where the proof is), and a record result is compared component by component, read from the fields. The witness is written as Java prints a record, `delayMillis(this=Backoff[baseMillis=1, capMillis=1], attempt=-1)`. A target identical in both versions needs no proof only when the records' constructors are too, since the harness builds the receiver through them. A static method that became a method of a record, or took one as a parameter (the components it took gathered into a record), is related to its previous version with `--before-arguments` over the components, `this.start, this.size, failedIndex`: the record is built in the new version only, the previous version gets the components, and the proof is of `new Batch(s, n).offsetToCommit(i)` against `offsetToCommit(s, n, i)` on every input the record's constructor accepts. A record the previous version takes that the new version has no record of the same components for is built from the new parameters by a constructor call among the expressions, the receiver's first: a record that gained, lost or retyped a component is related with `--before-arguments 'new Backoff(this.baseMillis, this.capMillis), attempt'`, a record's method made static with `'new Window(lo, hi), x'`, and a record parameter of other components with `'new Batch(batch.start, batch.size), failedIndex'`. The previous record is built under `before/` inside the same handler, so an input its constructor rejects is skipped as well; the report reads `behaves as the previous delayMillis(attempt) on new Backoff(this.baseMillis, this.capMillis)`, and a witness shows both versions as they received the input, `delayMillis(this=Backoff[baseMillis=1, capMillis=2, multiplier=2], attempt=-1), previously delayMillis(this=Backoff[baseMillis=1, capMillis=2], attempt=-1)`. The refusals for a record of other components or a receiver the new version lacks print the constructor call to give.
   A parameter of an application class is made the same way, by its constructor (the main brief's [decision 2](../llm-dlc/loops/foundations.md#decisions)): the class has one constructor a caller can use, whose arguments are primitives or objects made by their constructors in turn (`Line(Money price, int quantity)` of a `Money(long cents)`), and the harness's symbolic parameters are the primitive leaves of that construction, named by their path (`l.price.cents`, `l.quantity`). The domain says that is all it covers: `l: a Line made by its constructor, Line(price: Money(cents: long), quantity: int), from any arguments it accepts`, so a difference only in a state the constructor never makes (a quantity it rejects) is outside the claim, and the proof says nothing of a `Line` after other calls have changed it. The verdict says so too: `behaves as before on every input of constructor-made objects`, never `on every input` alone (examples tagged `object-inputs`; 152 is a bug only in a state calls reach and the constructor doesn't, verified within that claim). Such an object may be changed by the method, so both versions get their own object from the same arguments and are compared on its fields as they leave it: every instance field, primitive or an array of primitives, followed into the objects of application classes the fields refer to, two null references agreeing (`stated.observations.objects` lists them by path, `l: price.cents, quantity`). A witness is the construction, `bump(l=new Line(new Money(0), 1))`, and the replay says what each version left, `void, leaving l=Line{price=Money{cents=0}, quantity=3}`. A class that extends another, has several constructors, takes an array or another type in its constructor, or has a field of another type (a `String`) is refused with the field or argument named; so are objects that contain their own class, and an object made differently in the two versions unless a correspondence relates the two (below). A result of an application class other than a record of primitive components is compared the same way, field by field, two nulls agreeing (`the result, a Line compared field by field (price.cents, quantity)`), where it was compared by `Objects.equals` before; a result class with a field outside those kinds is refused naming it, and one whose fields changed between the versions too, unless a correspondence relates its classes. Identity is observed within each version, never across: the references are the result, each array parameter, each object parameter and every object or array field those reach, and every two of them both versions have under the same path and of the same type are compared as "holds before iff it holds now" (`stated.observations.identities`: `result == l`, `result.price == l.price`), a field of null reading as null and a version that throws having a null result. References of different types are left out, since a class an input is made of extends `Object` directly and so can never be the other's object; a record of primitive components, as a parameter or result, is a value and is compared by its components only. So an alias turned into a copy with the same values, which a caller sees by changing one, is refuted, and the replay says which relations hold in each version: `before: Line{price=Money{cents=0}, quantity=0}, …, with result == l and result.price == l.price`, `after: …, with result.price == l.price`; an array parameter handed back in place of a copy likewise (`filled(a=[])`, `before: [], with result == a`). Each object parameter is an object of its own and never null unless the check says otherwise: `--nullable l` lets `l` be null, and `--may-alias from,to` lets two parameters of one class (the receiver as `this`) be one object, any two of a chain of pairs too (also a claim's `ObjectDomain` `nullable` and `may_alias` through `spec::heap::check`, parameters only). The harness makes the choice with a boolean input of its own after the leaves (`l.null`, `to.same.from`), in both versions alike, null first, and a choice of a parameter that is null itself is passed over, so that one that may not be null never is. The domain says so (`…, from any arguments it accepts, or null`; `; from and to may be the same object`), and so do `stated.domain`'s `null` and `may_alias`. A witness keeps the choice: `move(from=new Line(new Money(0), 1), to=the same object as from)` is one object in the interpreter, the shrinker (which never changes a choice) and on the JVM, and `--json`'s call gives such an argument as `{"same": "from"}` or null. So a bug only when two parameters are one object, or only on null, is outside the default claim and refuted inside the wider one. A record of primitive components, an array parameter (a property check's `--nullable`, below) and a parameter the previous version is given by `--before-arguments` are refused by name. An object of a different shape in each version (`Quote(long cents, int quantity)` before, `Quote(Money amount, int quantity)` now) is related by a correspondence's input equations between their fields, `old.q.cents == new.q.amount.cents` and `old.q.quantity == new.q.quantity` (step H5 of [`foundations-heap.md`](../llm-dlc/loops/foundations-heap.md); `equivalence::Options::correspondence`, which `spec::heap::check` fills from a claim, and `--correspondence FILE` gives as JSON in the IR's form, `{"inputs": [{"old": "old.q.cents", "new": "new.q.amount.cents"}, …], "outputs": […]}`). The previous version's object is made from the new one's leaves as the equations name them, `new before.shop.Quote(q_amount_cents, q_quantity)` beside `new shop.Quote(new shop.Money(q_amount_cents), q_quantity)`; an input on which the two objects as made do not satisfy the equations is skipped, which the domain and the constructible assumption say, and which the vacuity probe counts. After the calls, the parameter's objects are compared under the equations instead of field by field, and so is a result of the same pair of classes (`the result, a Quote compared under the correspondence (old.result.cents == new.result.amount.cents, …)`), a path through null reading as absent and two absent agreeing; the identity relations are those both versions have, here `result == q`. So the equations must name a primitive field of each, of one type, and give every leaf of the previous version's construction; and every field of the previous version's object must be in one, or the check is refused, since an observation the old version was held to would otherwise leave the count. An equation's new side may also be an expression over the new object's primitive field paths that are leaves of its construction, of one parameter, giving the previous version's field (`int`, `long` or `boolean`): `Price(long cents)` before and `Price(long dollars, int cents)` now are related by `old.p.cents == new.p.dollars * 100 + new.p.cents`. It may read the new version's primitive parameters too, `new.n` (or only them, `old.l.count == new.n`): a `Line(long total)` that now holds its unit price, `Line(long price)`, beside a count both versions take, is related by `old.l.total == new.l.price * new.n`; and the field paths of another object parameter that are leaves of its construction, each read as the argument that object was made from, so that with the count kept by an `Order(int count)` passed beside the line it is `old.l.total == new.l.price * new.o.count` (refused where that object may be null or another parameter's, whose argument is then not its field). The harness computes the previous leaf from the new leaves and parameters before the calls, `new before.prices.Price((long) (p_dollars * 100 + p_cents))`, `new before.lines.Line((long) (l_price * n))`, `new before.orders.Line((long) (l_price * o_count))`, and compares the expression over the new object's paths and the parameters and other objects' arguments as the call got them with the previous field after the calls, absent where one of its paths goes through null; one that divides by zero skips the input as a constructor's rejection does. A result of the same pair of classes is not compared under an equation that reads a parameter, which is about the parameter in this call. Such an equation can change what an input means (`old.p.cents == new.p.dollars * 100 + new.p.cents + 1` makes a cent too much on every item agree), so it is the user's to state: `spec::heap::check` refuses one about an input the claim's preservation contract anchors, unless the input's derivation is one a person stated and has the equation among its `&&` conjuncts. A correspondence's output relation for the result takes the place of `--results-agree-when` (not both, and not with `--before-arguments`): a boolean over `old.result`, `new.result` and the new parameters (`new.n` or `n`), which becomes one over `previous` and `result`, so that a result that became a value object is related by `old.result == new.result.cents`. A result that is an object of an application class is in such a relation, or in `--results-agree-when`, by its field paths, of whatever shape in each version (`old.result.cents == new.result.amount.cents && old.result.quantity == new.result.quantity`), read through the object in the harness; two null results agree, one alone does not, and a path through a null field does not hold. The relation replaces equality of the result only: identity relations are still compared, so the alias-to-copy defect is refuted under it by `result == q`. It may read the previous version's parameters too: a primitive one, `old.by`, is the new version's in its place, and an object's primitive field path, `old.p.cents`, is read from the previous version's object as its call left it (rendered `p_before.cents`), so that a `raised(Price p, int by)` that returned whether it raised the price and now returns the amount it leaves, which callers read from the price before, is related by `new.result == old.p.cents && old.result == (old.by > 0)`. The new version's parameters stay as the call got them, so `new.p.dollars * 100 + new.p.cents` there is the amount before. An object read as a whole, a field of a primitive, and a name the previous version has no parameter of are refused by name. A replay evaluates it on each result's field paths as the call left them (`Replayed::result_paths`), and on the previous object's (`Replayed::object_paths`), and a witness on which it fails differs in `result`. An output relation for an object parameter's field as the calls leave it, `field:p.cents` (a previous version's path; `field:p` for the whole object), is a boolean over primitive field paths of that parameter's two objects, `old.p.…` and `new.p.…`, compared after the calls in place of the input equations about the path or under it, which still make the previous object and are still assumed of the two as made: a `raise` that now rounds up to whole dollars is related by `new.p.dollars * 100 + new.p.cents - old.p.cents >= 0 && new.p.dollars * 100 + new.p.cents - old.p.cents < 100`. A path through null makes it fail. The observations say which it is (`p: under the correspondence; p.cents under the output relation …`), a replay evaluates it on both objects' paths as the calls left them (`Replayed::object_paths`), and a witness on which it fails differs in `field:p.cents` (`p.cents as the calls leave it is not related by …`). A parameter of the same shape in both versions that no input equation relates takes such relations too, `field:l.quantity` beside nothing else, so that a `bump` that now adds two is related by `new.l.quantity == old.l.quantity + 1`: the two objects are made from the same leaves as without a correspondence, nothing is assumed of them as made, each relation is compared in place of equality for its path, and every other primitive path is still compared for equality (`l: price.cents; l.quantity under the output relation …`); one whose other fields include an array is refused. One for a parameter that is neither, for a path the previous version's object doesn't have, two whose paths overlap, and one that reads another parameter are refused by name. An output relation for an identity relation the check observes, `identity:result==q`, is a boolean over whether it holds in each version, written `old.result == old.q` and `new.result == new.q` (either way round, or with `!=`), compared in place of "holds before iff it holds now": a `withQuantity` that now hands back a copy on purpose is related by `old.result == old.q && new.result != new.q`, under which handing back the quote itself, always or only sometimes, is refuted. The observations say so (`result == q, under the output relation …`), a replay evaluates it on whether the relation holds in each version, and a witness on which it fails differs in `identity:result==q` (`result == q is not related by …: it holds before and holds now`). One for a relation the check doesn't observe, a second for the same one, and one that reads anything else (a field, a reference alone, references of two versions) are refused by name. An output relation for another observation (an array parameter), several for the result, an equation whose old side is not a field path, or whose new side reads the previous version's input, an object parameter as a whole, a field of another object parameter that is no leaf of its construction, or a parameter of another type than an integral one or `boolean`, and an equation about a parameter other than the one in its place are refused as not supported yet; equations about a parameter neither version has say nothing about the method and are left out with a note. The replays are compared through the equations too (`Replayed::views`), so two versions of different shapes that agree read as agreeing, while each shows its own object: `before: Quote{cents=0, quantity=1}, with result == q`, `after: Quote{amount=Money{cents=0}, quantity=1}`. A counterexample names the observations its replays differ in (`differs`: `result`, `exception`, `array:a`, `field:q`, with `field:q.cents` for each previous version's path its views read differently, or of an object compared field by field each primitive path its replays read differently, `identity:result==q`), and `stated.domain.input_objects` how many objects each version's inputs are made of, the previous version's first (`[1, 2]`).
6. A counterexample is shrunk in the interpreter, running the harness class JBMC checked on smaller inputs ([`shrink`](src/shrink.rs)), then replayed through both versions, and the two observed outcomes, with what each version left in an array it changed (`1, leaving a=[0, 0]`), are what the report shows ([`witness`](src/witness.rs)). A counterexample the interpreter cannot reproduce (both versions agree on it) is reported as *unverifiable*, not as a violation: it means JBMC had no bytecode for a method the target calls (one outside its models and the class path above, such as `Float.compare`, whose `floatToRawIntBits` is native) and treated it as returning an arbitrary value. A counterexample over objects (an object parameter made by its constructor, a result compared field by field, or versions differing in a field of an object or an identity relation) is run on a real JVM as well: the harness on the input, which makes the objects from the same leaves with the same identities as in the interpreter ([`jvm_witness`](src/jvm_witness.rs)). The JVM loads copies of the application classes the harness names with the class, its fields, its constructors and its static methods made public ([`relocate::opened`](src/relocate.rs)), since a record's fields are private and a class's often package-private, and a JVM refuses another package's `getfield` on them (`IllegalAccessError`); field resolution and those calls don't depend on access, and instance methods keep theirs, which decides overriding. The proof line then says `replayed in the interpreter and run on a JVM (JDK ...), where the harness fails on it too`, and `--json`'s counterexample has the JDK as `jvm`. A harness the JVM finds holding on the witness makes the result *unverifiable*, since the JVM is the reference; one the JVM could not run leaves the interpreter's replay, and the proof line says why.
7. `--json` prints the outcome instead of the report: the verdict, the domain, the proof line, the problem, the vacuity, the statement's path, the counterexample (its input, what each version did, the raw values, the input as found before shrinking and the interpreter runs the shrinking took, and the witness as data: `inputs`, each with its Java type and an exact value, a `long` as a decimal string and a `float` or `double` as Java's `toString` of it; `call`, the new version's class, class file, method descriptor, receiver as a record of its components and arguments, each naming the input it is `from`; `previous_call`, the previous version's, whose arguments under `--before-arguments` name the expression that computed them; and `found_inputs` before shrinking), the callees shared and the previous version's call. `search` is the checker run the verdict comes from: the engine (`jbmc` or `native`), the checker, the seconds, the unwinding and array bounds, the input range it ran over (`[0:20]`, or none for the whole range), the staging policy JBMC's stages followed when the verdict is JBMC's (`staging`: `staged`, `full-range` or `tight`), why the own checker gave no verdict before JBMC ran under `--engine auto`, and the own checker's numbers (paths, merges, solver calls, the divisions and multiplications built in full), the gap mode it ran under (`gap_mode`) and the gaps it met (`gaps`: each one's id, kind, call, sites, the approximation `--gaps assume` takes, and whether it was `refused` or `assumed`), under `--confirm` what JBMC made of the own checker's proof (`confirmation`: a `status` of `confirmed`, `disagreed`, `no-verdict` or `not-asked`, the checker, its seconds and the reason), the check's deadline (`deadline_seconds`), and every checker run of the check in order (`runs`: each one's checker, its `purpose`, `proof`, `fallback`, `shared` (once per refinement, with the callees left as stubs), `as-written` or `probe`, its input interval, its budget and seconds, and how it `ended`: `verified`, `violation`, `no-verdict`, or `out-of-time`, with the checker's own `ending`: `verified`, `counterexample`, `unwinding-failure`, `other-failure`, `timeout`, `memory-exhausted`, `killed`, `solver-failure`, `unsupported-input`, `unavailable`, `unreadable`, or the own checker's `no-verdict`; and where its seconds went, `phases`, the same for both checkers: `loading`, `lowering`, `symbolic`, `encoding`, `solving`, `trace` and `other`, with the `formula` it solved, JBMC's SSA `steps` and `conditions` and the `variables` and `clauses`, [`src/phases.rs`](src/phases.rs); the phases are exclusive, and a run whose phases add up past its seconds by more than 1% and 5 ms carries `phases_excess`, flagged rather than scaled), and the check's own steps around them (`phases`: the setup of the work directory, the harness, the gap scans and JBMC's preflights, the contracts, the replay and shrinking, the JVM witness run, and the rest). `replay` says where the witness was run again on both versions, `interpreter` (this crate's interpreter, not a JVM), and whether that reproduced the difference. `stated` is the statement the verdict is about, as data ([`src/statement.rs`](src/statement.rs)): a regression proof's ∀x ∈ D, A(x) ⇒ Obs(old, x) = Obs(new, x) (a property's likewise). The `domain` gives each parameter with its kind (`primitive`, `array`, `record` with its components, or `object`, made by its constructor, with the leaves of its construction), whether `null` is among its values and an array's longest length, whether two arrays may be one (`shared_arrays`, a property's), and the groups of parameters that may be one array or one object (`may_alias`). Each of the `assumptions` has a `kind`, its text and a `basis`: `stated` by the claim (`--unchanged-unless`, `--assume`), made by how the `harness` builds the statement (an input a record's constructor rejects, or on which `--before-arguments` throws, is skipped), the checker's `engine` semantics (the own checker takes every JDK class as initialized; JBMC stubs a JDK method it has no bytecode for), or a gap `assumed` under `--gaps assume`, with its id. Then the `observations` (what is compared of the result and of an exception, which arrays and objects are compared after the call, and the identity relations compared within each version), the `bounds` (the unwinding bound, the array bound, and whether the search was `complete`), the `models` (whether the tool's models were read, the `sha256:` digest of the bundle, and the JDK's version), the `checker` with its SAT solver and any fallback (`sat`: the `solver`, its `version`, its `source`, the Rust crate that bundles the own checker's or the JBMC executable it is linked into and whose signature gives its version, and its `configuration`, for JBMC the options every run passes), the `gap_mode`, and the `confirmation` status. Two verdicts whose proof lines read alike but whose statements differ differ here. The console report is in `output`.
8. `--details` (on `equivalence` and `prove`) writes what `--json` holds as `stated` and `search` under the verdict, for a person: the statement (its domain, each assumption with its basis, what is observed, the bounds, the models, the checker with its solver and gap mode, the confirmation and the vacuity), and where the time went (the check's total, the driver's steps, and each checker run with its purpose, stage, seconds, ending, the share of each phase and the formula's variables and clauses). [`src/details.rs`](src/details.rs) renders it; the default report is unchanged.

`--jbmc PATH` may be relative to the current directory: it is made absolute before JBMC runs in the work directory. A bare name is looked up on `PATH`.

**An ordinary receiver** (the objects stream's O1, [`construction::receiver`](src/construction.rs)). An instance method of a class that is not a record of primitive components is checked on a receiver made by its constructor, exactly as an object parameter is (`equivalence::made_of`): the class has one constructor a caller can use, its leaves are the harness's symbolic parameters under `this.` (`this.capacity`), and an input both versions' constructors reject is outside the statement, while one that only one version's reject is a difference (below, **A narrower constructor**). The domain says so (`this: a Throttle made by its constructor, Throttle(capacity: int), from any arguments it accepts`), and nothing else is claimed: not the states later calls reach. In a regression check both versions' receivers must be made the same way, of the same construction and fields; the receiver's fields are compared as the call leaves them, so a void method that changes its receiver differently is refuted on `field:this`, and `this` is a root of the identity relations, so a method that hands back its receiver, rewritten to hand back a copy, is refuted on `result == this`. A witness is replayed in the interpreter and run on a JVM, as one over an object parameter is. In a property check the method is called on its receiver (`invokevirtual`), the assumption, the assertion and the throws clauses read its fields as `this.f`, and the assertion can't call the method itself, which needs a receiver. The receiver's constructor is a root of each version's closure in the proof cache's key, so an edit of the constructor alone is another claim. A receiver outside that is refused by name: a constructor argument the stream has yet to make (a String, a dependency) says "the objects stream builds it", several constructors without a plan's choice, a superclass or a cycle are boundaries of their own, `--nullable this` is refused (a receiver is never null), and so are `--before-arguments` and a correspondence's equations about an ordinary receiver.

**A construction plan and a setup sequence** (the objects stream's O1 and O3, [`construction`](src/construction.rs)). `equivalence --plan FILE`, `prove --plan FILE` and a claim whose domain is `made_by: planned` (`spec::heap::check`, so also `compare`'s kernel under `--domains`) make the receiver and each object parameter as the plan's nodes say: each node by the constructor its descriptor names, which is how one of several constructors is chosen (never guessed), from primitive leaves named by their path from the root (`this.lo`, `q.amount.cents`) and objects made so in turn. A primitive parameter the plan leaves out is an input of its own. The domain gate compares the plan's classes with the claim's. The plan may end with a setup sequence of one or two void calls on the receiver (`take(I)V` on the leaf `setup.0.n`), the same in both versions on the same symbolic arguments: the witness is the construction, then the setup calls, then the target (`allows(this=new Throttle(2), n=1), after the setup this.take(setup.0.n=1)`), replayed in the interpreter and run on a JVM. In a regression check a setup call that throws ends that version's history, and its exception, a category of its step's own, is the outcome compared, so an input one version's setup rejects and the other's accepts is a difference, never dropped, and the receiver's fields are compared as the history left them. In a property check such a history reaches no state and is outside the property, as an input a constructor rejects is. The statement has a `setup` assumption and the bound `setupCalls`, and a planned claim's result names its label and restrictions, so a constructor-only claim says it is about the states right after construction and no setup claim passes for one. What a plan can't make yet is refused by its stream's name before any check: a null array, a choice or a shared node inside a nested object, a factory, a dependency, an adapted String, an adapted value inside a node, and a setup call that returns a value. A root may be an adapted list (below, "A list parameter of a regression check"). A regression claim with a setup sequence is cached as any other, its key rooting the setup methods (below), and the typed witness's call lists the setup calls with their arguments (`setup`). So is a planned property check under `prove --cache` (below, "The property cache").

**A plan's choices and shared nodes** (the objects stream's O2). A plan's root node may be null (`"nullable": true`), or one of the objects of other roots (`"same_as": [0]`, by their nodes' ids, of the same class), each a boolean flag of the harness as `--nullable` and `--may-alias` make it, both versions given the same choice; and one node at two roots is one object, always, with no flag (the later root is the earlier's object: `b: the same object as a` in the domain, `b=the same object as a` in the witness). Both versions' plans must make the same choices (refused by name otherwise), so that their identity relations start alike, and the JVM run of a witness rebuilds the identities it has, since it runs the harness. So a rewrite that is right only where two parameters are two objects is verified over two nodes and refuted over one, or over a choice of one. The receiver is never null. Inside a nested object a choice, or a node shared with a root or with another argument, is refused by name: the recipe makes an inner object as its constructor's argument, and the harness chooses only among the roots.

**Arrays a constructor takes** (the objects stream's O1). A constructor's argument may be a bounded array of integral or boolean elements, with a plan (`{"kind": "array", "path": "this.data", "element": "int", "max_length": 4}`) or without one (`equivalence::made_of`), so a receiver or parameter such as `Buffer(int[] data)` needs no adapter of the application's. The array is a leaf of the construction, a symbolic parameter of the harness (`this.data`), of length up to the check's array bound, not null, and no two arrays the same; the domain says so (`each array of its construction of length ≤ 4, not null, and no two the same array`), and the statement's bounds state the array bound. The previous version's object is made from its own copy, as an array parameter's call is, so the two versions' heaps are apart, and within a version the object and the caller share the array the caller passed. After the call the caller's array is compared too (`array:this.data`), so a constructor that keeps the caller's array where the previous one copied it, and a method that then writes into it, is refuted on that alone, though the receivers' fields agree. A plan's array must be bounded at the check's `--max-array-length`, and a null array or one value at two paths is refused by name. A property's expressions don't read an object's array fields yet (`this.data` is refused by name).

**A constructor's side effects** (the objects stream's O2, [`construction::side_effect`](src/construction.rs)). The checks make each object from the classes' initial state, so a constructor may change nothing outside the object it makes: one that writes a static field, itself or in an application method it reaches ([`purity`](src/purity.rs)'s walk), such as a count of the objects made or a registry, is refused by name wherever a check would make its object (a receiver, a parameter or an inner object of one, a plan's node, in either version: `counters.Counter's constructor has a side effect outside the object it makes, which is not supported: counters.Counter.<init> writes the static field counters.Counter.made`), since a verdict over it would be about the first object made only. A setup call that writes a static field is refused the same way, its effect being outside every observation of the check. A constructor's call into the JDK with an effect (`System.out`, a clock) is refused by the engine, as it is anywhere. Reading a constant, and calling a method that writes the object's own fields, are no side effects.

**A narrower constructor** (the objects stream's O2, [`Layout::compares_admission`](src/harness/mod.rs)). A new constructor that rejects an input the previous one accepted (`if (step < 2)` where it was `step < 1`) must not shrink a regression claim to the inputs both accept. So where every object is made in both versions, of the same shape (a receiver, a parameter, a plan's root, a record), the regression harness makes the new version's objects, then the previous version's, and compares their admission: an input both versions' constructors reject is outside the statement, and one that only one version's reject, narrower or wider, is a difference on the `exception`, refuted with a witness whose version that rejects it throws in its constructor (`<the constructor throws IllegalArgumentException("step below 1")>`, the message unchanged), replayed in the interpreter and run on a JVM. This replaces, for those objects, the rule above that an input a constructor of either version rejects is skipped; the statement's `constructible` assumption says which rule a check had. Under a claim whose contract doesn't require the `exception`, such a witness refutes nothing, and the result is unresolved, never verified. An object made through a correspondence's input equations, or in the new version only, keeps the old rule and its stated assumption: there an input either constructor rejects is skipped, and the statement says so. A property check is of one version, and an input its constructor rejects is outside the property, as before.

**A shrunk witness is the same failure** (the objects stream's O2, [`witness::shrink_in_harness_keeping`](src/witness.rs)). The harness alone, as the shrinker's oracle, takes any failure, so a witness of one difference could shrink into a witness of another, and be reported as the input found, shrunk: a receiver's field found to differ at `new Counter(20)` came down to `new Counter(1)`, where only the new constructor rejects the step, a difference on the `exception`. A candidate is now accepted only after it is replayed and found to be the same failure: in a regression check, the two versions' replays differ in exactly the observations the input found differs in; in a property check, the same throws clause applies and the method throws the same exception, or returns normally, as on the input found. So the witness on the page reproduces the failure found, which `found` names, and is run on a JVM as before. A shrunk recipe stays legal by construction: every candidate is the harness's own input, so it has the harness's domain (its scope and assumptions, and its constructors' admission), and it keeps a plan's choices as found, makes no array longer and no array null.

**What makes the inputs is part of the claim** (the objects stream's O2, [`harness::Layout::construction_roots`](src/harness/mod.rs)). A check's result depends on every method its harness calls to make the inputs, not only on the target. In each version these are every object's constructor, the inner objects' included and a plan's chosen descriptor among them, then the setup calls on the receiver, in order and each once. The previous version's are named as its own build names its classes. The shortcut for a target whose bytecode is identical in both versions compares these too. The proof cache's regression key roots the target and all of these, so an edit of a constructor or a setup method alone is another claim, never answered by a stored result.

**A replay that cannot run a version reproduces nothing** (the objects stream's O2, [`witness::differences`](src/witness.rs)). Where the interpreter cannot run one version on a counterexample (a JDK call it does not model, such as `String.format`, whose result depends on the default locale), that version's outcome is unknown, and differs from nothing. Before, it counted as a difference: a witness was reported refuted and `reproduced` with one version's outcome `<could not replay: ...>`, as in VF-015's step 4, and where the checker's approximation of a JDK call under `--gaps assume` (or a stub of JBMC's) took the method down a path the JVM never takes, that was a false refutation. Such a witness is now run on a JVM, as one through a contract always was, with or without contracts: it is a violation where the harness fails there, with the JVM's outcomes and their difference (each version alone, for static methods of the harness's parameters; otherwise no observation is named, and a claim that requires one stays unresolved), `replay.by` `jvm`; it is *unverifiable* where the JVM finds the versions agreeing, or the property holding, or cannot run it. A property's witness is treated alike.

## How a property proof works

A regression proof says "as before". A property proof says what the method guarantees, in the developer's words, and keeps it true. The statement is a Java boolean expression over the method's parameters, its `result`, and the method itself, committed next to the code in [`properties.contract`](../examples/apps/quorum/src/contract/properties.contract):

```
net.terminalvalue.quorum.replication.LastWriterWins#winner
  assume: tsA != tsB || nodeA != nodeB
  assert: result == 1 - winner(tsB, nodeB, tsA, nodeA)
```

1. The harness ([`harness::generate_property`](src/harness/mod.rs)) is generated as bytecode: return if the assumption is false, call the method once on symbolic arguments, catch anything it throws, and assert that it threw nothing and that the assertion holds. A call of the method inside the assertion is compiled to an `invokestatic`, which is how commutativity, idempotence, monotonicity or antisymmetry are stated; a boolean method with no assertion given is its own property (it must return `true`).
   A method that throws by design declares it, as JML's `signals` clause does: `throws: ArithmeticException when divisor == 0` (`--throws`, repeatable) says that the method throws that exception, or a subclass, exactly on the inputs where the condition holds, and that elsewhere it returns and the assertion holds. The harness computes which clause applies before the call and catches the declared class before the generic ones, so the exceptional path is proved with the normal one instead of being assumed away; a declared JDK exception JBMC has no model of (`ClassFormatError`) is taken from the JDK image with its superclasses. A void method's property can be its throws clauses alone. A refutation says what the clause required of the input: the declared exception, or a normal return.
2. JBMC proves the harness or finds an input, small values first ([`property`](src/property.rs)); the input is replayed in the interpreter and the report shows the method's result or exception on it. As for a regression proof, an input on which the replay finds the property holding is reported as *unverifiable*: a called method was missing from JBMC's class path.
3. The input JBMC found is whatever satisfied the solver, an eight-element array of nine-digit numbers as often as not. Before it is reported it is **shrunk** ([`shrink`](src/shrink.rs)): the generated harness class is run in the interpreter on smaller inputs, dropping array elements and moving numbers towards zero (by powers of two, the largest first, one scalar at a time and then every scalar of a sign together, for an end tied to a length) while the property still fails, until no single step keeps it failing. The witness on the page is that local minimum, the same on every run; the report also gives the input as JBMC found it and how many interpreter runs the shrinking took. `--no-shrink` reports JBMC's input as is.
4. `prove --properties FILE` proves every block of a module's file and exits 1 if any is violated or cannot be verified, so the properties are a build step like the contracts. Each block gets its own work directory, `property-N` in the order of the file, when there are several. `--json` prints a list of the outcomes, one per block: the verdict, the assumption, the assertion as checked, the throws clauses as given and as checked (`throws_checked`, each exception named in full), the domain, the proof line, the problem, the vacuity, the statement's path, the counterexample (its input, the method's outcome, what a throws clause required instead, the input as found before shrinking and the interpreter runs the shrinking took, and its `inputs`, `call` and `found_inputs` as for a regression proof), `search` and `replay` as for a regression proof, and the console report in `output`. A witness's `replay.reproduced` is false when the property calls the method under proof, since only the harness can evaluate it there, so the violation is the checker's word.

An array parameter of an integral or boolean element type (`int[] matches`, `char[] chars`, `byte[] out`) is a symbolic array: every length up to a bound (`--max-array-length`, 8 by default, or `arrays: N` in the property's block), every content, never `null`, and never the same array as another parameter, in both engines (JBMC under `--java-assume-inputs-non-null`). The domain line says so, `a: int[] of length ≤ 8, not null`, ending `; no two the same array` when there are two or more, since a claim the JVM refutes only on a `null` or on one array passed twice is outside it. A domain may be widened, with the tool's own checker alone (`--engine native` or `auto`; `--engine jbmc` and `--confirm` refuse it, since JBMC would prove the narrower claim, by name: `--json`'s `refused` is `widened-domain`): `--nullable a` lets `a` be null (`a: int[] of length ≤ 8, or null`), and `--may-alias a,b` lets `a` and `b` be one array (`; a and b may be the same array`), any two of a chain of pairs too. Such a parameter is a symbolic reference among null and the arrays it may be, the property says which it is with `a == null` and `a == b`, and a witness says it in turn: `twoArrays(a=[0], b=the same array as a)` passes one array twice in the interpreter, the shrinker and on a JVM, which never split it into two or join two into one. The property reads it as `matches.length` and `matches[i]`, and quantifies over it in JML's syntax, `(\forall int i; 0 <= i && i < matches.length; matches[i] != key)` and `(\exists int i; ...; ...)`, where the range must bound the variable below and above and any further conjunct filters. A quantifier is compiled to a loop in the harness, which JBMC unwinds, so the bound on the array is the bound on the proof: the search above is proved correct on every sorted table of up to eight pairs and every `int` key in a few seconds. A `result` that is an array is read the same way, and an array parameter is read *after* the call, so a method that writes into a buffer is held to what it wrote. A witness shows the arrays, shrunk, and the array a method left behind when it changed one. An array parameter is also passed by name to a call of the method under proof, `offsetOf(offsetDelta, k - 1)`, which is how a law about the previous element is stated. What the method changed is stated against what it received with JML's `\old`: `\old(out[i])` is the element before the call, from a copy the harness takes first, so `(\forall int i; result <= i && i < out.length; out[i] == \old(out[i]))` is a frame condition, the bytes past what the encoder wrote are as they were, and `(\forall int i; 0 <= i && i < keys.length; (\exists int j; 0 <= j && j < keys.length; keys[j] == \old(keys[i]) && offsets[j] == \old(offsets[i])))` says that an in-place sort is a permutation that keeps each offset with its key. The copy is as long as the bound on the arrays rather than the array's own length, which costs the solver thirty times less; `\old(a)` passed to a call gets an exact copy. A block of `properties.contract` may also set `unwind: N`, the loop unwinding bound for that property: a sort of four pairs and the pairing quantifier are both quadratic, and the proof takes fifteen seconds unwound five times where the default sixteen takes minutes.

A parameter of an application class is an object made by its constructor, as in a regression proof (step 5 there; step H2 of [`foundations-heap.md`](../llm-dlc/loops/foundations-heap.md)): the harness's symbolic inputs are the primitive leaves of its construction, the object is made from them before the assumption is checked, and an input the constructor rejects is outside the property, which a constructible assumption in the statement says. A record is made the same way, by its canonical constructor. The domain and the verdict say what that covers: `l: a Line made by its constructor, Line(price: Money(cents: long), quantity: int), from any arguments it accepts`, and `✓ objects.Kernel#bump satisfies `…` on every input of constructor-made objects`, so a property wrong only on a state the constructor never makes holds within the claim and says nothing outside it. The expressions read the object by its field paths, `l.quantity` and `l.price.cents` (a record's fields are its components), after the call in the assertion and before it under `\old`: `l.quantity == \old(l.quantity) + 1` holds a method to what it changed, the harness reading each `\old` path before the call. A `result` of an application class is read the same way, and references are compared by identity, `result == l`, `result.price == l.price`, `l == null`, so the alias-to-copy defect (a copy with the same values handed back in place of the object) fails `result == l` though every field agrees. A path through null throws `NullPointerException` as in Java, which fails the assertion and puts an input outside the assumption. `--nullable l` lets an object parameter be null and `--may-alias from,to` lets two of one class be one object, made by a boolean input of the harness's own after the leaves, as in a regression proof, so JBMC takes such a domain too; the domain says so (`…, or null`; `; from and to may be the same object`). A witness is the construction and keeps its choices: `move(from=new Line(new Money(0), 1), to=the same object as from)` is one object in the interpreter, the shrinker (which changes the leaves alone) and on a JVM. Since the property reads the heap, the interpreter checks a witness by running the harness itself on it, and the harness is run on a JVM too, the application's classes opened as for a regression witness: the proof line says `replayed in the interpreter and run on a JVM (JDK …), where the harness fails on it too`, and a harness the JVM finds holding makes the result *unverifiable*. Refused by name: a class outside a regression proof's kinds (a `String` field, several constructors), an array field in an expression, `\old` of an object, `==` between objects of two classes (never one object), and an array parameter's `--nullable` or `--may-alias` in a property that has object parameters too (not yet). A call of the method under proof, which takes objects, cannot appear in the property, and a throws clause's condition is evaluated in the harness only, so a counterexample over objects does not say which clause applied.

JML's generalized quantifiers fold a value over the range instead: `(\sum int i; 0 <= i && i <= k; offsetDelta[i])` adds (an `int` or a `long`, wrapping as Java's arithmetic does, so write `(long) a[i]` for a long sum of ints), `\num_of` counts the indices for which a boolean body holds, and `\max` and `\min` take the extreme of a numeric body, with JML's values over an empty range (0, 0, the type's smallest and its largest). They nest: `max_stack` is `(\max int k; 0 <= k && k <= delta.length; (\sum int i; 0 <= i && i < k; delta[i]))`, the largest prefix sum, and that is a property [Mica](../examples/apps/mica/README.md) proves of its assembler in about twenty seconds.

The five properties of the [Quorum](../examples/apps/quorum/README.md) module (quorum intersection, backoff bounds and monotonicity, the hybrid logical clock's monotonicity and symmetry, last-writer-wins antisymmetry) are proved in about four seconds in all, and the seven of [Crosscut](../examples/apps/crosscut/README.md) (a Kafka partitioner and batch commit, a retry policy, a JWT validator's skew, a token bucket's refill, a cache's expiry) in about forty, and the sixteen of [Mica](../examples/apps/mica/README.md) (`idiv` and `irem` at `Integer.MIN_VALUE / -1` and their `ArithmeticException` on zero, the exception table's `ClassFormatError` on a malformed entry, modified UTF-8's zero-free bytes and the encoder that writes them and leaves the rest of the buffer alone, a `lookupswitch` bisection within the sizes a `Code` attribute allows and its full correctness on every sorted table, the sort of a `lookupswitch`'s pairs as a permutation, the exception table's handler lookup, a power-of-two table size, the stack map frame offsets with their `+ 1`, the length of a `Code` attribute, constant pool numbering around a `long`, and `max_stack` as the largest prefix sum) in about a minute and a half, most of it the three sums and the sort. A property-based test states the same theorem and samples it; here the solver covers the domain, which is how [example 015](../examples/015-rounded-half-is-not-a-majority/README.md) catches `(n + 1) / 2` at `n = 2`, [example 016](../examples/016-backoff-cleanup-overflows-into-a-negative-delay/README.md) catches an overflow forty attempts in, [example 023](../examples/023-abs-partitioner-sends-one-key-to-a-negative-partition/README.md) catches `Math.abs(Integer.MIN_VALUE)`, and [example 034](../examples/034-idiv-overflow-check-throws-where-the-jvm-returns-min-value/README.md) catches an `idiv` that throws on the one input the specification says must not, and [example 054](../examples/054-exception-table-check-that-rejects-a-range-ending-at-code-length/README.md) catches a class file check that rejects a handler covering the last instruction, on the exceptional path a throws clause brings under the proof, and [example 055](../examples/055-encoder-that-zero-terminates-into-the-callers-buffer/README.md) catches an encoder that writes one byte past what it returns, against a frame condition in `\old`.

## How a boundary contract is checked

A Spring Boot service is mostly boundaries. The framework calls into it through annotations (`@GetMapping`, `@KafkaListener`, `@Scheduled`, `@EventListener`, `@Bean`), and what it promises to do around each call is an annotation too (`@Transactional`, `@PreAuthorize`, `@Valid`, `@Cacheable`, `@Async`, `@Retryable`), applied through a proxy that stands in front of the bean.
None of this is in the code's control flow, so none of it is in a unit test, and a guard that is dropped, a route that widens or a rollback rule that changes shows up in production first.

[`boundaries`](src/boundaries.rs) reads the `RUNTIME` annotations from the class files ([`classfile::annotations`](src/classfile/annotations.rs)) and writes them out as a contract: one block per bean with its stereotype, one line per entry point with its route composed from the class and method mappings (`POST /orders/{id}/cancellation (consumes application/json)`), the handler's signature with its parameter annotations and generic types, and the advice on it as indented lines.
Only the annotations of framework packages are read (Spring, Jakarta Validation and Transactions, Resilience4j, Micrometer); a class without one is not a boundary.

It then checks what the framework will do with each annotation, and records what it finds as `!` lines of the same contract:

- **self-invocation**: a method with proxied advice called on `this` from the same class, directly or from a lambda. The call never reaches the proxy, so the transaction is not started, the authorization is not checked, the cache is not consulted. The receiver is found by walking back over the argument expressions in the bytecode; a call on another instance of the class is not reported, because that instance is a proxy.
- **not proxied**: advice on a private, static or final method, or on a method of a final class, which the CGLIB proxy cannot intercept.
- **commits on a checked exception**: a `@Transactional` method that declares a checked exception its `rollbackFor` does not name. Spring rolls back on unchecked exceptions only; the declared one commits. The class hierarchy comes from the class path and the JDK image.
- **a lost `@Async` result**, a `@Cacheable` method returning `void`, a `@Scheduled` method with parameters, and **constraints that are never enforced**: `@Min`, `@NotBlank` and the like on the parameters of a method that is neither a request handler nor on a `@Validated` bean, or on a non-public method of one (method validation goes through the proxy).
- **a request body whose constraints do not run** ([`validation`](src/validation.rs)): a `@RequestBody` whose type carries constraints, taken without `@Valid` or `@Validated`; and a `@Valid`, which validates the `Default` group, or a `@Validated(G.class)`, which validates `G` and the groups it extends, on a body with constraints in other groups, named on the handler's line.
- **a parameter that cannot bind to the request** ([`binding`](src/binding.rs)): a `@PathVariable` whose name (the annotation's, else the parameter's) is a variable of no template of its route (`! @PathVariable id matches no variable in /holds/{holdId}: MissingPathVariableException, a 500 on every request`); a `@PathVariable`, `@RequestParam`, `@RequestHeader`, `@CookieValue` or `@MatrixVariable` with no name of its own on a parameter whose name the compiler did not record (no `MethodParameters` attribute, which `javac -parameters` writes; Spring 6.1 reads nothing else, so the request fails with a 500); a `required = false` binder with no `defaultValue` on a primitive, which cannot be null when the request leaves it out; two `@RequestBody` parameters; and **two handlers on one route**, found across the module: the same route on two methods, which Spring refuses at startup, and the same pattern under different variable names (`/tasks/{id}/owner` and `/tasks/{key}/owner`), which both match every such request with the same specificity, so Spring throws an ambiguity for it. None of these is a compile error, and only the duplicate route stops the context; the rest are a 500 on every request of the route, which the unit tests of the service do not make.
- **an exception nothing turns into a response** ([`failures`](src/failures.rs)): under each route, `throws` lists the exceptions it can throw (the `throw` statements, `orElseThrow` suppliers and Spring `Assert` calls in everything it reaches, less what a `catch` on the path takes without rethrowing) and what each becomes: the `@ExceptionHandler` that takes it (the controller's own first, then the `@ControllerAdvice` beans in `@Order`, the closest type within one) with the status it answers (`NotFoundException (404 by ApiErrors.notFound)`), the `@ResponseStatus` on the exception's class, the status a `ResponseStatusException` was built with, or `(500)`. An exception type of the module's own that nothing maps is a `!` line (`! throws HoldExpiredException: no @ExceptionHandler takes it and it carries no @ResponseStatus, so the response is a 500`); a JDK or framework exception that reaches the boundary is listed as a 500 without one, since a guard that fired is a 500 by design. Two `@ExceptionHandler` methods for one type in one advice are a `!` line too: Spring refuses the ambiguity at startup. A listener, a schedule or a bean method gets its `throws` line without outcomes: its container's error handler decides, and that configuration is not read.

Introducing one of these changes the contract, so the pull request shows it; fixing it changes the contract back. `verify` reports a difference as `boundaries-changed`, anchored to the first added member's source line.

After the beans comes the **activation** block ([`activation`](src/activation.rs)): what switches each kind of annotation on. `@Scheduled` runs only under `@EnableScheduling`, `@Async` under `@EnableAsync`, `@Cacheable` under `@EnableCaching`, `@PreAuthorize` under `@EnableMethodSecurity` (`@Secured` and `@RolesAllowed` need its `securedEnabled` and `jsr250Enabled`), `@Retryable` under `@EnableRetry`, an `@Aspect` under `@EnableAspectJAutoProxy`; `@Transactional`, `@KafkaListener`, `@RabbitListener`, `@JmsListener` and method validation are switched on by Spring Boot's auto-configuration when its conditions hold, `@Timed`, `@Counted` and `@Observed` by the aspect beans the AspectJ weaver makes possible, and `@Valid` by a Bean Validation provider on the class path. Without the switch nobody reads the annotation: the code compiles, the context starts, and every test that does not depend on the advice passes. The block's header names the application class and the packages it scans; each family the module uses is a line naming what enables it and how that configuration is reached (`@Scheduled: @EnableScheduling on net.terminalvalue.boxoffice.messaging.MessagingConfiguration, imported by TicketingApplication`, `@KafkaListener: @EnableKafka on KafkaAnnotationDrivenConfiguration.EnableKafkaConfiguration, auto-configured`, `@Valid: Bean Validation provider org.hibernate.validator.HibernateValidator in hibernate-validator-9.1.3.Final.jar`), and a family nothing enables is a `!` line with the nearest miss when there is one: a class that carries the switch but is not a component, a configuration outside the scanned packages, or an auto-configuration whose condition fails (`! no TimedAspect bean on a configuration in scope (MetricsAspectsAutoConfiguration defines one, but org.aspectj.weaver.Advice is not on the class path): no timer is recorded`). The configurations in scope are the local components in the scanned packages (the application class's own and its `scanBasePackages`), the classes of the class path in those packages, the `@Import`s of each, their nested configuration classes, and the auto-configurations the class path's `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` files and `spring.factories` list minus the application's `exclude`s, with `@ConditionalOnClass`, `@ConditionalOnMissingClass`, `@ConditionalOnResource` and `@ConditionalOnWebApplication` evaluated against the class path. Meta-annotations are followed, so `@Service` is a `@Component` and a composed annotation of the application's own that carries `@EnableAsync` counts.

After it comes the **configuration** block ([`config`](src/config.rs)): the module's keys, cross-checked three ways. The classes say what they read: `${key}` and `${key:default}` placeholders in any annotation (`@Value`, `@Scheduled`, `@KafkaListener`), the fields of a `@ConfigurationProperties` type under its prefix (nested types followed, a list field as `key[]`, a map field as `key.*`, a record's `@DefaultValue`s), `@ConditionalOnProperty`, and `environment.getProperty("key")` with a constant, in the module and its sibling modules. The application files under `--resources` (`application.yaml`, `application-prod.properties`, the same under `config/`, with `---` profile documents) say what is set. The configuration metadata on the class path (`META-INF/spring-configuration-metadata.json`, which every Spring Boot starter and every module built with the configuration processor carries) says what the framework binds, with types and deprecations. Names are compared in Boot's relaxed canonical form, so `maxSeats`, `max_seats` and `max-seats` are one key. Each key is a line with its type and the value each file gives it (`boxoffice.hold.max-seats: int = 8, 12 (prod)`, or `, default 8` when no file sets it), and under it who reads it (`@Value in TicketingApplication.holdPolicy(int, Duration), maxSeats, default 8`, `declared by KafkaProperties$Producer`). The `!` lines: a key set in a file that no class reads and no metadata declares (the typo, with the nearest known key named), a key the metadata marks deprecated (with its replacement, and whether Boot still binds it), a value that is not of the key's type (`int`, `Duration`, `DataSize`, `boolean`, an enum's constants, with Boot's relaxed matching), and a placeholder default that is not. A renamed key in the code, a mistyped key in the file, or a Boot upgrade that retires a key passes every test, since tests do not run with the production profile and a missing key quietly takes its default; here each is a changed line.

Then come the **wire types** ([`wire`](src/wire.rs)): the JSON shape of every type that crosses the boundary, which is what the other side of each route and topic depends on. The roots are the `@RequestBody` parameters and results of the handlers, the payloads of the message listeners, and every class with a Jackson annotation; the closure follows property types into the module and its sibling modules (the class path entries under `--base`), and stops at library types. Each type is a block: `record`, `class`, `enum` or `interface`, with its properties as Jackson finds them (record components; public fields, public getters, setters and `@JsonProperty` members, superclasses included) under their wire names (`@JsonProperty`, `@JsonNaming`), with the Bean Validation constraints before the type and inside it (`List<@NotBlank String>`, from the class file's type annotations) and a `?` on a property that may be null or absent (`Optional`, `@JsonInclude`), enum constants with their `@JsonProperty` names or the `@JsonValue` method, and for a polymorphic type the `@JsonTypeInfo` placement and each subtype's id (`subtype "PaymentCaptured" = PaymentEvent$PaymentCaptured`, and `type = "PaymentCaptured"` in the subtype's own block). A renamed component, a dropped `@JsonSubTypes` entry or a new enum constant changes no signature and passes every test that encodes and decodes with the same classes; here it is a changed line. The constraints are checked as Hibernate Validator will run them: a property whose type carries constraints that no `@Valid` on the property or inside its type leads into (`billing: @NotNull Billing` then `! constraints on Billing are not checked: no @Valid on billing`), a constraint on a type it has no validator for (`@Size` on an `int`, accepted by the compiler and thrown as `UnexpectedTypeException` at the first validation), and a null check on a primitive are `!` lines under the property.
The wire checks, as `!` lines of the type's block, were established against Jackson 3 as Spring Boot configures it: a permitted subtype of a sealed base that `@JsonSubTypes` does not list (it is written under its class name and rejected when read back), a subtype whose type id defaults to its class name, `@JsonTypeInfo(use = CLASS)` (Java class names on the wire), an interface or abstract class without `@JsonTypeInfo` (written as the runtime class's properties, with no id to read it back by), a class with no visible properties (written as `{}`), two properties with the same wire name, and a persistence type (`@Document`, `@Entity`, `@Table`) on the wire.
The contract ends with the **stored types** ([`store`](src/store.rs)): the shape of every Spring Data MongoDB document the module keeps, as the mapping layer writes it. Each `@Document` class is a block (`record, collection "seats"`) with its properties under their stored names (`_id: String (id)` for the `@Id` or the property named `id`, `due: Instant (dueAt)` for a `@Field` rename, a `@Transient` or `transient` field left out, `@Indexed`, `@Version` and the other Spring Data annotations before the type), and each local type a property embeds is a block of its own (`record, embedded`). Under the document go the `!` lines for the strings in the module's code that name a field it does not have: a `Criteria.where("x")` or `.and("x")`, an `Update.set("x", ...)`, `.unset("x")`, `.inc("x", ...)` and the other operators, an `Index().on("x", ASC)`, a `Sort.by("x")` or `Sort.Order.asc("x")`, a projection's `include("x")`, a repository method's `@Query("{ 'x': ?0 }")` with its `sort` and `fields`, and a `@CompoundIndex(def = "{'x': 1}")`. A string may name a property by its Java name or its stored name, as the query mapper accepts both; a dotted path goes through an embedded type's fields, through a collection or array to its element, through a map to any key, and stops at a leaf (`"assignee.email" is a String, which has no fields`); `$`-segments and array indices are skipped. The document a string is about is the one the method names (the `SeatDocument.class` it passes to the template, or the document it instantiates); a helper that names none takes the documents of its callers, and a string with no document in reach is checked against every document of the module. Nothing checks these strings otherwise: the driver sends them to the database, which matches, writes, indexes or sorts by whatever field that is, so a renamed record component leaves every query of it matching nothing (`! TicketingStore.holdByIdempotencyKey(String, String) queries "idempotencyKey": not a field of HoldDocument, so the condition tests a field that is never set`), every update of it writing a field nothing reads back, and every test that goes through the same strings passing; the nearest property is suggested when there is one (`(createdAt?)`).

Under each entry point and advised method go the **reach lines** ([`reach`](src/reach.rs)): what the method reaches, found by following the calls in the bytecode from it through the application's own classes (the module and its sibling modules on the class path) to the framework APIs that do the work. `reads` and `writes` list the documents, entities or tables (the Spring Data templates and repositories, the JPA `EntityManager`, `JdbcTemplate` and `JdbcClient`; what a call is of comes from the class literal it passes, else the static type of its entity argument, else the documents the method mentions, and a table from the SQL constant), `sends` the topics, exchanges or queues (the Kafka, RabbitMQ, JMS, Spring Cloud Stream and AWS templates; the constant string passed, else `to Kafka`), `calls` the HTTP requests (`RestTemplate`, the fluent `RestClient` and `WebClient`, an `@HttpExchange` or Feign interface, as `GET /users/{id}`) and `publishes` the application events. The walk is a may-reach approximation: a virtual call goes to every local subtype that overrides the method, a lambda to its body whether or not the receiver runs it, a call on `this` the same as any other; a call into Spring, the JDK or a driver is a leaf. So `POST /orders` reads `HoldDocument, OrderDocument, SeatDocument` and writes `OrderDocument, Outbox.Entry`, and a pull request that makes a handler touch a new collection, publish to a new topic or call another service changes the contract under that handler. Two `!` lines read these: a `GET` or `HEAD` route that writes, sends, publishes or makes a non-GET call (`! a GET that writes HoldDocument and SeatDocument: a safe method with side effects, so a retry, a prefetch or a crawler changes state`) and a `@Transactional(readOnly = true)` method that writes (`a read-only transaction drops or rejects writes`: Hibernate keeps the changes unflushed, PostgreSQL rejects the statement). Each effect is also placed with respect to transactions: inside one the method opens (its own `@Transactional`, or a lambda it hands to a `TransactionTemplate` or to a helper that runs its argument through one, like Box Office's `Transactions.run`), or with no transaction on the path; a `@Transactional` method of another class on the path accounts for its own effects, so a `!` line sits under the service method rather than under every route that calls it. Three more `!` lines read that placement: a transaction that sends or makes an HTTP call (`! a transaction that sends to payments.commands: the send is not part of the transaction, so a rollback leaves the message sent and a crash before the send leaves the commit unannounced`, the dual write an outbox exists to avoid; left alone when `spring.kafka.producer.transaction-id-prefix` makes the producer transactional), an event published with no transaction on the path while a `@TransactionalEventListener` waits for it (the listener does not run unless it asks for `fallbackExecution`), and an after-commit listener that writes (the transaction has committed and nothing commits again, so a JPA or JDBC write there is never committed unless the method is `@Transactional(propagation = REQUIRES_NEW)`).

The three Box Office modules that carry Spring annotations and the `contracts` module, whose wire types are the messages between the services, have their contracts checked in ([ticketing-service](../examples/apps/boxoffice/ticketing-service/src/contract/boundaries.contract), [payment-service](../examples/apps/boxoffice/payment-service/src/contract/boundaries.contract), [messaging](../examples/apps/boxoffice/messaging/src/contract/boundaries.contract), [contracts](../examples/apps/boxoffice/contracts/src/contract/boundaries.contract)), and `./gradlew check` verifies them when `jvmcontract` is on the `PATH`.

What it does not do: it reads the annotations as declared on the class, not the ones inherited from an interface or a superclass (Spring reads both); it does not follow a call through a field of the bean's own type; and it says nothing about JPA mappings, which are a schema, not a boundary. The proxy checks assume Spring's defaults (CGLIB proxies, rollback on unchecked exceptions), which `spring.aop.proxy-target-class` and a custom transaction attribute source can change. The wire types assume Jackson's default visibility and naming (`@JsonAutoDetect`, a `JsonMapper` customizer and the `spring.jackson.*` properties can change them), do not read mix-ins or custom serializers (a `@JsonSerialize` is shown as a detail, not applied), and show `Instant`, `UUID` and the other library types by name rather than by encoding. The configuration block reads the application files only (not environment variables, `spring.config.import`, config servers or command-line arguments, so a key no file sets is shown without a value, not as a problem), a key read through a non-constant name or a `PropertySource` of the application's own is invisible to it, a property with metadata hints is not checked against them, and a dependency without configuration metadata makes its keys look unbound (`additional-spring-configuration-metadata.json` in the dependency, or `ignored.properties` in the module's own, declares them). The validation checks know the built-in constraints of Jakarta Validation and Hibernate Validator and the JDK types they validate; a custom constraint is shown but not judged, `@Pattern` expressions are not compiled, a `@GroupSequence` or `@ConvertGroup` is not followed, and a type that cannot be found on the class path is not judged either. The activation block takes `@ConditionalOnBean`, `@ConditionalOnProperty` and `@Profile` as met (a switch behind a property it cannot see is reported as present), reads a module without an application class as part of a Boot application, follows no `ImportSelector` other than auto-configuration, matches the families it knows (Spring's own, Spring Security, Spring Retry, Micrometer, the servlet annotations) by the annotation written on the code rather than meta-present, and does not judge a listener of another library (`@SqsListener`). The stored types cover Spring Data MongoDB only (a JPA entity's queries are JPQL, which Hibernate checks at startup), read the field strings that are constants in the method that passes them (a name built at runtime or held in a `static final` of another class is invisible), do not follow aggregation pipelines (a stage after a `group` names computed fields), do not judge derived query methods (`findByHoldId`, which Spring Data checks at startup), and take a string in a method that names no document as being about every document of the module. The reach lines say what a method may reach, not when or in what order (a write under a condition is `writes`), follow no call made through reflection or a bean looked up by name, do not see what a framework does on the method's behalf (a transaction's commit, a listener's offset commit, an aspect), name a data call whose entity argument has no useful static type by the documents the method mentions, and treat the GET check as a statement about HTTP semantics: a GET that records a metric is flagged like one that extends a lease. They know a transaction by `@Transactional` and `TransactionTemplate` only: a `PlatformTransactionManager` driven by hand is not seen, a helper that takes a lambda and reaches a transaction is taken to run the lambda inside it (whether or not it does), and a Kafka or JMS transaction manager behind `@Transactional` is read as a database transaction. The binding checks read the route templates written in Spring's own mapping annotations (a composed mapping annotation of the application's own is not read), compare routes by their rendered form with the variable names dropped (two routes that differ in `consumes`, `produces`, `params` or `headers` are told apart, as Spring does by the request), take `required` and `defaultValue` as written on the annotation, and know nothing of a `ParameterNameDiscoverer` of the application's own. The throws lines see an exception built by `new` and thrown, returned by a method and thrown, held in a typed local, built by an `orElseThrow` supplier or raised by Spring's `Assert`; not what a framework or driver call throws (a `DataAccessException`, an `OptimisticLockingFailureException`), not a `throws` clause, and not the compiler's own `MatchException` or an `assert`. A handler's status is read from its `@ResponseStatus`, the first `HttpStatus` constant its body loads or the literal it passes to `ResponseEntity.status`, else the handler is named without one; a `catch` that rethrows its variable passes everything through and one that does not swallows all it catches, whatever else its body does; an `@Async` callee of another class throws on its own thread; and a `@ControllerAdvice` is matched by its packages, assignable types and annotations, with `@Order` and then the class name deciding between two that match.

## Observation specs

[`observations`](src/observations.rs) reads the boundary analysis's facts into the [foundations IR](#the-foundations-ir), one `EntryPointSpec` per route, message listener, schedule and application-event listener, under a stable id (`POST /quotes`, `kafka payments.events`, `schedule fixedDelay = 1000`, `event OrderPlaced`), so that two builds' specs can be compared by id. A spec has the entry point's **external inputs**, the inputs of its preservation contract, each with its Java type and how it is bound (a request parameter, path variable, header, cookie or body, Spring's default for an unannotated parameter, or a message's payload), derived by identity, since both versions get the same request, and for a body, part or payload of an application type its **wire shape** as the boundary contract's wire block renders it, `!` lines included (`PlaceOrder: billing: ! constraints on Billing are not checked: no @Valid on billing`); what a consumer **observes**: the result, the exception, a route's status for each outcome (first those the framework takes before the handler runs, with the requests each is for: a body's Bean Validation under `@Valid` or `@Validated`, a `MethodArgumentNotValidException` answered 400 unless an `@ExceptionHandler` takes it, for a body that fails one of the constraints it runs, and a parameter that can't bind as [`binding`](src/binding.rs) finds it, a `MissingPathVariableException` on every request; then a normal return, then each exception [`failures`](src/failures.rs) finds, with what decides its status), and one effect observation per modeled call (`effect:owner#name(descriptor)`) with the paths of its payload it snapshots at the call (each parameter of the call by name, an application class followed into its fields: `topic, data.total, data.quantity`); each **effect site** with its kind (`writes`, `sends`, `calls`, `publishes`; a read is a modeled call but no observation), its target, and its place relative to transactions as [`reach`](src/reach.rs) finds it; which **identity relations** count (none for a route or listener, whose consumers see serialized values); the **environment model** of its effects: every modeled call with the outcomes it may give, one model for both versions, a trace bound (4, or the number of effect sites when there are more, so that one pass through each fits) and exact order, and the model's restriction stated as an assumption (every modeled call returns normally); and what the analysis **can't see**, named, never dropped: a dynamic call site it doesn't follow (string concatenation), a call into a class it doesn't follow or an interface nothing implements, a target computed at run time, a parameter the framework supplies, a destination from configuration (a method an application class inherits from the library, `Enum.ordinal`, is a library call, not an unresolved one). The walk follows the module's classes, and with `--base DIR` those of its sibling modules too (the class path entries under `DIR`, compared canonically, as `verify --base` does for the boundary contract): Box Office's routes write through `messaging`'s outbox inside its transactions. The spec is static: it says what a change must preserve, and proves nothing. Its limits are the boundary analysis's. Every entry point of Box Office has one, held to golden text by `lib/tests/observations.rs` (`tests/fixtures/boxoffice-observations/`, rewritten with `JVMCONTRACT_BLESS=1`), which builds the app offline with its own Gradle build.

`observations --against OLD.json` compares two builds' specs ([`observations::compare`](src/observations.rs), the IR's `observe::compare`) into obligations, statically. Entry points correspond by what their consumers address: the same verb and route with path variable names aside (`GET /holds/{id}` is `GET /holds/{holdId}`), the same topic, queue or schedule. A renamed handler is the same entry point; a renamed route is one removed and one new, with the handler that now serves the new route named, since only a person can say the route change is intended; two that a key doesn't tell apart and whose handlers changed are unresolved. For each pair, every observation of the old entry point gets exactly one obligation, so the accounting holds by construction (`observations::unaccounted` checks it): **preserved, to prove**, where the two specs agree on its shape, which makes the obligation well formed and discharges nothing (an unchanged payload type is not preserved payload values); **changed**, where they don't: an outcome the framework takes before the handler runs that only one build has or that is for other requests (validation dropped, a new constraint, a path variable that no longer binds), a shared outcome mapped to another known status, a status one build answers for an exception it throws that no exception of the other is answered with (a normal return whose status is unknown doesn't hide that), a payload path gone or added, an effect site that moved into or out of a transaction or to another target (with what the new build attempts that the old doesn't named beside an attempt that is gone), a response of another type, and every observation of the handler when one build fails every request before it runs; preserved only with a person's approval recorded in the preservation contract, or a proof that the difference never shows; **removed**; and **unresolved**, where a status is unknown and nothing above changed. An observation only the new build has is **new**; in an entry point the old build has, an effect attempt the old trace never makes is a change to that trace unless a person approves it or a proof shows it is never reached, and the count says how many there are. Differences a proof must cover but that change no shape (an outcome replaced by one with the same status, a second call site of an effect) are listed on the preserved obligation. Two obligations aren't observations: `inputs`, changed when the external inputs, their bindings or their wire shapes differ (a new header, a new body property), since the input domain is the contract's and never inferred; and `unresolved`, which carries what the analysis can't see of either build. Each obligation says what discharging it would need. The text groups them by entry point and ends with the count and what no entry-point spec observes (`observations::NOT_OBSERVED`: configuration values, what an encoded payload holds beyond its snapshot paths, advice such as caching, field names in query strings; the boundary contract checks those); `--json` prints the IR's `Obligation`s. `lib/tests/observations.rs` compares each of Box Office's examples 110–119 with Box Office as it is (the patched modules compiled with `javac -g -parameters`, as the Gradle build does: the walk reads a local's type from the local variable table) and holds every obligation that isn't preserved-to-prove or unresolved to what the example's recorded boundary diff says changed at the entry points.

An entry point's obligations are discharged by its **effect trace** ([`effects`](src/effects.rs), the IR's `observe::check`, with `observe::effect_log` for the plan), under a deliberately narrow contract: the ordered trace of modeled boundary-call attempts, with the response and the supported failure outcome, is preserved under an explicit environment model. In both builds alike, every call site of a modeled call is rewritten into a **recording stub** (the call sites are redirected as [`shared`](src/shared.rs) redirects shared callees, no offset moving); a stub of an observed effect appends one attempt to a log, with its payload paths snapshotted at the call (`topic` as the string literal it is, `data.total` through the record's accessor), never a reference read later (where the call sites pass payloads of several classes, as a retry and a dead letter through one `send`, each path is read through the class the payload is, a path its class lacks is snapshotted as absent, and the class is snapshotted too, as `data.class`, so that payloads of two classes never compare equal), and gives back nothing or its type's default, so a handler that uses a modeled call's result is refused until modeled return values come. **One environment model** serves both builds: the claim's calls and both specs', in one order, each returning normally (the model's only outcome so far, stated as an assumption). A generated method in the handler's package makes the handler with its one constructor and every dependency `null` (an application class among them is refused, since it would be null too), calls it on the entry point's inputs (integral ones, for now) and returns the log: the outcome (a normal return or which exception class), the response, and the attempts in **exact order**. The existing regression harness proves the two builds' logs equal, as a new caller of [`equivalence`](src/equivalence.rs) with the own checker. What the stubs can't stand behind marks the log unresolved, differently in each build, so that no proof covers an input that reaches it and a counterexample on it is reported as **unresolved, never as a shorter trace**: an attempt past the trace bound, a string no literal of either build is, a call on a dependency the model doesn't have, a `NullPointerException` out of the handler (a null dependency called through a supertype, `Object.hashCode`, looks like any other call). The status is preserved when the outcomes are and the two builds' mappings agree statically. A counterexample is **replayed on a JVM** under the stubs, the harness on the witness and then each build's log on its own, decoded into what each attempted (`the old build returns 90 and attempts KafkaTemplate.send(topic="quotes", data.total=90, data.quantity=100); the new one returns 90 and attempts no modeled call`): a run under the modeled dependencies, not against a broker or a store, which the witness says. A spec with something unresolved is unresolved. `jvmcontract effects BEFORE AFTER` runs the check from the command line over two builds' class directories, for every entry point of the old one (or those of `--entry`), matched as `observations --against` matches them, under the claim each one's own spec makes (`effects::claim_for`: its inputs, every observation it has, its environment model, no change approved), and prints per entry point what each required observation became, the proof or the replayed witness or why it is unresolved, and the assumptions; `--report DIR` writes `effects.sarif`, an `effects-changed` finding per refuted entry point anchored at its handler (`--sources`, `--base`). `examples/tools/build.py` runs it as the B9 check of the route app's examples (`examples/apps/deliveries`, tag `effect-trace`). With `--cache DIR` each entry point's proof runs under the proof cache (`equivalence --cache`, [the foundations IR](#the-foundations-ir)): it is a regression check of the two rewritten builds, so its claim key digests their closures from the generated method, the recording stubs with them, and so the environment model the stubs encode (the modeled calls in log order, the payload paths each snapshots, the trace bound, the exception classes the outcome tells apart, the string literals a snapshot can name); everything else in the result (the specs' unresolved parts, the external inputs, the status mapping) is worked out again on every run, and a stored refutation's witness is replayed on a JVM again. A reuse names the run it came from by the builds that run was given, of which the proof's rewritten builds were copies (`equivalence::Options::copied_from`), not by the copies' temporary directory. `tests/effects.rs` proves the joint example's refactor and refutes its dropped and its duplicated event, its offset, and a trace past a bound of 1; and reuses the proof exactly when its claim is unchanged: a rerun is a hit, and one more attempt allowed, an event field no longer snapshotted, a `@ResponseStatus` added to the route or a dropped event in the handler is a miss (the stale-cache defect at the boundary), while a rerun of the dropped event reuses its stored refutation, replayed on a JVM again.

**Modelled results** (the [application-core environment stream](../llm-dlc/loops/application-core-environment.md)'s E1). A modeled call whose result the handler uses is answered, not refused, once it has a model of its results: a `CallModel` (`spec::plans`) on its `ModeledCall`, in the claim's environment model or declared with `effects --environment FILE` (or `compare --environment FILE`), a JSON list of `ModeledCall`s each with its model, which replaces the spec's call of that name. The coupling policy is [`environment`](src/environment.rs)'s, defined before either was built: a **deterministic read-only query** of one declared snapshot answers with one function of the call's key (its `key` paths, primitive arguments so far), the same for both builds and every call, so equal keys get equal answers and different keys independent ones whatever their position (a version that asks for another key is checked against that key's answer, never handed the other's answer at the same position); a **declared nondeterministic or fallible operation** (`choice`, with an occurrence policy) is a different model: under the `per-call` policy each call chooses any result, the same choice in both builds for the same key and the same occurrence of that key in the trace, so a second read of a key is an answer of its own, the n-th reads of a key in the two builds correspond, and different keys are still never coupled by position (a finite `script` is the brief's optional work, refused by name). The query is encoded as a table of `2 × bound` keys and answers and a default, among the generated method's inputs after the handler's, so the proof covers every snapshot: each build makes at most `bound` calls of it (one more marks the log past its bound), so any function on the keys the two ask for is one choice of the table, and every choice is one function, so a counterexample is one environment. A per-call choice is the same table with each entry used once per trace: a call takes the first entry of its key this trace hasn't used, so the n-th call of a key takes the n-th entry of that key in both builds, and any choice per key and occurrence is a table listing each key's answers in order (`(arg0=3) gives 1, then 2, any other key or later call of one gives 0`). The witness names it (`under the environment Rates.rate (rates.rate): (arg0=0) gives 1, any other key gives 0`) and the JVM replays it under the same stubs; the proof and the search name the table's inputs (`rates.rate[0].arg0`, `rates.rate[0]`, `rates.rate.default`), and the domain says the environment's answers are part of it. The model is in the proof's claim key, the table being the generated method's inputs and the stubs' code. A call the boundary walk can't follow on the model's owner (an interface nothing implements) is the call the model answers, where the owner's simple name names one class of either build; any other call on it is a stub that marks the log. A String key (the values stream's String) is compared by its content: the table's keys are Strings of at most the claim's String bound (`max_array_length`), any content, and a call keyed by a longer String marks the log unresolved, since answering it as the default would couple two such keys. What the model doesn't encode yet is refused by name (`Part::Environment`): a key through a field or the receiver's identity (the objects stream's plan), a result that isn't an integral or boolean primitive, a bound outside 1 to 8. `tests/environment.rs` proves a rewrite that uses a rate, refutes a wrong query key, an ignored rate and an event sent on the wrong branch of it, proves two keys asked for in the other order and one key asked for twice (and refutes the difference taken the other way round), leaves a call past the bound unresolved, and reuses the proof exactly while another bound or coupling is a miss. Under a per-call choice it proves the rewrite and two keys that always differ asked for in the other order, and refutes a wrong key, one read where the old build read a key twice (which the query proves), two reads of one key taken in the other order, and two keys that may be equal swapped, with `code = quantity` as the witness.

**DTO responses** (the environment stream's E3, applied at the merge). A model's normal result may be a DTO: `{"kind": "object", "plan": ..., "nullable": true, "identity": "fresh"}`, an object of an application class made by the one node of a construction plan (the objects stream's, `construction::root`) by the constructor it names, from primitive leaves named by their path from the plan's root (`result.unitCents`), or null where `nullable` says so. Each answer of the environment's table is then its null flag and its leaves, a function of the key like any answer (`offers.find[0].null`, `offers.find[0].unitCents`). The identity policy is the claim's, never assumed: under `fresh` every call gets a new object, under `stable` every call answered by the same entry gets the same object for the trace (a query only), so a handler that compares two responses by identity proves under one and is refuted under the other. The class must be data: primitive instance fields, no static field, no method beside its constructors; and no build may call a method on a response, write its field, or call `Object`'s identity-dependent methods (`hashCode`, `toString`, `wait`, `notify`) in a method that handles one. An object inside a DTO, an array or String field, a factory, a dependency or a setup call in its plan, and a stable identity under a per-call choice are refused by name. A response its constructor won't make from the chosen leaves marks the log unresolved, never the constructor's exception passed off as the dependency's. The witness names each answer (`gives a new Offer(unitCents=3, minimumUnits=1)`, `gives null`) and the JVM replays it under the stubs; the claim key covers the plan and the identity through the stubs' code and the DTO's constructor in the closure. `tests/environment_responses.rs` proves a rewrite, refutes a changed null branch and a changed field test, each replayed, shows the identity policy deciding, and refuses each case beyond data. The quote fixture's `offer-claim` (row E2) runs through `environment::check`, below.

**A method's claim under an environment** (the quote family's E1 and E2 rows, at the merge: `environment::check`, [`effects::check_planned`](src/effects.rs)). A claim about an ordinary method (`quotes.QuoteService#quote`) whose receiver and parameters its planned domain makes is checked by the effect check: its generated method takes the plan's flat inputs (`this.feeCents`, `request.code`, `request.quantities`) and the environment's tables, makes each root by the constructor its node names, every dependency of an application interface passed null and reached only through the stubs (`construction::flat_roots`), calls the method, and returns its log. A constructor's exception is the outcome, as the call's is, so an input only one build's constructors accept is a difference. A String input is the values stream's String, never null, of at most the claim's `max_array_length` code units; a plan that bounds a String or an array otherwise is refused, never checked under another label. A payload String is snapshotted by its content (its length, then its code units), within the same bound, a longer one leaving the result unresolved; a payload path of a call of one argument is read from it (`code` of `send(QuoteEvent event)`). The domain is enforced as the regression check's gate does: its classes are the plans', and an input-object or allocation bound the plan or the code exceeds leaves the result unresolved. An object inside another, a null or shared root, a factory, a setup sequence, a correspondence and an observation other than the result, the exception and the effects are refused by name. Under `--cache` its proof is keyed as any effect proof, the plan's construction being in the generated method's code. `tests/environment_quotes.rs` refutes a wrong String key and an event on the wrong branch, its code shown by content, each replayed; leaves a key or a payload past the bound unresolved; refuses each case above; and reuses a proof exactly but not under another bound or response policy.

**Modelled failures** (the environment stream's E2). A `CallModel`'s results may list, beside its one normal result, exception classes it may throw (`{"kind": "throws", "class": "java.io.IOException"}`), checked ones included; a call that returns nothing may be modelled by its failures alone. Each entry of the table, and the default, then also holds an outcome (`rates.rate[0].outcome`): `k` throws the `k`-th class, any other value gives the normal result. So which outcome a call gets is part of the same function of its key (and occurrence, under a per-call choice) as its value, the same in both builds, and the witness names it (`(arg0=0) throws java.io.IOException`, `(arg0=0) throws rates.RateUnavailable, any other key or later call of one gives 0`). The stub throws a new instance made by the class's public constructor without arguments, so a failure carries its class and no message, cause or stack: a build whose handler of a modelled failure (a catch of its class or a superclass, or a `finally`) reads more of it than its class, by calling a method on it or handing it on, is refused by name, never answered with an invented message; a rethrow, a class test and a null test are fine. A failure that escapes the handler is its outcome, by class, like its own exceptions. A class without such a constructor, an abstract one or a `NullPointerException` (which the check can't tell from a dependency left null) is refused. `tests/environment.rs` proves a rewrite that keeps a catch of a checked failure, refutes a newly missing catch and the failure's event dropped or sent on the wrong topic, each replayed on the JVM under the failing environment the shrunk witness names; refutes a dropped retry of an unchecked failure under a per-call choice, whose second call is an occurrence of its own, while under a query the retry can change nothing and its removal proves; refuses a handler that reads the failure's message or cause or wraps it; and keys another failure, or another class of it, apart in the proof cache. The JVM witness runner sizes its operand stack from the generated method's arguments (`jvm_witness::run`), so a refutation over wide tables is replayed like any other.

## Comparing two builds

`jvmcontract compare BEFORE AFTER` ([`compare`](src/compare.rs)) is the foundations IR's four parts run together, each fed by the others, with nothing written by hand: the [observation specs](#observation-specs) and their effect traces for the entry points, whose external inputs the specs anchor, so no mapping is involved; and, for the kernel, every changed method pair [alignment](#commands) matches apart from the entry points' handlers, checked by the regression check over objects under the correspondence alignment proposes for it, as its preservation contract the one its two signatures imply, and held, besides its result and exception, to the identity relation of the result with each object parameter of the result's class (a caller handed back the object it passed can tell it from a copy). A pair with several proposals, or one that is a person's decision, is not checked but asked. A pair's inputs are made by their constructors, unless a person declares the subject's domain: `--domains FILE` is a JSON object from each new method (`pkg.Class#method`, as the report names it) to a domain as a claim states one (its classes, bounds, `nullable`, `may_alias`, `made_by` and `label`), a [construction plan](#the-tools-own-checker) with its setup calls, say, and the subject's claim has that domain as it is, so the heap check enforces or refuses each part of it as it does a frozen claim's. The throttle family's `after-setup`, one unit short only once a call has taken some, is verified over the constructor domain and refuted, with the whole history run on a JVM, over the setup plan (`tests/compare_domains.rs`). A domain for a subject the run checks no claim of (an unchanged method, an entry point's handler, a misspelt name) is refused before any proof, and so is a field a domain doesn't have. The proof cache keys the check a domain makes (its harness, the methods that make its inputs, the stated domain), not its label or bounds, which the heap check enforces after it, so a constructor-only plan and no declared domain share one stored proof, each result stating its own domain. A proposal's evidence is the proof's, for the claim key it ran under; its intent stays proposed, and where no external contract anchors the inputs the report says that the relation is proved and whether it is the intended one is unconfirmed. With `--cache DIR` every proof runs under the proof cache, so an unchanged rerun is an exact hit (a key covers a method's closure, so a change elsewhere in the build leaves it a hit: the joint example's `alias-to-copy` changes a method `POST /quotes` doesn't reach, and that route's proof is reused) and a changed pure helper is proved once by a check of its own and taken as one function in its callers. That holds for the entry points' effect-trace proofs as for the kernel's checks, keyed as `effects --cache` keys them. The report ends with the effort: every decision a person made, by category (mapping, approved exclusion, domain restriction, observation change, environment assumption), zero included, so that effort can't hide by moving category (each modelled call of a declared `--environment` counts as one environment assumption, and each subject's declared domain as one domain restriction: the only inputs of a person's the run takes); the questions the run leaves (an entry point gone or changed in shape, a mapping to choose), each unresolved until a person answers; and what the verdicts rest on that nobody decided (the recording stubs, the environment model's one outcome). It exits 0 only when everything compared is verified and nothing is asked; `--report DIR` writes `compare.sarif`, an `effects-changed` finding per refuted entry point and a `behaviour-changed` one per refuted kernel pair. `tests/compare.rs` holds it to each row of the joint example's acceptance table, on the fixture and each of its defects. The examples tagged [`joint-run`](../examples/README.md#tag-joint-run) are the same run by `build.py`, on the [shop app](../examples/apps/shop/README.md): the verdict is the subject's, and the page lists every other part.

## The tool's own checker

JBMC is the bounded model checker the proofs were built on, and the limits that have bitten were its: no models of the class library beyond six classes, a string solver that overrides the class on the class path for `java.lang.Character`, a MiniSAT path that stalls, a 3 GB run that no option shortens. The models are the tool's own now ([above](#models-of-the-jdk)); the checker is becoming so too. [`bmc`](src/bmc/mod.rs) checks the same harness class JBMC is given, by executing its bytecode symbolically over bit-vectors ([`bmc::bits`](src/bmc/bits.rs): two's-complement circuits for the JVM's arithmetic, division included, with gate hashing so that the harness's check of a value and the method's computation of it are one circuit), one path at a time, asking a bundled SAT solver (CaDiCaL) at each branch which sides are feasible, and, when a path reaches the harness's `AssertionError`, for the input that takes it there. Each path carries models of its condition, the solver's answer when the path was split off, so a side of a branch that a model takes is known feasible and the solver is asked once per branch at most, about a side no model takes; a condition the path took before (the same comparison of the same bits, which the gate hashing makes the same literal, as a loop bound both versions test is) costs nothing. The hashing also makes a callee both versions call on the same arguments one circuit, so the checker never compares two copies of a division: the plain proof of [example 120](../examples/120-retry-after-rewritten-around-unchanged-refill-helpers/README.md), which JBMC did not finish in 60 s without the shared-callee stubs, takes it 1.1 s with the helpers as written. That input is looked for in the stages of JBMC's `staged` policy, inputs in `[0:20]`, then `[-100000:100000]`, then everything, so that the witness is readable, and the stage is reported as JBMC's is (`searching inputs in [0:20]`); a path that fails only on large values does not end the search, which goes on through the remaining paths, for as much solver work again as the first violation took (in conflicts, at least 10,000) and as many paths again (at least 64), in case one of them fails in a smaller stage; counted in work, not seconds, so that the witness is the same on every machine. The witness is then shrunk in the interpreter like JBMC's. A division or remainder is not built as a circuit at first: its quotient and remainder are bits the solver chooses under what holds of every division (the remainder is smaller than the divisor and takes the dividend's sign, a division by one or by the dividend itself is exact, a power of two divides a non-negative dividend by masking, and so on, a few hundred gates each where a 64-bit divider is some ten thousand), a proof that goes through under those facts holds, and a model the solver gives is checked against the real division of the values it chose and the circuit built only where it was wrong. Both versions mostly use the same remainder or compare it with something the facts settle, so the 64-bit remainders of [examples 120, 132 and 135](../examples/README.md#tag-own-checker) cost nothing or a fraction of a second where they took 1 to 12 s before. A multiplication is left to the solver the same way, under what holds of every product modulo the width (a factor of zero gives zero, of one the other factor, of minus one its negation, a power of two shifts by its exponent, the low eight bits are exact), with the multiplier built only where a model got a product wrong: the loop of `delay *= multiplier` in [example 131](../examples/131-backoff-with-a-multiplier-proved-equal-to-the-doubling-record-for-a-multiplier-of-two/README.md) is proved in 4 s instead of 22 with none of its 27 products built, the scope's multiplier of two being a power of two. A quotient times its divisor is not a product at all but the dividend less the remainder, `(a / b) * b` as `a - a % b`, which holds for every pair in two's complement, so the identity between a division and a multiplication that neither engine proved in a minute is the same bits on both sides: [example 138](../examples/138-a-window-start-computed-as-the-window-s-index-times-its-length-proved-equal-to-the-remainder-form/README.md) in 0.1 s. The solver is also not waited for on the other side of a branch: it is given as much work as all its calls so far did together, at least 10,000 conflicts, and a side it has not decided by then is explored later, once every decided path is done, with all the time left. The budget is counted in the solver's conflicts, not in seconds, so which side is left undecided, and with it the order of the paths, is the same on every machine; only the run's `--timeout` is the clock's. Refuting an infeasible side can be as hard as the whole proof (that one value is not a multiple of another, say) while the violation on the feasible side is found at once, as JBMC finds it without deciding the side: [example 134](../examples/134-a-window-counter-that-advances-by-one-window-leaves-its-start-behind-a-quiet-client/README.md) under its scope is such a probe, refuted in 2 s where the checker did not finish in two minutes waiting for it. Loops are unwound up to `--unwind`, exceptions are thrown and caught by class through the handler tables, calls into the application are inlined, and `Math.*Exact`, `floorDiv`/`floorMod`, `abs`/`min`/`max` and the wrappers' `compare`/`signum`/`numberOfLeadingZeros` are circuits with their overflow and division-by-zero paths. A model of a JDK class ([`models/`](models/README.md)) runs as bytecode in it, so `Character.digit` is the same function here, in JBMC and in the interpreter. An array of primitives is an object with a symbolic length and a cell per index it may have, as many as the bound on array parameters (`--max-array-length`, eight by default): a read at a symbolic index is a choice among the cells by the index, a write a conditional update of each cell, an index at or beyond the length or a negative size a branch to the exception, as a division by zero is, and the harness's copying and comparing loops over an array parameter run through it like the method's own. The bisection of a `lookupswitch` table over such an array, in [examples 140 and 141](../examples/README.md#tag-own-checker), is proved equal to its previous form on every strictly sorted table in 2 s where JBMC's one formula over the symbolic array takes 100 s and 2 GB, and the half-open form that reads past the end is caught in about a second where JBMC takes 23 s. Paths are merged where they meet, once the search has grown past a small one (512 paths, `Options::merge_after`): a path that reaches an instruction with more than one way in (the instruction after an `if`, a loop header, a handler) waits there, and when nothing else can run the paths waiting at the earliest such point are made one path, every value they differ in a choice by the condition of each, its condition the disjunction of theirs, and its models all of theirs, so that a branch each of whose sides some model takes costs no solver call. A reference they differ in becomes a symbolic one, one of their objects or `null` under the condition of each, while a reference every path agrees on stays a known object, as all were before: comparing one (`==`, `null`, `instanceof`) is a formula over those conditions, a field read through it chooses among the objects' fields and a write updates each object under its condition, and anything that needs the object itself (a call on it, a cast, an array access) splits the path per object again. Ten independent choices between two objects, then a write through the one chosen, are 22 paths merged where they were 1024 (`lib/tests/heap.rs`). A method of `n` independent branches is then `n` paths, not `2^n`, and a loop whose body branches three ways is a few paths per iteration: the ASCII fast path of Mica's constant-pool encoder, [examples 142 and 143](../examples/README.md#tag-own-checker), is proved equal to the previous version on every string and buffer of up to eight elements in 733 paths and 7 s where the unmerged search takes 11643 paths, and at twelve elements in 83 s and 155 MB where the unmerged search spends its budget of 200000 paths without a verdict and JBMC ran out of memory at 2.8 GB at eight. The solver's work moves rather than vanishes: on a merged path the question at a branch is over every path merged into it, so the comparisons at the end of the harness are each a proof over the merged formula, and a violation is found only once the paths that could reach the join have arrived, where the unmerged search sometimes hit it early. That is why a small search is left unmerged: the 64-bit arithmetic of examples 131, 134 and 139 took two to three times as long merged from the start, each solver call about a disjunction of paths rather than one, and a proof the unmerged search finishes in sixty paths gains nothing from merging; one that would take thousands becomes possible.

Its fragment, today: methods over `int`, `long`, `short`, `byte`, `char` and `boolean`, and records of such components as the regression proofs build them (an object with fields, its constructor inlined, so the proofs of [examples 126 to 131](../examples/README.md#tag-record-components) run through it); arrays of those primitives, an array parameter of every length up to `--max-array-length` with symbolic elements and an array the method makes of a constant size or of one the solver proves within that bound (a copy of a parameter, say); arrays of references, made the same way, whose cells hold objects or `null` (an index that is an input splits the path per cell, since a reference is not a choice among bits), and an array's `clone()`; enums, their constants made through the model of `java.lang.Enum` (`name()`, `ordinal()`, `toString()`, `equals`), `$VALUES`, and javac's `$SwitchMap` classes; strings and other objects only as opaque values (a message built for an exception); application classes' static fields, and their initializers run where the JVM runs them (JVMS §5.5: superclasses and superinterfaces with a default method first, `ExceptionInInitializerError` from one that throws, `NoClassDefFoundError` at a later use), unless an initializer is outside the fragment; no multi-dimensional `multianewarray`, no floating point, no JDK static state beyond compile-time constants, no JDK call outside the list above (`System.arraycopy` and `java.util.Arrays` included). Anything else is refused with a reason, and `--engine auto` then hands the harness to JBMC with a `note:` line saying why; `--engine native` reports the refusal as *unverifiable*; `--engine jbmc`, the default, does not try it. A violation it finds is replayed and shrunk in the interpreter exactly as JBMC's, so an engine mistake on a violation would show as "does not reproduce" rather than as a false witness; its proofs rest on the circuits' correctness, which the unit tests check against Rust's integer semantics on the edge cases of every operation and the integration tests cross-check with JBMC on the fixture proofs (both checkers must agree on each verdict, the shrunk witnesses included). What it does not do yet, and JBMC does: arrays of a computed size beyond the bound, an `aastore` that throws `ArrayStoreException`, the merging of paths whose objects differ (one allocated an exception the other did not: they wait at the same join and go on separately), and floating point. It is a start, not a replacement; the default stays JBMC until the two have agreed on the examples' proofs under the pipeline.

Every instruction and call is implemented as the JVM does it, modelled, refused, or a *gap*: a construct the checker does not implement faithfully, with a stable id from what it is (`jdk-constructor:java.util.ArrayList.<init>(I)V@jdk-25.0.4.1`); the table is in the module docs of [`bmc`](src/bmc/mod.rs), and a test holds it to every opcode. The gaps it meets are a JDK constructor (`new ArrayList<>(n)`, which throws for a negative `n`), a `void` JDK instance method (`Random.nextBytes`, which fills its argument), a JDK instance method returning an object, a string concatenation that would call `toString` on an object, an application class's initializer the engine does not run, since it is outside the fragment (one that reaches what the engine refuses, floating point say, or reads the statics of such a class; met at the class's first `new`, `getstatic`, `putstatic` or `invokestatic`, after its superclasses', as JVMS §5.5 orders them; a JDK class is taken to be initialized already), and two calls whose value the proof reads: a JDK instance method returning an integer, a `char` or a `boolean` (`jdk-primitive-method`, `Random.nextInt(bound)`), and a static JDK method the engine does not model (`jdk-static-method`, `Integer.numberOfTrailingZeros`, `Arrays.fill`); a JDK method with a floating-point parameter or result, or an array result, is refused outright. Not a gap are the calls it reproduces exactly (`Object.<init>`, `Record.<init>`, a JDK exception's constructor with nothing, a message, or a message and a cause, the `Math` operations above, the models). `--gaps strict`, the default, refuses a gap by name: the path that reaches it ends there, a run that met one has no verdict unless another path is a violation, the reason lists every gap met with where, and `--engine auto` does not then ask JBMC, which approximates a call it has no bytecode for too, without naming it, unless every gap refused is a class initializer, which JBMC runs, or a call of a JDK class JBMC is given the bytecode of (`Math`, `StrictMath`, `Integer`, `Long`, `Short`, `Byte`). `--gaps assume` keeps the approximation (the constructor does nothing else, the `void` method nothing, the other returns a new object, the initializer has run already and thrown nothing) and the verdict says so: `✓ ... on every input, assuming 1 behaviour the tool's own checker does not implement (--gaps assume)`, with an `assumed:` line per gap. A call whose value the proof reads has no approximation, since the engine could only make the value up: `--gaps assume` refuses it as strict does, the reason saying that only a contract closes it. A monitor is implemented: `NullPointerException` on `null`, and nothing else in a run of one thread. So are identity and fields: a field is resolved as the JVM resolves it (JVMS §5.4.3.2), so a field a subclass declares again is a second field, in the checker and in the interpreter that replays its witnesses alike, and every load of one string or class literal is the same object, as the JVM interns strings. `jvmcontract gaps` ([`bmc::gaps`](src/bmc/gaps.rs)) lists the gaps a proof reaches statically, before anything is proved, walks each initializer the engine runs as it walks a method, and gives each class initializer that is a gap a shape from its bytecode and the application methods it calls: an `enum`'s, one that `throws`, one that reads or writes `other-statics` (javac's `$SwitchMap` class for a switch over an enum), one that assigns only `constants` or literal tables, or `other`.

`--gaps advised` is the gap protocol ([`src/advice.rs`](src/advice.rs)): the tool hands the agent driving it the gaps it cannot close, before it solves anything. A property or regression proof builds its harness, then scans the harness and every method it may reach, on the class path the engine is given, with no solver. A gap with no contract stops the run: the verdict is *unverifiable*, with the finding `gaps-need-contracts`, a `gap` line per gap saying what its contract must state, and a template, written to `contracts.template` in the work directory. Under `--json` the outcome's `advice` has, for each gap: its id, the call with its owner, name, descriptor, parameters (named as the class file names them, `arg0` for a JDK class, which keeps no names) and result type, the sites, what `--gaps assume` would take it to do, the parts a contract must state (`must_state`: its `result`, `exceptions`, effect on the `receiver` and the `arguments`, the static `state` a class initializer sets, and `purity`, each with a question), and its block of the template. It also has the claim in words, and what the engine refuses whatever the contracts say (`outside`). A template block is headed by the gap's id and has `call:`, `assume:`, `throws: ... when ...`, `assert:` and `modifies:` lines, in the property syntax of `prove`, plus `written-by:`. With no gap the run is strict's: advised is strict given no contracts.

`--contracts FILE` (under `--gaps advised`) gives the tool contracts for its gaps ([`src/gap_contracts.rs`](src/gap_contracts.rs)), in the format of the template: `kind: gap-contracts`, then a block per gap under its id, with `call:` naming the parameters, `assume:` (the inputs it is about; `true` if absent), `throws: X when c` (repeatable; the first whose condition holds decides), `assert:` (what holds after the call, over the arrays it modifies and, for a call that returns an integer, a `char` or a `boolean`, over `result`, `0 <= result && result < bound`; for a call that returns an object, which object: `result == this`, `result == <parameter>`, `result == null`, `\fresh(result)`), `modifies:` (`nothing`, `this`, or parameters that are arrays of primitives) and `written-by:`. The conditions are `prove`'s expressions over the primitive parameters and arrays of them. A contract the engine can apply closes its gap: the scan no longer stops for it, and the engine runs a generated method in place of the call, which throws what the contract says where it says, gives each array it modifies any elements its assertion admits, and returns the object it names; on an input outside `assume:` the gap is open and refused. An initializer whose contract throws nothing and modifies nothing is taken to have run. A contract it cannot apply is refused with the reason (a key still `TODO`, a call that does not match the id, `this` or an object parameter in a condition, a result it cannot choose an object for, an initializer that throws or sets state, `\old`, a string conversion, another JDK's version), in a `note:` line and in the advice for its gap (`refused_contract`); the advice also lists the gaps contracts closed (`closed`), and its template has only the gaps still open. The engine gives a primitive result any value of its type, which the assertion then constrains. Each contract the engine can apply is then **tested on a real JVM** ([`src/contract_testing.rs`](src/contract_testing.rs)), since the interpreter and the engines share models and their agreement says nothing about the JVM: a generated class, run once by the `java` of the JDK the gap ids name, calls the JDK's own method on the boundary values of each parameter's type (every combination, up to 512), then on 256 random inputs drawn with a recorded seed (arrays of up to four elements; an instance method on an object built by its class's constructor of no arguments; an initializer by loading its class), a static method by itself, and checks the contract on each with the bytecode the engine's method for it uses: inside `assume:`, the first throws clause that holds before the call decides, and the JVM must throw exactly that class, or, where none holds, return, with every array `modifies:` leaves out unchanged, the result the object named, and `assert:` holding. An input on which the JVM runs out of the test's 128 MB or its stack (`new ArrayList<>(Integer.MAX_VALUE)`) says nothing either way and is counted apart, since a proof is about a JVM with enough of both. A contract no input refutes is `tested`, with the number of inputs, how many returned and threw as each clause says, the seed and the JDK. One the JVM refutes is refused, its gap stays open, and the advice for the gap carries the counterexamples (`counterexamples`, each an `input` with what the contract `expected` and what the JVM `observed`), so the agent gets them with the reason: `a JVM refutes it: on capacity=-1 the JVM's call throws java.lang.IllegalArgumentException: Illegal Capacity: -1, where the contract says it returns normally (83 of 128 inputs refute it, ...)`. One the JVM cannot test (a parameter of an object type, a receiver it cannot build, no JVM found) is `trusted`, with why. Before the test, a contract for a **static JDK method of primitive parameters** is **proved against the JDK's own bytecode** ([`src/contract_proving.rs`](src/contract_proving.rs)) where the method is in the own checker's fragment. A generated statement per contract (method `p<i>` of `GapContractProofs`) calls the method, whose class is taken from the JDK image onto the class path as bytecode to run, and checks the contract as the JVM test does, the exception's class exact (the engine's `sameClass` intrinsic), under `--gaps strict`, unwinding loops 16 times, 30 s per contract. A contract proved, which the JVM does not refute either, is `proved`, the strongest level, with the class, the JDK, the class file's `sha256:` digest, the checker, the unwinding and the paths (`proof`): `Integer.numberOfTrailingZeros` and `Integer.divideUnsigned` are. A proof that refutes a contract gives an input the JVM test runs too, so only the JVM makes it a counterexample: a contract for `numberOfTrailingZeros` that is wrong only at `i = 777776`, which neither the boundary values nor the random ones reach, is refused at it. A witness the JVM does not reproduce is a disagreement with the JVM, and leaves the contract tested. Every contract not proved says why in `unproved`: an instance method's receiver has state the checker does not keep, a proof covers arrays only up to a bound where the call may be given a longer one, or the checker gave no proof (a gap, a static field that is not a constant, a loop past the bound). A proof is about the JDK's bytecode, which HotSpot may run as an intrinsic of the same meaning, and takes the JDK's classes as initialized, as every proof of the checker does. A contract is about arrays that are there: at a `null` array the engine meets the gap. A verdict that rests on contracts says so, counting them at each level: `✓ ..., relying on 2 contracts for gaps of the tool's own checker, 1 tested, 1 trusted (--gaps advised)`, then a `contract:` line per gap with what it states, who wrote it, and what backs it (`tested on 128 inputs on JDK 25.0.4.1 (seed 1), 38 more running out of the test's memory, none refuting it`). In the statement each is an assumption of kind `contract` with the basis `proved`, `tested` or `trusted`. A tested contract is evidence, not a proof: the test sees no receiver state and only the inputs it ran. A witness found through a contract that the interpreter, which runs the JDK's call, does not reproduce is no verdict, and names the contracts as the likely cause; one the interpreter cannot run (it has no `java.util.Random`) is run on a JVM ([`jvm_witness`](src/jvm_witness.rs)), since a contract admits what the JDK's call may never do (any value in a range, any elements of an array), and only a run of the JDK's call shows whether the JVM does it. A generated class, `WitnessRun`, calls the harness the checker proved on the witness, with the JDK's real calls where the contracts stood, then the method alone (each version alone, for a regression proof of static methods of the harness's parameters) for the outcome to report. An `AssertionError` from the harness makes the witness a violation, its proof line saying `run on a JVM (JDK ...) with the JDK's own calls where the contracts stood` and `replay.by` `jvm`, not shrunk, since the interpreter is the shrinker's oracle; a harness that returns makes it no verdict, `... does not reproduce on a JVM`, with what the method did there. In a regression proof each version's call takes a value of its own under a contract, so a call the two versions make alike can differ under it although the JDK's does not: such a witness is common there, and the JVM run shows it for what it is. A refuted assertion on a primitive result says what the JVM returned: `on i=0 the JVM's call returns 32, where the contract says it returns with `assert: 0 <= result && result < 32` holding`. `--engine auto` does not hand JBMC a run that applied a contract, and `--confirm` does not ask it, since JBMC cannot apply one. On the conformance corpus, contracts that state what the JVM does are all tested, none refuted, and decide 5 of the 6 claims strict refuses for a gap as the JVM decides them; the other reaches a JDK call with no contract. (Before Phase 5 of `llm-dlc/loops/engine-priorities.md` there were 9, three of them class initializers, which the own checker now runs.) The examples tagged [`advised-contracts`](../examples/README.md#tag-advised-contracts) are the loop on an app kernel, recorded through `build.py` (`approach.gaps: advised`, `approach.contracts`, whose file is part of the claim): an agent's contract the JVM refutes, going back to it with the counterexamples, and a proof that closes on contracts at two levels. Under `--engine jbmc`, and in JBMC's turn under `auto`, the same protocol runs on JBMC's gaps, and JBMC applies the contracts ([`src/jbmc_contracts.rs`](src/jbmc_contracts.rs), described with JBMC's gaps above). On the conformance corpus it asks for contracts on exactly the claims strict refuses for a gap, and decides every other claim as strict does.

**The contract library** ([`src/contract_library.rs`](src/contract_library.rs), [`models/contracts/`](models/contracts/README.md)) keeps contracts that were checked once, so the agent does not write them again and no run checks them again. It is built into the binary, as the models are: a `.contracts` file per JDK class, in the format above, and `checked.json`, a record of each check (the contract's digest over its gap and keys, the JDK it ran on, the jvmcontract that ran it, and the evidence with its proof and JVM test). Under `--gaps advised`, a gap the harness reaches that the agent's `--contracts` has no contract for takes the library's. The agent's contract comes first even when it is refused, so a wrong contract goes back to the agent rather than being replaced. A library contract whose record holds (the same contract, the same JDK, and for a proof the same class file in the JDK image) is applied with the record's evidence and no proof or JVM test, and its `contract:` line ends `checked once, on JDK 25.0.4.1 by jvmcontract 0.1.0, and recorded in the contract library, not checked again by this run` (`recorded` in the JSON). One with no record that holds, as after a JDK upgrade, is checked by the run as the agent's are, with a `note:`; a contract written for another JDK is checked under the run's JDK's id. `jvmcontract gap-contracts [--dir DIR] [--record]` checks every contract of a library on this JDK (the built-in one, or a directory's) and exits 1 when one is refused or has no record that holds; `--record` writes the evidence to `DIR/checked.json`, keeping the records of other JDKs. `--no-contract-library` closes gaps with the agent's contracts only. On the conformance corpus the library alone decides the same five claims as the corpus's own contracts, with no JVM test run. `--max-trust N` is the policy for trusted contracts (open question 7 of the brief: CI passes `--max-trust 0`): when more than N of the contracts for the gaps a proof reaches are trusted, each of those is refused, `it is trusted: nothing has checked it, since ...; the proof would rest on 1 trusted contract, and --max-trust 0 allows none`, and its gap goes back to the agent before anything is solved. The [`verify-bytecode` skill](../plugins/jvmcontract/skills/verify-bytecode/SKILL.md) is the agent's side: its proofs run under `--engine auto --gaps advised --max-trust 0`; it writes a contract for each gap from the JDK's documentation, runs again, corrects a refuted one from its counterexamples, reports the verdict with its contracts' evidence levels, and offers the ones it wrote that held for this library, checked with `gap-contracts --dir`.

**Transcripts** ([`src/bmc/transcript.rs`](src/bmc/transcript.rs)): with `JVMCONTRACT_TRANSCRIPTS` naming a directory, every check the own checker runs writes there every clause it gives the SAT solver and every call it makes, in order, as CaDiCaL's incremental CNF (`p inccnf`, a call an `a` line of its assumptions), each call followed by a comment with its answer, its time and its time limit. A check is hundreds of incremental calls on one growing formula, with lemmas added between them that depend on the models given, so a solver is judged on that sequence rather than on one final formula. `jvmcontract transcript FILE` runs one again, each call with its recorded limit, and reports the time against the recorded time and any answer that differs.

**The solver interface** ([`src/bmc/sat.rs`](src/bmc/sat.rs)): the engine schedules the queries (`src/bmc/mod.rs`: the probes, the deferred paths, the refinement loop), bit-blasts them (`src/bmc/bits.rs`), and hands the solver only clauses, a per-call time limit and calls under assumptions, reading a model's values back, through the `Sat` trait. CaDiCaL is the one the tool uses by default; a transcript's replay goes through the same trait, so another solver behind it can be judged on the engine's own sequence of queries. The other is Bitwuzla ([`src/bmc/bitwuzla.rs`](src/bmc/bitwuzla.rs)), for the solver comparison: it is given the engine's clauses, a variable a Boolean constant and a clause an `or`, so only the solver differs, not the encoding. Nothing links it: its C API is loaded at run time from a build of 0.8.2 ([`solvers/bitwuzla`](solvers/bitwuzla/README.md)), named by `JVMCONTRACT_BITWUZLA` or else in `~/tools/bitwuzla/current`. `JVMCONTRACT_SOLVER=bitwuzla` runs every check of the process on it, with Bitwuzla's options after a colon if any (`bitwuzla:preprocess=0`, by the long names of its command line, each checked against the library's own description of it), and the results name it with those options (`checker.solver`, the transcripts' headers); `jvmcontract transcript --solver bitwuzla` replays a transcript on it. `JVMCONTRACT_SOLVER=bitwuzla-words` is the word-level prototype: a solver may take terms (`Terms` in `sat.rs`), and then the encoding defines each gate to it as a Boolean term and each arithmetic operation, comparison, symbolic shift and `ite` of two values as one bit-vector term, rather than bit-blasting them; arrays stay bounded cells, and no transcript is kept. [`solvers/compare.py`](solvers/compare.py) puts the solvers side by side on the benchmark's five largest-formula workloads, on clauses and (`--words`) on terms, as pipeline jobs. Its models differ from CaDiCaL's, so a violation's input and the number of solver calls may differ too, but not the verdict. The comparison's results and the recommendation drawn from them, to keep CaDiCaL and bit-blasting, are in [`solvers/README.md`](solvers/README.md).

`--engine auto --confirm` has JBMC prove again, in one run over every input, a statement the own checker proved: the one expensive check, ten to a hundred times the own checker's time on the recorded examples, so it is asked for rather than taken. JBMC is a second implementation of the JVM's semantics with models of its own, so its proof is evidence that the own checker's was of the statement asked. The verdict says what came of it, on a line under `✓`: `confirmed: JBMC 6.11.0 proves it too, over every input`; `not confirmed: JBMC gave no verdict (...)`, the proof standing as the own checker's alone; or `not confirmed: JBMC was not asked`, when the own checker assumed a JDK call (`--gaps assume`) that JBMC would approximate as well, without naming it. JBMC refuting the proof is neither verdict: the result is *unverifiable*, "the engines disagree", with JBMC's witness as the counterexample and the interpreter's run of it shown, which decides nothing, since the interpreter shares the own checker's models; a JVM run on the witness settles which engine is wrong. The exception is a refutation through a construct JBMC runs otherwise than the JVM (a *defect*, above) whose witness the interpreter does not reproduce: that refutation is the defect's, as a JBMC proof through one is refused, so JBMC gives no verdict and the proof stands as the own checker's alone, the line naming the defect. So does a refutation through a stub JBMC's preflight finds (a method it approximates without implementing, a *gap* above) whose witness the interpreter does not reproduce: a stub returns any value of its type, and the refutation is that value, as a JBMC proof through a stub confirms nothing under strict (VF-023: JBMC's stub of `List.size()` refutes the size of a list the own checker proves). A witness that reproduces is a disagreement whatever JBMC reaches. A class initializer assumed to have run is checked: JBMC runs it. A violation the own checker finds is not sent to JBMC: it is replayed like any other. A proof that rests on contracts for gaps (`--gaps advised`) is confirmed on the same contracts: JBMC's preflight names its gaps, the contracts the own checker applied are applied at their call sites as under `--engine jbmc` ([`src/jbmc_contracts.rs`](src/jbmc_contracts.rs)), and JBMC's proof is held to what it still approximates; the confirmation says it rests on them (`search.confirmation.reason`). It checks the reasoning given the contracts, not the contracts, whose evidence the verdict states. A gap JBMC has that no contract closes leaves it no verdict.

**Values (the values stream's, [`application-core-values.md`](../llm-dlc/loops/application-core-values.md)).** The interpreter holds a String as the JVM does, as UTF-16 code units (`interp::JStr`): an isolated surrogate, an embedded NUL and a supplementary character's pair are each kept as they are, never turned into U+FFFD, which would make two different Java Strings one. Every String and `StringBuilder` operation it models works on code units, as the JDK's do (`reverse` keeps a pair together, `indexOf(int)` takes a supplementary code point, `strip` and `isBlank` use `Character.isWhitespace`'s set). An operation whose meaning comes from Unicode's tables (case conversion, `equalsIgnoreCase`, number syntax) is refused on a String with an isolated surrogate, and `Integer.parseInt` on one with any code unit outside ASCII (`Character.digit` takes every Unicode digit), rather than answered for a text it isn't. `tests/values.rs` runs each modelled operation on a JVM and in the interpreter on the boundary cases (isolated surrogates, pairs split and joined, NUL, U+FFFD) and requires the same code units, or a refusal where one is listed: evidence of the level `tested`. A string literal is read by its code units as the class file holds them, an isolated surrogate in its source included (since the application-core merge): the class reader keeps the units of a `CONSTANT_Utf8` that isn't well-formed UTF-16 (`ConstantPool::utf16`), and such a String constant loads as `BootstrapArg::Units`, which the interpreter, the own checker, a concatenation's recipe, the effect check's payload snapshot and the body shape a closure digests read unit for unit; a reader that takes only well-formed text refuses it. Names and descriptors are still read as text. Copying a version into its package (`relocate`) keeps such an entry's bytes. Before, `"\uDBFF"` and `"\uDBFE"` both read as `"\uFFFD"` for every engine and for the JVM run of a relocated version: a rewrite to the JVM's constant was refuted, a changed literal or payload topic proved, and a proof stored for one literal reused for the other. `tests/string_literals.rs`, `tests/effects.rs`'s payload literal and the values corpus's `literalLoneSurrogate` cases check it.

The own checker's Strings are bounded and have content (`bmc`, V1's second step): a String is an object whose code units are a symbolic length and a cell per unit it may have, any of the 65,536 values, so the solver finds an isolated surrogate or a NUL as readily as a letter. A literal has its units, one interned object per literal; `length`, `isEmpty`, `charAt` (with `StringIndexOutOfBoundsException`), `equals` (identity apart: equal content behind two references is two objects) and `startsWith` (with `NullPointerException` on null) are modelled on content, and a compiler-generated concatenation of Strings, `char`s and constants has the content of its parts. A String parameter of a harness is taken only under a bound the check states (`bmc::Parameters::max_string_length`): every content up to it is an input, it is nullable or one String with another as an array parameter is, and its witness is its code units (`raw_arrays`, in decimal). A concatenation that could pass `bmc::MAX_STRING_CONTENT` (64) units has no content, and asking for it ends the path as a named limit, never a truncated String; a number concatenated (numeric formatting) gives a String with no content, whose methods are the `jdk-primitive-method` gap they were. `tests/values.rs` checks harness-shaped methods (`tests/fixtures/values/values/Checks.java`): the quote fixture's `Codes.vip` rewrite proved, its dropped-prefix defect refuted, and every witness replayed on the JVM and in the interpreter.

A String's value adapter is `values::StringAdapter`: its domain (`spec::plans::ValueDomain`: the bound, whether null is a value, and the model's evidence, `values::string_model`, of the level `tested` on JDK 25.0.5, with what it leaves out), the bound passed to the own checker (`StringAdapter::bound`), a String argument read out of the checker's witness (`StringAdapter::read`: its units, null, or an earlier argument's object), and `encode` and `rebuild` between the interpreter's `JStr` and a witness's units, for snapshots and replay. A String longer than the bound is refused by each, never cut to it.

**A String parameter of a regression check** (wired at the application-core merge, for V1): `values::adapter` gives the regression check the String adapter, of at most `--max-array-length` code units (8 by default) and never null, as an array parameter isn't. The harness passes the one String to both versions (it is immutable, so needs no copy), the own checker makes it under that bound (`bmc::Parameters::max_string_length`), and two String parameters are two objects. The witness's String is read by the adapter's rule (`values::string_units`, a `jbmc::Argument::String` of code units), shrunk by dropping a unit or making one that isn't printable ASCII an `a`, each candidate replayed before it is taken, rendered as a Java literal with every other unit escaped (`"VI"`, `"\udbff"`), and rebuilt as a fresh String for the replay by the rule `rebuild` applies (`values::new_string`). Since the interpreter's String is a model, sampled and not proved, the witness is also run on a JVM, as `new String(char[])` of its units, and the JVM is the reference. The statement states the parameter as a value (`ParameterKind::Value`, its bound), `Bounds::max_value_length` and the model's evidence (`Models::values`), and the cache's claim key covers the bound and the String model's identity, its snapshot rule included. JBMC is not asked: `--engine jbmc` is refused, since JBMC's Strings are its own model and its witness's String isn't read, and under `--confirm` the confirmation is `not-asked`, saying why. Left out, each refused by name: a String parameter of a property check (the expressions have no String terms), a String result (the harness compares it with `Objects.equals`, which the own checker refuses as a gap), a plan root that is a String, and a null String. `tests/value_parameters.rs` checks it: the quote fixture's `Codes.vip` rewrite proved and its `wrong-prefix` defect refuted on a witness replayed on a JVM, an isolated surrogate crossing to the JVM unit for unit, the refusals, and a cached proof reused exactly and not under another bound.

The own checker runs the immutable lists `List.of` and `List.copyOf` make as the models' bytecode (`lib/models/java/util/`, the same classes JBMC runs; `models::CHECKER_RUNS`), and holds their state as an application class's: a list's elements are fields of its objects (a `List12`'s two, a `ListN`'s array), and `ImmutableCollections`' initializer makes the one empty list (`ClassPath::checker_class`). An interface call on a list or its iterator is dispatched to the model's method, so order, duplicates and aliases between elements are the elements' references, a null element is a `NullPointerException`, every change an `UnsupportedOperationException`, and `get` out of range throws the class the JDK's throws (`IndexOutOfBoundsException` from a list of one or two, `ArrayIndexOutOfBoundsException` from any other). `copyOf` of another implementation reaches that implementation's methods, which stay JDK gaps, and the gap scan counts a call on a list as no gap only where the models implement it. A regression check's list parameter is taken by the list adapter (below); elsewhere a check's lists are the ones its code makes.

A list's value adapter is `values::ListAdapter`, for the immutable lists of at most `max_length` (10 at most, `List.of`'s fixed forms) objects of one application class, null among them where the domain says so. Its domain (`ValueDomain` of kind `list`) states the model's evidence (`values::list_model`: the models, with the SHA-256 of their bytecode, `tested` on JDK 25.0.5, and what they leave out). Since the own checker runs the models, a list has no symbolic form of its own: a harness makes one as an application would, by `List.of` over `max_length` objects it made by the construction plan, from int choices the checker is free in (`ListAdapter::choices`, `admitted` and `java`): whether it is null, its length, and for each element after the first which of the objects made so far it is, so that every pattern of duplicates and aliases is a choice. The witness's list is read from those choices as the plan's nodes in order (`ListAdapter::read`, `WitnessValue::List`), and `encode` and `rebuild` go between it and the interpreter's list, by the interpreter's own `List.of` over the nodes' objects (`values::Nodes`): the one empty list, and the JDK's class for its length. A list outside the family (an `ArrayList`), longer than the bound, or holding an object the plan didn't make is refused by each, never cut or copied in. A list of Strings is refused by name, a domain's or a parameter's (`List<String>`): its domain bounds the elements' code units (`ElementKind::String`'s `max_length`, apart from the list's), but no acceptance case needs one, so no harness, witness or replay makes it. A regression check takes a list parameter, as the next paragraph says; every other place a list is met (a property's parameter, a result, a field, a payload) `values::adapter` refuses by name.

**A list parameter of a regression check** (wired at the application-core merge, for V2): a `java.util.List` parameter whose generic signature names one element class (`List<Line>`) is a `harness::Slot::List`, of at most `--max-array-length` elements (8 by default, 10 at most) and never null. The element class is an object of an application class made by its constructor, or a record, whose construction takes primitives only and whose fields are primitive, the same shape in both versions. The harness makes `max_length` objects of it in each version from the same leaves, `lines.m0` … (every one made, whether the list holds it or not, and their admission compared as an object parameter's is), and each version's list from the adapter's int choices over its own objects, in the shape `ListAdapter::java` writes: skipping the choices `ListAdapter::admitted` doesn't admit before anything is made, element 0 the first object, element `i` the one its pick names among the first `i + 1`, then `List.of` over the first `length` of them. The harness's class file (version 49) can't `invokestatic` an interface's method, so it calls `List.of` through a branchless class of version 52 written beside it (`harness::LISTS_CLASS`). After the calls each object's fields are compared, as an object parameter's are, so a kernel that changes an element (or one object twice) is observed. The witness is the flat choices and leaves, so the checker's reader, the shrinker, the cache's stored witness and the JVM run of the harness take it as they are; its list is read by `ListAdapter::read`, rendered as `List.of(new Line(1, 1), the same object as lines[0])`, typed in the shared witness form as a list of nodes with the objects as components, and rebuilt for the interpreter's replay over each version's objects by `rebuild`. The witness is also run on a JVM, which is the reference. The statement states the parameter as a value (`java.util.List<basket.Line>`, its bound), `Bounds::max_value_length`, the list model's evidence, the objects' constructor once for all of them, the list and its made objects among the input objects, and the objects' fields as one observation of the list (`lines: m0.unitCents, m0.quantity, …`, so a claim's `field:lines` is compared); the cache's claim key covers the bound, the list model's identity (its bytecode and snapshot rule), the elements' constructors as roots, and the helper class. JBMC is not asked: `--engine jbmc` is refused, since JBMC runs the list models its own way (VF-023), and under `--confirm` the confirmation is `not-asked`. Left out, each refused by name: a raw `List`, a wildcard's or a type variable's; elements made from arrays or objects, or with a field of one (the identity relations among their references aren't observed); an object result the check doesn't follow into its fields (an interface, an abstract class, a JDK class such as `Object`), which could be one of the elements unobserved; a list with `--before-target`, `--before-arguments`, `--results-agree-when` or a correspondence; `--nullable` or `--may-alias` of a list; and a list parameter of a property check. An object result the check follows (`Basket#first`'s `Line`) is compared by its fields, and for identity with each of the list's objects, before and now (`harness::Root::Element`): `result == lines[0]` for the first, which is always the list's element 0 when it has one, and `result == lines.m1` … for the others, each the element at every index whose pick is it, so comparing them compares the result with every element. A construction plan's root may be such a list (`PlanValue::Adapted` of a `ValueKind::List` of objects, named as the root), as the frozen basket claims have it: `construction::check_plans` resolves its domain under this tool's list model (`values::resolve`, which refuses another model's identity, another JDK or a stronger level than the model has), refuses one that may be null, an adapted String root and roots that differ between the versions, and the check makes it as above under the domain's own bound (the frozen claims' 3), not `--max-array-length`. `tests/value_parameters.rs` checks it: the basket fixture's rewrites of `total` and `clearAll` proved under a bound of 3, the `duplicate-skipped` and `alias-blind` defects refuted on a witness whose second element is the first's object, replayed in the interpreter and on a JVM; the planned `basket-first-claim`'s identity preserved by the rewrite and refuted where the result is a copy of the first line (with the allocation bound raised to the copy's two objects); the refusals, the plan's included; and a cached proof reused exactly but not under another bound, a plan's included, or after an edit of the elements' constructor.

Each operation of the String and list models has an evidence record of its own, `values::OPERATIONS`: the String literal, the compiler's concatenation, `length`, `isEmpty`, `charAt`, `equals` and `startsWith`, and `List.of`'s fixed forms, `copyOf`, `size`, `isEmpty`, `get`, the iterator's path and the changes the lists refuse. Each names what implements it in the own checker, the interpreter and for JBMC, the JDK it was sampled on (25.0.5), the inputs it admits, the exceptions it was seen to throw, what it leaves out, its level (`tested`, never `proved`) and the boundary cases that sample it (`lib/tests/fixtures/values/values/Operations.java`). `lib/tests/values.rs` runs every case on the JVM, in the interpreter and in the own checker, through a generated check of the JVM's outcome (a String by its code units, an exception by its exact class), and fails unless all three agree, unless the exceptions a record's cases throw are exactly the ones it lists, and unless every String method the checker models on content has a record.

An operation outside these records is a named gap under the strict engine, never a verdict. A String method other than the five is the JDK call it is, as before. A list method the models implement but no record samples (`contains`, `indexOf`, `equals`, `hashCode`, `toArray`, `addAll`, `sort` …, and `List.of`'s array form) is too, where a call from outside the models reaches it: the own checker and its gap scan take it for the JDK call it names (`gaps::outside_the_list_records`, `values::samples_list_call`) and no longer run the models' bytecode for it, which JBMC still runs. `lib/tests/values.rs` checks 20 such operations under strict, each claim true on the JVM, each run without a verdict and naming its gap, and the scan reporting the same gap.

The crate's modules follow the pipeline: [`classfile`](src/classfile/mod.rs) parses class files (and writes small ones), [`classpath`](src/classpath.rs) is the closed world of application classes plus the JDK read by [`jimage`](src/jimage.rs) and [`zip`](src/zip.rs), [`purity`](src/purity.rs), [`domain`](src/domain.rs) and [`interp`](src/interp/mod.rs) derive behavioural contracts for [`verifier`](src/verifier.rs), [`capabilities`](src/capabilities.rs) and [`api`](src/api.rs) derive the module-level ones, [`relocate`](src/relocate.rs), [`harness`](src/harness/mod.rs), [`jbmc`](src/jbmc.rs) and [`equivalence`](src/equivalence.rs) run regression proofs, [`tla`](src/tla.rs) generates protocol operators and runs TLC, [`statemachine`](src/statemachine.rs) draws a contract, and [`sarif`](src/sarif.rs) writes reports.

## What is new compared with the Java proof of concept

- **No JVM.** Contracts are derived by interpreting the bytecode, with the JDK's shape read from its image. Nothing is loaded, reflected on or executed by a JVM, so the tool is one static binary that starts in milliseconds and cannot be influenced by the class path of the build it runs in.
- **A complete purity proof over the domain.** The effect monitor catches every write to pre-existing state during the executed cases, including the array and collection stores the static analysis could not see.
- **Instance methods** of finite types (an enum's `discount()`, a record's `isFinal()`): the receiver is the first dimension of the domain.
- **No `javac` in the proof pipeline.** The JBMC harness is generated as bytecode; the scope expression is compiled by the tool, with Java's typing rules.
- **Property proofs** (`prove`): a postcondition or a law about a method, stated next to the code and proved over every input by the same machinery as the regression proofs. The expression language gained `result`, calls of the method under proof, and JML's quantifiers over array parameters and results, `\forall`, `\exists`, `\sum`, `\num_of`, `\max` and `\min`, compiled to loops in the generated harness.
- **Shrunk counterexamples.** A refuting input is shrunk in the interpreter, running the same harness class JBMC checked, so the witness on the page is small and the same on every run, with JBMC's own input kept beside it.
- **Exceptional behaviour** (`throws:`, JML's `signals`): a property declares the exception a method throws and the condition under which it throws it, and the proof covers the exceptional path with the normal one, instead of assuming the throwing inputs away.
- **Pre-state values** (`\old`, JML's): a property reads an array parameter after the call and, under `\old`, as the call received it, so a method that writes into an array is held to a frame condition, or proved a permutation.
- **Regression proofs over arrays**: a method that takes or returns arrays is proved to behave as its previous version with no property written at all, the previous version being the specification: the results, the exceptions and what each version leaves in the arrays are compared, and the differing input is shrunk.
- **Shared callees in regression proofs**: a callee both versions call unchanged is one function in both, so the solver relates the versions' uses of it and never its arithmetic, and a target identical in both versions, with everything it reaches, is verified without a solver.
- **Records in regression proofs**: a method of a record whose components are primitive, or one taking or returning such a record, is proved on the components, the record built from them in each version through its constructor, so that the proof is over the record's invariant and a record result is compared component by component. A static method that became a method of a record, or took one as a parameter, is related to its previous version with `--before-arguments` over the components; a record whose components changed, or a record's method made static, by building the previous record from the new parameters with a constructor call among them, `new Backoff(this.baseMillis, this.capMillis), attempt`. A record result whose components changed, or a result that became a record or stopped being one, is related by `--results-agree-when` over the components, `previous.startNanos == result.startNanos && previous.count == result.count`: each record's components are read into the relation, two null records agree, and one alone does not.
- **API contracts**, the fourth lockfile: the public surface of a module, diffed like the others.
- **Capability contracts per dependency** (`capabilities --each a.jar b.jar`), the hook the Java README left open.
- **A TLC runner** that parses the verdict, state counts and the counterexample trace into data, with optional deadlock checking (`--deadlock`, whose trace is reported like an invariant violation), and temporal properties: a liveness property under fairness, or a refinement of a more abstract specification (`PROPERTIES` in the configuration), reported with the property's name (TLC does not name it; the runner checks them one at a time when there are several) and, for a liveness counterexample, how the behaviour goes on forever after the trace. Also a **state-machine view** of a contract (Mermaid or Graphviz) that names unreachable and terminal states.
- **JSON output** for every command, **execution cost** per derivation (`--cost`), and a step and depth budget, so a method that does not terminate on some input is refused instead of hanging.

## Models of the JDK

JBMC has no bytecode for the class library, and the interpreter has natives for the part of it that pure domain code uses. Where the two must agree on a JDK class neither has, the tool ships a model: a small Java class with the behaviour programs observe, compiled into the binary, put on JBMC's class path by `equivalence` and `prove`, and executed by the interpreter in place of its natives for the methods the model defines. A few are for JBMC alone (`java.lang.Enum`, `List.of` and `List.copyOf` with the JDK's immutable lists), where the interpreter's natives already behave as the JVM does and stay; the tool's own checker runs `Enum`'s too (`models::CHECKER_RUNS`), as it has no natives; the conformance corpus checks both the natives and the models against a JVM. The catalogue, what each model keeps and leaves out, and how to add one are in [`models/README.md`](models/README.md). JBMC runs without its string solver (`--no-refine-strings`), which would otherwise replace calls of `java.lang.Character` by approximations of its own ahead of the model; `--refine-strings` turns it back on, and `--no-models` leaves the models out. JBMC is also asked for its bundled CaDiCaL (`--sat-solver`), since the MiniSAT path it takes without the string solver stalled on array proofs that CaDiCaL settles in a second.

## The foundations IR

`src/spec/` holds the shared types of the [foundations loop](../llm-dlc/loops/foundations.md): a comparison's
preservation contract (its external inputs and the observations the old version is held to, which inference may not
change), the object part of an input domain (classes, input-object and allocation bounds per version, nullability,
aliasing, and how inputs are made, labelled in every result), observations beyond result and exception (field paths,
identity relations within a version, effects as modeled boundary-call attempts), the correspondence between old and
new internal states (of which `--before-arguments` and `--results-agree-when` are special cases,
`Correspondence::from_flags`), the hints file (each hint with an intent state and an evidence state, kept apart, and
optionally its rank among alternatives, the static facts it was proposed on, and for a candidate answer to a
person's decision what to decide and what approving it would mean), and the canonical claim a cache key
digests. `Statement` carries them in its optional `spec` field. Each of the loop's
four streams owns one interface file there (`heap.rs`, `cache.rs`, `observe.rs`, `align.rs`), which returns a named
`Unsupported` until that stream implements it (`observe::entry_points`, `compare`, `effect_log` and `check` give the [observation specs](#observation-specs), their obligations and the effect trace); `tests/foundations.rs` checks every part against the joint example in
`tests/fixtures/foundations/`, each part under the golden files, and `tests/compare.rs` checks them run together by [`compare`](#comparing-two-builds), each fed by the others. Method correspondence and the argument, record and result
mappings (`align`, `src/alignment.rs` and `src/alignment/mappings.rs`), and what their proofs settle
(`src/alignment/proofs.rs`), are scored against the hand-written mappings of
the regression examples in [`examples/tools/alignment/`](../examples/tools/alignment/README.md); field correspondence
(`src/alignment/fields.rs`), which none of them needs, is checked on the joint example, through `align.rs`. The
questions a person decides, and their approval, are `src/alignment/questions.rs`; the evidence of a decision on a
rerun, `src/alignment/evidence.rs`.

The [application-core loop](../llm-dlc/loops/application-core.md) extends the IR with four interfaces in `src/spec/plans.rs`, each refusing unknown fields and variants, as the claim's object domain and its bounds do (a variant without fields too, such as `{"kind": "per-call"}`, which serde's `deny_unknown_fields` doesn't reach as a unit variant, so each is an empty struct variant: a script stated under it is never dropped): a **construction plan** (a bounded DAG of constructor- or factory-made nodes with stable ids, shared nodes for aliasing, typed leaves, bounded arrays, adapted values and dependencies, the roots, and an optional short setup sequence), carried by a domain made `planned`; a **value domain** (a String's or an immutable list's bounds and its model's evidence level) with the **witness value** a replay rebuilds (UTF-16 code units, never a Rust string); a modelled call's **call model** (a stable id, the argument key, query or choice coupling, the results or exceptions it permits, and its bound), carried by a `ModeledCall`; and a helper's **summary** (its read footprint, alias and null facts, domain, bounds, relation, effects and the proofs it rests on). Until its stream builds one, a claim that carries it is refused as `Unsupported` naming that stream (`objects`, `values`, `environment`, `reuse`), never checked as the case the checks make today. Each stream has a module of its own, registered in `lib.rs` with its call sites in place, so that it starts without editing a shared file: [`construction`](src/construction.rs) (objects: a planned domain, `--plan FILE` of `equivalence` and `prove`, and an ordinary receiver, asked where a check meets an instance method), [`values`](src/values.rs) (a `ValueAdapter` for a `String` or `List` parameter, asked where a check meets one), [`environment`](src/environment.rs) (a call's model, and the calls `--environment FILE` of `effects` and `compare` declares) and [`reuse`](src/reuse.rs) (`prove --cache`, and helpers' summaries). Until its stream builds a part, each returns `Unsupported` naming the stream, and the check refuses, adding those words to its own. `tests/application_core.rs` is the loop's integration contract: each acceptance row a unit run reaches, on the frozen fixtures of `tests/fixtures/application-core/`, must reach the verdict their `golden/expected.json` fixes, or the named refusal of a stream that owns the row, and nothing else. The statement has the streams' kinds already (a `value` parameter, the `environment`, `summary` and `setup` assumptions, value, setup and trace bounds, and the value models' evidence levels), each absent until a stream fills it, and so does the examples' result schema, with a replay `by` `model`.

**The property cache** (`prove --cache DIR`, the reuse stream's R1, [`reuse`](src/reuse.rs)) keeps property results in the regression proofs' store, keyed by the same canonical claim digest, not in a second cache. A property claim's first assumption says it is one, so no regression claim of the same target can share its key. Its other parts: the target's parameters by name and type, since a property names them; the closure of the target and of every constructor its object inputs, its result and its declared exceptions are made with, recursively, and of a construction plan's makers and setup calls; the assumption, the assertion, the throws clauses, the meaning of `\old`, the null and alias choices and the construction plan whole; the unwinding and array bounds; and the tools, with every checker setting that can change a verdict. Every field of `property::Options` is named in the projection, as projected or as deciding no verdict, so a field another stream adds makes `--cache` refuse the check until it is named, as do `--engine jbmc` and `auto`. The lookup comes before anything is prepared. A verified hit gives back the stored outcome with its statement, marked as reused in its output, its proof line and its `reuse` field (an exact hit, with the key and the run it came from), and no checker runs. A refutation is stored with the harness it was found in, which the key determines, and only when its witness, read back as stored, fails that harness in the interpreter. A refuted hit is used only once that witness fails the stored harness again on the classes as they are now, and otherwise the check proves again. An unresolved result is never stored, and a result that can't be stored says why in its own output. A planned check (`prove --cache --plan`) is cached as any other. `tests/reuse.rs` covers an exact hit of each kind, a planned property's exact rerun reused and an edit of its setup method alone proved again and refuted with the whole history, a stale witness proved again, an input's changed constructor invalidating a proof of an unchanged method, a key per assertion, assumption, throws clause, domain, bound and plan history, none for an unrelated change, and no key shared with the target's regression claim.

`spec::heap::check` is the heap stream's: the regression check of a `pkg.Class#method` claim on the own checker,
strict, under the claim's bounds and correspondence (step 5 above). It accounts for every required observation: preserved
by a proof that compared it, refuted where the replayed witness differs in it (the rest of a refuted claim stay
unresolved, since a refutation proves nothing of them), and unresolved where the check doesn't compare it. A
witness that differs only in observations the claim doesn't require refutes nothing, and the result is unresolved
with the witness shown, and so does a witness no JVM has run (step 6 above). A required observation the claim's
correspondence gives an output relation for is compared under that relation, not for equality, so it is held to
something the preservation contract doesn't say: unresolved, whatever the check finds (a relation like `true` would
otherwise hide the offset defect, and a relation the versions break would refute an equality that may hold), until a
person approves the change in the contract's `approved_changes`, when it is changed with approval if proved and
refuted if the witness breaks the relation. A relation for a field path bears on the required observations of that
path, of paths under it and of the object above it (`field:p` as well as `field:p.cents`), and is approved by a change
of its own path or one above it; a witness that differs in `field:p.cents` refutes a required `field:p` as well. So
it is for a parameter of the same shape in both versions with no input equations, whose other paths a proof
preserves (`field:l.price.cents` beside a relation for `field:l.quantity`). A relation for an identity relation bears on that relation, named either way round (`identity:q==result` is
`identity:result==q`): a copy handed back on purpose is changed with approval only once a person approved it. An input equation that computes a field of an input the contract anchors
(`old.p.cents == new.p.dollars * 100 + new.p.cents` about a `p` whose derivation is `identity`, and as much one
that gives it from a parameter or another object's field, `old.l.total == new.l.price * new.n`, `old.l.count == new.n`
or `old.l.total == new.l.price * new.o.count`) is refused as
`Unsupported`, the right expression as well as an offset one, which the tool can't tell apart: only an equation between
two paths, which says where each version holds the same value, or one among the conjuncts of a derivation a person
stated for the input, relates an anchored input. A version whose inputs are made of more objects than the claim's input-object bound gives
an unresolved result rather than one about inputs outside the claim. So does a version whose code may make more objects
in one call than its allocation bound: the own checker follows every allocation within the unwinding bound, so the
check counts them from the bytecode, each `new`, array instruction and `invokedynamic` of the application code the call
runs, on every branch and through every call and dispatch target, and none bounds what is made in a loop or a
recursion. What a JDK method makes is not counted. A claim whose preservation contract names an input
the subject doesn't take (by name and type; the receiver is `this`) is refused as `Unsupported`, naming the method's
parameters: a claim anchors only what its subject receives. A claim the check refuses before a statement (a
named gap) is `Unsupported` with the gap's words; one about effects or an entry point is the observations stream's.

**The domain gate.** Every option of a claim's object domain is enforced or refused, never run as whatever
constructor domain the check happens to make. A domain made field by field, or of invariants, is refused: neither is
built. A constructor domain's `calls` (each `before: shop.Quote(long cents, int quantity)`, the version, then the
class and its parameters' types and names) and `classes` are compared, once `equivalence::run` has built its harness
layout and before any helper proof, cache lookup or proof, with the constructors the harness calls in each version and
the classes they make. Each side must name exactly what the other does, so a factory, a constructor left out, another
constructor, a class left out or another class is refused as `Unsupported`, naming both lists. `nullable` and
`may_alias` (parameters only) and both bounds are enforced as above. The `label` is the claim's own words: the result
states the check's domain, and the claim key covers the label.

A target's **code closure** ([`closure`](src/closure.rs)) is what a proof of it reads in one build, as parts, each
with a digest: every application method it may run (static and special calls by resolution, virtual and interface
calls through every class a call may dispatch to, lambda bodies, the initializers of the classes involved), every
application class involved (its hierarchy, fields with their constants and annotations, and its annotations), the
dispatch targets of each virtual or interface call as a set, and, for a closure that touches Spring, the
application files. Two builds' closures of a target are equal exactly when none of those parts changed, and
otherwise name the parts that did: a new subclass that overrides a method a call may dispatch to changes the
closure with no body changed, and an unrelated class or a subclass that overrides nothing leaves it alone. The JDK,
the tool's models and the tool itself are not in a closure; the canonical claim names them apart.

A prepared claim's **key** ([`spec::cache`](src/spec/cache.rs)) is the SHA-256 of the canonical claim written
canonically (object keys sorted), under a line naming the projection's version. Each version's code is the
digest of the closures of its roots ([`closure::version_digest`](src/closure.rs)): the method compared, and every
constructor or factory its inputs are made with, those of the objects an input is made from included (a regression
claim's, as its harness calls them). The tool is digests too ([`proof_cache`](src/proof_cache.rs)): the
running executable's bytes, the JDK's whole `release` file, and the models, so a rebuilt binary with the same version
number is another claim. The projection knows every field of the claim by its path: a field it doesn't know (one
another part adds) makes the claim uncacheable rather than leaving it out of the key, and so does a part never
computed. A planned domain's plan for each version and a modelled call's model are digested whole, once each reads
back exactly as its strict type of [`spec::plans`](src/spec/plans.rs), which refuses every field and variant it
doesn't declare (`spec::cache::TYPED`); `tests/reuse.rs` changes each part of the frozen claims' histories, model
outcomes and value bounds and finds another key every time. Every value domain in them (a plan's adapted values, at
its roots, in its nodes and setup calls, and a modelled call's adapted or object response) is first resolved under
this tool's String and list models (`values::resolve_claim`), so the key digests the models' identities and evidence,
never the words a claim stands for them with: a claim stated in those words and the same claim stated by the
identities are one key, a stated level no stronger than the model's and what a claim says the model leaves out give
way to the model's own record, and a claim stated under another model, another JDK or a stronger level, or over a
domain the adapters refuse, is uncacheable by name (`tests/values.rs`). The proof cache is a local directory of result records, one per key; only verified and refuted results are
stored, a refutation with its witness, and an entry that can't be read or is for another key is a miss.

`equivalence --cache DIR` uses it ([`proof_cache::Regression`](src/proof_cache.rs)), under `--engine native` only
for now: JBMC's own identity is not yet in the key, so a claim JBMC may decide is uncacheable, and says so in a note.
The lookup is on the prepared claim (the harness generated, the shared callees planned), whose parts are the
preservation contract, the observations, the flags' correspondence, the bounds, the statement's assumptions and
domain, the harness's digest, both versions' closures, and the tools with every setting that can change a verdict
(the gap mode, the contracts' digest, the solver). The deadline is not: it only decides whether a verdict is reached,
and an unresolved result is never stored. A verified hit gives back the stored result and statement with `reuse` set
to an exact reuse naming the claim key and the run it came from, and no checker runs. A refuted hit first replays the
stored witness in the harness on both versions as they are now, and is a miss if it no longer reproduces; a
refutation whose witness doesn't reproduce in the interpreter, as stored, is not stored at all.

With `--cache`, a **changed helper proved equivalent** is shared too ([`shared`](src/shared.rs),
[`proof_cache::Helpers`](src/proof_cache.rs)), narrowly: a static helper both versions call, pure in each (as for an
unchanged shared callee), over integral values only, raising no exception of its own (a regression proof compares
exceptions by class, not message), whose classes have no static initializer. It is proved first as a check of its
own (the same builds and settings, the helper as the target, nothing restricting its inputs), within half the
caller's time, or found in the cache under that check's key. A proof on every input makes it one function in both
versions: under the own checker, the previous version's calls are redirected to the new version's method, so the
proof is of the versions as they behave and needs no refinement. The caller's statement gains an assumption of
kind `callee`, basis `proved`, whose id is the helper proof's key, so the caller's own key changes with it. The
assumption names the helper's claim and not the run that proved it, so the caller's key is the same whichever run or
cache the helper's proof came from. Since
the helper's proof covers every input, every call in either version is in its domain; a proof with a narrower domain
(`--unchanged-unless`, mapped arguments, a relation between results) is never used, as it would need an assertion at
each call. A refuted or unresolved helper stays as written in both versions, with a note saying why, and the
caller's check finds what the change does there. A helper is never proved within its own proof, directly or
through others: the checks in progress are a stack, and a helper on it stays as written. `build.py` runs a B9
example this way when its `approach.cache` says so, with a fresh cache under the build (the examples tagged
[`proved-helpers`](../examples/README.md#tag-proved-helpers)).

A **read-only heap helper** (the application-core loop's R2, [`reuse::footprint`](src/reuse/footprint.rs)) gets a
summary of its own proof ([`reuse::summarize`](src/reuse.rs)), narrowly: an instance method, not overridden by any
application class, whose code is total and read-only over primitive fields of its receiver and primitive arguments,
with a primitive result. Its read footprint is established from its bytecode, not listed: the only reference it ever
handles is its receiver, loaded only to read one of its fields at once, so its `getfield`s are all it reads of the
heap, and since it writes nothing its outcome is a function of those fields' values and its arguments. A write, an
allocation, an exception of its own, a static field, a call outside the application and the JDK's arithmetic
classes, a call on an object, an override, recursion, a reference other than the receiver, an array, a division by
anything but a non-zero constant, and floating point are each refused by name. The helper is then *lifted*: a static
method of a class of its own whose parameters are its arguments and then the values of the fields either version
reads, its code the helper's with each field read replaced by a parameter (tested against the helper on a JVM). The
two versions' lifted helpers are proved by a regression check of their own under the cache, and the summary names
that proof's key, the fields and arguments read, its domain (every value of them, whatever else a receiver holds),
and the proofs it rests on. A helper whose versions differ, or whose two versions read fields the other's receiver
doesn't declare alike (a change of layout, with no representation adapter established), has none.
A changed caller checked with `--cache` and `--engine native` reuses the summary of a changed helper it calls
([`shared::substitute`](src/shared.rs)): each call of the helper, in both versions, goes to that version's adapter, a
static method that reads the footprint's fields from the actual receiver at that call, as its own version lays them
out, and calls the new version's lifted helper. So two calls on one object around a mutation, or a call on an object
another parameter may write, are different inputs, and a receiver state a history reached is covered, since the
summary's proof is over every value of the fields. The caller's claim carries the whole summary as an assumption of
kind `summary`, with its proof's key, since that proof is positional in the fields' values. A helper with no summary
keeps its body in both versions. `tests/reuse_summaries.rs` holds these: on the frozen quote fixture's `fee` and its
`helper-extra-field` defect, and on a caller of a tariff's fee, whose stale read, read through an alias, extra read
and broken precondition are each refuted with a replayed witness, and whose classes with the summary applied agree
with the versions as written on a JVM.

**Preparation, measured** (the application-core loop's R3): [`tests/preparation.rs`](tests/preparation.rs), ignored
inline and run as a queued job, times a `compare` run on the joint example cold, as an unchanged rerun, on the
`offset` defect and as its rerun, stage by stage at the proof cache's own steps
([`reuse::preparation`](src/reuse/preparation.rs)), with each repeated stage timed apart and compilation reported
apart; its reports go to `benchmark/preparation/`. In release (job `20261108-060410`), a
rerun whose proofs are all exact hits spent 185 of its 210 ms before the lookups, and opening the JDK image took 6.3
ms each time: every class path with the JDK opens it, 28 times in a rerun and 50 in a cold run, and each open built
the table of every class in the image. That table is now the one product of preparation cached:
[`jimage`](src/jimage.rs) builds it once per process for each index and shares it, keyed by the index's bytes, which
every open reads again, so that an image changed in place, or another JDK at the same path, gets a table of its own.
Resources are still read from the file opened, and the proof cache's keys are unchanged. With it (job
`20261108-063259`, the same verdicts), an open that builds the table takes 7.9 ms and one that shares it 0.06 ms; the
rerun takes 8.6 ms in process and 66 ms as a process, the cold run 66 ms and 125 ms, and the defect's cold run 1.58 s,
1.48 s of it solving. A whole build still compiles first: `javac` takes about 0.4 s per build. These are a rerun's
preparation, not a cheaper proof of a changed method. With the acceptance contract's other two cases added (job
`20261108-114325`, the edits in [`fixtures/preparation`](tests/fixtures/preparation/README.md)), an unrelated edit
is 5 exact hits, 64 ms as a process, like an unchanged rerun's 63 ms. A safe rewrite of the helper `discount` proves
4 of its 5 proofs again, 139 ms against a cold run's 127 ms: its caller `total` is proved on the helper's new proof,
named by key, and the route's effect proof holds the helper's body, so only `withQuantity` is an exact hit. Helper
evidence is reused by key, not made cheaper to obtain.

`impact --before DIR --after DIR` ([`impact`](src/impact.rs)) says which claims a change from one build to another
invalidates. The claims are `--target`s, or a `--claims` file (`build.py`'s `claim.json` or `--plan` output serves as
it is, with `previousSymbol` for a renamed method). A claim's code is what its key digests: the closures of the
target and of the canonical constructor of each record its inputs are made with. Per claim, it is *invalidated*,
with each part that differs (`changed method k/Pricing.discount(J)J`; a class's declaration, a dispatch set, a
configuration file, a name that appeared or went), or with the reason when the target is gone; *unchanged*, so a
cached result is still hit on its code; or *unresolved*, when the first build has no such method.
[`examples/tools/impact_check.py`](../examples/tools/impact_check.py) checks it on the B9 and B11 examples of the
javac apps: for each example, every claim of its app against the unpatched build and the build with its patch,
judged against what the class files show independently of the closure walk (which classes' bytes changed, and which
application classes each target's class refers to or may dispatch to).

Every check with `--cache` notes its own time with the cache, apart from the checker's (`search.seconds`): computing
the claim's key (both versions' closures, the harness's digest and the tools') and looking it up, a refuted hit's
replay included. The note is this run's even on an exact hit, whose report is otherwise the stored one. Each changed
helper's own check is timed in a note too. [`examples/tools/economics.py`](../examples/tools/economics.py) measures
what the cache saves on the recorded B9 and B11 examples of the javac apps. It runs a cold run, a warm rerun, and
runs after four kinds of change to each app (an unrelated edit, a behaviour-preserving helper rewrite, a
representation change, a real regression; [`examples/tools/economics/`](../examples/tools/economics/README.md)). For
each run it reports how each claim was served (an exact hit, nothing to prove, a changed helper's proof found or made
in the run, proved or refuted again), the checker's, the cache's, the helpers' and the remaining time, and whether
every warm verdict is the cold one. It is heavy, so it runs as a pipeline job.

## Limits

- The interpreter models a subset of the JDK. Code outside it is *unverifiable*, never wrong; the message names the method. JBMC's view of the JDK is narrower still: it gets six JDK classes (`Byte`, `Short`, `Integer`, `Long`, `Math`, `StrictMath`) and the tool's [models](models/README.md) of a few more (the boxing caches, `Character.digit`, `java.nio.charset`, `Enum`, `List.of` and `List.copyOf`), and treats every other JDK class as a stub with nondeterministic fields and results, so a class whose static initializer reads a JDK static the tool does not model, or a call into a JDK method it does not, can end in a `NullPointerException` or an arbitrary result the JVM never produces. The replay in the interpreter is the check that catches most of these (a witness the interpreter cannot reproduce is reported as unverifiable, not as a violation); the fix is a model. Enum `hashCode` is deterministic here (the constant's name hash) where a JVM's is identity-based, and `ClassCastException` messages omit the class-loader suffix a JVM adds.
- Regression proofs take a record only when every component is primitive (a record holding a `String`, an array or another record is refused with the reason, unless it is part of an object made by its constructor, step 5), compare a record result by its fields rather than by its `equals`, and relate a record of other components, or one the new version lacks, only through a constructor call given with `--before-arguments`, and a record result of other components only through a relation over the components given with `--results-agree-when` (without one, the tool proposes it). A record among the previous version's parameters is built from values, not from an array or another record. Property proofs (`prove`) are still over static methods, and over objects only those made by their constructor.
- The tool's own checker (`--engine native`/`auto`) covers methods over integers, arrays of them and records of them, without other objects or floating point; the rest is JBMC's, and under `auto` the hand-over is printed. It finds a violation fast and proves a property path by path, the paths merged where they meet and a solver call at most per branch, which is where JBMC's one formula can still win: the partitioner property of [example 023](../examples/023-abs-partitioner-sends-one-key-to-a-negative-partition/README.md) is a 32-bit remainder the checker proves in about 30 s and JBMC in a few. A division is left to the solver under cheap facts and built in full only where a model got it wrong, and a branch side the solver does not decide in the time its calls took so far is explored later, so the 64-bit remainders of the rate-limit kernels cost it fractions of a second; a multiplication is left to the solver likewise, and a quotient times its divisor is rewritten as the dividend less the remainder, so the identity of a 64-bit division and multiplication that was slow in both engines (examples 133 and 138) is its in a fraction of a second, where JBMC still does not finish in a minute. An array is a cell per index up to the bound, read by a choice among them and written by a conditional update of each, so a search over a short table (examples 140 and 141) is seconds for it where JBMC's formula over the symbolic array is a minute and two gigabytes.
- Regression and property proofs cover primitive parameters, arrays of primitives and straight-line arithmetic well, and get expensive with it: equivalence of two 64-bit multiplications with the overflow check behind `Math.multiplyExact` is proved in about ten seconds; a 64-bit division on each side can exhaust the solver, which is reported as *unverifiable*, unless the division is in a callee both versions call unchanged, which the proof takes as one function in both and the solver never sees ([example 120](../examples/120-retry-after-rewritten-around-unchanged-refill-helpers/README.md): a time-out at a minute becomes a proof in a second). Identities between a division and a multiplication (`(x / p) * p` against `x - x % p`, or the sum of `floorDiv` shares against the amount) are what JBMC's SAT backend cannot do in minutes; the tool's own checker rewrites the first (example 138) and leaves the second out of reach; state such properties as laws the solver can check by comparison, as the token bucket's are. Loops the unwinding bound does not cover are reported the same way.
- Arrays are bounded in length (`--max-array-length`), and what the SAT backend does with them is uneven: a regression proof runs both versions over the same symbolic arrays and so costs about twice a property proof of one, and `--unwind` drives the cost as much as `--max-array-length` does: two modified UTF-8 encoders ran out of memory at the defaults (8 and 16), but were proved equal in 94 seconds and 600 MB at 3 and 6, where a difference is found in five seconds (the proof at the defaults is the [own checker's](#the-tools-own-checker), [examples 142 and 143](../examples/README.md#tag-own-checker), in seconds); binary search over a sorted array of up to eight elements is proved in seconds, and so is an encoder writing into a buffer, but a quantifier that repeats a linear scan's comparisons (that the entry a scan returns is the first match, or that -1 means no match) did not finish in minutes even on four entries, eight writes at symbolic positions followed by a quantifier over the result take minutes where three take a second, and a method that allocates `new byte[n]` with `n` computed from the data never finished at all (give it the caller's buffer instead). A sum is cheap when the kernel accumulates in the order the property states it and exponential when it does not: a `Code` attribute length that adds the nested attributes' sizes into a total that already holds the fixed part took 80 seconds against `12 + codeLength + 8 * handlers + (\sum ...)` on four attributes and did not finish on six, while the same kernel summing the nested sizes first and adding the fixed part last is proved on eight in nine seconds (the SAT backend has no associativity; the two adder chains must be matched bit by bit). The witness elements of an array are not constrained by the small-inputs stage, which is what shrinking is for.
- Capability contracts stop at the module's own bytecode; what a library does with the calls made into it is the library's own contract.
- Boundary contracts read the annotations a class declares, not those it inherits from an interface or a superclass, and report a self-invocation only when the receiver is `this` loaded directly; the proxy checks assume Spring's defaults.
- `\old` applies to array parameters, which are the values a call can change; `\old(x)` of a scalar is `x`, and `result` has no pre-state. The copy it reads is taken in the harness, so a property with `\old` costs the solver the copy's stores, and a quadratic method under a quadratic quantifier (a sort, proved a permutation) needs the unwinding bound set to the arrays' bound plus one (`unwind:`) to finish in seconds rather than minutes.
- Throws clauses are matched in order, as Java's `catch` clauses are: declare a subclass before its superclass, or the superclass's handler takes the throw and the subclass's clause is reported violated. The declared class must be on the class path or in the JDK image; the exceptions JBMC models itself (`java.lang.Error`, `RuntimeException` and the common `java.lang` exceptions) are left to its models.
- The TLA+ operator generator assumes a contract of the shape `method(State, Input[...]) => Outcome[...]`, as a state machine over an enum and a sealed input type.

## Tests

```bash
cargo test --manifest-path lib/Cargo.toml
```

The unit tests need nothing. The integration tests compile the Java fixtures in [`tests/fixtures`](tests/fixtures) with `javac`; the regression tests also need `jbmc`, and the model-checking test needs TLC. A missing tool fails the tests that need it, so a passing run means they ran. To skip them instead, set `JVMCONTRACT_SKIP_MISSING_TOOLS=1`, and expect a passing run to prove less. The **conformance corpus** ([`tests/conformance.rs`](tests/conformance.rs), over [`Conformance.java`](tests/conformance/conformance/Conformance.java)) holds the tool to a real JVM rather than to itself, since the interpreter and the engines share models. Each case is a small method with claims about it: the gaps and their reproducers, identity and class initialization, exceptions, aliasing, `null` arrays, record constructors, dispatch, and arithmetic edge cases (`MIN_VALUE / -1`, negative remainders, shift counts out of range, narrowing). A [runner](tests/conformance/Runner.java) executes each case's calls on the JVM, each in a class loader of its own, and each claim's generated harness on them and on every witness an engine found. The test fails on: a call where the interpreter and the JVM disagree; a `Verified` under `--gaps strict` for a claim the JVM refutes, or one under `--gaps assume` that names no gap; a violation the JVM does not reproduce; and a native verdict other than the one recorded. JBMC, `--engine auto`, and `--engine auto --confirm` under strict and assume run the same corpus in an ignored test, `cargo test --release --test conformance -- --ignored`, which is a pipeline job; there a JBMC confirmation of a claim the JVM refutes fails the test, and so does a disagreement over one it does not. What `--confirm` does with each of JBMC's answers is tested inline, with a script standing in for JBMC. The conformance corpus is also the first group of the **benchmark corpus** ([`benchmark/`](benchmark/README.md), step 5a of the brief), with real regressions (a documented bug's broken and fixed versions) and held-out performance cases; `benchmark/run.py` runs each on both engines under each gap mode and keeps correctness, coverage, time and memory apart, with every expected answer and every witness checked on the JVM. [`tests/skill.rs`](tests/skill.rs) checks that every `jvmcontract` command the `verify-bytecode` skill names in code, and every option on it, is one the CLI accepts. Inside this repository they also derive the Box Office contracts and check that they are identical to the ones the Java tool committed, and that the generated TLA+ operator is identical to the one the Python generator wrote.
