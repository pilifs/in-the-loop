# jvmcontract

Formal verification of JVM bytecode, as *contracts* derived from the compiled code and checked in next to it.
The build fails when the code no longer matches its contract. A developer who changes behaviour on purpose regenerates the contract, and the pull request then shows reviewers exactly which behaviour changed, and only that.
Nobody writes a specification.

This is the Rust library and command line behind the [examples](../examples/README.md) of this repository.
It started as a port of the Java proof of concept in [`examples/tools/contracts`](../examples/tools/contracts/README.md) and the Python scripts around it, and goes further: it runs without a JVM, its purity proof is complete over the executed domain, it needs no Java compiler for its symbolic proofs, and it adds contract kinds and views the original did not have.

| Contract | For | The contract is | Proved by | Approach |
|---|---|---|---|---|
| **Behavioural** | A pure method with finitely many inputs (enums, booleans, records, sealed types), static or an instance method of such a type | The outcome of every input | Purity from bytecode, then every input executed in the built-in interpreter under an effect monitor | [B8](../examples/approaches.md#b8-behavioural-contracts-poc-in-toolscontracts) |
| **Regression** | A method with unbounded inputs (`long`, `int`, ...) | The previous version, outside the inputs the developer declares as changed | Both versions in one program, a generated bytecode harness, bounded model checking with JBMC, the counterexample replayed in the interpreter | [B9](../examples/approaches.md#b9-regression-verification-poc-in-toolscontracts) |
| **Property** | A method with unbounded inputs | A statement the developer makes about it, committed next to the code: a postcondition (`result >= baseMillis && result <= capMillis`) or a law (`result == merge(b, a)`) | A generated bytecode harness that assumes, calls and asserts; JBMC proves it over every input or finds one, replayed in the interpreter | [B11](../examples/approaches.md#b11-property-proofs-in-lib) |
| **Capability** | A module, or a dependency jar | Every JDK capability (clock, network, reflection, ...) and library its bytecode can reach | A closed-world walk over every call site | [B10](../examples/approaches.md#b10-capability-contracts-poc-in-toolscontracts) |
| **API** | A module | Every public type and member, with its exact signature | Read from the class files | |
| **Boundary** | A Spring Boot module | Where the framework enters it (routes, listeners, schedules, bean definitions), the advice on each bean (transactions, security, validation, caching, retries), the places where an annotation does not do what it says, the configuration keys (what the classes read, what `application.yaml` sets, what the class path's metadata declares, cross-checked), the wire types (the JSON shape of each request, response and message) and the stored types (the shape of each MongoDB document, with the query strings that name a field it does not have), and under each entry point what it reaches: the documents and tables it reads and writes, the topics it sends to, the HTTP calls it makes, the events it publishes | Read from the annotations in the class files and the application files, with a closed-world walk over the module's own calls | [B12](../examples/approaches.md#b12-boundary-contracts-in-lib) |
| **Protocol** | A distributed system | A TLA+ operator generated from a behavioural contract, inside a model checked by TLC | TLC, over every interleaving within bounds | [D1](../examples/approaches.md#level-d-distributed-systems) |

Every verdict is one of three. *Verified*: the code behaves exactly as its contract says, for every input. *Violation*: behaviour changed and the developer did not say so, with a concrete witness. *Unverifiable*: the tool refuses to give a verdict, because "we could not check" must never read as "fine".
Every verdict can be written as SARIF for GitHub code scanning and SonarQube.

## Install

```bash
cargo install --path lib          # from this repository: puts `jvmcontract` on your PATH
cargo build --release -p jvmcontract --manifest-path lib/Cargo.toml   # or just build it
```

It needs nothing else to derive behavioural, capability and API contracts: no JVM, no `javac`.
It reads the JDK's own class files from the `lib/modules` image of the JDK found through `JAVA_HOME` or `java` on the `PATH`, to know the shape of JDK types (a built-in table of `java.base` facts covers the common ones when no JDK is found).
Regression and property proofs need [JBMC](https://github.com/diffblue/cbmc) on the `PATH`, except where the tool's [own checker](#the-tools-own-checker) applies (`--engine native` or `auto`: methods over integers, arrays and records of them); the models of the JDK classes JBMC has no bytecode for ship with the tool ([`models/`](models/README.md)), and so does the SAT solver the checker uses (CaDiCaL, compiled by `cargo build`, which therefore needs a C++ compiler). Model checking needs TLC (`~/tools/tla2tools.jar`, `$TLA2TOOLS_JAR`, or `tlc` on the `PATH`); `$JVMCONTRACT_JAVA_OPTS` passes JVM flags to it, such as a heap size for `--coverage` on a large model.

Each JBMC run is limited to 3 GiB of address space, so a proof that runs away ends as "cannot be verified" rather than exhausting the machine. `JVMCONTRACT_JBMC_MEMORY_MB` changes the limit, and 0 turns it off. JBMC is read through `--json-ui` ([`src/jbmc.rs`](src/jbmc.rs)): its property results, the trace of the failed one, whose input values are read from their bits, and its overall `cProverStatus`. Only `success` with every property holding counts as a proof: a solver that gives up leaves no property failed and the status `error`, which is no verdict. Each run says how it ended, with the kinds of no verdict apart: an unwinding failure, another property failing, a timeout, memory exhausted, a kill, a solver failure, JBMC refusing the program, or output it cannot read. The console text was read before step 4b of `llm-dlc/loops/sound-verdicts.md`; that reader was removed once both readings had agreed on every run of every recorded JBMC example (88 runs, pipeline jobs 20261106-073804 and 20261106-123940).

JBMC's own approximations are gaps, in the same modes as the own checker's ([`src/jbmc_gaps.rs`](src/jbmc_gaps.rs), step 4c of the brief). Before JBMC's proof, the tool lists JBMC's goto program on the harness (`--show-goto-functions`, which converts what the proof would and solves nothing; `jbmc-goto.txt` in the work directory) and walks JBMC's own call graph from the harness. A method reached with no bytecode on JBMC's class path is JBMC's stub, which returns any value of its type (`null` or a new object for an object) and does nothing else: a JDK one has the own checker's id (`jdk-constructor:java.util.ArrayList.<init>(I)V@jdk-...`), any other is `missing-body`. An `invokedynamic` JBMC links to no class of its own making takes the value zero or `null` (`invokedynamic`: a string concatenation, a record's `equals`, `hashCode` or `toString`, a lambda for an interface JBMC has no class file of). And a method that synchronizes is a `monitor` gap, since JBMC drops monitor instructions, so `synchronized (null)` throws nothing there. The stubs JBMC's stub reproduces exactly (the constructors of `Object`, `Record` and the JDK's exceptions, and a JDK constructor that only calls one of them) are no gap, and nor are the stubs only a JDK class's initializer reaches, which the statement's engine assumption covers. Under `--gaps strict` a JBMC proof that reaches a gap is no verdict, and a counterexample stands when the interpreter replays it; under `--gaps assume` the verdict names each one (`assuming 1 behaviour JBMC does not implement`). Under `--gaps advised` JBMC applies the contracts for its gaps ([`src/jbmc_contracts.rs`](src/jbmc_contracts.rs)): a gap its program reaches with no contract stops the run with the advice, as the own checker's do, and each contract is checked (proved, tested on a JVM, or trusted, or the library's record) as for the own checker. JBMC applies one by running the same contract method: each call site of the gap, in the harness and the application's classes, is rewritten into a call of it (`jbmc-contracts/` in the work directory), and the intrinsics it calls are JBMC's `org.cprover.CProver` (`nondetInt`, `assume`), with an input outside the contract's `assume:` a failed property of its own, which is no verdict. A call site whose JDK method an application class overrides is left as it is, and its gap stays open. What no contract closes under JBMC (a monitor, an `invokedynamic`, a missing body outside the JDK) is listed in the advice as approximated whatever the contracts, and refused as under strict. `build.py` runs a recorded example JBMC proves in `assume` too.

## Commands

```bash
# Behavioural, capability and API contracts of a module, as a build step (exit 1 on any drift).
jvmcontract verify --contracts src/contract --classes build/classes/java/main \
    --sources src/main/java --base . --report build/reports/contracts --module ticketing-domain
jvmcontract update --contracts src/contract --classes build/classes/java/main --module ticketing-domain \
    --add 'net.example.OrderLifecycle#decide' --add capabilities --add api --add boundaries   # add contracts, or rewrite after an intended change

# One contract, printed (add --json for tooling, --cost for the execution cost).
jvmcontract derive 'net.example.OrderLifecycle#decide' --classes build/classes/java/main
# A target is `pkg.Class#method`; an overloaded method is named with its parameter types, in Java's spelling.
jvmcontract derive 'net.example.Pricing#discount(Tier, boolean)' --classes build/classes/java/main

# A regression proof between two builds, for a method whose inputs are not finite.
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.HoldPolicy#totalCents' \
    --unchanged-unless 'seats >= 8' --report build/reports/contracts
# The same for a method over arrays (symbolic, up to --max-array-length elements): what each version returns, throws
# and leaves in the arrays is compared, and the differing input is shrunk before it is reported.
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.Utf8#encodeInto'
# Across a signature change: the previous version, renamed or moved, is named, and its arguments are expressions
# over the new parameters; the proof is of new(x) against old(f(x)).
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.Writes#winner' \
    --before-target 'net.example.LastWriterWins#winner' --before-arguments 'tsA, nodeA, tsB, nodeB'
# A result that changed its type or meaning (a boolean that became the time left) is related to the previous one by
# a boolean expression over the new parameters, `previous` and `result`, which takes the place of equality.
jvmcontract equivalence --before base/classes --after head/classes --target 'net.example.Expiry#remainingNanos' \
    --before-target 'net.example.Expiry#isExpired' --results-agree-when 'previous == (result <= 0)'

# A property of one method, proved over every input, or refuted with a witness.
jvmcontract prove 'net.example.Backoff#delayMillis' --classes build/classes/java/main \
    --assume 'attempt >= 0 && baseMillis > 0 && capMillis >= baseMillis' \
    --assert 'result >= baseMillis && result <= capMillis && (attempt == 0 || result >= delayMillis(attempt - 1, baseMillis, capMillis))'
jvmcontract prove --properties src/contract/properties.contract --classes build/classes/java/main   # every property of a module, as a build step
jvmcontract prove 'net.example.LookupSwitch#find' --classes build/classes/java/main --max-array-length 8 \
    --assume '(\forall int i; 0 < i && i < matches.length; matches[i - 1] < matches[i])' \
    --assert '(result == -1 && (\forall int i; 0 <= i && i < matches.length; matches[i] != key)) || (result >= 0 && result < matches.length && matches[result] == key)'
jvmcontract prove 'net.example.StackMapTable#offsetOf' --classes build/classes/java/main \
    --assume '0 <= k && k < offsetDelta.length' \
    --assert 'result == k + (\sum int i; 0 <= i && i <= k; offsetDelta[i]) && (k == 0 || result > offsetOf(offsetDelta, k - 1))'   # a refuting input is shrunk before it is shown
jvmcontract prove 'net.example.Arithmetic#idiv' --classes build/classes/java/main \
    --throws 'ArithmeticException when divisor == 0' --assert 'divisor != -1 || result == -dividend'   # the exceptional path, proved with the normal one
jvmcontract prove 'net.example.Backoff#delayMillis' --classes build/classes/java/main --engine auto \
    --assert 'result >= 0'   # the tool's own checker where the method is over integers, JBMC elsewhere (--engine native: the tool's own only)
jvmcontract prove 'net.example.Pool#size' --classes build/classes/java/main --engine native \
    --assert 'result > 0' --gaps assume   # a JDK call the own checker does not implement (a gap) is assumed and named in the verdict, not refused

# A capability contract of each dependency, from the jars.
jvmcontract capabilities --each build/libs/*.jar

# The boundary contract of a Spring Boot module: routes, listeners, schedules, bean definitions, the advice on each
# bean, the `!` lines where an annotation does not do what it says (a @Transactional method called on `this`, advice
# on a private or final method, a checked exception that commits, an @Async result lost), the configuration keys
# (what the classes read, what application.yaml sets, what the dependencies' metadata declares, with `!` lines for a
# key nothing binds, a deprecated key and a value of the wrong type), the wire types (the JSON shape of each
# request, response and message, as Jackson encodes it), the stored types (the shape of each MongoDB document,
# with a `!` line for a query, update, index or sort string that names a field the document does not have) and,
# under each entry point, what it reaches: `reads`, `writes`, `sends`, `calls`, `publishes` (a GET that writes is a `!` line).
jvmcontract boundaries build/classes/java/main --classpath "$(./gradlew -q :ticketing-service:printRuntimeClasspath)" \
    --resources src/main/resources --module ticketing-service

# The protocol model: a TLA+ operator from a contract, then TLC.
jvmcontract tla src/contract/OrderLifecycle.decide.contract spec/OrderLifecycleContract.tla
jvmcontract tlc spec/BoxOffice.tla --json
jvmcontract tlc spec/ClassInit.tla --deadlock    # also report a reachable state in which no action is enabled
jvmcontract tlc spec/TwoPhaseCommit.tla          # the configuration's PROPERTIES (liveness, refinement) are checked after the invariants
jvmcontract tlc spec/RaftElection.tla            # an action property [][A]_v among them is reported by name, with the run up to the offending step
jvmcontract tlc spec/RaftElection.tla --config spec/RaftElectionInductive.cfg   # another configuration of the same model: here INIT is an invariant, and a counterexample is one step from a state it admits
jvmcontract tlc spec/RaftElection.tla --coverage   # and what the verdict rests on: the rows of each generated operator a step of the model takes, and the rows none does

# Views: the state machine a contract describes, a class file's structure, and the models of the JDK the proofs use.
jvmcontract statemachine src/contract/OrderLifecycle.decide.contract --format mermaid
jvmcontract inspect build/classes/java/main/net/example/OrderLifecycle.class --code
jvmcontract models                               # what is modelled and why; --write DIR writes the class files out

# The gaps of the tool's own checker a method reaches: what it approximates rather than implements, found from the
# bytecode alone (a JDK constructor or instance method, a class initializer, a string conversion), each with a
# stable id; add --json for tooling.
jvmcontract gaps --classes build/classes/java/main --target 'net.example.Pricing#total'
# The own checker's solver calls, recorded (any command; one file per check) and run again on the bundled CaDiCaL.
JVMCONTRACT_TRANSCRIPTS=build/transcripts jvmcontract equivalence --engine native ...
jvmcontract transcript build/transcripts/4711-1.icnf    # --json for every call; exit 1 if an answer differs
jvmcontract transcript --solver bitwuzla build/transcripts/4711-1.icnf    # the same calls on Bitwuzla
```

The contract file formats are those of the Java tool, so existing contracts verify unchanged, and `verify`/`update` take the same options as the Java tool's `Main`, so the [`boxoffice.contracts`](../examples/apps/boxoffice/build-logic/src/main/kotlin/boxoffice.contracts.gradle.kts) Gradle plugin can run either. A Gradle task for the Rust tool is an `Exec`:

```kotlin
tasks.register<Exec>("verifyContracts") {
    group = "verification"
    dependsOn("classes")
    commandLine("jvmcontract", "verify", "--contracts", "src/contract", "--module", project.name,
        "--classes", sourceSets.main.get().output.classesDirs.asPath,
        "--sources", "src/main/java", "--base", rootDir.path, "--report", layout.buildDirectory.dir("reports/contracts").get().asFile.path)
}
tasks.named("check") { dependsOn("verifyContracts") }
```

## How a behavioural contract is proved

The contract of [`OrderLifecycle#decide`](../examples/apps/boxoffice/ticketing-domain/src/main/java/net/terminalvalue/boxoffice/ticketing/domain/OrderLifecycle.java) is [36 lines](../examples/apps/boxoffice/ticketing-domain/src/contract/OrderLifecycle.decide.contract): every (status, input) pair and what the method does with it.
The tool derives it in three steps, each of which can refuse, and a refusal fails the build:

1. **Purity, from bytecode** ([`purity`](src/purity.rs)). It walks every application method the target can reach, following virtual calls through sealed hierarchies and rejecting calls whose implementations it cannot enumerate. It rejects writes to static fields, reads of mutable static fields, writes to fields outside constructors, native methods, and any JDK call outside the short list in [`trusted.rs`](src/trusted.rs). That list is the trusted base, and each run prints the entries it relied on.
2. **A finite domain, from types** ([`domain`](src/domain.rs)). Enums, booleans, records of finite types and sealed interfaces have finitely many values. Each reference parameter also takes `null`.
3. **Execution of every input** ([`interp`](src/interp/mod.rs)). A pure method with finitely many inputs is fully described by its outcomes on all of them. The interpreter executes the application's bytecode as written and models the JDK natively; it has no clock, no randomness and no I/O, so every execution is deterministic by construction.

The interpreter carries a **dynamic effect monitor**. Every heap object remembers the epoch it was allocated in, and a write to an object from an earlier epoch (an argument, an enum constant, a static array) stops execution and makes the verdict *unverifiable*. Because the domain is executed completely, this check is a complete proof that the method changes nothing that existed before the call, which closes the gaps a static analysis leaves: the Java tool documented that stores into arrays and collections passed in were not tracked; here they are caught. The static analysis remains the first step, because it refuses early with a precise message, and because its trusted list is what a reviewer audits.

Anything the interpreter does not model stops execution with an *unverifiable* verdict rather than a guess. The model covers what pure domain code uses: strings and `StringBuilder`, boxed primitives, `Math`, `Objects`, `Optional`, immutable and mutable collections, enums, records (including the generated `equals`, `hashCode` and `toString`), exceptions with the messages the JDK gives them, string concatenation, pattern-matching `switch` over sealed types and enums, lambdas and method references. Locale-dependent methods (`String.format`, `toUpperCase(Locale)`), regular expressions, streams and reflection are outside it.

On the Box Office domain module, deriving the 36-case contract takes about 15 milliseconds, JDK image included (only its index is read; classes are fetched on demand). The Java tool needed a Gradle build and a JVM start.

## How a regression proof works

[`HoldPolicy#totalCents(long, int)`](../examples/apps/boxoffice/ticketing-domain/src/main/java/net/terminalvalue/boxoffice/ticketing/domain/HoldPolicy.java) has 2^96 inputs. The statement proved is "the new bytecode behaves as the old bytecode on every input, except the inputs the developer declared as changed":

1. The old classes are copied into a `before` package by rewriting their constant pools ([`relocate`](src/relocate.rs)), so both versions load side by side.
2. A harness class is **generated directly as bytecode** ([`harness`](src/harness/mod.rs)): it calls both versions on the same arguments, catches what each throws, and asserts that the results and exception types agree. An array parameter is copied first, exactly as long, so that the version before writes into the copy and the version after into the array, and the two are compared element by element after the calls, as an array result is; two `NaN` results count as agreeing. The `--unchanged-unless` expression is parsed and type-checked with Java's rules ([`harness::expr`](src/harness/expr.rs)) and compiled into the harness, so no Java compiler is needed; JML's quantifiers may range over an array parameter in it. A statement that skips inputs before the calls (a scope, a record whose constructor may reject an input, previous-version arguments that may throw) may skip every input in the domain, and a scope every input satisfies, or one over an array's length that the bound on the arrays never reaches (`matches.length <= 8` at the default bound of eight), is proved vacuously: the verdict is still *verified*, since the statement is true, and a line `vacuously: no input in the domain reaches the calls, ...` says it covers nothing. The tool finds this by proving a probe, the same harness with the two calls replaced by the assertion's failure, with its own checker (an input that reaches the calls violates the probe), whichever engine proved the statement; `prove --assume` is probed the same way ([examples 144 and 145](../examples/README.md#tag-vacuous-proof)). The probe's answer is a status in the statement (`stated.vacuity`): `non-vacuous`, with the probe's witness under a line `not vacuous: f(...) reaches the calls`; `vacuous`; or `unknown`, with a line `vacuity unknown: ...` naming why the probe gave no verdict (a gap the own checker refuses in a record's constructor, a timeout). A statement that skips no input before the calls is `non-vacuous` by the harness, and identical bytecode by being identical. Only a *verified* statement has a status, and a vacuous or unknown one still exits 0. A statement over a record built through its constructor says, in a line `constructors: ...` and among its assumptions, that it is about the records both versions' constructors accept: whether the constructors accept the same inputs is another obligation, which this proof does not discharge. The previous version need not have the target's name or parameters: a method renamed or moved is named with `--before-target`, and one whose parameters were reordered, added, removed or retyped is called with the arguments `--before-arguments` gives, expressions over the new parameters (`tsA, nodeA, tsB, nodeB` for a reordering, `start, (int) (end - start), failed` for a size that became an end offset, an array passed by name), compiled into the harness in the same way; the statement proved is then "new(x) agrees with old(f(x))" for the stated relation, and the report shows a counterexample as both versions received it ([example 121](../examples/121-tie-break-parameters-grouped-by-kind-proved-under-the-reordering/README.md)). An input for which an argument expression throws (a division by zero) is outside the relation and skipped, as an input in the scope is. A result that changed its type or meaning is related to the previous one by `--results-agree-when`, a boolean expression over the new parameters, `previous` (the previous version's result) and `result` (the new one's), which takes the place of equality whenever both versions return (`previous == (result <= 0)` for a boolean that became the time left, `result == previous * 1000L` for seconds that became milliseconds); the versions must still throw alike, and a relation that throws on a pair of results does not hold ([examples 122 and 123](../examples/README.md#tag-signature-change)). Without it, differing return types are refused. The same statement is written out as Java source for readers.
3. The two versions' bytecode is compared before any solver runs ([`shared`](src/shared.rs)). A target identical in both, together with everything it reaches (constant pool references resolved, so renumbering does not count), is verified with nothing to prove. A callee both versions call unchanged, that is a pure function of its primitive arguments (no fields, no arrays, nothing of the JDK beyond its arithmetic and the building of an exception), is taken as *one function in both versions*, as relational verification does with an uninterpreted function: a generated stub class keeps a memo table per such callee, giving arguments seen before the outcome they got and new arguments an arbitrary one, a result or an exception of a type the callee can throw, and the call sites of both versions are redirected to it. The solver then relates how the two versions use the callee and never its arithmetic, which is what makes a refactor around a 64-bit division cost a second instead of a time-out. The abstraction is sound for a proof, since the stub behaves as every function the callee could be; a counterexample found with it is replayed through the bytecode as written and, when it does not reproduce, the proof is run again with the callees as written. A callee of a few instructions without a loop, a multiplication, a division or a remainder (`Math.min`, `Math.abs`) is computed as written in both versions rather than shared: as one function its result on different arguments in the two versions is unconstrained, so a counterexample through it rarely reproduces and the rerun costs more than the comparison it stands for. `--no-shared-callees` skips both.
4. JBMC turns the harness into a satisfiability problem over bit-vectors ([`jbmc`](src/jbmc.rs)). Small inputs are searched first so that a counterexample is readable (`[0:20]`, then `[-100000:100000]`); the last stage is the proof over the whole domain. A stage runs only where its interval leaves out a value of some primitive input of the harness: JBMC's `--java-assume-inputs-interval` does not bound the elements of an array, so a harness over arrays alone runs once, and one over bytes skips the second stage ([`deadline`](src/deadline.rs)). The whole check, the own checker and JBMC's stages and fallback and the vacuity probe, has one deadline, `--timeout`: a preliminary stage gets at most an eighth of it and hands on to the next when that runs out, the own checker under `--engine auto` gets all but the quarter kept for JBMC, and the last stage what is left. `--confirm` is a second check with a deadline of its own. The real bytecode of `java.lang.Math`, `StrictMath` and the integer wrappers (`Integer`, `Long`, `Short`, `Byte`), taken from the JDK image, is on JBMC's class path, so `Math.multiplyExact` and `Integer.numberOfLeadingZeros` are analysed as written.
5. A method of a record whose components are primitive, or one that takes or returns such a record, is proved on the components ([`harness::Layout`](src/harness/mod.rs)): they are the harness's symbolic parameters, named `this.component` for the receiver's and `other.component` for a parameter's (a scope may write the receiver's as the method does, `baseMillis`), the record is built from them in each version through its canonical constructor, an input a constructor of either version rejects is outside the statement (the record's invariant is where the proof is), and a record result is compared component by component, read from the fields. The witness is written as Java prints a record, `delayMillis(this=Backoff[baseMillis=1, capMillis=1], attempt=-1)`. A target identical in both versions needs no proof only when the records' constructors are too, since the harness builds the receiver through them. A static method that became a method of a record, or took one as a parameter (the components it took gathered into a record), is related to its previous version with `--before-arguments` over the components, `this.start, this.size, failedIndex`: the record is built in the new version only, the previous version gets the components, and the proof is of `new Batch(s, n).offsetToCommit(i)` against `offsetToCommit(s, n, i)` on every input the record's constructor accepts. A record the previous version takes that the new version has no record of the same components for is built from the new parameters by a constructor call among the expressions, the receiver's first: a record that gained, lost or retyped a component is related with `--before-arguments 'new Backoff(this.baseMillis, this.capMillis), attempt'`, a record's method made static with `'new Window(lo, hi), x'`, and a record parameter of other components with `'new Batch(batch.start, batch.size), failedIndex'`. The previous record is built under `before/` inside the same handler, so an input its constructor rejects is skipped as well; the report reads `behaves as the previous delayMillis(attempt) on new Backoff(this.baseMillis, this.capMillis)`, and a witness shows both versions as they received the input, `delayMillis(this=Backoff[baseMillis=1, capMillis=2, multiplier=2], attempt=-1), previously delayMillis(this=Backoff[baseMillis=1, capMillis=2], attempt=-1)`. The refusals for a record of other components or a receiver the new version lacks print the constructor call to give.
6. A counterexample is shrunk in the interpreter, running the harness class JBMC checked on smaller inputs ([`shrink`](src/shrink.rs)), then replayed through both versions, and the two observed outcomes, with what each version left in an array it changed (`1, leaving a=[0, 0]`), are what the report shows ([`witness`](src/witness.rs)). A counterexample the interpreter cannot reproduce (both versions agree on it) is reported as *unverifiable*, not as a violation: it means JBMC had no bytecode for a method the target calls (one outside its models and the class path above, such as `Float.compare`, whose `floatToRawIntBits` is native) and treated it as returning an arbitrary value.
7. `--json` prints the outcome instead of the report: the verdict, the domain, the proof line, the problem, the vacuity, the statement's path, the counterexample (its input, what each version did, the raw values, the input as found before shrinking and the interpreter runs the shrinking took, and the witness as data: `inputs`, each with its Java type and an exact value, a `long` as a decimal string and a `float` or `double` as Java's `toString` of it; `call`, the new version's class, class file, method descriptor, receiver as a record of its components and arguments, each naming the input it is `from`; `previous_call`, the previous version's, whose arguments under `--before-arguments` name the expression that computed them; and `found_inputs` before shrinking), the callees shared and the previous version's call. `search` is the checker run the verdict comes from: the engine (`jbmc` or `native`), the checker, the seconds, the unwinding and array bounds, the input range it ran over (`[0:20]`, or none for the whole range), why the own checker gave no verdict before JBMC ran under `--engine auto`, and the own checker's numbers (paths, merges, solver calls, the divisions and multiplications built in full), the gap mode it ran under (`gap_mode`) and the gaps it met (`gaps`: each one's id, kind, call, sites, the approximation `--gaps assume` takes, and whether it was `refused` or `assumed`), under `--confirm` what JBMC made of the own checker's proof (`confirmation`: a `status` of `confirmed`, `disagreed`, `no-verdict` or `not-asked`, the checker, its seconds and the reason), the check's deadline (`deadline_seconds`), and every checker run of the check in order (`runs`: each one's checker, its `purpose`, `proof`, `fallback`, `shared`, `as-written` or `probe`, its input interval, its budget and seconds, and how it `ended`: `verified`, `violation`, `no-verdict`, or `out-of-time`, with the checker's own `ending`: `verified`, `counterexample`, `unwinding-failure`, `other-failure`, `timeout`, `memory-exhausted`, `killed`, `solver-failure`, `unsupported-input`, `unavailable`, `unreadable`, or the own checker's `no-verdict`; and where its seconds went, `phases`, the same for both checkers: `loading`, `lowering`, `symbolic`, `encoding`, `solving`, `trace` and `other`, with the `formula` it solved, JBMC's SSA `steps` and `conditions` and the `variables` and `clauses`, [`src/phases.rs`](src/phases.rs)), and the check's own steps around them (`phases`: the setup of the work directory, the harness, the gap scans and JBMC's preflights, the contracts, the replay and shrinking, the JVM witness run, and the rest). `replay` says where the witness was run again on both versions, `interpreter` (this crate's interpreter, not a JVM), and whether that reproduced the difference. `stated` is the statement the verdict is about, as data ([`src/statement.rs`](src/statement.rs)): a regression proof's ∀x ∈ D, A(x) ⇒ Obs(old, x) = Obs(new, x) (a property's likewise). The `domain` gives each parameter with its kind (`primitive`, `array`, or `record` with its components), whether `null` is among its values and an array's longest length, and whether two arrays may be one (`shared_arrays`: never today). Each of the `assumptions` has a `kind`, its text and a `basis`: `stated` by the claim (`--unchanged-unless`, `--assume`), made by how the `harness` builds the statement (an input a record's constructor rejects, or on which `--before-arguments` throws, is skipped), the checker's `engine` semantics (the own checker takes every JDK class as initialized; JBMC stubs a JDK method it has no bytecode for), or a gap `assumed` under `--gaps assume`, with its id. Then the `observations` (what is compared of the result and of an exception, and which arrays are compared after the call), the `bounds` (the unwinding bound, the array bound, and whether the search was `complete`), the `models` (whether the tool's models were read, the `sha256:` digest of the bundle, and the JDK's version), the `checker` with its SAT solver and any fallback, the `gap_mode`, and the `confirmation` status. Two verdicts whose proof lines read alike but whose statements differ differ here. The console report is in `output`.
8. `--details` (on `equivalence` and `prove`) writes what `--json` holds as `stated` and `search` under the verdict, for a person: the statement (its domain, each assumption with its basis, what is observed, the bounds, the models, the checker with its solver and gap mode, the confirmation and the vacuity), and where the time went (the check's total, the driver's steps, and each checker run with its purpose, stage, seconds, ending, the share of each phase and the formula's variables and clauses). [`src/details.rs`](src/details.rs) renders it; the default report is unchanged.

`--jbmc PATH` may be relative to the current directory: it is made absolute before JBMC runs in the work directory. A bare name is looked up on `PATH`.

## How a property proof works

A regression proof says "as before". A property proof says what the method guarantees, in the developer's words, and keeps it true. The statement is a Java boolean expression over the method's parameters, its `result`, and the method itself, committed next to the code in [`properties.contract`](../examples/apps/quorum/src/contract/properties.contract):

```
net.terminalvalue.quorum.replication.LastWriterWins#winner
  assume: tsA != tsB || nodeA != nodeB
  assert: result == 1 - winner(tsB, nodeB, tsA, nodeA)
```

1. The harness ([`harness::generate_property`](src/harness/mod.rs)) is generated as bytecode: return if the assumption is false, call the method once on symbolic arguments, catch anything it throws, and assert that it threw nothing and that the assertion holds. A call of the method inside the assertion is compiled to an `invokestatic`, which is how commutativity, idempotence, monotonicity or antisymmetry are stated; a boolean method with no assertion given is its own property (it must return `true`).
   A method that throws by design declares it, as JML's `signals` clause does: `throws: ArithmeticException when divisor == 0` (`--throws`, repeatable) says that the method throws that exception, or a subclass, exactly on the inputs where the condition holds, and that elsewhere it returns and the assertion holds. The harness computes which clause applies before the call and catches the declared class before the generic ones, so the exceptional path is proved with the normal one instead of being assumed away; a declared JDK exception JBMC has no model of (`ClassFormatError`) is taken from the JDK image with its superclasses. A void method's property can be its throws clauses alone. A refutation says what the clause required of the input: the declared exception, or a normal return.
2. JBMC proves the harness or finds an input, small values first ([`property`](src/property.rs)); the input is replayed in the interpreter and the report shows the method's result or exception on it. As for a regression proof, an input on which the replay finds the property holding is reported as *unverifiable*: a called method was missing from JBMC's class path.
3. The input JBMC found is whatever satisfied the solver, an eight-element array of nine-digit numbers as often as not. Before it is reported it is **shrunk** ([`shrink`](src/shrink.rs)): the generated harness class is run in the interpreter on smaller inputs, dropping array elements and moving numbers towards zero (by powers of two, the largest first, one scalar at a time and then every scalar of a sign together, for an end tied to a length) while the property still fails, until no single step keeps it failing. The witness on the page is that local minimum, the same on every run; the report also gives the input as JBMC found it and how many interpreter runs the shrinking took. `--no-shrink` reports JBMC's input as is.
4. `prove --properties FILE` proves every block of a module's file and exits 1 if any is violated or cannot be verified, so the properties are a build step like the contracts. Each block gets its own work directory, `property-N` in the order of the file, when there are several. `--json` prints a list of the outcomes, one per block: the verdict, the assumption, the assertion as checked, the throws clauses as given and as checked (`throws_checked`, each exception named in full), the domain, the proof line, the problem, the vacuity, the statement's path, the counterexample (its input, the method's outcome, what a throws clause required instead, the input as found before shrinking and the interpreter runs the shrinking took, and its `inputs`, `call` and `found_inputs` as for a regression proof), `search` and `replay` as for a regression proof, and the console report in `output`. A witness's `replay.reproduced` is false when the property calls the method under proof, since only the harness can evaluate it there, so the violation is the checker's word.

An array parameter of an integral or boolean element type (`int[] matches`, `char[] chars`, `byte[] out`) is a symbolic array: every length up to a bound (`--max-array-length`, 8 by default, or `arrays: N` in the property's block), every content, never `null`, and never the same array as another parameter, in both engines (JBMC under `--java-assume-inputs-non-null`). The domain line says so, `a: int[] of length ≤ 8, not null`, ending `; no two the same array` when there are two or more, since a claim the JVM refutes only on a `null` or on one array passed twice is outside it. The property reads it as `matches.length` and `matches[i]`, and quantifies over it in JML's syntax, `(\forall int i; 0 <= i && i < matches.length; matches[i] != key)` and `(\exists int i; ...; ...)`, where the range must bound the variable below and above and any further conjunct filters. A quantifier is compiled to a loop in the harness, which JBMC unwinds, so the bound on the array is the bound on the proof: the search above is proved correct on every sorted table of up to eight pairs and every `int` key in a few seconds. A `result` that is an array is read the same way, and an array parameter is read *after* the call, so a method that writes into a buffer is held to what it wrote. A witness shows the arrays, shrunk, and the array a method left behind when it changed one. An array parameter is also passed by name to a call of the method under proof, `offsetOf(offsetDelta, k - 1)`, which is how a law about the previous element is stated. What the method changed is stated against what it received with JML's `\old`: `\old(out[i])` is the element before the call, from a copy the harness takes first, so `(\forall int i; result <= i && i < out.length; out[i] == \old(out[i]))` is a frame condition, the bytes past what the encoder wrote are as they were, and `(\forall int i; 0 <= i && i < keys.length; (\exists int j; 0 <= j && j < keys.length; keys[j] == \old(keys[i]) && offsets[j] == \old(offsets[i])))` says that an in-place sort is a permutation that keeps each offset with its key. The copy is as long as the bound on the arrays rather than the array's own length, which costs the solver thirty times less; `\old(a)` passed to a call gets an exact copy. A block of `properties.contract` may also set `unwind: N`, the loop unwinding bound for that property: a sort of four pairs and the pairing quantifier are both quadratic, and the proof takes fifteen seconds unwound five times where the default sixteen takes minutes.

JML's generalized quantifiers fold a value over the range instead: `(\sum int i; 0 <= i && i <= k; offsetDelta[i])` adds (an `int` or a `long`, wrapping as Java's arithmetic does, so write `(long) a[i]` for a long sum of ints), `\num_of` counts the indices for which a boolean body holds, and `\max` and `\min` take the extreme of a numeric body, with JML's values over an empty range (0, 0, the type's smallest and its largest). They nest: `max_stack` is `(\max int k; 0 <= k && k <= delta.length; (\sum int i; 0 <= i && i < k; delta[i]))`, the largest prefix sum, and that is a property [Mica](../examples/apps/mica/README.md) proves of its assembler in about twenty seconds.

The five properties of the [Quorum](../examples/apps/quorum/README.md) module (quorum intersection, backoff bounds and monotonicity, the hybrid logical clock's monotonicity and symmetry, last-writer-wins antisymmetry) are proved in about four seconds in all, and the seven of [Crosscut](../examples/apps/crosscut/README.md) (a Kafka partitioner and batch commit, a retry policy, a JWT validator's skew, a token bucket's refill, a cache's expiry) in about forty, and the sixteen of [Mica](../examples/apps/mica/README.md) (`idiv` and `irem` at `Integer.MIN_VALUE / -1` and their `ArithmeticException` on zero, the exception table's `ClassFormatError` on a malformed entry, modified UTF-8's zero-free bytes and the encoder that writes them and leaves the rest of the buffer alone, a `lookupswitch` bisection within the sizes a `Code` attribute allows and its full correctness on every sorted table, the sort of a `lookupswitch`'s pairs as a permutation, the exception table's handler lookup, a power-of-two table size, the stack map frame offsets with their `+ 1`, the length of a `Code` attribute, constant pool numbering around a `long`, and `max_stack` as the largest prefix sum) in about a minute and a half, most of it the three sums and the sort. A property-based test states the same theorem and samples it; here the solver covers the domain, which is how [example 015](../examples/015-rounded-half-is-not-a-majority/README.md) catches `(n + 1) / 2` at `n = 2`, [example 016](../examples/016-backoff-cleanup-overflows-into-a-negative-delay/README.md) catches an overflow forty attempts in, [example 023](../examples/023-abs-partitioner-sends-one-key-to-a-negative-partition/README.md) catches `Math.abs(Integer.MIN_VALUE)`, and [example 034](../examples/034-idiv-overflow-check-throws-where-the-jvm-returns-min-value/README.md) catches an `idiv` that throws on the one input the specification says must not, and [example 054](../examples/054-exception-table-check-that-rejects-a-range-ending-at-code-length/README.md) catches a class file check that rejects a handler covering the last instruction, on the exceptional path a throws clause brings under the proof, and [example 055](../examples/055-encoder-that-zero-terminates-into-the-callers-buffer/README.md) catches an encoder that writes one byte past what it returns, against a frame condition in `\old`.

## How a boundary contract is checked

A Spring Boot service is mostly boundaries. The framework calls into it through annotations (`@GetMapping`, `@KafkaListener`, `@Scheduled`, `@EventListener`, `@Bean`), and what it promises to do around each call is an annotation too (`@Transactional`, `@PreAuthorize`, `@Valid`, `@Cacheable`, `@Async`, `@Retryable`), applied through a proxy that stands in front of the bean.
None of this is in the code's control flow, so none of it is in a unit test, and a guard that is dropped, a route that widens or a rollback rule that changes shows up in production first.

[`boundaries`](src/boundaries.rs) reads the `RUNTIME` annotations from the class files ([`classfile::annotations`](src/classfile/annotations.rs)) and writes them out as a contract: one block per bean with its stereotype, one line per entry point with its route composed from the class and method mappings (`POST /orders/{id}/cancellation (consumes application/json)`), the handler's signature with its parameter annotations and generic types, and the advice on it as indented lines.
Only the annotations of framework packages are read (Spring, Jakarta Validation and Transactions, Resilience4j, Micrometer); a class without one is not a boundary.

It then checks what the framework will do with each annotation, and records what it finds as `!` lines of the same contract:

- **self-invocation**: a method with proxied advice called on `this` from the same class, directly or from a lambda. The call never reaches the proxy, so the transaction is not started, the authorization is not checked, the cache is not consulted. The receiver is found by walking back over the argument expressions in the bytecode; a call on another instance of the class is not reported, because that instance is a proxy.
- **not proxied**: advice on a private, static or final method, or on a method of a final class, which the CGLIB proxy cannot intercept.
- **commits on a checked exception**: a `@Transactional` method that declares a checked exception its `rollbackFor` does not name. Spring rolls back on unchecked exceptions only; the declared one commits. The class hierarchy comes from the class path and the JDK image.
- **a lost `@Async` result**, a `@Cacheable` method returning `void`, a `@Scheduled` method with parameters, and **constraints that are never enforced**: `@Min`, `@NotBlank` and the like on the parameters of a method that is neither a request handler nor on a `@Validated` bean, or on a non-public method of one (method validation goes through the proxy).
- **a request body whose constraints do not run** ([`validation`](src/validation.rs)): a `@RequestBody` whose type carries constraints, taken without `@Valid` or `@Validated`; and a `@Valid`, which validates the `Default` group, or a `@Validated(G.class)`, which validates `G` and the groups it extends, on a body with constraints in other groups, named on the handler's line.
- **a parameter that cannot bind to the request** ([`binding`](src/binding.rs)): a `@PathVariable` whose name (the annotation's, else the parameter's) is a variable of no template of its route (`! @PathVariable id matches no variable in /holds/{holdId}: MissingPathVariableException, a 500 on every request`); a `@PathVariable`, `@RequestParam`, `@RequestHeader`, `@CookieValue` or `@MatrixVariable` with no name of its own on a parameter whose name the compiler did not record (no `MethodParameters` attribute, which `javac -parameters` writes; Spring 6.1 reads nothing else, so the request fails with a 500); a `required = false` binder with no `defaultValue` on a primitive, which cannot be null when the request leaves it out; two `@RequestBody` parameters; and **two handlers on one route**, found across the module: the same route on two methods, which Spring refuses at startup, and the same pattern under different variable names (`/tasks/{id}/owner` and `/tasks/{key}/owner`), which both match every such request with the same specificity, so Spring throws an ambiguity for it. None of these is a compile error, and only the duplicate route stops the context; the rest are a 500 on every request of the route, which the unit tests of the service do not make.
- **an exception nothing turns into a response** ([`failures`](src/failures.rs)): under each route, `throws` lists the exceptions it can throw (the `throw` statements, `orElseThrow` suppliers and Spring `Assert` calls in everything it reaches, less what a `catch` on the path takes without rethrowing) and what each becomes: the `@ExceptionHandler` that takes it (the controller's own first, then the `@ControllerAdvice` beans in `@Order`, the closest type within one) with the status it answers (`NotFoundException (404 by ApiErrors.notFound)`), the `@ResponseStatus` on the exception's class, the status a `ResponseStatusException` was built with, or `(500)`. An exception type of the module's own that nothing maps is a `!` line (`! throws HoldExpiredException: no @ExceptionHandler takes it and it carries no @ResponseStatus, so the response is a 500`); a JDK or framework exception that reaches the boundary is listed as a 500 without one, since a guard that fired is a 500 by design. Two `@ExceptionHandler` methods for one type in one advice are a `!` line too: Spring refuses the ambiguity at startup. A listener, a schedule or a bean method gets its `throws` line without outcomes: its container's error handler decides, and that configuration is not read.

Introducing one of these changes the contract, so the pull request shows it; fixing it changes the contract back. `verify` reports a difference as `boundaries-changed`, anchored to the first added member's source line.

After the beans comes the **activation** block ([`activation`](src/activation.rs)): what switches each kind of annotation on. `@Scheduled` runs only under `@EnableScheduling`, `@Async` under `@EnableAsync`, `@Cacheable` under `@EnableCaching`, `@PreAuthorize` under `@EnableMethodSecurity` (`@Secured` and `@RolesAllowed` need its `securedEnabled` and `jsr250Enabled`), `@Retryable` under `@EnableRetry`, an `@Aspect` under `@EnableAspectJAutoProxy`; `@Transactional`, `@KafkaListener`, `@RabbitListener`, `@JmsListener` and method validation are switched on by Spring Boot's auto-configuration when its conditions hold, `@Timed`, `@Counted` and `@Observed` by the aspect beans the AspectJ weaver makes possible, and `@Valid` by a Bean Validation provider on the class path. Without the switch nobody reads the annotation: the code compiles, the context starts, and every test that does not depend on the advice passes. The block's header names the application class and the packages it scans; each family the module uses is a line naming what enables it and how that configuration is reached (`@Scheduled: @EnableScheduling on net.terminalvalue.boxoffice.messaging.MessagingConfiguration, imported by TicketingApplication`, `@KafkaListener: @EnableKafka on KafkaAnnotationDrivenConfiguration.EnableKafkaConfiguration, auto-configured`, `@Valid: Bean Validation provider org.hibernate.validator.HibernateValidator in hibernate-validator-9.1.3.Final.jar`), and a family nothing enables is a `!` line with the nearest miss when there is one: a class that carries the switch but is not a component, a configuration outside the scanned packages, or an auto-configuration whose condition fails (`! no TimedAspect bean on a configuration in scope (MetricsAspectsAutoConfiguration defines one, but org.aspectj.weaver.Advice is not on the class path): no timer is recorded`). The configurations in scope are the local components in the scanned packages (the application class's own and its `scanBasePackages`), the classes of the class path in those packages, the `@Import`s of each, their nested configuration classes, and the auto-configurations the class path's `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` files and `spring.factories` list minus the application's `exclude`s, with `@ConditionalOnClass`, `@ConditionalOnMissingClass`, `@ConditionalOnResource` and `@ConditionalOnWebApplication` evaluated against the class path. Meta-annotations are followed, so `@Service` is a `@Component` and a composed annotation of the application's own that carries `@EnableAsync` counts.

After it comes the **configuration** block ([`config`](src/config.rs)): the module's keys, cross-checked three ways. The classes say what they read: `${key}` and `${key:default}` placeholders in any annotation (`@Value`, `@Scheduled`, `@KafkaListener`), the fields of a `@ConfigurationProperties` type under its prefix (nested types followed, a list field as `key[]`, a map field as `key.*`, a record's `@DefaultValue`s), `@ConditionalOnProperty`, and `environment.getProperty("key")` with a constant, in the module and its sibling modules. The application files under `--resources` (`application.yaml`, `application-prod.properties`, the same under `config/`, with `---` profile documents) say what is set. The configuration metadata on the class path (`META-INF/spring-configuration-metadata.json`, which every Spring Boot starter and every module built with the configuration processor carries) says what the framework binds, with types and deprecations. Names are compared in Boot's relaxed canonical form, so `maxSeats`, `max_seats` and `max-seats` are one key. Each key is a line with its type and the value each file gives it (`boxoffice.hold.max-seats: int = 8, 12 (prod)`, or `, default 8` when no file sets it), and under it who reads it (`@Value in TicketingApplication.holdPolicy(int, Duration), maxSeats, default 8`, `declared by KafkaProperties$Producer`). The `!` lines: a key set in a file that no class reads and no metadata declares (the typo, with the nearest known key named), a key the metadata marks deprecated (with its replacement, and whether Boot still binds it), a value that is not of the key's type (`int`, `Duration`, `DataSize`, `boolean`, an enum's constants, with Boot's relaxed matching), and a placeholder default that is not. A renamed key in the code, a mistyped key in the file, or a Boot upgrade that retires a key passes every test, since tests do not run with the production profile and a missing key quietly takes its default; here each is a changed line.

Then come the **wire types** ([`wire`](src/wire.rs)): the JSON shape of every type that crosses the boundary, which is what the other side of each route and topic depends on. The roots are the `@RequestBody` parameters and results of the handlers, the payloads of the message listeners, and every class with a Jackson annotation; the closure follows property types into the module and its sibling modules (the class path entries under `--base`), and stops at library types. Each type is a block: `record`, `class`, `enum` or `interface`, with its properties as Jackson finds them (record components; public fields, public getters, setters and `@JsonProperty` members, superclasses included) under their wire names (`@JsonProperty`, `@JsonNaming`), with the Bean Validation constraints before the type and inside it (`List<@NotBlank String>`, from the class file's type annotations) and a `?` on a property that may be null or absent (`Optional`, `@JsonInclude`), enum constants with their `@JsonProperty` names or the `@JsonValue` method, and for a polymorphic type the `@JsonTypeInfo` placement and each subtype's id (`subtype "PaymentCaptured" = PaymentEvent$PaymentCaptured`, and `type = "PaymentCaptured"` in the subtype's own block). A renamed component, a dropped `@JsonSubTypes` entry or a new enum constant changes no signature and passes every test that encodes and decodes with the same classes; here it is a changed line. The constraints are checked as Hibernate Validator will run them: a property whose type carries constraints that no `@Valid` on the property or inside its type leads into (`billing: @NotNull Billing` then `! constraints on Billing are not checked: no @Valid on billing`), a constraint on a type it has no validator for (`@Size` on an `int`, accepted by the compiler and thrown as `UnexpectedTypeException` at the first validation), and a null check on a primitive are `!` lines under the property.
The wire checks, as `!` lines of the type's block, were established against Jackson 3 as Spring Boot configures it: a permitted subtype of a sealed base that `@JsonSubTypes` does not list (it is written under its class name and rejected when read back), a subtype whose type id defaults to its class name, `@JsonTypeInfo(use = CLASS)` (Java class names on the wire), an interface or abstract class without `@JsonTypeInfo` (written as the runtime class's properties, with no id to read it back by), a class with no visible properties (written as `{}`), two properties with the same wire name, and a persistence type (`@Document`, `@Entity`, `@Table`) on the wire.
The contract ends with the **stored types** ([`store`](src/store.rs)): the shape of every Spring Data MongoDB document the module keeps, as the mapping layer writes it. Each `@Document` class is a block (`record, collection "seats"`) with its properties under their stored names (`_id: String (id)` for the `@Id` or the property named `id`, `due: Instant (dueAt)` for a `@Field` rename, a `@Transient` or `transient` field left out, `@Indexed`, `@Version` and the other Spring Data annotations before the type), and each local type a property embeds is a block of its own (`record, embedded`). Under the document go the `!` lines for the strings in the module's code that name a field it does not have: a `Criteria.where("x")` or `.and("x")`, an `Update.set("x", ...)`, `.unset("x")`, `.inc("x", ...)` and the other operators, an `Index().on("x", ASC)`, a `Sort.by("x")` or `Sort.Order.asc("x")`, a projection's `include("x")`, a repository method's `@Query("{ 'x': ?0 }")` with its `sort` and `fields`, and a `@CompoundIndex(def = "{'x': 1}")`. A string may name a property by its Java name or its stored name, as the query mapper accepts both; a dotted path goes through an embedded type's fields, through a collection or array to its element, through a map to any key, and stops at a leaf (`"assignee.email" is a String, which has no fields`); `$`-segments and array indices are skipped. The document a string is about is the one the method names (the `SeatDocument.class` it passes to the template, or the document it instantiates); a helper that names none takes the documents of its callers, and a string with no document in reach is checked against every document of the module. Nothing checks these strings otherwise: the driver sends them to the database, which matches, writes, indexes or sorts by whatever field that is, so a renamed record component leaves every query of it matching nothing (`! TicketingStore.holdByIdempotencyKey(String, String) queries "idempotencyKey": not a field of HoldDocument, so the condition tests a field that is never set`), every update of it writing a field nothing reads back, and every test that goes through the same strings passing; the nearest property is suggested when there is one (`(createdAt?)`).

Under each entry point and advised method go the **reach lines** ([`reach`](src/reach.rs)): what the method reaches, found by following the calls in the bytecode from it through the application's own classes (the module and its sibling modules on the class path) to the framework APIs that do the work. `reads` and `writes` list the documents, entities or tables (the Spring Data templates and repositories, the JPA `EntityManager`, `JdbcTemplate` and `JdbcClient`; what a call is of comes from the class literal it passes, else the static type of its entity argument, else the documents the method mentions, and a table from the SQL constant), `sends` the topics, exchanges or queues (the Kafka, RabbitMQ, JMS, Spring Cloud Stream and AWS templates; the constant string passed, else `to Kafka`), `calls` the HTTP requests (`RestTemplate`, the fluent `RestClient` and `WebClient`, an `@HttpExchange` or Feign interface, as `GET /users/{id}`) and `publishes` the application events. The walk is a may-reach approximation: a virtual call goes to every local subtype that overrides the method, a lambda to its body whether or not the receiver runs it, a call on `this` the same as any other; a call into Spring, the JDK or a driver is a leaf. So `POST /orders` reads `HoldDocument, OrderDocument, SeatDocument` and writes `OrderDocument, Outbox.Entry`, and a pull request that makes a handler touch a new collection, publish to a new topic or call another service changes the contract under that handler. Two `!` lines read these: a `GET` or `HEAD` route that writes, sends, publishes or makes a non-GET call (`! a GET that writes HoldDocument and SeatDocument: a safe method with side effects, so a retry, a prefetch or a crawler changes state`) and a `@Transactional(readOnly = true)` method that writes (`a read-only transaction drops or rejects writes`: Hibernate keeps the changes unflushed, PostgreSQL rejects the statement). Each effect is also placed with respect to transactions: inside one the method opens (its own `@Transactional`, or a lambda it hands to a `TransactionTemplate` or to a helper that runs its argument through one, like Box Office's `Transactions.run`), or with no transaction on the path; a `@Transactional` method of another class on the path accounts for its own effects, so a `!` line sits under the service method rather than under every route that calls it. Three more `!` lines read that placement: a transaction that sends or makes an HTTP call (`! a transaction that sends to payments.commands: the send is not part of the transaction, so a rollback leaves the message sent and a crash before the send leaves the commit unannounced`, the dual write an outbox exists to avoid; left alone when `spring.kafka.producer.transaction-id-prefix` makes the producer transactional), an event published with no transaction on the path while a `@TransactionalEventListener` waits for it (the listener does not run unless it asks for `fallbackExecution`), and an after-commit listener that writes (the transaction has committed and nothing commits again, so a JPA or JDBC write there is never committed unless the method is `@Transactional(propagation = REQUIRES_NEW)`).

The three Box Office modules that carry Spring annotations and the `contracts` module, whose wire types are the messages between the services, have their contracts checked in ([ticketing-service](../examples/apps/boxoffice/ticketing-service/src/contract/boundaries.contract), [payment-service](../examples/apps/boxoffice/payment-service/src/contract/boundaries.contract), [messaging](../examples/apps/boxoffice/messaging/src/contract/boundaries.contract), [contracts](../examples/apps/boxoffice/contracts/src/contract/boundaries.contract)), and `./gradlew check` verifies them when `jvmcontract` is on the `PATH`.

What it does not do: it reads the annotations as declared on the class, not the ones inherited from an interface or a superclass (Spring reads both); it does not follow a call through a field of the bean's own type; and it says nothing about JPA mappings, which are a schema, not a boundary. The proxy checks assume Spring's defaults (CGLIB proxies, rollback on unchecked exceptions), which `spring.aop.proxy-target-class` and a custom transaction attribute source can change. The wire types assume Jackson's default visibility and naming (`@JsonAutoDetect`, a `JsonMapper` customizer and the `spring.jackson.*` properties can change them), do not read mix-ins or custom serializers (a `@JsonSerialize` is shown as a detail, not applied), and show `Instant`, `UUID` and the other library types by name rather than by encoding. The configuration block reads the application files only (not environment variables, `spring.config.import`, config servers or command-line arguments, so a key no file sets is shown without a value, not as a problem), a key read through a non-constant name or a `PropertySource` of the application's own is invisible to it, a property with metadata hints is not checked against them, and a dependency without configuration metadata makes its keys look unbound (`additional-spring-configuration-metadata.json` in the dependency, or `ignored.properties` in the module's own, declares them). The validation checks know the built-in constraints of Jakarta Validation and Hibernate Validator and the JDK types they validate; a custom constraint is shown but not judged, `@Pattern` expressions are not compiled, a `@GroupSequence` or `@ConvertGroup` is not followed, and a type that cannot be found on the class path is not judged either. The activation block takes `@ConditionalOnBean`, `@ConditionalOnProperty` and `@Profile` as met (a switch behind a property it cannot see is reported as present), reads a module without an application class as part of a Boot application, follows no `ImportSelector` other than auto-configuration, matches the families it knows (Spring's own, Spring Security, Spring Retry, Micrometer, the servlet annotations) by the annotation written on the code rather than meta-present, and does not judge a listener of another library (`@SqsListener`). The stored types cover Spring Data MongoDB only (a JPA entity's queries are JPQL, which Hibernate checks at startup), read the field strings that are constants in the method that passes them (a name built at runtime or held in a `static final` of another class is invisible), do not follow aggregation pipelines (a stage after a `group` names computed fields), do not judge derived query methods (`findByHoldId`, which Spring Data checks at startup), and take a string in a method that names no document as being about every document of the module. The reach lines say what a method may reach, not when or in what order (a write under a condition is `writes`), follow no call made through reflection or a bean looked up by name, do not see what a framework does on the method's behalf (a transaction's commit, a listener's offset commit, an aspect), name a data call whose entity argument has no useful static type by the documents the method mentions, and treat the GET check as a statement about HTTP semantics: a GET that records a metric is flagged like one that extends a lease. They know a transaction by `@Transactional` and `TransactionTemplate` only: a `PlatformTransactionManager` driven by hand is not seen, a helper that takes a lambda and reaches a transaction is taken to run the lambda inside it (whether or not it does), and a Kafka or JMS transaction manager behind `@Transactional` is read as a database transaction. The binding checks read the route templates written in Spring's own mapping annotations (a composed mapping annotation of the application's own is not read), compare routes by their rendered form with the variable names dropped (two routes that differ in `consumes`, `produces`, `params` or `headers` are told apart, as Spring does by the request), take `required` and `defaultValue` as written on the annotation, and know nothing of a `ParameterNameDiscoverer` of the application's own. The throws lines see an exception built by `new` and thrown, returned by a method and thrown, held in a typed local, built by an `orElseThrow` supplier or raised by Spring's `Assert`; not what a framework or driver call throws (a `DataAccessException`, an `OptimisticLockingFailureException`), not a `throws` clause, and not the compiler's own `MatchException` or an `assert`. A handler's status is read from its `@ResponseStatus`, the first `HttpStatus` constant its body loads or the literal it passes to `ResponseEntity.status`, else the handler is named without one; a `catch` that rethrows its variable passes everything through and one that does not swallows all it catches, whatever else its body does; an `@Async` callee of another class throws on its own thread; and a `@ControllerAdvice` is matched by its packages, assignable types and annotations, with `@Order` and then the class name deciding between two that match.

## The tool's own checker

JBMC is the bounded model checker the proofs were built on, and the limits that have bitten were its: no models of the class library beyond six classes, a string solver that overrides the class on the class path for `java.lang.Character`, a MiniSAT path that stalls, a 3 GB run that no option shortens. The models are the tool's own now ([above](#models-of-the-jdk)); the checker is becoming so too. [`bmc`](src/bmc/mod.rs) checks the same harness class JBMC is given, by executing its bytecode symbolically over bit-vectors ([`bmc::bits`](src/bmc/bits.rs): two's-complement circuits for the JVM's arithmetic, division included, with gate hashing so that the harness's check of a value and the method's computation of it are one circuit), one path at a time, asking a bundled SAT solver (CaDiCaL) at each branch which sides are feasible, and, when a path reaches the harness's `AssertionError`, for the input that takes it there. Each path carries models of its condition, the solver's answer when the path was split off, so a side of a branch that a model takes is known feasible and the solver is asked once per branch at most, about a side no model takes; a condition the path took before (the same comparison of the same bits, which the gate hashing makes the same literal, as a loop bound both versions test is) costs nothing. The hashing also makes a callee both versions call on the same arguments one circuit, so the checker never compares two copies of a division: the plain proof of [example 120](../examples/120-retry-after-rewritten-around-unchanged-refill-helpers/README.md), which JBMC did not finish in 60 s without the shared-callee stubs, takes it 1.1 s with the helpers as written. That input is looked for in the stages JBMC is run through, inputs in `[0:20]`, then `[-100000:100000]`, then everything, so that the witness is readable, and the stage is reported as JBMC's is (`searching inputs in [0:20]`); a path that fails only on large values does not end the search, which goes on through the remaining paths, for as long again as the first violation took, in case one of them fails in a smaller stage. The witness is then shrunk in the interpreter like JBMC's. A division or remainder is not built as a circuit at first: its quotient and remainder are bits the solver chooses under what holds of every division (the remainder is smaller than the divisor and takes the dividend's sign, a division by one or by the dividend itself is exact, a power of two divides a non-negative dividend by masking, and so on, a few hundred gates each where a 64-bit divider is some ten thousand), a proof that goes through under those facts holds, and a model the solver gives is checked against the real division of the values it chose and the circuit built only where it was wrong. Both versions mostly use the same remainder or compare it with something the facts settle, so the 64-bit remainders of [examples 120, 132 and 135](../examples/README.md#tag-own-checker) cost nothing or a fraction of a second where they took 1 to 12 s before. A multiplication is left to the solver the same way, under what holds of every product modulo the width (a factor of zero gives zero, of one the other factor, of minus one its negation, a power of two shifts by its exponent, the low eight bits are exact), with the multiplier built only where a model got a product wrong: the loop of `delay *= multiplier` in [example 131](../examples/131-backoff-with-a-multiplier-proved-equal-to-the-doubling-record-for-a-multiplier-of-two/README.md) is proved in 4 s instead of 22 with none of its 27 products built, the scope's multiplier of two being a power of two. A quotient times its divisor is not a product at all but the dividend less the remainder, `(a / b) * b` as `a - a % b`, which holds for every pair in two's complement, so the identity between a division and a multiplication that neither engine proved in a minute is the same bits on both sides: [example 138](../examples/138-a-window-start-computed-as-the-window-s-index-times-its-length-proved-equal-to-the-remainder-form/README.md) in 0.1 s. The solver is also not waited for on the other side of a branch: it is asked for as long as all its calls so far took together, at least a second, and a side it has not decided by then is explored later, once every decided path is done, with all the time left. Refuting an infeasible side can be as hard as the whole proof (that one value is not a multiple of another, say) while the violation on the feasible side is found at once, as JBMC finds it without deciding the side: [example 134](../examples/134-a-window-counter-that-advances-by-one-window-leaves-its-start-behind-a-quiet-client/README.md) under its scope is such a probe, refuted in 2 s where the checker did not finish in two minutes waiting for it. Loops are unwound up to `--unwind`, exceptions are thrown and caught by class through the handler tables, calls into the application are inlined, and `Math.*Exact`, `floorDiv`/`floorMod`, `abs`/`min`/`max` and the wrappers' `compare`/`signum` are circuits with their overflow and division-by-zero paths. A model of a JDK class ([`models/`](models/README.md)) runs as bytecode in it, so `Character.digit` is the same function here, in JBMC and in the interpreter. An array of primitives is an object with a symbolic length and a cell per index it may have, as many as the bound on array parameters (`--max-array-length`, eight by default): a read at a symbolic index is a choice among the cells by the index, a write a conditional update of each cell, an index at or beyond the length or a negative size a branch to the exception, as a division by zero is, and the harness's copying and comparing loops over an array parameter run through it like the method's own. The bisection of a `lookupswitch` table over such an array, in [examples 140 and 141](../examples/README.md#tag-own-checker), is proved equal to its previous form on every strictly sorted table in 2 s where JBMC's one formula over the symbolic array takes 100 s and 2 GB, and the half-open form that reads past the end is caught in about a second where JBMC takes 23 s. Paths are merged where they meet, once the search has grown past a small one (512 paths, `Options::merge_after`): a path that reaches an instruction with more than one way in (the instruction after an `if`, a loop header, a handler) waits there, and when nothing else can run the paths waiting at the earliest such point are made one path, every value they differ in a choice by the condition of each, its condition the disjunction of theirs, and its models all of theirs, so that a branch each of whose sides some model takes costs no solver call. A method of `n` independent branches is then `n` paths, not `2^n`, and a loop whose body branches three ways is a few paths per iteration: the ASCII fast path of Mica's constant-pool encoder, [examples 142 and 143](../examples/README.md#tag-own-checker), is proved equal to the previous version on every string and buffer of up to eight elements in 733 paths and 7 s where the unmerged search takes 11643 paths, and at twelve elements in 83 s and 155 MB where the unmerged search spends its budget of 200000 paths without a verdict and JBMC ran out of memory at 2.8 GB at eight. The solver's work moves rather than vanishes: on a merged path the question at a branch is over every path merged into it, so the comparisons at the end of the harness are each a proof over the merged formula, and a violation is found only once the paths that could reach the join have arrived, where the unmerged search sometimes hit it early. That is why a small search is left unmerged: the 64-bit arithmetic of examples 131, 134 and 139 took two to three times as long merged from the start, each solver call about a disjunction of paths rather than one, and a proof the unmerged search finishes in sixty paths gains nothing from merging; one that would take thousands becomes possible.

Its fragment, today: methods over `int`, `long`, `short`, `byte`, `char` and `boolean`, and records of such components as the regression proofs build them (an object with fields, its constructor inlined, so the proofs of [examples 126 to 131](../examples/README.md#tag-record-components) run through it); arrays of those primitives, an array parameter of every length up to `--max-array-length` with symbolic elements and an array the method makes of a constant size or of one the solver proves within that bound (a copy of a parameter, say); arrays of references, made the same way, whose cells hold objects or `null` (an index that is an input splits the path per cell, since a reference is not a choice among bits), and an array's `clone()`; enums, their constants made through the model of `java.lang.Enum` (`name()`, `ordinal()`, `toString()`, `equals`), `$VALUES`, and javac's `$SwitchMap` classes; strings and other objects only as opaque values (a message built for an exception); application classes' static fields, and their initializers run where the JVM runs them (JVMS §5.5: superclasses and superinterfaces with a default method first, `ExceptionInInitializerError` from one that throws, `NoClassDefFoundError` at a later use), unless an initializer is outside the fragment; no multi-dimensional `multianewarray`, no floating point, no JDK static state beyond compile-time constants, no JDK call outside the list above (`System.arraycopy` and `java.util.Arrays` included). Anything else is refused with a reason, and `--engine auto` then hands the harness to JBMC with a `note:` line saying why; `--engine native` reports the refusal as *unverifiable*; `--engine jbmc`, the default, does not try it. A violation it finds is replayed and shrunk in the interpreter exactly as JBMC's, so an engine mistake on a violation would show as "does not reproduce" rather than as a false witness; its proofs rest on the circuits' correctness, which the unit tests check against Rust's integer semantics on the edge cases of every operation and the integration tests cross-check with JBMC on the fixture proofs (both checkers must agree on each verdict, the shrunk witnesses included). What it does not do yet, and JBMC does: arrays of a computed size beyond the bound, an `aastore` that throws `ArrayStoreException`, the merging of paths whose objects differ (one allocated an exception the other did not: they wait at the same join and go on separately), and floating point. It is a start, not a replacement; the default stays JBMC until the two have agreed on the examples' proofs under the pipeline.

Every instruction and call is implemented as the JVM does it, modelled, refused, or a *gap*: a construct the checker does not implement faithfully, with a stable id from what it is (`jdk-constructor:java.util.ArrayList.<init>(I)V@jdk-25.0.4.1`); the table is in the module docs of [`bmc`](src/bmc/mod.rs), and a test holds it to every opcode. The gaps it meets are a JDK constructor (`new ArrayList<>(n)`, which throws for a negative `n`), a `void` JDK instance method (`Random.nextBytes`, which fills its argument), a JDK instance method returning an object, a string concatenation that would call `toString` on an object, an application class's initializer the engine does not run, since it is outside the fragment (one that reaches what the engine refuses, floating point say, or reads the statics of such a class; met at the class's first `new`, `getstatic`, `putstatic` or `invokestatic`, after its superclasses', as JVMS §5.5 orders them; a JDK class is taken to be initialized already), and two calls whose value the proof reads: a JDK instance method returning an integer, a `char` or a `boolean` (`jdk-primitive-method`, `Random.nextInt(bound)`), and a static JDK method the engine does not model (`jdk-static-method`, `Integer.numberOfLeadingZeros`, `Arrays.fill`); a JDK method with a floating-point parameter or result, or an array result, is refused outright. Not a gap are the calls it reproduces exactly (`Object.<init>`, `Record.<init>`, a JDK exception's constructor with nothing, a message, or a message and a cause, the `Math` operations above, the models). `--gaps strict`, the default, refuses a gap by name: the path that reaches it ends there, a run that met one has no verdict unless another path is a violation, the reason lists every gap met with where, and `--engine auto` does not then ask JBMC, which approximates a call it has no bytecode for too, without naming it, unless every gap refused is a class initializer, which JBMC runs, or a call of a JDK class JBMC is given the bytecode of (`Math`, `StrictMath`, `Integer`, `Long`, `Short`, `Byte`). `--gaps assume` keeps the approximation (the constructor does nothing else, the `void` method nothing, the other returns a new object, the initializer has run already and thrown nothing) and the verdict says so: `✓ ... on every input, assuming 1 behaviour the tool's own checker does not implement (--gaps assume)`, with an `assumed:` line per gap. A call whose value the proof reads has no approximation, since the engine could only make the value up: `--gaps assume` refuses it as strict does, the reason saying that only a contract closes it. A monitor is implemented: `NullPointerException` on `null`, and nothing else in a run of one thread. So are identity and fields: a field is resolved as the JVM resolves it (JVMS §5.4.3.2), so a field a subclass declares again is a second field, in the checker and in the interpreter that replays its witnesses alike, and every load of one string or class literal is the same object, as the JVM interns strings. `jvmcontract gaps` ([`bmc::gaps`](src/bmc/gaps.rs)) lists the gaps a proof reaches statically, before anything is proved, walks each initializer the engine runs as it walks a method, and gives each class initializer that is a gap a shape from its bytecode and the application methods it calls: an `enum`'s, one that `throws`, one that reads or writes `other-statics` (javac's `$SwitchMap` class for a switch over an enum), one that assigns only `constants` or literal tables, or `other`.

`--gaps advised` is the gap protocol ([`src/advice.rs`](src/advice.rs)): the tool hands the agent driving it the gaps it cannot close, before it solves anything. A property or regression proof builds its harness, then scans the harness and every method it may reach, on the class path the engine is given, with no solver. A gap with no contract stops the run: the verdict is *unverifiable*, with the finding `gaps-need-contracts`, a `gap` line per gap saying what its contract must state, and a template, written to `contracts.template` in the work directory. Under `--json` the outcome's `advice` has, for each gap: its id, the call with its owner, name, descriptor, parameters (named as the class file names them, `arg0` for a JDK class, which keeps no names) and result type, the sites, what `--gaps assume` would take it to do, the parts a contract must state (`must_state`: its `result`, `exceptions`, effect on the `receiver` and the `arguments`, the static `state` a class initializer sets, and `purity`, each with a question), and its block of the template. It also has the claim in words, and what the engine refuses whatever the contracts say (`outside`). A template block is headed by the gap's id and has `call:`, `assume:`, `throws: ... when ...`, `assert:` and `modifies:` lines, in the property syntax of `prove`, plus `written-by:`. With no gap the run is strict's: advised is strict given no contracts.

`--contracts FILE` (under `--gaps advised`) gives the tool contracts for its gaps ([`src/gap_contracts.rs`](src/gap_contracts.rs)), in the format of the template: `kind: gap-contracts`, then a block per gap under its id, with `call:` naming the parameters, `assume:` (the inputs it is about; `true` if absent), `throws: X when c` (repeatable; the first whose condition holds decides), `assert:` (what holds after the call, over the arrays it modifies and, for a call that returns an integer, a `char` or a `boolean`, over `result`, `0 <= result && result < bound`; for a call that returns an object, which object: `result == this`, `result == <parameter>`, `result == null`, `\fresh(result)`), `modifies:` (`nothing`, `this`, or parameters that are arrays of primitives) and `written-by:`. The conditions are `prove`'s expressions over the primitive parameters and arrays of them. A contract the engine can apply closes its gap: the scan no longer stops for it, and the engine runs a generated method in place of the call, which throws what the contract says where it says, gives each array it modifies any elements its assertion admits, and returns the object it names; on an input outside `assume:` the gap is open and refused. An initializer whose contract throws nothing and modifies nothing is taken to have run. A contract it cannot apply is refused with the reason (a key still `TODO`, a call that does not match the id, `this` or an object parameter in a condition, a result it cannot choose an object for, an initializer that throws or sets state, `\old`, a string conversion, another JDK's version), in a `note:` line and in the advice for its gap (`refused_contract`); the advice also lists the gaps contracts closed (`closed`), and its template has only the gaps still open. The engine gives a primitive result any value of its type, which the assertion then constrains. Each contract the engine can apply is then **tested on a real JVM** ([`src/contract_testing.rs`](src/contract_testing.rs)), since the interpreter and the engines share models and their agreement says nothing about the JVM: a generated class, run once by the `java` of the JDK the gap ids name, calls the JDK's own method on the boundary values of each parameter's type (every combination, up to 512), then on 256 random inputs drawn with a recorded seed (arrays of up to four elements; an instance method on an object built by its class's constructor of no arguments; an initializer by loading its class), a static method by itself, and checks the contract on each with the bytecode the engine's method for it uses: inside `assume:`, the first throws clause that holds before the call decides, and the JVM must throw exactly that class, or, where none holds, return, with every array `modifies:` leaves out unchanged, the result the object named, and `assert:` holding. An input on which the JVM runs out of the test's 128 MB or its stack (`new ArrayList<>(Integer.MAX_VALUE)`) says nothing either way and is counted apart, since a proof is about a JVM with enough of both. A contract no input refutes is `tested`, with the number of inputs, how many returned and threw as each clause says, the seed and the JDK. One the JVM refutes is refused, its gap stays open, and the advice for the gap carries the counterexamples (`counterexamples`, each an `input` with what the contract `expected` and what the JVM `observed`), so the agent gets them with the reason: `a JVM refutes it: on capacity=-1 the JVM's call throws java.lang.IllegalArgumentException: Illegal Capacity: -1, where the contract says it returns normally (83 of 128 inputs refute it, ...)`. One the JVM cannot test (a parameter of an object type, a receiver it cannot build, no JVM found) is `trusted`, with why. Before the test, a contract for a **static JDK method of primitive parameters** is **proved against the JDK's own bytecode** ([`src/contract_proving.rs`](src/contract_proving.rs)) where the method is in the own checker's fragment. A generated statement per contract (method `p<i>` of `GapContractProofs`) calls the method, whose class is taken from the JDK image onto the class path as bytecode to run, and checks the contract as the JVM test does, the exception's class exact (the engine's `sameClass` intrinsic), under `--gaps strict`, unwinding loops 16 times, 30 s per contract. A contract proved, which the JVM does not refute either, is `proved`, the strongest level, with the class, the JDK, the class file's `sha256:` digest, the checker, the unwinding and the paths (`proof`): `Integer.numberOfLeadingZeros` and `Integer.divideUnsigned` are. A proof that refutes a contract gives an input the JVM test runs too, so only the JVM makes it a counterexample: a contract for `numberOfLeadingZeros` that is wrong only at `i = 777777`, which neither the boundary values nor the random ones reach, is refused at it. A witness the JVM does not reproduce is a disagreement with the JVM, and leaves the contract tested. Every contract not proved says why in `unproved`: an instance method's receiver has state the checker does not keep, a proof covers arrays only up to a bound where the call may be given a longer one, or the checker gave no proof (a gap, a static field that is not a constant, a loop past the bound). A proof is about the JDK's bytecode, which HotSpot may run as an intrinsic of the same meaning, and takes the JDK's classes as initialized, as every proof of the checker does. A contract is about arrays that are there: at a `null` array the engine meets the gap. A verdict that rests on contracts says so, counting them at each level: `✓ ..., relying on 2 contracts for gaps of the tool's own checker, 1 tested, 1 trusted (--gaps advised)`, then a `contract:` line per gap with what it states, who wrote it, and what backs it (`tested on 128 inputs on JDK 25.0.4.1 (seed 1), 38 more running out of the test's memory, none refuting it`). In the statement each is an assumption of kind `contract` with the basis `proved`, `tested` or `trusted`. A tested contract is evidence, not a proof: the test sees no receiver state and only the inputs it ran. A witness found through a contract that the interpreter, which runs the JDK's call, does not reproduce is no verdict, and names the contracts as the likely cause; one the interpreter cannot run (it has no `java.util.Random`) is run on a JVM ([`jvm_witness`](src/jvm_witness.rs)), since a contract admits what the JDK's call may never do (any value in a range, any elements of an array), and only a run of the JDK's call shows whether the JVM does it. A generated class, `WitnessRun`, calls the harness the checker proved on the witness, with the JDK's real calls where the contracts stood, then the method alone (each version alone, for a regression proof of static methods of the harness's parameters) for the outcome to report. An `AssertionError` from the harness makes the witness a violation, its proof line saying `run on a JVM (JDK ...) with the JDK's own calls where the contracts stood` and `replay.by` `jvm`, not shrunk, since the interpreter is the shrinker's oracle; a harness that returns makes it no verdict, `... does not reproduce on a JVM`, with what the method did there. In a regression proof each version's call takes a value of its own under a contract, so a call the two versions make alike can differ under it although the JDK's does not: such a witness is common there, and the JVM run shows it for what it is. A refuted assertion on a primitive result says what the JVM returned: `on i=0 the JVM's call returns 32, where the contract says it returns with `assert: 0 <= result && result < 32` holding`. `--engine auto` does not hand JBMC a run that applied a contract, and `--confirm` does not ask it, since JBMC cannot apply one. On the conformance corpus, contracts that state what the JVM does are all tested, none refuted, and decide 5 of the 6 claims strict refuses for a gap as the JVM decides them; the other reaches a JDK call with no contract. (Before Phase 5 of `llm-dlc/loops/engine-priorities.md` there were 9, three of them class initializers, which the own checker now runs.) The examples tagged [`advised-contracts`](../examples/README.md#tag-advised-contracts) are the loop on an app kernel, recorded through `build.py` (`approach.gaps: advised`, `approach.contracts`, whose file is part of the claim): an agent's contract the JVM refutes, going back to it with the counterexamples, and a proof that closes on contracts at two levels. Under `--engine jbmc`, and in JBMC's turn under `auto`, the same protocol runs on JBMC's gaps, and JBMC applies the contracts ([`src/jbmc_contracts.rs`](src/jbmc_contracts.rs), described with JBMC's gaps above). On the conformance corpus it asks for contracts on exactly the claims strict refuses for a gap, and decides every other claim as strict does.

**The contract library** ([`src/contract_library.rs`](src/contract_library.rs), [`models/contracts/`](models/contracts/README.md)) keeps contracts that were checked once, so the agent does not write them again and no run checks them again. It is built into the binary, as the models are: a `.contracts` file per JDK class, in the format above, and `checked.json`, a record of each check (the contract's digest over its gap and keys, the JDK it ran on, the jvmcontract that ran it, and the evidence with its proof and JVM test). Under `--gaps advised`, a gap the harness reaches that the agent's `--contracts` has no contract for takes the library's. The agent's contract comes first even when it is refused, so a wrong contract goes back to the agent rather than being replaced. A library contract whose record holds (the same contract, the same JDK, and for a proof the same class file in the JDK image) is applied with the record's evidence and no proof or JVM test, and its `contract:` line ends `checked once, on JDK 25.0.4.1 by jvmcontract 0.1.0, and recorded in the contract library, not checked again by this run` (`recorded` in the JSON). One with no record that holds, as after a JDK upgrade, is checked by the run as the agent's are, with a `note:`; a contract written for another JDK is checked under the run's JDK's id. `jvmcontract gap-contracts [--dir DIR] [--record]` checks every contract of a library on this JDK (the built-in one, or a directory's) and exits 1 when one is refused or has no record that holds; `--record` writes the evidence to `DIR/checked.json`, keeping the records of other JDKs. `--no-contract-library` closes gaps with the agent's contracts only. On the conformance corpus the library alone decides the same five claims as the corpus's own contracts, with no JVM test run. `--max-trust N` is the policy for trusted contracts (open question 7 of the brief: CI passes `--max-trust 0`): when more than N of the contracts for the gaps a proof reaches are trusted, each of those is refused, `it is trusted: nothing has checked it, since ...; the proof would rest on 1 trusted contract, and --max-trust 0 allows none`, and its gap goes back to the agent before anything is solved. The [`verify-bytecode` skill](../plugins/jvmcontract/skills/verify-bytecode/SKILL.md) is the agent's side: its proofs run under `--engine auto --gaps advised --max-trust 0`; it writes a contract for each gap from the JDK's documentation, runs again, corrects a refuted one from its counterexamples, reports the verdict with its contracts' evidence levels, and offers the ones it wrote that held for this library, checked with `gap-contracts --dir`.

**Transcripts** ([`src/bmc/transcript.rs`](src/bmc/transcript.rs)): with `JVMCONTRACT_TRANSCRIPTS` naming a directory, every check the own checker runs writes there every clause it gives the SAT solver and every call it makes, in order, as CaDiCaL's incremental CNF (`p inccnf`, a call an `a` line of its assumptions), each call followed by a comment with its answer, its time and its time limit. A check is hundreds of incremental calls on one growing formula, with lemmas added between them that depend on the models given, so a solver is judged on that sequence rather than on one final formula. `jvmcontract transcript FILE` runs one again, each call with its recorded limit, and reports the time against the recorded time and any answer that differs.

**The solver interface** ([`src/bmc/sat.rs`](src/bmc/sat.rs)): the engine schedules the queries (`src/bmc/mod.rs`: the probes, the deferred paths, the refinement loop), bit-blasts them (`src/bmc/bits.rs`), and hands the solver only clauses, a per-call time limit and calls under assumptions, reading a model's values back, through the `Sat` trait. CaDiCaL is the one the tool uses by default; a transcript's replay goes through the same trait, so another solver behind it can be judged on the engine's own sequence of queries. The other is Bitwuzla ([`src/bmc/bitwuzla.rs`](src/bmc/bitwuzla.rs)), for the solver comparison: it is given the engine's clauses, a variable a Boolean constant and a clause an `or`, so only the solver differs, not the encoding. Nothing links it: its C API is loaded at run time from a build of 0.8.2 ([`solvers/bitwuzla`](solvers/bitwuzla/README.md)), named by `JVMCONTRACT_BITWUZLA` or else in `~/tools/bitwuzla/current`. `JVMCONTRACT_SOLVER=bitwuzla` runs every check of the process on it, with Bitwuzla's options after a colon if any (`bitwuzla:preprocess=0`, by the long names of its command line, each checked against the library's own description of it), and the results name it with those options (`checker.solver`, the transcripts' headers); `jvmcontract transcript --solver bitwuzla` replays a transcript on it. `JVMCONTRACT_SOLVER=bitwuzla-words` is the word-level prototype: a solver may take terms (`Terms` in `sat.rs`), and then the encoding defines each gate to it as a Boolean term and each arithmetic operation, comparison, symbolic shift and `ite` of two values as one bit-vector term, rather than bit-blasting them; arrays stay bounded cells, and no transcript is kept. [`solvers/compare.py`](solvers/compare.py) puts the solvers side by side on the benchmark's five largest-formula workloads, on clauses and (`--words`) on terms, as pipeline jobs. Its models differ from CaDiCaL's, so a violation's input and the number of solver calls may differ too, but not the verdict.

`--engine auto --confirm` has JBMC prove again, in one run over every input, a statement the own checker proved: the one expensive check, ten to a hundred times the own checker's time on the recorded examples, so it is asked for rather than taken. JBMC is a second implementation of the JVM's semantics with models of its own, so its proof is evidence that the own checker's was of the statement asked. The verdict says what came of it, on a line under `✓`: `confirmed: JBMC 6.11.0 proves it too, over every input`; `not confirmed: JBMC gave no verdict (...)`, the proof standing as the own checker's alone; or `not confirmed: JBMC was not asked`, when the own checker assumed a JDK call (`--gaps assume`) that JBMC would approximate as well, without naming it. JBMC refuting the proof is neither verdict: the result is *unverifiable*, "the engines disagree", with JBMC's witness as the counterexample and the interpreter's run of it shown, which decides nothing, since the interpreter shares the own checker's models; a JVM run on the witness settles which engine is wrong. A class initializer assumed to have run is checked: JBMC runs it. A violation the own checker finds is not sent to JBMC: it is replayed like any other. A proof that rests on contracts for gaps (`--gaps advised`) is confirmed on the same contracts: JBMC's preflight names its gaps, the contracts the own checker applied are applied at their call sites as under `--engine jbmc` ([`src/jbmc_contracts.rs`](src/jbmc_contracts.rs)), and JBMC's proof is held to what it still approximates; the confirmation says it rests on them (`search.confirmation.reason`). It checks the reasoning given the contracts, not the contracts, whose evidence the verdict states. A gap JBMC has that no contract closes leaves it no verdict.

## Library use

```rust
use jvmcontract::{classpath::ClassPath, verifier::Verifier, capabilities};

let mut cp = ClassPath::new();
cp.add("build/classes/java/main".as_ref())?;
let cp = cp.with_default_jdk();

let derivation = Verifier::new(&cp).derive("net.example.OrderLifecycle#decide");
if let Some(contract) = &derivation.contract {
    println!("{}", contract.render());          // or contract.cases, Contract::diff(&old, &new)
}
let report = capabilities::analyse_classpath(&cp)?;
println!("{}", report.render("my-module"));
# Ok::<(), jvmcontract::Error>(())
```

The crate's modules follow the pipeline: [`classfile`](src/classfile/mod.rs) parses class files (and writes small ones), [`classpath`](src/classpath.rs) is the closed world of application classes plus the JDK read by [`jimage`](src/jimage.rs) and [`zip`](src/zip.rs), [`purity`](src/purity.rs), [`domain`](src/domain.rs) and [`interp`](src/interp/mod.rs) derive behavioural contracts for [`verifier`](src/verifier.rs), [`capabilities`](src/capabilities.rs) and [`api`](src/api.rs) derive the module-level ones, [`relocate`](src/relocate.rs), [`harness`](src/harness/mod.rs), [`jbmc`](src/jbmc.rs) and [`equivalence`](src/equivalence.rs) run regression proofs, [`tla`](src/tla.rs) generates protocol operators and runs TLC, [`statemachine`](src/statemachine.rs) draws a contract, and [`sarif`](src/sarif.rs) writes reports.

## What is new compared with the Java proof of concept

- **No JVM.** Contracts are derived by interpreting the bytecode, with the JDK's shape read from its image. Nothing is loaded, reflected on or executed by a JVM, so the tool is one static binary that starts in milliseconds and cannot be influenced by the class path of the build it runs in.
- **A complete purity proof over the domain.** The effect monitor catches every write to pre-existing state during the executed cases, including the array and collection stores the static analysis could not see.
- **Instance methods** of finite types (an enum's `discount()`, a record's `isFinal()`): the receiver is the first dimension of the domain.
- **No `javac` in the proof pipeline.** The JBMC harness is generated as bytecode; the scope expression is compiled by the tool, with Java's typing rules.
- **Property proofs** (`prove`): a postcondition or a law about a method, stated next to the code and proved over every input by the same machinery as the regression proofs. The expression language gained `result`, calls of the method under proof, and JML's quantifiers over array parameters and results, `\forall`, `\exists`, `\sum`, `\num_of`, `\max` and `\min`, compiled to loops in the generated harness.
- **Shrunk counterexamples.** A refuting input is shrunk in the interpreter, running the same harness class JBMC checked, so the witness on the page is small and the same on every run, with JBMC's own input kept beside it.
- **Exceptional behaviour** (`throws:`, JML's `signals`): a property declares the exception a method throws and the condition under which it throws it, and the proof covers the exceptional path with the normal one, instead of assuming the throwing inputs away.
- **Pre-state values** (`\old`, JML's): a property reads an array parameter after the call and, under `\old`, as the call received it, so a method that writes into an array is held to a frame condition, or proved a permutation.
- **Regression proofs over arrays**: a method that takes or returns arrays is proved to behave as its previous version with no property written at all, the previous version being the specification: the results, the exceptions and what each version leaves in the arrays are compared, and the differing input is shrunk.
- **Shared callees in regression proofs**: a callee both versions call unchanged is one function in both, so the solver relates the versions' uses of it and never its arithmetic, and a target identical in both versions, with everything it reaches, is verified without a solver.
- **Records in regression proofs**: a method of a record whose components are primitive, or one taking or returning such a record, is proved on the components, the record built from them in each version through its constructor, so that the proof is over the record's invariant and a record result is compared component by component. A static method that became a method of a record, or took one as a parameter, is related to its previous version with `--before-arguments` over the components; a record whose components changed, or a record's method made static, by building the previous record from the new parameters with a constructor call among them, `new Backoff(this.baseMillis, this.capMillis), attempt`. A record result whose components changed, or a result that became a record or stopped being one, is related by `--results-agree-when` over the components, `previous.startNanos == result.startNanos && previous.count == result.count`: each record's components are read into the relation, two null records agree, and one alone does not.
- **API contracts**, the fourth lockfile: the public surface of a module, diffed like the others.
- **Capability contracts per dependency** (`capabilities --each a.jar b.jar`), the hook the Java README left open.
- **A TLC runner** that parses the verdict, state counts and the counterexample trace into data, with optional deadlock checking (`--deadlock`, whose trace is reported like an invariant violation), and temporal properties: a liveness property under fairness, or a refinement of a more abstract specification (`PROPERTIES` in the configuration), reported with the property's name (TLC does not name it; the runner checks them one at a time when there are several) and, for a liveness counterexample, how the behaviour goes on forever after the trace. Also a **state-machine view** of a contract (Mermaid or Graphviz) that names unreachable and terminal states.
- **JSON output** for every command, **execution cost** per derivation (`--cost`), and a step and depth budget, so a method that does not terminate on some input is refused instead of hanging.

## Models of the JDK

JBMC has no bytecode for the class library, and the interpreter has natives for the part of it that pure domain code uses. Where the two must agree on a JDK class neither has, the tool ships a model: a small Java class with the behaviour programs observe, compiled into the binary, put on JBMC's class path by `equivalence` and `prove`, and executed by the interpreter in place of its natives for the methods the model defines. A few are for JBMC alone (`java.lang.Enum`, `List.of` and `List.copyOf` with the JDK's immutable lists), where the interpreter's natives already behave as the JVM does and stay; the tool's own checker runs `Enum`'s too (`models::CHECKER_RUNS`), as it has no natives; the conformance corpus checks both the natives and the models against a JVM. The catalogue, what each model keeps and leaves out, and how to add one are in [`models/README.md`](models/README.md). JBMC runs without its string solver (`--no-refine-strings`), which would otherwise replace calls of `java.lang.Character` by approximations of its own ahead of the model; `--refine-strings` turns it back on, and `--no-models` leaves the models out. JBMC is also asked for its bundled CaDiCaL (`--sat-solver`), since the MiniSAT path it takes without the string solver stalled on array proofs that CaDiCaL settles in a second.

## Limits

- The interpreter models a subset of the JDK. Code outside it is *unverifiable*, never wrong; the message names the method. JBMC's view of the JDK is narrower still: it gets six JDK classes (`Byte`, `Short`, `Integer`, `Long`, `Math`, `StrictMath`) and the tool's [models](models/README.md) of a few more (the boxing caches, `Character.digit`, `java.nio.charset`, `Enum`, `List.of` and `List.copyOf`), and treats every other JDK class as a stub with nondeterministic fields and results, so a class whose static initializer reads a JDK static the tool does not model, or a call into a JDK method it does not, can end in a `NullPointerException` or an arbitrary result the JVM never produces. The replay in the interpreter is the check that catches most of these (a witness the interpreter cannot reproduce is reported as unverifiable, not as a violation); the fix is a model. Enum `hashCode` is deterministic here (the constant's name hash) where a JVM's is identity-based, and `ClassCastException` messages omit the class-loader suffix a JVM adds.
- Regression proofs take a record only when every component is primitive (a record holding a `String`, an array or another record is refused with the reason), compare a record result by its fields rather than by its `equals`, and relate a record of other components, or one the new version lacks, only through a constructor call given with `--before-arguments`, and a record result of other components only through a relation over the components given with `--results-agree-when` (without one, the tool proposes it). A record among the previous version's parameters is built from values, not from an array or another record. Property proofs (`prove`) are still over static methods.
- The tool's own checker (`--engine native`/`auto`) covers methods over integers, arrays of them and records of them, without other objects or floating point; the rest is JBMC's, and under `auto` the hand-over is printed. It finds a violation fast and proves a property path by path, the paths merged where they meet and a solver call at most per branch, which is where JBMC's one formula can still win: the partitioner property of [example 023](../examples/023-abs-partitioner-sends-one-key-to-a-negative-partition/README.md) is a 32-bit remainder the checker proves in about 30 s and JBMC in a few. A division is left to the solver under cheap facts and built in full only where a model got it wrong, and a branch side the solver does not decide in the time its calls took so far is explored later, so the 64-bit remainders of the rate-limit kernels cost it fractions of a second; a multiplication is left to the solver likewise, and a quotient times its divisor is rewritten as the dividend less the remainder, so the identity of a 64-bit division and multiplication that was slow in both engines (examples 133 and 138) is its in a fraction of a second, where JBMC still does not finish in a minute. An array is a cell per index up to the bound, read by a choice among them and written by a conditional update of each, so a search over a short table (examples 140 and 141) is seconds for it where JBMC's formula over the symbolic array is a minute and two gigabytes.
- Regression and property proofs cover primitive parameters, arrays of primitives and straight-line arithmetic well, and get expensive with it: equivalence of two 64-bit multiplications with the overflow check behind `Math.multiplyExact` is proved in about ten seconds; a 64-bit division on each side can exhaust the solver, which is reported as *unverifiable*, unless the division is in a callee both versions call unchanged, which the proof takes as one function in both and the solver never sees ([example 120](../examples/120-retry-after-rewritten-around-unchanged-refill-helpers/README.md): a time-out at a minute becomes a proof in a second). Identities between a division and a multiplication (`(x / p) * p` against `x - x % p`, or the sum of `floorDiv` shares against the amount) are what JBMC's SAT backend cannot do in minutes; the tool's own checker rewrites the first (example 138) and leaves the second out of reach; state such properties as laws the solver can check by comparison, as the token bucket's are. Loops the unwinding bound does not cover are reported the same way.
- Arrays are bounded in length (`--max-array-length`), and what the SAT backend does with them is uneven: a regression proof runs both versions over the same symbolic arrays and so costs about twice a property proof of one, and `--unwind` drives the cost as much as `--max-array-length` does: two modified UTF-8 encoders ran out of memory at the defaults (8 and 16), but were proved equal in 94 seconds and 600 MB at 3 and 6, where a difference is found in five seconds (the proof at the defaults is the [own checker's](#the-tools-own-checker), [examples 142 and 143](../examples/README.md#tag-own-checker), in seconds); binary search over a sorted array of up to eight elements is proved in seconds, and so is an encoder writing into a buffer, but a quantifier that repeats a linear scan's comparisons (that the entry a scan returns is the first match, or that -1 means no match) did not finish in minutes even on four entries, eight writes at symbolic positions followed by a quantifier over the result take minutes where three take a second, and a method that allocates `new byte[n]` with `n` computed from the data never finished at all (give it the caller's buffer instead). A sum is cheap when the kernel accumulates in the order the property states it and exponential when it does not: a `Code` attribute length that adds the nested attributes' sizes into a total that already holds the fixed part took 80 seconds against `12 + codeLength + 8 * handlers + (\sum ...)` on four attributes and did not finish on six, while the same kernel summing the nested sizes first and adding the fixed part last is proved on eight in nine seconds (the SAT backend has no associativity; the two adder chains must be matched bit by bit). The witness elements of an array are not constrained by the small-inputs stage, which is what shrinking is for.
- Capability contracts stop at the module's own bytecode; what a library does with the calls made into it is the library's own contract.
- Boundary contracts read the annotations a class declares, not those it inherits from an interface or a superclass, and report a self-invocation only when the receiver is `this` loaded directly; the proxy checks assume Spring's defaults.
- `\old` applies to array parameters, which are the values a call can change; `\old(x)` of a scalar is `x`, and `result` has no pre-state. The copy it reads is taken in the harness, so a property with `\old` costs the solver the copy's stores, and a quadratic method under a quadratic quantifier (a sort, proved a permutation) needs the unwinding bound set to the arrays' bound plus one (`unwind:`) to finish in seconds rather than minutes.
- Throws clauses are matched in order, as Java's `catch` clauses are: declare a subclass before its superclass, or the superclass's handler takes the throw and the subclass's clause is reported violated. The declared class must be on the class path or in the JDK image; the exceptions JBMC models itself (`java.lang.Error`, `RuntimeException` and the common `java.lang` exceptions) are left to its models.
- The TLA+ operator generator assumes a contract of the shape `method(State, Input[...]) => Outcome[...]`, as a state machine over an enum and a sealed input type.

## Tests

```bash
cargo test --manifest-path lib/Cargo.toml
```

The unit tests need nothing. The integration tests compile the Java fixtures in [`tests/fixtures`](tests/fixtures) with `javac`; the regression tests also need `jbmc`, and the model-checking test needs TLC. A missing tool fails the tests that need it, so a passing run means they ran. To skip them instead, set `JVMCONTRACT_SKIP_MISSING_TOOLS=1`, and expect a passing run to prove less. The **conformance corpus** ([`tests/conformance.rs`](tests/conformance.rs), over [`Conformance.java`](tests/conformance/conformance/Conformance.java)) holds the tool to a real JVM rather than to itself, since the interpreter and the engines share models. Each case is a small method with claims about it: the gaps and their reproducers, identity and class initialization, exceptions, aliasing, `null` arrays, record constructors, dispatch, and arithmetic edge cases (`MIN_VALUE / -1`, negative remainders, shift counts out of range, narrowing). A [runner](tests/conformance/Runner.java) executes each case's calls on the JVM, each in a class loader of its own, and each claim's generated harness on them and on every witness an engine found. The test fails on: a call where the interpreter and the JVM disagree; a `Verified` under `--gaps strict` for a claim the JVM refutes, or one under `--gaps assume` that names no gap; a violation the JVM does not reproduce; and a native verdict other than the one recorded. JBMC, `--engine auto`, and `--engine auto --confirm` under strict and assume run the same corpus in an ignored test, `cargo test --release --test conformance -- --ignored`, which is a pipeline job; there a JBMC confirmation of a claim the JVM refutes fails the test, and so does a disagreement over one it does not. What `--confirm` does with each of JBMC's answers is tested inline, with a script standing in for JBMC. The conformance corpus is also the first group of the **benchmark corpus** ([`benchmark/`](benchmark/README.md), step 5a of the brief), with real regressions (a documented bug's broken and fixed versions) and held-out performance cases; `benchmark/run.py` runs each on both engines under each gap mode and keeps correctness, coverage, time and memory apart, with every expected answer and every witness checked on the JVM. [`tests/skill.rs`](tests/skill.rs) checks that every `jvmcontract` command the `verify-bytecode` skill names in code, and every option on it, is one the CLI accepts. Inside this repository they also derive the Box Office contracts and check that they are identical to the ones the Java tool committed, and that the generated TLA+ operator is identical to the one the Python generator wrote.
